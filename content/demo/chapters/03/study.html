DEMO101 — Building a Study Hub

Week 3: Practice and Progress

A chapter is not finished when it reads well; it is finished when a reader can practise it. This chapter covers the four data files, the graph that connects concepts across chapters, and the review loop that turns both into progress.

The practice loop

Reading builds recognition. Practice builds recall. The difference only shows up when the page is closed.

Every course in this engine is designed around a four-step loop. A reader reads a section, recalls its shape from memory, tests that recall against questions, and reviews only what the test exposed. The content pack supports each step with a different file, and each file has a different shape because each one answers a different question.

quiz.json

Multiple-choice entries with one correct option and an explanation of why it is correct.

flashcards.json

Prompt and answer pairs, scored and scheduled by the reader's own confidence.

kg.json

The concept graph: what the ideas are and how strongly they relate.

mkg.json

The same graph for the foundations pages, so formulas and definitions are reachable too.

Retrieval practice

Recalling an idea without looking at it. It feels harder than re-reading and produces more durable memory, which is why every practice file in the pack asks the reader to produce an answer rather than recognise one.

Write practice against a frozen page. Quiz entries and flashcards quote your anchors, and the concept graph links to them. Draft them while the page is still moving and you will rewrite the data twice.

Writing quiz entries

A quiz entry is four fields of content and two fields of bookkeeping. The bookkeeping is where mistakes live.

Each entry records the chapter it belongs to, whether it tests the study page or the foundations page, the question, four options, the index of the correct option, and an explanation. The explanation is not decoration: it is the part a reader actually learns from when they get the question wrong, so it should say why the right answer is right rather than restate it.

FieldMeaningRule
chChapter number.Must match a chapter in the manifest.
type"study" or "math".Decides which page the entry is filed under.
qThe question.One idea per question; no compound stems.
optsFour options.Exactly four, and all four must be distinct.
answerIndex of the correct option.Zero-based: the first option is 0.
expWhy the correct answer is correct.Explain the reason, not the position.

The zero-based index is the single most common authoring error in the whole pack, because it is off by one from the way people count options out loud. It is also invisible: an entry whose answer points at the wrong option still renders perfectly.

Vary the correct position

If the correct option is third in every entry, a reader learns the pattern instead of the material. Six entries per chapter, with the answer spread across all four positions, is enough to keep the pattern from forming.

Flashcards and decks

Two things called cards: a deck widget for use inside a section, and scored flashcards for review.

The flashcard file stores one record per card with a chapter, a front and a back. Those cards are scored: the reader reports whether the recall was easy, close, or missed, and the engine schedules the next appearance. Five cards per chapter is deliberate. A deck of forty is a reading list in disguise and gets abandoned in a week.

The deck widget below is the unscored cousin. It lives inside a section, rehearses one idea at a time, and leaves no trace. Use it for material the reader needs before continuing: a definition they will need in the next paragraph, a rule they are about to apply.

Mapping concepts

The concept graph is six values per node and three per edge. Most of the design work is in choosing the labels.

A node is written as a six-element tuple. The order is fixed, and every element earns its place: the identifier lets edges refer to the node, the chapter files it under a page, the difficulty scales how large it is drawn, the label is what the reader sees, the definition is the sentence they get on hover, and the link takes them to the section that teaches it.

PositionValueNotes
0Node idShort, unique, and stable; edges refer to nodes by this string.
1ChapterThe chapter the concept is taught in.
2Difficulty1 to 3. Drives the node radius, not the difficulty of the wording.
3LabelThe concept name, short enough to read at a glance.
4DefinitionOne line, complete enough to stand alone.
5LinkA relative path to a real anchor on one of your pages.

An edge is a three-element tuple: the two node ids it joins, and a strength. The strength is the element that causes the most confusion, because in the node tuple the second position is a chapter. In an edge it is not:

Edge elementMeaningRange
0From node idMust exist in the node list.
1To node idMust exist, and must not equal the first id.
2Strength4 to 9. A number outside this range draws nothing.

Why 4 and not 1. The graph view has a strength threshold, and its default hides anything weaker than 4. An edge tagged with a chapter number looks like a deliberate weak link and disappears; an edge tagged 4 or above is visible at the default setting.

The second graph, mkg.json, uses the same shape for the foundations pages. Its links point mostly at anchors of the form math.html#sec-m-…, so a reader who clicks a formula lands on the derivation rather than on the summary of it.

Spacing a session

The order of a review session matters more than its length. Twenty-five focused minutes beat an hour of re-reading.

The sequence widget below is a session plan. Put the steps in the order you would actually run them, then check. Every step is something the reader produces, not something they consume.

Gaps over scores

A score tells you how the session went. A list of gaps tells you what to do next. Keep the list, and let the score look after itself.

Measuring progress

Progress is stored per course, keyed by the manifest, and measured in the units the reader actually completed.

The engine writes progress against the storageKey from the manifest, so two courses on the same machine never mix their records. Within a course, the units are concrete: sections visited, quick checks answered, quiz entries attempted, cards recalled. A reader's progress bar moves when they finish something, which means the author's job is to make sure the units are worth finishing.

The race widget below compares recall coverage across the three chapters. Bars are drawn as a proportion of the declared maximum, so a course-wide scale keeps the comparison honest.

Signals worth trusting

  • Sections a reader can summarise without opening.
  • Quiz entries answered correctly twice, a week apart.
  • Cards that moved from missed to easy.

Signals that flatter

  • Pages scrolled to the bottom.
  • Quick checks answered with the page still visible.
  • Cards rated easy on the first attempt.

Wrapping up

You now have the whole pack: a manifest, six pages, four data files, and one habit.

The course you have just read is the sample pack that ships with the engine. Everything in it was written the way this chapter describes: prose first, structure second, practice material last. If you are starting your own course, copy this pack, delete the chapters, and keep the manifest and the data shapes.

Before you do, answer one question about the graph files, and read the worked answer on repairing a dead link. Those two exercises cover the failures that are hardest to see.

Quick check
An edge in kg.json reads ["hashmap", "load-factor", 2]. What is wrong with it?
Nothing: two ids and a strength is the correct edge shape
The second id should be a chapter number
The strength is below the 4-to-9 range, so the edge never draws
The tuple is missing a definition string

Worked answer — repairing a dead link. A node labelled "balance band" carries the link ../chapters/01/math.html#sec-m-budget, and clicking it goes nowhere. Repair it in five steps.

  1. Separate the path from the fragment. The reference splits into ../chapters/01/math.html and sec-m-budget. One of the two is wrong, and they fail differently: a bad path finds no file, a bad fragment finds a file with no matching anchor.
  2. Check the file first. The path resolves from the folder that holds the data file, climbs one level to the pack root, and descends into the chapter 1 folder. That file exists, so the path is sound and the fragment is the suspect.
  3. Read the target's anchors. Chapter 1's foundations page has sec-m-hero, sec-m-count, sec-m-budget, sec-m-ids, sec-m-anchors and sec-m-practice. The fragment is present — so the fault is not in the page at all.
  4. Reconsider the meaning. The node is about the balance band, which is defined in the section titled "Counting a page", not in the reading-budget section. The link resolves, but it resolves to the wrong anchor. Broken links are not the only bad links; a link to the wrong section is worse, because it looks like it worked.
  5. Fix and re-verify. Point the node at ../chapters/01/math.html#sec-m-count, then re-run the validation script that checks every node link against the anchors in its target file. That check catches both faults at once, which is why it belongs in the build rather than in a review.

If you take one habit away from this chapter, take that one: validate the links, then read the page as a reader would. The script can prove that an anchor exists. Only a reader can tell you whether it was the right anchor.
