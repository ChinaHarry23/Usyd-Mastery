DEMO101 — Building a Study Hub

Week 2: Interactive Widgets

A widget is a placeholder plus a JSON config. This chapter mounts six of the engine's eight interactive types on one page — five declared in JSON and one animated canvas stepper built in a chapter script — explains what each config key means, and shows the strict JSON rules that decide whether the widget appears at all.

Declarative widgets

You describe the widget; you do not build it. Two elements do all the work.

Every interactive block in this course is declared the same way. First a placeholder element names a widget type and points at a config block. Then a script block of type application/json holds the configuration. On load, the engine scans the page for placeholders, reads each config, and mounts the interaction in place of the empty div.

Declarative No JavaScript is required in the chapter script, the config is data rather than code, and a broken widget fails in one place instead of taking the page down with it.

The table below is the whole catalogue, read from the renderer rather than invented. The middle column lists the keys a widget cannot work without; the right column gives the shape of one item in the widget's list, because that is where most authoring mistakes live.

Placeholder

An empty element carrying data-ix="type" and data-ix-src="#config-id". The engine replaces its contents with the mounted widget; the element itself stays in place, so layout does not shift.

The config is content

Because a widget config is data, it can live next to the prose it illustrates, be reviewed like prose, and be diffed like prose. That is the reason the declarative path exists at all: a widget you can review is a widget that stays correct.

Strict JSON rules

Widget configs are parsed, not interpreted. A single stray character costs you the whole block.

Three rules cover almost every failure. First, every key and every string value is wrapped in double quotes; JSON has no bare words. Second, a double quote inside a string must be escaped with a backslash, because an unescaped quote ends the string early and leaves the rest of the line as syntax errors. Third, a string may not contain a raw line break: keep a value on one line, and use the structure of the config — more steps, more cards, more rows — when an idea needs more room.

MistakeWhat the parser seesFix
"label": "the "main" step"The string ends after the ; the next token is unexpected.Escape both quotes: \"main\"
A value that wraps to a second lineA control character inside a string.Rewrite as one line, or split into two steps.
Trailing comma after the last itemAn empty element where a value was expected.Remove the comma; JSON forbids trailing commas.
data-ix-src="#typo"No config block with that id, so nothing mounts.Match the id exactly, including the #.

An empty widget area is nearly always one of these four problems, and the page itself will not tell you which. Parse the block on its own before you go looking for a styling fault: the failure is almost never in the stylesheet.

Steppers

A stepper is the one widget that cannot be declared. Its frames are functions, so it is built in the chapter script instead.

Every other widget on this page is a placeholder plus a JSON block. A stepper is different: each frame carries a draw(ctx, w, h, k) function that paints the canvas, and a function cannot be written in JSON at all. Its placeholder therefore carries a plain id and no data-ix attribute, and the chapter script mounts it by hand:

Interactive.stepper("ix-ch2-stepper", {
  title: "How complete is your chapter?",
  height: 240,
  frames: [
    { title: "Empty folder", caption: "chapters/04 exists and holds nothing.",
      draw: function (ctx, w, h, k) { k.clear(); /* paint this frame */ } }
  ]
});

The renderer supplies the frame dots, the transport buttons and the caption line; your draw function only paints the picture. Inside it, k is a kit of canvas helpers — box(), label(), bar(), dot(), arrow(), highlight() — and the same placeholder can be rebuilt in place by calling Interactive.destroy(id) first, which is what a language swap needs.

The example below is mounted by chapters/02/study.js and walks the seven milestones from an empty folder to a validated pack. Every frame paints the same scale with the current milestone marked, so the position changes while the layout stays put. That ratio is the subject of the foundations page for this week.

Declarative first, imperative second. Reach for a stepper only when the widget has to draw something. If the content is a list of strings or records, one of the seven declarative types above expresses it, and the config stays reviewable as data.

Matching pairs

A matcher is the cheapest way to test whether a reader can tell similar things apart.

Each entry in pairs is a two-element array: the left-hand item first, then its partner. The engine shuffles the right column, and the reader works left to right until every pair is joined. Because the pairing is the answer, a matcher is only fair when the two columns are genuinely distinguishable: eight interchangeable definitions make a guessing game rather than a test.

Hotspot diagrams

A hotspot widget puts numbered markers on a picture you supply and explains each one on demand.

The config carries the drawing itself in the svg key as an inline SVG string — or a bitmap in the img key, never both — plus a list of points. Each point has x and y coordinates expressed as percentages of the drawing box, a label, and a detail sentence. Percentages rather than pixels mean the diagram keeps working when the page is narrow, which is the whole reason the coordinates are relative.

Draw for one idea

A diagram that needs six markers is usually three diagrams. If two markers explain the same relationship, the drawing is carrying two lessons and the reader will only remember one of them.

Flip-card decks

A deck is a light recall tool: a prompt on the front, the answer on the back, one card at a time.

Each entry in cards supplies a front and a back. Unlike the course-wide flashcard data, which is scored and scheduled, a deck widget is unscored and immediate: it belongs inside a section when the reader needs to rehearse something before continuing. Keep fronts short enough to read at a glance, and keep backs to a single idea.

Comparison bars

A race widget turns a small table of numbers into bars that a reader can compare without reading the numbers.

The config declares a max and a list of rows. Each row carries a name, a numeric value, and a display string that names the unit. Bars are drawn as a fraction of the maximum, so the scale is set by you rather than by the data: setting max above the largest value leaves visual headroom, and setting it below the largest value quietly clips the leader.

The rows below are an honest account of where the minutes went while writing this chapter. The widget is a comparison, not a claim about your own work, so the numbers are illustrative.

Prose is the slow part, and that is fine. Configs and data files fail loudly and get fixed in minutes. Explanations fail quietly, which is why they deserve the largest share of the budget.

Pipelines

A pipeline is a sequence with a point: the nodes run in order and each one hands something to the next.

The config is a title and a list of nodes, each with a label and a note sentence. Use it for processes where order is meaningful and the output of one node is the input of the next. If a reader could reorder your nodes without changing the meaning, you want a sequence widget instead, where reordering is the exercise.

When a widget does not appear, this pipeline is also the debugging order: confirm the section reached the page, confirm the placeholder survived the build, confirm the config parses, then confirm the widget renderer exists for that type name.

That check is mechanical enough to automate, which makes it a good first imperative widget. The panel below is mounted by chapters/02/study.js: it walks every placeholder on this page, parses the config block each one points at, checks the required keys and the shape of each list item, and reports the result. It shares its script with the stepper above, and between them they are the two widgets on this page that JSON cannot declare.

Worked answer — a widget that refuses to mount. A pipeline widget shows its title but no nodes. Diagnose it in the order the pipeline runs, and stop as soon as a stage explains the symptom.

  1. Section reached the page. The title is visible, so the placeholder mounted and the section was built. Skip the build entirely.
  2. Placeholder survived. The title comes from the config, which means the config was found and parsed. A missing config cannot produce a title.
  3. Config shape. The renderer drew a shell and then found nothing to draw inside it, which points at the list key rather than the header keys. A pipeline reads nodes; steps is the key a sequence reads.
  4. The fix. Rename the list to nodes, and rename each item's detail to note, which is the key the pipeline reads for the second line. Every label stays as it is.
  5. Prevent the repeat. Add the widget type to your validation script with the list key it requires. A one-line check turns a silent empty box into a named error at the point the block is parsed.

The general lesson is worth more than the fix: a widget that renders its frame has parsed successfully. Failures before that point produce an empty placeholder; failures after it produce a frame with missing parts, which narrows the search to a single key.
