Foundations: the notation and the grammar of requirements

This page is the reference card for the week. Part one is notation: every symbol in a feature diagram and a use case diagram, what it reads as, and what it commits you to. Part two is grammar: how to turn a sentence a stakeholder would say into a statement an engineer can implement and a tester can falsify, and where the functional/non-functional line actually falls.

The requirement-model notation card

Three diagrams carry this week's marks. Every element below appears in the lecture deck or in Tutorial 3, and the arrowheads are where the marks are lost.

Notation
Reads as
Meaning and commitment
Stick figure, outside the boundary
Actor
An entity — person, organisation or outside system — that interacts with the system to achieve one or more goals. Named by a noun; it plays a role, so one person can be several actors across systems.
Ellipse inside the boundary
Use case
A collection of possible interactions between actors and a system relating to one or more goals. Named verb + noun. Gives context to the requirements, facilitates agreement, and is a collection of possible scenarios.
Rectangle
System boundary
The scope of the system, typically defined by the requirements document. A large system may have one boundary per module with an overall boundary spanning them.
Solid line, no arrowhead
Association / communication link
The participation of an actor in a use case. The tutorial adds the semantics: the actor and the use case communicate with one another using messages. Every actor must be linked to at least one use case.
Dashed arrow → child use case, «include»
Include
One use case relies on another's functionality: a step in the scenario is a sub-use case at a lower level, with its own sub-goals and actors. The main use case includes actions from the child.
Dashed arrow → base use case, «extend»
Extend
An optional step added to a use case without affecting the specification of the original. Requires extension points — the named places where an extension can be woven in — and carries a condition such as [service successful].
Solid line with hollow triangle → parent
Generalization
A parent–child relationship between use cases. The child is an enhancement of the parent, connected at the base of the arrow, with the tip at the parent.
Extension point (named, e.g. X1)
Where an extension attaches
Advertised on the base use case and referenced by the extending use case. Without a declared extension point there is nowhere for the extension to be woven in.
Filled circle on a refinement edge
Mandatory sub-feature
In a feature diagram: the child feature must be selected. Feature diagrams are a graphical representation of domain concepts and their refinements.
Hollow circle on a refinement edge
Optional sub-feature
The child feature can be selected or not selected.
Filled arc over sibling edges
Or-group
At least one of the sub-features must be selected.
Hollow arc over sibling edges
Alternative (xor) group
Exactly one of the sub-features must be selected — the e-shop example's choice between a standard and a high-standard security policy.
Dashed arrow between branches, with a condition
Cross-tree constraint
A dependency that the tree structure cannot express: the tutorial's e-shop forces any system including credit-card payment to implement the high-security policy.
The two arrowheads, in one line each. Include: the base needs the child, so the arrow leaves the base and points at the child. Extend: the child may be woven into the base, so the arrow leaves the extending use case and points at the base. If you can say which use case would be incomplete without the other, you have the direction.
A dashed arrow runs from Login to Withdraw Cash with no stereotype shown. What is wrong with the diagram?
Nothing — the arrow simply means that login is used by withdrawing cash
The relationship is ambiguous: a dashed arrow must carry «include» or «extend», because the stereotype is what distinguishes them
It should be a solid line, because generalization uses dashed arrows

Grammar of a requirement statement

The deck's complaint about informal specification is not that it is informal — it is that you cannot mechanically check it. The fix is a shape every requirement can be poured into.

The five-slot shape

A checkable requirement names a subject (which system or component), a trigger or condition (when it applies), a response (what must happen), an object (to what), and a measure (how it is demonstrated). Anything missing from those five slots becomes an assumption, and assumptions are where projects fail.

Stated as relationships

Two relationships cover everything on this page. The first says a requirement is a mapping from a condition to an obliged response:

\[ R \;=\; \langle\, C \;\longrightarrow\; O \,\rangle \]

The second says that a requirement is only verifiable when the obligation carries a measure that a test could falsify:

\[ \text{verifiable}(R) \iff \exists\, m : O \text{ is decidable within } m \]

This is why “the system shall be user-friendly” is not a requirement and “the response shall be returned within 400 ms for 95% of requests” is. The first has no \(m\); the second does.

SlotThe tutorial's use case header field it matchesWhat goes wrong when it is absent
SubjectName — the use case or component being specifiedNobody knows which part of the system owes the behaviour
Trigger or conditionTrigger, preconditionThe requirement fires at the wrong time or never; the precondition becomes an untested assumption
ResponseGoal, main success scenario stepThe requirement describes a wish rather than an obligation
ObjectActors and the data they exchangeTwo teams implement incompatible interfaces around the same sentence
MeasureSuccess condition, failure conditionNo test can be written, so the requirement is never actually accepted or rejected
Which of these is written in a form a test can falsify?
The system shall respond quickly and behave robustly under load
When the door is opened while the system is enabled, the system shall sound the audible alarm and send a message to the police if no valid fingerprint is scanned within 30 seconds
The system shall support fingerprint identification and audible alarms

Functional vs non-functional, and the quality taxonomy

The deck frames the split simply: functional requirements describe what a software system should do, non-functional requirements place constraints on how it does so — performance characteristics such as accessibility and reliability.

Quality characteristicThe non-functional questionWhat makes it testable
PerformanceHow fast, for how many, under what load?A percentile and a load: 95th percentile under 200 concurrent users
ReliabilityHow often may it fail, and for how long?Availability over a stated window, and a maximum outage duration
AccessibilityWho must be able to use it, with what assistance?A named conformance target and an assistive-technology test
UsabilityHow long until a first-time user succeeds?A task time or completion rate with a stated user population
SecurityWho may read, write, send or change what?An authority list per role — the deck's separation of capability from permission
MaintainabilityHow easily can a change be introduced?Ease of diagnosing problems and of introducing modifications, stated as a change-cost budget
The deck's own warning: “for very many systems, these are not always separable concerns”. Treat the functional/non-functional split as a convention for organising a specification, not as a claim that the two kinds of requirement are independent. The split becomes actively misleading when a performance bound is what selects the algorithm.
The secure access specification says a valid fingerprint must be scanned within 30 seconds of the door opening. How should this be classified?
Functional, because it describes what the system does when the door opens
Non-functional: it constrains how the identification function must perform rather than adding a new behaviour
Neither — it is a design constraint that belongs in the architecture, not in requirements

The five defects of a requirement statement

The deck lists five issues with requirement statements, and the tutorial's ad hoc diagram section explains the consequences. Each defect has a mechanical test you can run before anyone builds anything.

DefectWhat it looks likeThe test that catches itRepair
Ambiguity “The system shall notify the user promptly” Ask two readers to write the acceptance test. If they differ, it is ambiguous. Name the channel and the bound: in-app banner within 2 seconds.
Incompleteness The panic button is described, but nothing says what happens if the telephone line is down Walk the scenario step by step and ask what happens when each step fails. Add the extension scenario, with its own failure condition.
Conflict “The alarm shall always sound on intrusion” and “pressing panic shall not sound the alarm” Search the set for pairs whose conditions can hold simultaneously. Scope one of them, or introduce the priority rule explicitly.
Difference in priority Everything is “shall”; nothing says what is dropped if time runs out Ask which requirement the customer would trade away first. Record priority, and keep the reason with it.
Perceived stakeholder urgency The loudest stakeholder's requirement is treated as the most important Compare the stated urgency against the project's actual ranking. Make the ranking explicit and agreed, so urgency is a decision rather than a default.

Why the informal specification is not sufficient (the deck's six reasons, turned into checks). You cannot, from prose alone: identify potential conflicts and inconsistencies between requirements; determine interdependencies between individual requirements; ensure all requirements are covered; understand precisely what needs to be implemented; trace requirements to implementation and vice versa; or provide a basis for comprehensive testing. The deck adds the operational reason: you also need the requirements in electronic form so they can be searched, linked and traced.

Worked example — mining the informal specification. The tutorial's secure-access prose is three paragraphs long. Extract the checkable requirements it already contains, and repair the two defects it hides.

1

Identify the subject and the trigger. Subject: the security system software. Triggers named in the prose: the monitor being powered on, the panic button, the door opening, the Enable button, and the motion detector reporting entry through a window. Five triggers is five requirement groups, not one paragraph.

2

Extract the measures. The prose contains three numbers and one identifier that are easy to read past: within 30 seconds of the door opening, 45 seconds to leave after enabling, and the 8-digit id registered with the police at installation. A statement without these numbers cannot be tested, so they belong in the requirement, not in the narrative.

3

Notice the deliberate asymmetry. On a panic press a message is sent and “the audible alarm does not sound”; on a failed scan or a window entry both happen. That is a genuine design decision, and it is the classic place where two requirements appear to conflict until you scope them by trigger.

4

Repair the incompleteness. Nothing in the prose says what happens if the telephone line to the police is unavailable. That is an extension scenario: retry, buffer the message, or fall back to a local alarm — and the choice is a requirement, not an implementation detail.

5

Repair the ambiguity. “A room in which only authorized people are allowed to linger” never defines linger. Either the system tracks duration and raises an occupancy violation, or it does not; the requirements document has to decide, because the motion detector's behaviour depends on the answer.

6

Write one requirement properly. “When the door to the secured area is opened while the system is enabled, the system shall sound the audible alarm and send a message containing the 8-digit system id to the police station if no valid fingerprint is scanned within 30 seconds of the door opening.” Subject, trigger, response, object and measure — and a test falls straight out of it.

Worked rewrites

Four statements from the week's worked examples, rewritten so that each one names its condition, its obligation and its evidence.

Before — a capability list

“The AI health agent shall be user-friendly and provide accurate advice quickly.” Three adjectives, three unmeasurable claims, and no way to tell a passing implementation from a failing one.

After — obligations with evidence

Functional: “The agent shall check reported symptoms for emergency warning signs before offering any advice.” Non-functional: “The agent shall return its triage summary with low latency and a high-accuracy model” — and the deck's agentic list adds the human checkpoint: the response is prepared but not sent until a clinician approves.

StatementDefectRewrite
The agent should be helpful Ambiguity — no measure, no condition The agent shall state, for each recommendation, the approved clinical guidance it relied on
The system shall book an appointment Incompleteness — no precondition, no failure branch Given a patient whose symptoms require evaluation, the agent shall book the earliest slot the patient confirms; if no slot is available within 14 days it shall alert the clinician instead
The agent shall always answer immediately and shall always consult a clinician first Conflict — the two obligations cannot both hold The agent shall produce a draft response immediately and shall not send it until a clinician approves; the patient sees a status indication meanwhile
Every feature in the backlog is mandatory Difference in priority — nothing can be traded Split the backlog into must/should/could and record, for each must, which stakeholder goal it serves
The binding thread. Requirements modelling is a small but crucial step in requirements engineering, and the deck's reason is traceability: models are what let a tool relate a requirement to the design that realises it and the test that demonstrates it. A prose document can be read; a model can be queried.

Worked answer — classifying a mixed requirement set. Sort the deck's agentic-software requirements, then say what each classification commits you to.

1

“The agent shall check reported symptoms for emergency warning signs.” Functional: it names an obligation to perform a check. Its evidence is a test case per warning-sign class, including the negative cases where no warning sign is present.

2

“Generate content based on natural language” and “conversation with human”. Functional, and deliberately coarse. The use case model is where they become precise: actors, preconditions, a main success scenario and extension scenarios for unclear input.

3

“Low latency”. Non-functional, and useless until quantified. Repair it into a percentile plus a load, then check whether the number is achievable given the model choice — if it is not, the constraint has just redefined the functional requirement.

4

“High accuracy LLM model (NLP and Computer Vision)”. Non-functional, and the hardest to test. Accuracy needs a population, a metric and a threshold: on which cases, measured how, above what value. Without those three it is an aspiration.

5

“User-friendly CHI”. Non-functional and unmeasurable as written. Convert to a task-completion measure with a population: a first-time patient completes the intake conversation without assistance.

6

The agentic additions. Authority is functional in form but constrains the design space like a non-functional requirement, and it must be separated from capability: what the agent may do is not what it can do. Human checkpoints are functional obligations with a clear test: with approval absent, no advice is sent and a draft is saved.

Two requirements read: “the alarm shall sound on any intrusion” and “a panic press shall message the police without sounding the alarm”. Which defect is present, and what is the cleanest repair?
Ambiguity; rewrite both with a time bound
Conflict; scope each requirement by its trigger so the panic path is excluded from the intrusion rule
Incompleteness; add the missing failure conditions
