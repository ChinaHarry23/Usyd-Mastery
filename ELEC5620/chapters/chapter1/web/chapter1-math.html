Foundations: the vocabulary and the notation of modelling

Week 1 is conceptual rather than mathematical, so this page does the equivalent job: it pins down the definitions the lecture relies on, gives you a reference card for the UML notation the whole unit is written in, makes the model–metamodel hierarchy explicit, shows the same treatment applied to behaviour notation, and ends with the traceability checklist that turns a pile of diagrams into a defensible architecture submission.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Model

A deliberately incomplete representation of a system, built to answer one class of question about it. The omission is not a defect: a model that kept every detail would be as hard to reason about as the system itself.

Abstraction

The act of dropping detail that is irrelevant to the question at hand while preserving what is relevant. In the lecture it is the architect's first qualification — the capacity for abstract thinking, or seeing beyond the technology and the code.

Software architecture — Clements, Bass, Kazman (2012)

The set of structures needed to reason about the system, comprising software elements, relations among them, and properties of both.

Software architecture — ISO/IEC/IEEE 42010

The fundamental organization of a system embodied in its components, their relationships to each other and to the environment, and the principles guiding its design and evolution. A system is a collection of components organized to accomplish a specific function or set of functions.

Model-based software engineering

Expressing a system's requirements, architecture, structure and behaviour as models precise enough to be analysed, validated and transformed, and treating those models as the primary engineering artefact rather than as an illustration of code already written.

Architectural decay

The gradual corruption of architectural design decisions through seemingly minor fixes and modifications, caused by the difficulty of comprehending an architecture by observing details and the difficulty of enforcing architectural design decisions in the process of implementation.

UML notation reference card

Every mark on a UML diagram carries meaning, and the examinable part is the meaning rather than the drawing. Use this card to check that you can name what an adornment asserts before you use it.

How to read the card

Column one is the mark, column two is how to say it aloud, column three is the claim you have made by drawing it. If you cannot state the claim, remove the adornment: an unadorned relationship is honest, an incorrect one is a defect in the model.

Model, metamodel and the three-level hierarchy

The single most useful idea for Week 2 and for the Stage 1 report: a model is only checkable because the language it is written in has its own definition.

Metamodel

A metamodel is a model of a modelling language. It defines what elements exist (Class, Association, State, Transition), how they may be combined (an Association connects two Classifiers), and what they mean. UML's metamodel is what makes a UML diagram checkable: a diagram that violates it is not an unusual design, it is not a model of the language at all.

Why this matters for your project

  • A stereotype is only legal because the metamodel permits it — which is why «agent» can carry a contract rather than being decoration.
  • Consistency checking is metamodel checking: unresolved references and impossible multiplicities are violations, not style choices.
  • Transformation rules are written against the metamodel, so a toolchain can only generate from elements the metamodel knows about.

What is not a metamodel question

  • Whether the design is good — the metamodel has nothing to say about quality.
  • Whether the naming matches the domain — that is a review question.
  • Whether the requirements are complete — that is traceability, on the checklist below.

The three levels, and the direction the arrows point

Everything in the model below sits at M1, and everything the tool checks about it belongs to M2. The distinction is examinable because it explains what a tool can and cannot tell you.

1. The hierarchy is a relation, not a pyramid of boxes

Write x ∈ M for “x is an instance in the model M”. Then each level is an instance of the level above and a model of the level below:

\[ \underbrace{a}_{\text{M0 instance}} \;\in\; \underbrace{M}_{\text{M1 model}} \;\in\; \underbrace{\mathrm{MM}}_{\text{M2 metamodel}} \]

Practical consequence: “is this diagram legal?” is a question about MM, while “is this diagram right?” is a question about the system in M0. A tool can only answer the first.

2. The IEEE 42010 definition is a tuple

The standard's sentence can be written as a five-part description. With C the components, R the relations among them and to the environment, and P the principles guiding design and evolution:

\[ \mathrm{Architecture} \;=\; \langle\, C,\; R,\; P \,\rangle \qquad\text{where } R \subseteq C \times C \;\cup\; C \times \mathrm{Env} \]

Two things follow. First, an architecture that lists only C is incomplete — the lecture's gloss is that the manner in which parts are assembled is fundamental. Second, P is not documentation: it is the constraint set that any future design decision must satisfy, which is why it belongs in the architecture record rather than in a wiki page.

3. Traceability is a relation between two models, not a document

Let Req be the set of requirements and Des the set of design elements. A traceability link is a pair (r, d) asserting that d exists in order to satisfy r:

\[ T \;\subseteq\; \mathrm{Req} \times \mathrm{Des} \]

Coverage in each direction is then a statement about the projection of T:

\[ \text{forward coverage} = \frac{|\pi_{\mathrm{Req}}(T)|}{|\mathrm{Req}|}, \qquad \text{backward coverage} = \frac{|\pi_{\mathrm{Des}}(T)|}{|\mathrm{Des}|} \]

A requirement with no image in T is unimplemented; a design element with no preimage is unjustified. Both are findings you can report, and both are cheaper to find on the model than in the code.

4. Design risk falls as understanding rises

The lecture's exploration picture plots problem understanding and confidence, the cost of design change, and design risk against time. Modelling moves the moment at which the critical understanding threshold is reached from T1 (implementation evaluation) back to T2 (model evaluation):

\[ \mathrm{Cost}_{\text{fix at }T_2} \;\ll\; \mathrm{Cost}_{\text{fix at }T_1} \]

Stated as a design rule rather than a graph: spend effort on the model while the cost of changing it is still near zero. That is the whole economic case for MBSE, and it is the sentence to write when an exam question asks why architecture is worth the time.

Behaviour notation: the same treatment for state

Structure notation answers “what is there?”. Behaviour notation answers “what happens, in what order, and under what conditions?” — and it is where models earn their keep, because conditions are checkable and prose is not.

State machine

A model of the lifetime of one object: the finite set of states it can be in, the events that cause transitions between them, the guards that decide which transition is taken, and the effects that run as a result. It answers a different question from an activity diagram, which models work flowing between many activities.

A state machine is a labelled directed graph

With states S, an initial pseudostate s0, a set of final states F ⊆ S, events E, guards G and effects A, a machine is:

\[ M \;=\; \langle\, S,\; s_0 \in S,\; F \subseteq S,\; \delta \,\rangle, \qquad \delta \;\subseteq\; S \times E \times G \times A \times S \]

Each transition is a 5-tuple (source, event, guard, effect, target). The notation event [guard] / effect is just that tuple written along one arrow, which is why the parts can be omitted independently: [guard] alone is a transition with no trigger, and / effect alone runs on any trigger from that state.

Determinism is a property you have to design for

Two transitions out of the same state with the same event are ambiguous unless their guards are mutually exclusive. For every state s and event e:

\[ \bigl|\{\, t \in \delta \;:\; t_{\text{src}} = s \;\wedge\; t_{\text{ev}} = e \;\wedge\; t_{\text{guard holds}} \,\}\bigr| \;\le\; 1 \]

When two guards can be true together, the machine has silently become a choice, and the choice is being made by whichever branch the implementation happens to test first. The fix is either to make the guards exclusive or to model an explicit choice pseudostate so the decision is visible on the diagram.

Worked example — from a paragraph of requirements to a checkable machine. Requirement, as written by a group in Week 1: “After the customer accepts a recommendation, the system reserves the shoes if they are in stock; if the store cannot confirm stock, or the recommendation confidence was low, the founder is asked to approve before anything is reserved.”

1

Find the states, not the steps. A state is a condition held over time. Reading the paragraph: a recommendation is pending, a reservation exists, an escalation is awaiting a person, and the order is completed. Four states. “Check stock” is not one of them — it is an action inside a transition.

2

Find the triggers. Two external events: accept() from the customer, and approve() from the founder. Creation is an initial pseudostate, not an event.

3

Write the guards as the conditions in the prose. The paragraph contains two: stock confirmed, and confidence adequate. Combine them: accept() [inStock && confidence ≥ θ] / reserve() and accept() [!(inStock && confidence ≥ θ)] / escalate(). The negation matters — without it the machine is nondeterministic, and the determinism condition above is violated in exactly the state where being wrong is most expensive.

4

Add the effects. reserve() on the happy path, escalate() on the exception path, resolve() and ship() afterwards. Effects are where the model touches the real system, so each one should name something the requirements actually promised.

5

Audit against the prose. Walk the paragraph and check that every clause maps to a transition, a guard or a state. Here the clause “before anything is reserved” is a reachability claim: no path may enter Reserved from a low-confidence recommendation. That is the kind of claim a model can be checked against, and a paragraph cannot.

Two transitions leave the same state on the same event: accept() [express] and accept() [international]. What is wrong?
Nothing is wrong: a state may have as many outgoing transitions as it needs
The guards must be mutually exclusive, otherwise the machine is ambiguous when both are true
Both transitions must be merged into a single transition with a combined effect

MBSE traceability checklist

Stage 1 marks models, not diagrams. Run this checklist over your submission before you write the report — every item is something a marker or an interviewer can ask about in one sentence.

Every element has a reason

Point at any class, component or state and finish the sentence “this exists because requirement R…”. If you cannot, the element is either unjustified or a requirement is missing from the document.

Every adornment is a claim

Multiplicities, diamonds and arrows are constraints. Each one should be defensible in the interview, and each one you cannot defend should be removed rather than softened.

Assumptions bound the model

An assumption states when the design stops being valid — for example “the inventory API always responds within two seconds”. That is what makes change assessment possible later.

Consistency across views

The same concept must have the same name and the same relationships in every diagram. Divergence between a class diagram and a sequence diagram is the most common self-inflicted Stage 1 defect.

Worked answer — auditing one candidate architecture against the checklist. Candidate: “The chat interface calls the LLM directly, which then decides whether to ask the inventory service about stock.”

1

Concern and quality attribute. The driving concern here is trust: a recommendation the customer acts on must be accurate. The quality attribute is reliability of the recommendation, with auditability as a close second. Write both down before judging the design.

2

Requirement trace. Which requirement justifies letting the model choose when to query inventory? If the answer is “flexibility”, the requirement does not exist yet and the design decision is premature. If the answer is a named optional feature, it is justified — and it is optional, which matters for the trade-off.

3

Structure. The chat interface now depends on both the LLM and, transitively, the inventory service. Draw the components and the interfaces: the diagram will show that the interface has acquired a dependency it does not need, which is accidental complexity introduced by the wiring.

4

Behaviour. Model the risky sequence as a state machine. Question: what is the machine's state while the LLM is deciding whether to call inventory? If the answer is “none, it is just waiting”, then failures and retries have nowhere to live — which is precisely the kind of flaw that is cheap to find here and expensive to find in Stage 2.

5

Assumption and change assessment. Record the assumption that makes the design acceptable — for example “the LLM is used for language, never for the stock decision” — then assess what changes if that assumption is dropped: the inventory call must move behind a deterministic component, and the confidence guard must be evaluated outside the model. That is a change assessment argued from the model, and it is what the deliverable is asking for.

6

Verdict in one sentence. The candidate is rejected because it assigns a deterministic decision to a non-deterministic component, creating a dependency that requirement traceability cannot justify; the revised design puts an inventory component behind a stable interface and keeps the LLM on the language path only.

Which finding is the strongest evidence that a design is under-specified rather than merely incomplete?
A class is missing one of the operations described in the report
A multiplicity of 1..* is stated on an association where nobody can say whether zero is legal
Two diagrams use slightly different names for the same component
