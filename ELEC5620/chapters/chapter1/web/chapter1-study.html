Why Software Engineering Needs Models

The unit opens with a claim that carries the whole semester: software design is too complex, too time consuming and too risky to do entirely in code, so you use a model to simplify the problem.

Where architecture sits

Software architecture is a kind of software design in the software engineering domain, and architecture details are a subset of software design. The lecture draws it as three nested boxes: Software Engineering ⊇ Software Design ⊇ Software Architecture. Everything in this unit is therefore design work at the coarsest level of detail — the level at which you decide what the parts are and how they talk to each other.

Software

A collection of instructions, often in the form of code, which tell the computer how to act.

Hardware

The platform, often in the form of a machine, which actually completes the work.

Software is anything that tells hardware what to do and how to do it. Software projects can be massive and large-scale, and they can be very diverse. Those two facts are the reason an engineering discipline exists around them: software engineering focuses on the development and use of rigorous methods for designing and constructing software artefacts that will reliably perform specified tasks. It is explicitly more than an IT skill set — it draws on engineering mathematics, professional engagement and other engineering domain knowledge.

The economic argument for modelling. The lecture's picture of architectural exploration is a set of four curves against time: problem understanding and confidence rises, the cost of design change rises, and design risk falls. Repeating the evaluation of architectural models early — by simulation and by formal and informal analysis — reaches the critical understanding threshold through model evaluation at time T2 instead of through implementation evaluation at time T1. Flaws found at T2 are far cheaper to fix than the same flaws found after the code exists.
Model

A model is a deliberately incomplete representation of a system, built to answer one class of question about it. It is not a worse copy of the code: the omission is the feature. A model of a system that kept every detail would be as hard to reason about as the system itself.

Abstraction

Abstraction is the act of dropping detail that is irrelevant to the question at hand while preserving what is relevant. The lecture makes it the first of the architect's qualifications: the capacity for abstract thinking — seeing beyond the technology and the code. “Fundamental” in the IEEE definition of architecture means exactly this: irrelevant details are omitted.

Different models answer different questions about the same system. That is why a project produces several diagrams rather than one, and why “draw me the model” is never a well-formed request.

ModelQuestion it answersDetail it deliberately omits
Context / use caseWho uses the system, and for what outcome?Internal structure, ordering of steps
ComponentWhat are the parts, and what do they expose?Class-level detail inside each part
ClassWhat concepts exist, and how are they related?Objects, threads, timing
SequenceIn what order do messages flow for one scenario?Alternative scenarios, internal state
State machineWhat states can one object be in, and what moves it?Who else is involved, how long it takes
DeploymentWhere does each part actually run?Source layout, algorithms
Exam framing: never answer “a model is a simplified version of the system” and stop. The markable version names the purpose: a model is built to reason about a specific aspect, so its value depends on whether the details it dropped were the right ones for that question.
Why does the lecture begin the unit with architecture rather than with code?
Because software design is too complex, time consuming and risky to do without first simplifying the problem with a model
Because architecture diagrams remove the need to write code at all
Because it is the fastest way to allocate work across a group of five

What Software Architecture Is

Two definitions from the deck do the heavy lifting. Learn both, because exam questions quote them and then ask you to unpack one word.

Definition — Clements, Bass, Kazman (2012)

“The software architecture of a system is the set of structures needed to reason about the system, which comprise software elements, relations among them, and properties of both.”

Definition — ISO/IEC/IEEE 42010

“Architecture: the fundamental organization of a system embodied in its components, their relationships to each other and to the environment, and the principles guiding its design and evolution.” A system is a collection of components organized to accomplish a specific function or set of functions.

What IEEE 42010 is for

The standard is the IEEE Recommended Practice for Architectural Description of Software-Intensive Systems. Its goals are to facilitate the expression and communication of architectures (specification and design, and documentation), to define key terms, principles and guidelines, and to provide a framework for other related IEEE standards.

The lecture unpacks the IEEE sentence word by word, and each gloss is worth marks on its own.

Word in the definitionWhat it commits you to
fundamentalIrrelevant details are omitted ⇒ abstraction. Architecture is what is left after you remove everything you could reasonably change without changing the system's character.
organizationBoth structural and behavioural. The lecture is explicit that the unit covers both aspects of software architecture.
componentsArchitecture involves decomposition. If you cannot name the parts, you have not described an architecture.
relationshipsThe manner in which the parts are assembled is fundamental to an architecture. The same components wired differently are different architectures.
guiding principlesLike the basic tenets of a constitution: the rules that constrain later design and evolution decisions.

The lecture's worked example. A simple architecture model is drawn with three things on it at once: a layering structure (an application layer above a services layer), a horizontal structure (a set of peer components — the deck names them Boobler, Fuber, Gruber and Dabbler), and end-to-end behaviours traced across them (A → B → C). Beside it sits the design principle that motivates the whole shape: “To support high availability, the system must not have a single point of failure.” One picture, three kinds of architectural statement.

Architectural specification is iterative. The lecture places the same picture of stakeholders and their concerns next to a diagram of components being refined: “refining the design over time until it satisfies all the requirements”. There is no single pass in which you get the architecture right, which is precisely why a cheap, revisable model beats committing to code.
A team documents “the order service calls the payment service, and no service may call the order service back.” Which part of the IEEE 42010 definition is doing the work?
fundamental — irrelevant details are omitted
components — architecture involves decomposition
relationships and guiding principles — how the parts may be assembled

Complexity, Decay and Why Architecture Matters

Architecture is not valuable in the abstract. It is valuable at three specific moments in a system's life, and it decays when nobody defends it.

When architecture matters

PhaseWhat the architecture does for you
During inception and design Facilitates system consistency and simplifies design; helps predict key system qualities; and helps identify requirements — modelling is not only downstream of the requirements, it is a way of finding them.
During implementation Helps identification and allocation of development work, and guides finer-grained design decisions.
During maintenance and evolution Reduces the likelihood of architectural decay during fine-grained maintenance, and identifies the feasibility and potential cost of evolution alternatives.
Architectural decay

The gradual corruption of architectural design decisions through seemingly minor fixes and modifications. It has two principal causes, and both are about the difficulty of seeing the whole:

  • the difficulty of comprehending an architecture by observing details;
  • the difficulty of enforcing architectural design decisions in the process of implementation.

Note what decay is not. It is not a single bad decision; it is the accumulation of individually reasonable ones. That is why the counter-measures are a documented architecture (so the whole can be comprehended) and a modelled, traceable design (so the decisions can be enforced) — not simply “better programmers”.

Two kinds of complexity

Essential complexity

Complexity that belongs to the problem: the domain really is intricate, the rules really do interact, the human situation really is ambiguous. Modelling cannot remove it — the only honest responses are to understand it better and to represent it explicitly.

Accidental complexity

Complexity introduced by the way we chose to build the solution: the framework, the data model we picked, the premature optimisation, the tangled dependencies. This is the part modelling and architecture actually attack.

Why the distinction earns marks. A tempting but wrong answer to “how does modelling reduce complexity?” is “it makes the problem simpler”. A model does not simplify the problem; it simplifies your access to it by separating the two kinds of complexity and letting you attack the accidental one deliberately. Applied to the project: recommending a running shoe that fits is genuinely hard (essential); discovering that the inventory adapter has leaked into the ranking logic is not (accidental).
A team ships a working system. Over two years, each release adds a small shortcut until the ordering, pricing and notification logic are entangled across four services. What has happened?
Essential complexity increased because the business domain became harder
Architectural decay: architectural decisions were corrupted by minor fixes and modifications
Nothing architectural — the code simply reflects normal staff turnover
A developer spends three days writing an adapter because the inventory vendor's API returns availability as a nested array, then has to change it again when the vendor updates the schema. Which kind of complexity is that?
Essential — deciding which shoe to recommend is inherently difficult
Accidental — the vendor's response shape is a property of our chosen solution, not of the problem
Neither — three days of work is simply normal development cost

Worked example — classifying complexity in a real system. Scenario: the One-Person AI Company recommends a running shoe, checks stock, and reserves a pair.

1

List the difficulties, not the features. Deciding what “fits” means from a foot scan; ranking shoes when fit, comfort, price and availability disagree; knowing when a recommendation is uncertain enough to escalate.

2

Mark the essential ones. Fit, ranking trade-offs and the escalation threshold are essential. No amount of refactoring makes them go away — a human founder still has to own the judgement.

3

Mark the accidental ones. The inventory vendor's REST shape leaking into the ranking rules; the recommendation logic being reachable only through the chat handler; three copies of the confidence threshold. These are self-inflicted.

4

Decide which one the model attacks. The architecture model puts an integration layer between inventory and ranking, and names the confidence policy once. That is accidental complexity removed by a structural decision — and it is why the decision is worth recording before the code is written.

5

State the risk. If the model had tried to remove the essential complexity — for example by pretending a single numeric score can rank fit, comfort and price without a stated trade-off — the design would have become simpler to draw and wrong in use. Modelling removes the accidental and exposes the essential.

MBSE: The Model as the Primary Artefact

Model-based software engineering is not “drawing some diagrams before coding”. It is a change in which artefact carries the design.

Model-Based Software Engineering

MBSE is the practice of expressing a system's requirements, architecture, structure and behaviour as models that are precise enough to be analysed, checked and transformed, and of treating those models as the primary engineering artefact rather than as an illustration of code that has already been written. Model-driven engineering (MDE) is the stronger form of the same idea, in which the model is the source from which other artefacts — documentation, interfaces, and in part the implementation — are generated.

QuestionCode-firstModel-based
What is the primary artefact?The source codeThe model; code is one derived artefact
Where do design decisions live?Implicitly, in the structure of the codeExplicitly, in a notation with defined semantics
How is a design flaw found?By running it, or by reading all of itBy evaluating the model before implementation
How is the design communicated?By walking someone through the codeBy a diagram a stakeholder can read
What happens as the system ages?Architectural decay, discovered lateDecay is detectable against the recorded design
When is it the wrong choice?Rarely, for genuinely small systemsWhen the ceremony costs more than the system is worth

The prerequisite warning from the deck, in its own terms. “UML is not helpful to coding in many cases (e.g., Agile). But it is a good language for communication.” Read that as a claim about which job the model is doing. A model is not a compiler input in this unit; it is how a design becomes discussable, reviewable, traceable and markable.

The UML Landscape

UML is the notation the whole unit is written in. Week 1 assumes familiarity and warns that the unit will do a deep dive into its semantics — so it is worth knowing exactly which diagram does which job before Week 5 and Week 6 arrive.

Unified Modeling Language

UML is a standardised graphical language for specifying, visualising, constructing and documenting the artefacts of a software-intensive system. It is a language, so it has a metamodel that fixes what each element means; it is unified, so the same notation serves requirements, architecture, structure and behaviour; and it is a modelling language, so it describes designs rather than implementations.

Structure diagrams — what the system is

  • Class — concepts, attributes, operations and their relationships
  • Component — replaceable parts and the interfaces they expose
  • Package — grouping and namespaces
  • Deployment — which part runs on which node
  • Object — a snapshot of instances at one moment

Behaviour diagrams — what the system does

  • Use case — actors and the outcomes they want
  • Activity — the flow of work, with decisions and concurrency
  • State machine — the states of one object and what moves it
  • Sequence — messages between lifelines in time order
  • Communication — the same interactions, organised around the links instead of the clock

Two of those pairs are easy to confuse under exam pressure, and both confusions are about what the diagram puts first.

PairFirst diagramSecond diagramHow to choose
Sequence vs communication Sequence organises interactions by time: lifelines down the page, messages in order. Communication organises the same interactions by structure: objects and links, with numbered messages. Use sequence when the ordering is the point; use communication when the wiring is the point.
Activity vs state machine Activity models work that flows between activities and can fork or join. State machine models one object's state, with transitions triggered by events and guarded by conditions. Ask how many objects are in the picture. Many, flowing: activity. One, changing: state machine.

Building a class diagram, one decision at a time

The fastest way to internalise UML is to watch a diagram acquire meaning. The animation below starts from a single empty class and adds exactly one modelling decision per step — attributes and operations, then an association with multiplicity, then aggregation, then composition, then generalisation, and finally the stereotype that binds the model to the project's agent architecture.

The rule that matters most: every element you add is a claim. An association with multiplicity 1..* says the domain can never contain a shoe with no model; a filled diamond says the part cannot outlive the whole. If you cannot defend the claim, use a plain association — an unadorned relationship is honest, a wrong adornment is a defect.
You need to show that a ShoeModel cannot exist without the Manufacturer that produces it, and that deleting the manufacturer deletes the model. Which notation is correct?

Aggregation — a hollow diamond at the manufacturer end
Composition — a filled diamond at the manufacturer end

The one-sentence company brief

The tutorial's central exercise is a template, and its shape is a modelling decision in disguise: it forces you to name the actor, the situation, the cause, the agent roles and the human decision that stays human.

For [target user] in [situation], [problem] occurs because [cause]. Our one-person AI company coordinates [agent roles] to [outcome], while the human founder approves [high-impact decision].

Specific user Real evidence Measurable value Multi-agent roles Human accountability

Worked example — StrideWise AI, the tutorial's own case, decomposed.

1

Separate the surface request from the underlying need. The customer says “I want to buy a pair of running shoes.” What is actually unresolved is financial confidence (is this good value?), fit accuracy (will it hurt?) and trust (there are too many options to evaluate).

2

State the business goal separately. Higher conversion, lower product return rates and increased customer trust. Note that the first two are measurable and the third is not — the model has to carry both without pretending they are the same kind of thing.

3

Write the brief in one sentence. For runners who struggle to choose suitable shoes, the wrong shoe is bought because fit, style and budget cannot be compared in the shop. StrideWise AI coordinates fit-analysis, product-research, inventory and customer-support agents to recommend available shoes matching the customer's feet, running style and budget, while the human founder approves health-related advice and uncertain recommendations.

4

Read the brief back as a design. “Coordinates four agents” is a component diagram. “Approves health-related advice” is a state machine with an escalation transition. “Recommends available shoes” is a sequence diagram with an inventory call. “Uncertain recommendations” is a guard condition. The sentence already contains the models.

5

Apply the design test from the lecture. Can the company deliver value repeatedly without the founder touching every step? If not, simplify the promise or redesign the workflow. Note that the test is not “can the AI do everything” — it is “is the human attention allocated to the right steps”.

The Project: A One-Person AI Company

The project theme is not a generic software exercise. It is a specific organisational idea, and the models you build have to describe that organisation.

The one-person AI company

A company owned and directed by one founder, in which AI agents, software and specialist contractors perform the repeatable work under the founder's control. It can research markets, create content, sell, support customers, analyse data and run back-office workflows, while the founder owns judgement, relationships and accountability.

The design principle stated in the deck. Design from customer value backward, not from available tools — in four moves: narrow the promise (one customer, one painful job, one measurable outcome), map the work (separate judgement, repeatable tasks and risky exceptions), build guardrails (data access, quality checks, approvals, fallbacks) and create memory (store decisions, examples, metrics and lessons in one system). The design test is a single question: can the company deliver value repeatedly without the founder touching every step? If not, simplify the promise or redesign the workflow.

The worked example in both the lecture and the tutorial is a hypothetical patient-navigation agency: the founder partners with clinics and employers to help patients understand referrals, prepare for appointments and complete non-clinical follow-up, while licensed clinicians retain every diagnosis and treatment decision. Notice how precisely the boundary is drawn — the agents handle coordination, the humans keep the clinical judgement. That boundary is an architectural decision, and it is the kind of decision the marker is looking for.

Worked example — turning a topic into a modelled scope. A group proposes a “smart campus study assistant”. Here is the Week 1 work that has to happen before any diagram is worth drawing.

1

Narrow the promise. Not “helps students study” but “for a first-year student the night before a lab, the wrong prerequisite is revised because the unit outline and their own notes cannot be compared in one place”. One user, one painful job, one measurable outcome.

2

Map the work. Repeatable: retrieving the outline, extracting deadlines, checking coverage. Judgement: deciding what the student should revise. Risky exceptions: the student is behind on a prerequisite, or the outline changed mid-semester.

3

Build guardrails. Which data the agents may read, what quality check a generated study plan must pass, which changes require approval, and what happens when a source is unavailable. Each of these becomes a constraint later, so name them now.

4

Create memory. Store the decisions, the examples and the metrics in one system, so that the model of the system and the record of what was learned do not drift apart.

5

Run the design test. Can this deliver value repeatedly without the founder touching every step? If the honest answer is no because the plan always needs a human rewrite, narrow the promise to “assembles the evidence a student needs for a revision decision” and let the human make the decision. You have just made your first architectural decision, and it is defensible in one sentence.

Week 1 Recap

A model is a deliberate omission

An incomplete representation built to answer one class of question. Architecture is the model at the coarsest level: software engineering ⊇ software design ⊇ software architecture.

Core definition

IEEE 42010 in five words

Fundamental (abstraction) · organization (structure and behaviour) · components (decomposition) · relationships (assembly) · guiding principles (the constitution).

Definition to reproduce

Decay is accumulation, not one mistake

Architectural decay is the gradual corruption of design decisions by minor fixes. Its causes are the difficulty of comprehending the whole from the details, and of enforcing the decisions during implementation.

Failure mode

MBSE moves the artefact

The model becomes the primary engineering artefact: analysed, validated and transformed, with requirements traceable to design elements — instead of an illustration of code already written.
