What Structure Modelling Is For

Part 1 of the deck opens with a claim about who a model is written for, and Part 2 closes by showing what the notation can and cannot say about run-time reality. Both halves answer the same question: what exactly do you get when you model structure?

Definition — structure modelling

Structure modelling deals with the representation of entities that take up space (ultimately, physical) and which have state and may have behaviour. Concretely it is the modelling of design-time classes, of run-time instances (objects) and their relationships (links), and of the specifications of those run-time entities and relationships.

Code is intended for machines

The deck opens with SystemC source for a producer/consumer pair: modules, ports, sensitivity lists, constructors, a container that wires two processes together through a link object. Every token exists to satisfy a compiler.

The structurally identical picture beside it — a «sc_method» producer box, a «sc_link_mp» link1 box, an «sc_slave» consumer box, joined with a start input and an out1 → in1 connection — says the same thing to a person in one glance.

Models are intended for people

The deck names exactly two key features of model-based methods: abstraction and automation. Abstraction is what lets one diagram replace forty lines of source; automation is what lets the diagram become an artefact you can generate from, check and transform.

UML is the running example because it is the most widely taught and used modelling language, and because it descends from three separate modelling traditions — Booch, OMT and OOSE — that were merged into one notation.

UML was originally intended for descriptive models, and also supports prescriptive (for example executable) models. That single sentence decides how you read every diagram in this unit. A descriptive model documents a system that already exists or has been decided; a prescriptive model is the specification that the system will be built to conform to — and, in the executable case, the thing that runs.

Elementary Structural Concepts

Before notation there is ontology. The deck spends its first eight slides on four concepts — value, object, object identity and link — because every UML adornment you will draw later is a claim about one of them.

Value

A representation of information that is universal, unique and unchanging: numbers, characters, strings, symbols and icons. Typically written as a symbol or a string — 7, VII, "seven", "fubar", "+". To be useful in a program a value must be stored in some container where it can be read and written.

Object and object identity

An object is a complex value container with a unique identity conforming to a Class type. It may own attribute slots (value containers for attribute values) and may be capable of performing behaviours (operations). The deck's warning about attributes is exact: an attribute slot holds a value; the identity does not.

Object identity is an immanent property of an instance, acquired upon creation and retained unchanged throughout its lifetime, which distinguishes that object from all others. Identity does not change when attribute values change, and it does not change when the type of the object is changed (type reclassification).

The deck's identity example

One object, prince : Adult, at two times. At t = 1958 its name slot holds "Prince"; at t = 1993 the same slot holds "The Artist Formerly Known As Prince". The attribute slot changed; the object did not. Identity is what the attribute slots are attached to.

Why this matters in a diagram

Every association you draw is a promise about links between object identities, not between values. Two objects with identical attribute values are still two links; one object whose values changed is still one link. Multiplicity ranges count identities.

Link — and the two kinds

A link is a tuple of value containers (link ends) that store object identifiers and conforming to an Association type. Links can be created and destroyed dynamically, and a link may itself have an identity — some links are objects.

The deck separates two kinds by asking who owns the ends. In kind (a) the link ends are owned by the linked objects: obj1 holds obj2.id and obj2 holds obj1.id. In kind (b) both ends are owned by the link itself, so the link is a first-class object and the linked objects hold nothing.

The dot notation, and why it appears everywhere. When a class box shows a feature typed by another class, the notation signals that ClassA has a feature typed by ClassB: an object obj1 : ClassA reaches obj2 : ClassB through the dot path obj1 → obj2. A navigable association end is the diagram-level way of saying the same thing, which is why the class box and the association line are two views of one model element.
The model and the thing modelled. The deck spends a slide on the most common confusion in the unit. The word “Batmobile” names both the toy (the model, M1) and the real vehicle (the modelled world, M0), and the two are related by «represents». Underneath that, Adult is a type — a specification of a category of entities sharing the same kinds of properties; Alice : Adult is an instance specification; Alice herself is the individual in M0. Keep the three layers apart and the rest of the week is mechanical.

Classes and Associations as Classifiers

The single most useful move in Week 5 is to stop treating an association as a line and start treating it as a classifier — a thing with its own instances, its own ends and its own properties.

Classifier

A classifier is a specification of a collection of entities (things, concepts) that (1) share a set of characteristics (features) and (2) can be classified (divided) into sub-collections according to the nature of some of their characteristics. People can be classified by gender into men and women, or by age into adults and children — two different classification criteria on one collection.

Kinds of classifier in UML include classes, associations, association classes, data types, enumerations, interfaces, behaviours (activities, interactions, state machines), signals, use cases, collaborations, components and nodes.

Class

A specification of a collection of object instances characterised by the same set of features and behaviours. Its instances are objects.

Association

A specification of a collection of links whose ends conform respectively to the same type. Its instances are links. Both classes and associations are classifiers, and all classifiers can serve as types.

The exercise the deck sets, and the answer to memorise. Explain why Association is a classifier. Because it satisfies both clauses: it specifies a collection of entities (the links), those links share a set of characteristics (their ends, and any properties the association itself owns), and the collection can be divided into sub-collections according to the nature of those characteristics — which is exactly what association specialisation does later in the deck.

Multiplicity: where it applies, and its modifiers

Multiplicity

Multiplicity specifies usages that are collections: attributes, association ends, parameters and anything else whose value can be a collection. It can specify ranges with an upper and a lower bound, where 0 means the absence of elements and * (or [0..*]) means an open-ended upper bound.

{unique} — default true

No two elements of the collection can have the same value. Write {nonunique} to say the opposite. Because it is the default, forgetting to write it is a claim that the collection is a set.

{ordered} — default false

The elements of the collection are ordered in some appropriate manner, so the collection is a sequence rather than a bag or set. Write {unordered} to state the default explicitly.

In the deck's own notation the {unique, ordered} modifier is attached to the 0..* child end; the same slide also shows multiplicity on plain attributes (name : String [1..*]), which is the reminder that multiplicity is not an association-only concept. The tutorial adds the vocabulary: [1..*] is one-to-many and [*..*] is many-to-many.
Tutorial exercise — extend the model. The Week 5 tutorial asks you to extend the class diagram to show explicitly the relationships between (1) an Adult and his or her sons and (2) an Adult and his or her daughters. The honest answer needs no new association: Child already carries gender : [M, F], so “sons” and “daughters” are subsets of Adult.children selected by that attribute. Expressing them as two separate associations would duplicate the same links and lose the fact that they partition one collection.

Interfaces, dependencies and the shorthand

Interfaces

Like classes, interfaces define a set of features, but they are restricted to declarations only — interfaces cannot have instances. A classifier realises an interface when it provides implementations, directly or indirectly, for all of the interface's features. A classifier uses an interface when it requires the services of some object that realises it, which is one of the standard methods of decoupling elements from each other.

The deck's example

«interface» JetEngineControl declares +thrust : Real, +status : [OK, Fail] and the operations accelerate(), decelerate(), reverseThrust(), ignite() and powerDown(). Pilot has a «uses» relationship to it; RollsRoyce Engine and GE Engine both realise it.

The trap in the shorthand

The lollipop does not represent an interface instance. It is a combination of an interface and a realisation relationship — one icon standing for two model elements. That is the whole reason the alternative notation is compact, and the reason an examiner can ask you to expand it.

Dependencies

A dependency is an informal statement that one or more client items require one or more supplier items in some way: a change in a supplier affects the clients. The semantics are deliberately open (loose), but they can be specialised — the deck shows Factory and Car joined by a plain dependency, then the same pair joined by a dependency carrying the user-defined stereotype «manufacturedBy», and then the same dashed arrow reused between Car, Motorcycle and Factory.

A model shows Pilot connected to a lollipop labelled JetEngineControl. What is actually being asserted?
That a single instance of the interface is attached to the Pilot
That a classifier realises the interface and the Pilot uses its services
That Pilot depends on JetEngineControl in the loose dependency sense

Generalisation, Sets and Association Specialisation

Generalisation is the subset–set relationship UML uses for classification. The interesting exam material is not the arrowhead; it is what happens when you have two classification criteria at once, and what happens when you specialise an association rather than a class.

Generalisation

Generalisation is a subset–set relationship: the instances of the subclass are a subset of the instances of the superclass, and the diagram's arrow signifies a graphical operation — all features of the superclass are also present in the subclass. Specialisation is the reverse process, in which a subclass refines or extends the characteristics of the superclass to create more specific subtypes.

What inheritance copies, mechanically

BankAccount declares /customers : BankCustomer, credit (amount: Amount) and debit (amount) : Boolean. CorporateAccount adds owner : CorporateCustomer — and the deck's point is that the two operations and the derived attribute are also present in the subclass. They are not redrawn; they are inherited.

Two criteria on one class

Person can be partitioned by an age criterion into Adult and Child, and by a gender criterion into Males and Females. Each partition is a generalisation set, and the label on the shared arrowhead names the criterion. A person is in exactly one subset of each set.

Generalisation sets exist because multiple classification criteria are possible for a given class. Without the set label, two arrowheads hanging off Person would be ambiguous: are Adult and Males alternatives, or independent axes? The criterion label (age, gender) answers that, and it is what makes the multiple-inheritance-free modelling of several simultaneous partitions legal in UML.

Composition, Aggregation, Association Classes and Constraints

This is the densest page of the deck, and the part most likely to be examined directly: the two diamonds, the two ways to give an association properties of its own, and the two notations for a constraint.

💎 Composition — the black diamond

Implies ownership of one element by another: an instance of Person owns an instance of String that specifies that person's name. The semantics are deletion semantics — when the owner is removed, all its owned elements are also removed with it. The deck's instance view is a Person named Bran whose :String has value = "Bran".

🃏 Aggregation — the white diamond

Intended to support a user-defined weak form of ownership, for example in a UML profile. In standard UML its semantics are the same as a regular association — the deck prints the Adult 0..1 child — 0..* Child fragment twice to make the point that nothing changes when the diamond is added.

The examinable asymmetry: the black diamond adds real semantics (deletion propagates from whole to part); the white diamond adds none in standard UML unless a profile defines what the weak ownership means. A question that asks you to choose between them is really asking whether the part's lifetime is bound to the whole's.

Giving an association its own properties

Option A — the association class

Some associations have properties in addition to the ends. The deck's example attaches Job with a salary to the Person 1..* — 0..* Company association. One link, one salary: the property belongs to the link, not to either object, which is exactly the “link ends owned by the link itself” case from the elementary concepts.

Option B — a class plus two associations

The alternative replaces the association class with an ordinary class Job standing between Person and Company, each side 0..*. It avoids the complexities involved with association class semantics, such as writing constraints — but the deck's note is the price: it requires a coupling between the links of those two associations.

Constraints: what a diagram cannot draw

Constraint

A constraint captures some semantics for elements of a namespace. It is expressed in either a formal language or a natural one — the deck lists the Object Constraint Language (OCL), English, and, in its own words, Australian. There are two notation choices: written in line inside the element, as in size : Integer {size >= 0}, or attached as a note, with the same text in a rectangle joined to the element by a dashed line.

Invariants and OCL. A constraint whose text is a boolean expression that must hold in every valid system state is an invariant. OCL is the formal option in the deck's list, and it is the reason the earlier sections matter: an invariant is written over the model's elements — its classes, their attributes, and the collections given by association ends. The 1..2 and 0..* you set earlier are structural constraints; an OCL invariant is how you say something the diagram has no symbol for.
A diagram puts a filled diamond at the String end of Person 0..1 name — 1 String. What has the modeller committed to?
That the name can be shared between persons, but weakly
That the Person owns the String, and removing the Person removes that String
That the String attribute is instantiated at the same moment as the Person

Tutorial exercise — explain why Association is a classifier, and answer the two set questions. Worked answer using the Adult/Child model.

1

What is the content of the set children of Karl? Every Child linked to Karl by a link of the association. If the diagram shows Karl linked to Cory, Ida and Dee, the set is exactly {Cory, Ida, Dee} — and the 1..2 at the parents end tells you that each of those three children has one or two parents, of whom Karl is one.

2

What is the set parents of Cory? Every Adult linked to Cory. The 1..2 bound says the set has size one or two, so a link to Karl alone is a valid configuration, and so is a link to Karl and Jill. Karl.children->includes(Cory) and Cory.parents->includes(Karl) are two navigations of the same link.

3

Why Association is a classifier. A classifier is a specification of a collection of entities that share a set of characteristics and can be divided into sub-collections according to the nature of some of those characteristics. An association specifies the collection of links; those links share their ends and any properties the association owns (the Job.salary case); and the collection can be divided into sub-collections — the corporate and personal links — which is association specialisation. Both clauses hold, so an association is a classifier, and like every classifier it can serve as a type.

4

Extend the model for sons and daughters. Do not add associations. Child already has gender : [M, F], so “sons” and “daughters” are the two subsets of Adult.children obtained by selecting on that attribute. Two extra associations would state the same links twice, break the 0..* multiplicity's meaning, and lose the fact that the two subsets are disjoint and together cover the whole collection. If you must expose them as navigable features, add derived ends with {subsets children}.

5

The sentence that earns the mark. “An association is a classifier because its instances are links, those links share the association's ends and owned properties, and the collection of links can be partitioned by association specialisation — which is precisely the definition of a classifier, and the reason an association can carry its own attributes as an association class.”

Objects, Roles and Collaborations

Part 2 asks the question that makes class diagrams honest: how many different run-time configurations does one class diagram describe? The deck answers it three ways — an object diagram, a role, and a collaboration — and each answer is more reusable than the last.

The five-year-old and the computer scientist. Asked to draw a picture of a car, the five-year-old draws boxes for the parts and lines for the connections between them: left front wheel, engine, right front wheel, body, rear wheels. The deck's point is that this is not a childish drawing — it is a structure model, and it is the same shape as the diagram the computer scientist produces. Boxes are parts; lines are connections.
The questionnaire that exposes the limit of class diagrams

The deck shows a class diagram with ClassA linked to ClassB by two 1-to-1 association ends, named al (left) and ar (right). How many different run-time configurations are described by this class diagram? The answer is that there is no finite number. Configuration (1) is one ClassA linked to one ClassB; configuration (2) is two; then three; and so on. The diagram is a specification with infinitely many instances, which is exactly what makes it worth having — and exactly why it cannot show you one run.

Object diagrams, and their limitation

An object diagram represents a snapshot of some specific system at some point in time. The deck is careful about what follows: object diagrams can only serve as examples, not as general architectural specifications — unless a profile is defined. Two snapshots of the same four-node linked structure at times T and T+1 differ only by one added node, and the class diagram that describes both is silent about the difference.

Role — a prototypical instance

A role is a representation of an instance with a specific responsibility in some broader generalised context (a collaboration). The deck's example is the role of Hamlet in Shakespeare's play: the role can be filled by different actual individuals — Laurence Olivier in one production, Kenneth Branagh in another — and one actor instance may fill two roles in the same production (Olivier played Hamlet and the Ghost). What is needed is a way of talking about prototypical instances across time.

Collaboration

A collaboration describes a set of collaborating roles communicating via connectors that represent communication links. Collaborations represent a network of cooperating object instances whose identities have been abstracted away. The deck's MicroHamlet collaboration has a connector line to a constrained role (Hamlet : YoungMan), unconstrained roles (Gertrude, Ophelia, Ghost), and an «abstraction» dependency from each concrete production (MicroHamlet(1948), MicroHamlet(1996)) to the collaboration.

Collaboration uses

Applying a collaboration specification to a particular situation is a collaboration use. The deck's BrokeredSale binds the roles of a Sale — Buyer, Seller — to a wholesale and a retail context, with broker and producer connectors tying them together.

Collaborations are classifiers

They can be refined using inheritance, which opens the possibility of defining generic architectural structures. TwoViewMVC has two view roles plus ctrlr and model; ThreeViewMVC refines it by adding a third view role while keeping the same controller and model roles.

The one line to remember from Part 2: a collaboration has no encapsulation shell — it cannot be instantiated as objects. That is the whole difference from the structured class in the next section, and it is why collaborations model patterns while structured classes model components.
Agentic AI, object level. For agent systems the deck uses object diagrams to show how agents are instantiated at run time, with BDI-style objects: agent instances (doctorAgent1), belief objects (KnowledgeBase, UserProfile), desire/goal objects (BookAppointment), intention/plan objects (SendReminder) and environment objects (HospitalSystem). The analytic point is the many-to-many structure: each agent has two beliefs, and each belief associates with two agents, so patientProfile is shared rather than owned. Compare that with the composition on Person and String: a shared belief is an association, never a composition.
Two agent instances share one patientProfile : Belief object. What does the deck's analysis imply about how that link should be modelled?
As a composition from each agent to the belief
As an association with many-to-many ends, since the belief is shared
By giving each agent its own copy of the belief attribute

Worked example — choose between a class diagram, an object diagram and a collaboration. Four scenarios from the Week 5 material, each answer in one paragraph.

1

“Describe every legal state of the linked-node structure.” Class diagram. It constrains Node with left 0..1 and right 0..1, which permits every chain, tree and ring the run time can produce. No object diagram can do this, because each one fixes a single number of nodes.

2

“Show the reviewer the four objects that exist right now, and what happened when a fifth was added.” Two object diagrams, at T and T+1. They are snapshots and can only serve as examples — but an example is exactly what is wanted here, because the interesting claim is about one specific run.

3

“Capture the pattern that two productions of the same play share, so that a third can be compared against it.” A collaboration. The roles Gertrude, Ophelia, Hamlet and Ghost abstract away which individual fills each one, and the two historical productions depend on the collaboration with «abstraction». 4

“Record which beliefs are shared between agent instances and which belong to one agent only.” A class diagram for the rules (DoctorAgent * — * Belief, plus any composition for beliefs that really are private), then one object diagram to demonstrate the sharing that motivated the rule. Structured Classes: Ports, Parts and Connectors

UML added structured classifiers primarily for architectural modelling. Where a class diagram says what things are, a structured class opens a class up and shows how its components are wired together at run time.

Structured class

A class with an external structure (port interaction points) and an internal (collaboration) structure. Think of it as “opening up” a class and showing how its components are wired together at runtime. The heritage is architectural description languages: the UML-RT profile (Selic and Rumbaugh, 1998), ACME (Garlan et al.) and SDL (ITU-T standard Z.100).

The port structural pattern

Ports are distinct interaction points of an object for multiple, possibly simultaneous collaborations. They let an object distinguish between different external collaborators without direct coupling to them. One basic purpose of ports, the deck notes, is the separation of roles.

Ports and interfaces

Ports can provide and/or require interfaces. The general case is both: the deck's DataBase has an adminPort that provides DBserver (readDB, writeDB, notifyOfChange) and a clientPort that requires DBclient (change (d)). Uni-directional ports are also common.

Why multiple interfaces per port should be avoided. The deck gives three reasons and they are all examinable: it creates potential conflicts (name clashes) and requires some kind of disambiguation mechanism; the semantics are unclear if the interfaces have protocol state machines attached; and it is much less problematic to simply define separate ports for each interface. The slide's own illustration is WebServer.read (id) and Library.read (id) colliding on one port.
Internal structure, and the question the deck leaves open. A structured class can contain collaboration structures comprising parts that are usages of other structured or basic classes. A part is drawn inside the class box as partF : F, and a delegation connector joins a port on the boundary to a part, or one part to another. The deck's unanswered question is deliberately provocative: should all attributes in a class become parts in its structured class? The defensible answer is no — a value-typed attribute such as name : String has no interaction points to wire, so it stays an attribute, while a component with ports and its own internal structure earns a part.

An agent's sub-components — belief base, desire/goal manager, intention/plan manager, reasoning/decision engine and communication interface — are modelled as parts of a structured class, not as attributes. Week 5 Recap

Four concepts under the notation

Value (unchanging, no identity), object (a container with identity from creation), identity (unchanged by attribute values or reclassification) and link (a tuple of ends conforming to an association type).

Elementary structure

Every association is a classifier

Its instances are links; its features are its ends and any owned properties; it can be specialised. That is why it can carry attributes as an association class.

The key abstraction

Black diamond owns, white diamond does not

Composition carries deletion semantics: remove the owner and the owned elements go with it. Aggregation in standard UML has the same semantics as a plain association.

Two diamonds

Precision comes from constraints

Multiplicity gives ranges; {unique} and {ordered} shape the collections; {subsets} and {union} link refined associations to general ones; invariants in OCL say what the diagram cannot draw.
