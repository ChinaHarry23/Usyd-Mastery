Foundations: the notation and the laws behind structure models

Week 5 is a notation week, so this page does the job a formula sheet would do for a numerical unit. It pins down the definitions the deck relies on, collects every structural symbol in one reference card, writes the associations you draw as a grammar you can check, gives multiplicity and composition their algebra, and ends with the OCL and checklist material that turns a plausible diagram into a specified one.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on diagrams. Write each of these in one sentence, with the consequence included.

Structure modelling

The representation of entities that take up space (ultimately, physical) and which have state and may have behaviour: design-time classes, run-time instances (objects) and their relationships (links), and the specifications of those run-time entities and relationships.

Value, object, identity

A value represents information that is universal, unique and unchanging. An object is a complex value container with a unique identity conforming to a Class type, which may own attribute slots and perform behaviours. Object identity is an immanent property acquired upon creation and retained unchanged throughout the object's lifetime — it survives changes to attribute values and even to the object's type.

Link, class, association

A link is a tuple of value containers (link ends) that store object identifiers and conforming to an Association type. A class is a specification of a collection of object instances characterised by the same set of features and behaviours. An association is a specification of a collection of links whose ends conform respectively to the same type.

Classifier

A specification of a collection of entities that (1) share a set of characteristics (features) and (2) can be classified (divided) into sub-collections according to the nature of some of their characteristics. Classes and associations are both classifiers, and all classifiers can serve as types.

Generalisation and specialisation

Generalisation is a subset–set relationship between a superclass and a subclass. Specialisation is the reverse process, in which a subclass refines or extends the characteristics of the superclass to create more specific subtypes. The arrow signifies a graphical operation: all features of the superclass are also present in the subclass.

Composition, aggregation, constraint

Composition (filled diamond) implies ownership with deletion semantics: when the owner is removed, all its owned elements are removed with it. Aggregation (hollow diamond) supports a user-defined weak form of ownership; in standard UML its semantics are the same as a regular association. A constraint captures some semantics for elements of a namespace and is expressed in a formal or a natural language.

The grammar of a precise association

Almost every mark lost on a class diagram comes from an association that is missing one of five parts. Write the association as a sentence with slots and check them off in order.

1. An association is a five-slot sentence

Write each association in this form and no slot can be silently omitted:

\[ A:\ \underbrace{C_1}_{1}\ \underbrace{\text{name}_1}_{\text{role}}\ \underbrace{m_1}_{\text{mult}}\ \xrightarrow{\ \text{label}\ }\ \underbrace{m_2}_{\text{mult}}\ \underbrace{\text{name}_2}_{\text{role}}\ \underbrace{C_2}_{2} \]

The two classes fix what is linked, the two roles fix how the link reads in each direction, the two multiplicities fix how many links each instance may have, and the label names the association itself. Adding a diamond, a navigability arrow or a stereotype extends the sentence; it never replaces a slot.

2. Read a multiplicity from the far end

For an association \(A\) with ends \(e_1\) on \(C_1\) and \(e_2\) on \(C_2\), the multiplicity written at \(e_1\) bounds the number of \(C_1\) instances reachable from one \(C_2\) instance:

\[ \forall\, c_2 \in C_2:\ \bigl|\{\, c_1 \in C_1 \mid (c_1, c_2) \in L_A \,\}\bigr| \in [\,m_1^{lo},\, m_1^{hi}\,] \]

With the deck's Adult 1..2 parents — 0..* children Child this yields two constraints at once: every Child has between one and two Adult links, and a Child may have none at all — the second because \(0\) is the lower bound at the children end, which bounds the Adults reachable from a Child by \(0..*\).

3. The set-valued reading of an end

Each end is also a query. If the end children on Adult has multiplicity \(0..*\), then for a given Adult instance \(a\):

\[ \texttt{a.children} \;=\; \{\, c \in \texttt{Child} \mid (a, c) \in L_A \,\}, \qquad \texttt{a.children->includes(Cory)} \iff (a, \texttt{Cory}) \in L_A \]

The deck writes both directions of the same link: Karl.children->includes(Cory) and Cory.parents->includes(Karl). Two navigations, one link — which is why navigability arrows describe reachability, not the existence of the link.

4. Composition is a lifetime rule, not a strength

Write \(W\) for the whole and \(P_w\) for the set of parts composed into \(w\). Composition adds one law that a plain association does not have:

\[ w \notin \text{extent}(W) \;\Longrightarrow\; \forall\, p \in P_w:\ p \notin \text{extent}(\text{type}(p)) \]

Deleting the whole deletes its parts. Nothing in the notation says when a part is created, and nothing stops a part from being an ordinary object while it lives. Aggregation contributes no such law in standard UML: the hollow diamond is a hook for a profile-defined weak ownership, and without that profile it denotes the same set of links as a plain association.

Navigability in full. Given one instance in a relationship, an arrow tells you whether you can determine the instances of the other class that are related to it. The tutorial's spreadsheet example is the cleanest statement of the asymmetry: from a spreadsheet you can locate all the cells it contains, but from a cell you cannot determine its spreadsheet; from a cell you can obtain the related expression and value, but from a value you cannot find the cell it is an attribute of.
An association A 0..1 — 1..* B has its 0..1 written at the end attached to A. What does it constrain?
How many B instances each A is linked to
How many A instances each B is linked to
How many A instances may exist in the whole system

The algebra of multiplicity

Multiplicity is a constraint language with a small algebra. Knowing which strings are legal, what each default means, and what a range implies about the number of configurations is what separates a drawn diagram from a specified one.

Multiplicity stringLegal link countsReading
1exactly 1Mandatory, single
0..10 or 1Optional, single — the deck uses it for Person 0..1 name String and Node right 0..1
1..*1 or moreMandatory, collection — the tutorial's one-to-many
0..*0 or moreOptional collection — the deck's Child end
*0 or moreShorthand for 0..*: an open-ended upper bound
2..42, 3 or 4A bounded range; any lower and upper bound may be written

1. A range has a lower and an upper bound

Every multiplicity is a pair, and the two bounds do different jobs:

\[ m = [\,m^{lo},\, m^{hi}\,], \qquad 0 \le m^{lo} \le m^{hi} \le \infty, \qquad m^{lo} = 0 \iff \text{optional}, \qquad m^{hi} = \infty \iff \texttt{*} \]

Legal collections are those scoring between the two bounds. Where \(m^{lo}=0\), an object may exist with no links at that end at all — which is a design decision worth stating out loud, because it says the system tolerates the absence.

2. How many run-time configurations does a class diagram admit?

Let \(n_1\) and \(n_2\) be the numbers of instances of the two ends. The number of possible link sets for the association is bounded by

\[ |\mathcal{L}_A| \;\le\; 2^{\,n_1 n_2} \qquad\text{and, when both upper bounds are finite,}\qquad |\mathcal{L}_A| \;\le\; \binom{n_1 n_2}{\,n_1 m_2^{hi}\,} \]

The deck's questionnaire is the intuition: with one 1-to-1 pair of ends over two classes, configuration (1) is one ClassA and one ClassB, configuration (2) is two of each, configuration (3) is three, and so on without limit. A class diagram is a specification with infinitely many instances, which is exactly why a single object diagram cannot stand in for it.

3. Multiplicity is not an association-only concept

Multiplicity specifies usages that are collections — attributes, association ends, parameters — so the same ranges appear on attributes:

\[ \texttt{name} : \texttt{String}\,[1..*] \qquad\text{and}\qquad \texttt{/customers} : \texttt{BankCustomer} \]

The first says the name slot holds one or more strings. The second says the derived feature is itself a collection of BankCustomer, which is why the deck can attach {union} to it when the association is specialised.

4. The two modifiers, and their defaults

The modifiers say what kind of collection the end holds:

\[ \{unique\} \;=\; \text{default } true \qquad \{nonunique\} \;=\; \text{false} \qquad \{ordered\} \;=\; \text{default } false \qquad \{unordered\} \;=\; \text{true} \]

Two consequences worth memorising. Omitting {unique} asserts that no two elements of the collection have the same value, so a design that needs duplicates must write {nonunique} explicitly. And because {ordered} defaults to false, the deck's {unique, ordered} at the parents end is a real claim: the parents of a child form an ordered set, not a bag.

An end carries the multiplicity 0..* with no modifier strings. What has the modeller asserted about that collection?
That it is an unordered set — elements are unique and the order is not meaningful
That it is an ordered sequence of unique elements
That duplicates are permitted, because nothing was said about uniqueness

Specialisation, subsets and unions

The deck's refined accounts / customers model is the densest constraint diagram in Week 5. Written as set algebra it becomes easy to reproduce from memory.

1. A specialised association is a subset of the general one

Write \(L_g\) for the links of the general association and \(L_s\) for the links of a specialisation of it. Then

\[ L_s \;\subseteq\; L_g, \qquad \text{extent}(C_s) \subseteq \text{extent}(C_g),\ \text{extent}(K_s) \subseteq \text{extent}(K_g) \]

where \(C\) and \(K\) are the two ends. The deck marks this in notation as {subsets accounts} on the specialised end. The practical consequence is the one the model exists for: a link between a CorporateAccount and a PrivateCustomer is not merely unusual, it is unrepresentable.

2. A derived union end is the union of its subsets

The general end is marked {union} and prefixed with /. Writing \(S_1, \dots, S_k\) for the specialised ends:

\[ \texttt{/accounts} \;=\; \bigcup_{i=1}^{k} S_i \qquad \text{so no link exists at the general end that no subset covers} \]

Together, subsetting and union make the two views agree in both directions: nothing in a subset is outside the union, and nothing in the union is outside every subset. This is why the deck calls the result a more refined specification rather than a second, competing model.

3. Generalisation sets and their constraint strings

A class may be partitioned by several criteria at once, one generalisation set per criterion. For a set with subsets \(T_1,\dots,T_n\) of a class extent \(E\):

\[ \bigcup_{i} T_i = E \quad (\text{complete}) \qquad\text{or}\qquad \bigcup_{i} T_i \subsetneq E \quad (\text{incomplete}) \] \[ T_i \cap T_j = \varnothing \ \ (i \neq j) \quad (\text{disjoint}) \qquad\text{or}\qquad T_i \cap T_j \neq \varnothing \quad (\text{overlapping}) \]

The deck's Person is partitioned by age into Adult and Child, and by gender into Males and Females. Each partition is complete and disjoint, and neither partition constrains the other — a person is in exactly one subset of each set, and the two axes vary independently.

4. Association class versus class plus two associations, as a cardinality claim

Let \(J\) be the association class on an association between \(P\) and \(C\). Then

\[ |\text{extent}(J)| \;=\; |L_{PC}| \qquad\text{whereas, in the reified form,}\qquad |\text{extent}(J)| \ \text{is constrained only by a coupling invariant} \]

The equality in the association-class form is structural: one Job per Person–Company link, by construction. In the reified form, Job is an ordinary object with two 0..* ends, so nothing stops a job being rewired to another pair — which is precisely the “coupling between links” the deck warns about, and the reason it has to be written as a constraint rather than read off the diagram.

A general end is marked {union} /accounts and its two specialised ends are marked {subsets accounts}. Which legal configuration would break the model?
A corporate link that appears both in C-accounts and in /accounts
A link that appears in /accounts but is covered by neither C-accounts nor P-accounts
Two corporate accounts linked to the same corporate customer

Worked example — specify an association completely. Task: take the tutorial's “every spreadsheet contains some number of cells” relationship and write it as a precise model element, slot by slot.

1

Classes. Spreadsheet and Cell. Both are classifiers and both serve as types. Cell additionally relates to Expression and Value, which is the tutorial's second example and a separate association.

2

Roles. The end at Spreadsheet is named containedIn, and the end at Cell is named cells. Reading the association out loud gives “every spreadsheet contains some number of cells”, and reading it backwards gives “a cell is contained in exactly one spreadsheet” — which is the test the tutorial applies: a good relationship name makes sense when you read it out loud.

3

Multiplicities. cells : 0..* read from Spreadsheet would allow an empty spreadsheet; use 1..* if an empty spreadsheet is not a legal object. containedIn : 1 read from Cell, because the tutorial's navigability discussion states that from a cell you cannot determine its spreadsheet — that is about reachability, not about the link existing, so the end is still 1.

4

Navigability. Add an arrow towards Cell only. Given a spreadsheet you can locate all of its cells; given a cell the diagram gives you no way to reach the spreadsheet, even though the link exists and its multiplicity is 1. Navigability is a statement about the model's intended access paths.

5

The second association, and the constraint. Cell evaluatesTo Value and Cell hasExpression Expression, both navigable from the cell and not from the value or the expression. The invariant that makes the model work is context Cell inv valueMatchesExpression: self.expression.evaluate() = self.value — a statement no diamond, arrow or multiplicity can draw.

6

The full sentence. “Spreadsheet 1 cells: Cell 1..* ->, Cell containedIn: Spreadsheet 1, navigable from Spreadsheet to Cell only, with the invariant that a cell's value equals the evaluation of its expression.” Five slots filled, one constraint attached, and no ambiguity left for a reader to resolve.

Invariants and OCL

The deck lists OCL as the formal option for constraints. This section gives you the small set of OCL forms that covers almost every structural rule a Week 5 model needs, each written over the notation already on this page.

Constraint and invariant

A constraint captures some semantics for elements of a namespace and may be written in a formal or a natural language. A constraint whose expression is a boolean that must hold in every valid system state is an invariant. OCL is the Object Constraint Language, and it is written over the model: its self is the element the constraint is attached to, and its navigation expressions are the association ends and attributes already in the diagram.

Partition coveragePayment.allInstances->forAll(p | p.oclIsKindOf(CardPayment) or p.oclIsKindOf(InvoicePayment))A {complete} generalisation set

1. Every model element has a context, and the context is where the constraint lives

The general shape of an attached constraint is

\[ \texttt{context}\ \langle\text{element}\rangle\ \texttt{inv}\ \langle\text{name}\rangle:\ \langle\text{boolean expression over } \texttt{self}\rangle \]

The deck's size : Integer {size >= 0} is the in-line form of a constraint whose context is the attribute's owning class; written out it becomes context Stack inv nonNegativeSize: self.size >= 0. The inline form is shorter, the named form is referenceable — and an invariant is only useful when something can check it.

2. A cardinality bound is an invariant, so multiplicity and OCL say the same thing

For an end children with multiplicity \(1..2\), the notation and the OCL are two spellings of one law:

\[ \texttt{children} : [1..2] \quad\equiv\quad \texttt{self.children->size() >= 1}\ \texttt{and}\ \texttt{self.children->size() <= 2} \]

Two consequences follow for exam answers. First, drawing a multiplicity is doing specification, not decoration. Second, any rule that cannot be reduced to a bound — “the sum of the quantities of the lines equals the order's item count”, for instance — has to be a separate invariant, because there is no multiplicity symbol for it.

3. The reified-association coupling, written properly

The alternative to an association class needs one invariant per direction of the coupling. With Job linked to Person and to Company:

\[ \texttt{context Job inv oneLinkPerPair:}\quad \texttt{Person.allInstances->forAll(p | Company.allInstances->forAll(c | p.jobs->select(j | j.company = c)->size() <= 1))} \]

This is what “a coupling between links of these associations” means once it is written down, and it is the price of avoiding association class semantics. Note the shape of the argument: the constraint is not about one object, it is about a pair of objects, which is exactly what an association class expresses structurally.

Where structured classes change the question. Ports and parts are structural elements too, so their rules are also invariants: a delegated connector must join a port on the boundary to a part that provides or requires the matching interface, and a part's type must conform to the part : Type declaration. The deck's unanswered question — whether every attribute should become a part — is answerable in these terms: an element with no interaction points and no internal structure has nothing to which a connector could attach.
A modeller writes context Order inv minOneLine: self.lines->size() >= 1 on top of an association whose lines end is already 1..*. What has happened?
The invariant restates the lower bound already carried by the multiplicity, so nothing new is constrained
The invariant overrides the multiplicity and silently makes the end optional
The constraint is illegal, because size() may only be used in global expressions

Worked example — make a loose diagram precise. Starting point: the deck's questionnaire diagram, ClassA al 1 — 1 ar ClassB, drawn with two 1-to-1 association ends. Harden it in four moves.

1

Name the association, not the ends only. Replace al and ar with role names that read aloud: leftOf and rightOf if the structure is positional, or parent and child if it is hierarchical. An association label in the middle of the line names the relationship itself, and the deck's rule is that a good name makes sense when read out loud.

2

State navigability in one direction only. If the intended traversal is from the container to its contents, arrow only that way. As the tutorial's spreadsheet example shows, being unable to reach back from a cell to its spreadsheet is a modelling decision, not an omission — but it must be a decision.

3

Decide whether the parts may be shared, and say so. A 1-to-1 pair of ends allows a chain and a ring; it does not by itself forbid one ClassB from being the ar of two different ClassA instances — the multiplicity at the al end would have to be 1 to enforce that, and it is. Write the exclusivity invariant anyway if the diagram is split across views: context ClassB inv singleOwner: ClassA.allInstances->select(a | a.ar = self)->size() <= 1.

4

Replace the unbounded count with a rule. The questionnaire showed that the diagram admits 1, 2, 3, … pairs. If the domain has a bound — say at most four — it must be written, because the notation has no global bound: context ClassA inv boundedFanOut: self.ar->size() <= 4. And if the structure is required to be acyclic, that too is an invariant, and it is the classic example of a rule no class diagram can draw.

5

Check what is left unstated. Lifetime (composition or plain association), the collection's kind ({unique}, {ordered}), and any coupling between two associations. If all three are answered, the diagram is a specification; if any is unanswered, a reader is free to choose — and a different reader will choose differently.

Class-diagram checklist for the lab

Laboratory 5 Part Two asks for a class diagram with classes and relationships, interfaces and their implementations, multiplicity on every association, and attributes and methods, using correct UML notation. Run this list before you submit.

Classes and relationships

Every major class identified; associations, generalisations, aggregations and compositions distinguished, with the diamond only where lifetime is really bound.

Interfaces

Declared with the «interface» keyword or the lollipop form, restricted to declarations, and realised by named classes with every feature implemented.

Multiplicity

On every association, at both ends, with the modifiers written where the default would be wrong.

Attributes and methods

Visibility markers on each feature, types after the colon, return types after the parameter list, and derived features marked with /.
