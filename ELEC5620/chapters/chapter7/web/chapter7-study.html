Names and Namespaces

Everything in this week's deck is built on one small idea: a named element is owned by exactly one namespace, and a qualified name is the path you walk to reach it.

Definition — namespace

A namespace is a collection of owned model elements that may be identified by their names. The features of a class (its attributes, operations, and so on) form a namespace; so do a package, a class, a state and a behaviour. Many different manifestations of the namespace concept exist in UML, and the rules below hold for all of them unless a profile tightens them.

Definition — name

A UML name is specified by a string. There is no pre-defined character set and no size limit, so Alice, R2->D2, 4 Sale, селић, 多音字 are all legal. Note the consequence the deck spells out: an empty name is a valid name.

Rule 1 — uniqueness is preferred, not required

Names in a namespace are not necessarily unique. UML tolerates:

  • two operations with the same name but different parameter sets (overloading), and
  • an operation and an attribute of the same class sharing a name.

Because uniqueness is only preferred, a name alone is not always enough to identify an element — which is exactly why the qualified name exists.

Rule 2 — namespaces nest, so names qualify

Namespaces can contain other namespaces, which makes the name space hierarchical. A qualified name joins the levels with a double colon:

System::CoolingSubsystem::ACUnit

Read it as a path: from the outermost namespace inwards, to the element itself. Anything you can say about a filesystem path you can say about it — there is a root, there are intermediate containers, and there is a leaf.

Exam framing: do not answer “names must be unique”. The defensible statement is “names within a namespace need not be unique — overloading and attribute/operation collisions are legal — but uniqueness is preferred, and a qualified name disambiguates”.
A class has an attribute balance and an operation balance(). The model is validated. What does UML say?
The model is invalid: names inside a namespace must be unique
It is legal, because names in a namespace are not necessarily unique
It is legal only because one of the two elements has an empty name

The Concept of Visibility

Names tell you what an element is called. Visibility tells you who is allowed to say it.

Definition — visibility

Every named element owned by a UML namespace has a defined visibility: the capacity for that element to be referenced by other model elements, possibly in other namespaces. Visibility is therefore a property of the reference, not of the element's meaning.

KindSymbolWho may reference itDeck's example
Public+All elements that can access its namespaceA class exposed as part of a package's API
Private−Only elements within the namespace that owns itA helper attribute used by the class's own operations
Protected#Only elements in its extended namespaceA class attribute visible to all subclasses of that class
Package~Only other elements in the same packageA class attribute visible to all elements in the same package as the class
The distinction that gets marked: private is bounded by the owning namespace; protected is bounded by the owning namespace plus everything that extends it (subclasses); package is bounded by the enclosing package, regardless of inheritance. Two elements can therefore both be “not public” and still differ in who can see them.

Worked example — marking up a class and reading the result. Take this class body as the model gives it and decide what each member's visibility buys you.

Account ──────── + id : String - salt : String # auditTrail : Log ~ feeSchedule : Money + debit(amount : Money) : Boolean - hash(p : String) : String
1

+ id and + debit() are the API. They are referenceable by anything that can reach the Account namespace, so they are the only members a collaborating class in another package may name.

2

- salt and - hash() are the implementation. Private members are referenceable only inside Account's own namespace. A subclass cannot reach salt, so it cannot break the hashing scheme by accident.

3

# auditTrail is the inheritance contract. Protected members are referenceable from the extended namespace, so every subclass may append to the audit trail while unrelated classes still cannot see it.

4

~ feeSchedule is the package contract. Package visibility is a sibling of class visibility, not a weaker form of it: a class outside the package fails even if it inherits from Account, and a class inside the package succeeds even if it does not.

5

The exam sentence. “Visibility constrains which model elements may reference a named element: + for all elements that can access its namespace, − for the owning namespace only, # for its extended namespace, and ~ for the enclosing package.”

UML Packages

Packages are the workhorse of model organisation: a means for grouping the parts of a model so that a human can find them.

Definition — package

A Package is a means for grouping the parts of a model. A package is a kind of namespace: public elements from other packages can be imported into the package namespace, which is analogous to “external” declarations in programming.

The sentence students lose marks on: packages are (typically) not intended to model anything. They are analogous to file-system folders — an organisational device for the modeller, not a claim about the system being modelled. The moment a package is presented as a domain concept, the model has smuggled an implementation decision into the analysis.

What goes in a package

  • Classes, interfaces, data types and enumerations
  • Other packages — containment nests, so a package may hold packages
  • Associations and other relationships, as owned model elements
  • Diagrams, as partial views of the contents

How a package appears in a diagram

In diagrams a package is A rectangle with a small tab. Packages are often drawn with their (partial) contents inside, and those contents may themselves be packages. “Partial” is the load-bearing word: a package frame on a diagram is a view, never a complete inventory.

Two equivalent ways to show containment

Both forms are namespace containment. The filled (“black”) diamond is reserved for run-time containment — composition of instances — and reusing it here would conflate a design-time grouping decision with a run-time ownership claim.

Partitioning question to ask yourself: the deck's first question is how to partition your model. A defensible partition follows a stable seam — a subsystem, a layer, a viewpoint — and can be explained in one sentence. A partition that follows whoever happened to draw each class produces a model that only its author can navigate.
Why does the deck insist that a package is not intended to model anything?
Because packages cannot own classes or other model elements
Because it is an organisational device analogous to a file-system folder, not a claim about the system
Because only a Model may carry a viewpoint attribute

Package Import, Access and Merge

Three relationships assemble model content across namespaces. They differ in what becomes visible and in whether the imported element is owned afterwards.

Package Import — «import»

The importing namespace gains the public contents of the target. In the deck's example, after X imports Y, namespace X contains the names:

A, B, C, Y::C, E

… but not D, because D is private. And note the second half of the rule: Y::C and E are not owned by X. Importing makes names available; it does not transfer ownership.

Package Access — «access»

Access is the private-import variant: the target's public contents become available to the accessing namespace without being re-exported from it. This is why the deck's access example asks two different questions — what X contains after accessing Y, and what a third namespace H can then see:

  • X sees the public contents of Y, including the alias Y::C.
  • H sees X's own public names, and does not inherit X's access to Y.

The question mark over D in the deck's slide is the point: private elements stay private under every one of these relationships.

Element import — alias and local visibility

An imported element can be given a local alias and a local visibility. The deck shows the same class imported twice with different results, and asks you to notice the difference:

In XWhat was importedHow X now refers to itLocal visibility
First formY::C imported with the alias BB — the local name, not Y::C{-C}: private within X, so nobody outside X gains the name
Second formY::E imported under its own nameY::E — the qualified name is kept+Y::E: public, so it becomes part of X's exported surface
Element merge — «merge»

Merging combines the contents of the target with the source rather than making them visible: in the deck's diagram, Y's A and C appear in X alongside X's own D and B. Merge is the relationship you use when two models of the same thing have to become one.

Namespace X imports namespace Y. Which statement about the result is correct?
X now owns every element it can name from Y
X can name Y's public elements, including qualified names such as Y::C, but does not own them and cannot see D
X can name D as well, because import copies the whole target namespace

Worked example — predicting the contents of a namespace after import. Given Y with +B, +C, −D and +E, and X with its own A, C and an «import» to Y:

1

List what X had. A and C are owned by X and stay exactly as they were. Import never deletes or renames the importer's own elements.

2

Add Y's public names. B and E become nameable in X, because they are public in Y.

3

Handle the collision honestly. C now exists twice: X's own C and Y's C. UML resolves this with the qualified name, so the imported one is written Y::C. That is why the deck's answer reads “A, B, C, Y::C, E” rather than listing C once.

4

Exclude the private element. D is − in Y, so it is visible only inside the namespace that owns it. X cannot name it, and no import changes that.

5

State ownership separately from nameability. Y::C and E are nameable in X but owned by Y. If the answer to an exam question is the set of names X contains, the set is {A, B, C, Y::C, E}; if the question is what X owns, the answer excludes the last two.

Worked example — choosing between import, access and merge. Three situations, three relationships. Deciding which one applies is the whole skill.

1

Situation A: the reporting package needs to read the domain types. Use «import» if the reporting package's own clients should be able to name those types, because import makes the public contents part of the importer's namespace surface.

2

Situation B: the reporting package needs the types internally, but must not re-export them. Use «access». The names are available to the accessing namespace without becoming part of what its own clients see — the deck's H cannot reach Y through X.

3

Situation C: two teams modelled the same subsystem and the model must contain it once. Use «merge». Merge combines contents rather than granting visibility, so the elements of the target appear in the source and the model keeps a single definition of each element.

4

Then tighten the surface. For any element that did cross a boundary, give it a local alias and an explicit local visibility — the deck's {-C} and +Y::E. An alias keeps the local namespace readable; a local visibility keeps it honest.

5

Note the cycle you have to avoid. If X imports Y and Y merges X, the definitions are no longer layered. Draw the relationships first and check that the graph is acyclic; a cycle here is a design defect, not a tooling problem.

Organising Behaviour Inside the Model

Packages partition structure. The same model also has to partition behaviour — and behaviour has its own containers, which follow the same namespace rules.

BehaviourWhat it describes (Week 7 tutorial)Where it lives in an organised model
ActivityA parameterised behaviour represented as a coordinated flow of actions, with action, object and control nodes; the diagram shows the flow of execution between actions, object nodes and control nodesOwned by the package or class whose behaviour it describes; reusable activities are candidates for a model library
InteractionThe communications between collaborating instances via messages; it requires a prior definition of a collaboration structure that defines the contextOwned by the collaboration or use case it realises; nested inside the package that owns the participating classifiers
State machineDiscrete, event-driven behaviour of part of the designed system through finite state transitions, with initial pseudostate, state, trigger, transition, behaviour and final stateOwned by the classifier whose lifecycle it describes — a class namespace contains its states just as it contains its attributes

The state is a namespace too

The deck's list of namespace manifestations is explicit: Package, Class, State, Behaviour. A composite state owns its substates, its entry and exit behaviours and its internal transitions, so the qualified name of a nested state is a path through the state machine — and the same uniqueness and visibility rules apply inside it.

Event vocabulary you must keep straight

  • Event — an instantaneous change of state in the system.
  • Message event — an object receives a call of an operation or a signal.
  • Change event — a change in the system configuration.
  • Time event — occurs at the specified time.
  • Event occurrence — an instance of an event: it occurs at a particular time instant and has no duration.
A state machine has a composite state Connected containing a substate Authenticated. Which statement is correct?
Substates are a drawing convenience and create no namespace structure
A composite state owns its substates, so the state behaves as a namespace and the substate has a qualified name
Substates belong to the enclosing package directly, so no state is ever a namespace

Week 7 Recap

A namespace owns names

Names are strings with no character-set or length limit, and an empty name is legal. Uniqueness is preferred but not required, which is why nested namespaces give you qualified names with ::.

Naming

Visibility is about reference

+ for all who can access the namespace, − for the owning namespace, # for the extended namespace, ~ for the enclosing package.

Access control

Packages organise, they do not model

Analagous to file-system folders — a namespace, not a claim about the system. Public elements of other packages can be imported into it.

Partitioning

Model = package + viewpoint

Drawn with a triangle, typically top level but still containable. A «modelLibrary» is just a tagged package intended for reusable fragments.

Special packages

Import makes visible; merge combines

After X imports Y, X contains A, B, C, Y::C, E but not D, and it does not own what it imported. Aliases and local visibility then trim the surface.

Relationships

The black diamond is run-time

Namespace containment uses the circle-and-cross. The filled diamond means run-time containment, so the two must never be swapped.

Notation trap
The one-sentence version: model organisation is the discipline of putting every named element in exactly one namespace, deciding who may reference it, and drawing the design-time relationships that assemble a large model out of packages, models and libraries without ever confusing that assembly with run-time structure.
