Foundations: the rules that keep a large model usable

Week 7 has no formulas in the numerical sense, so this page does the equivalent job: it pins down the definitions the lecture relies on, puts every piece of package notation on one reference card, states the naming, visibility and containment rules precisely enough to check a model against them, and finishes with the checklist that turns “organise your model” into a procedure.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Name

A UML name is specified by a String. There is no pre-defined character set and no size limit, and an empty name is a valid name. The deck's own examples include Alice, R2->D2, 4 Sale, селић and 多音字.

Namespace

A namespace is a collection of owned model elements that may be identified by their names. UML has many manifestations of the concept: Package, Class, State and Behaviour are all namespaces, so a class's features form a namespace and so does a composite state's substates.

Qualified name

Namespaces can contain other namespaces, which makes the name space hierarchical. A qualified name walks the nesting with a double colon: System::CoolingSubsystem::ACUnit names the element ACUnit inside the namespace CoolingSubsystem inside the namespace System.

Visibility

Named elements owned by a UML namespace have a defined visibility: the capacity for an element to be referenced by other model elements, possibly in other namespaces. Four kinds are pre-defined: + public, − private, # protected, ~ package.

Package

A Package is a means for grouping the parts of a model. It is a kind of namespace, so public elements from other packages can be imported into the package namespace — analogous to “external” declarations in programming. Packages are (typically) not intended to model anything; they are analogous to file-system folders.

Model and model library

A Model is just a special kind of package: no substantive semantic difference from any other package, one additional attribute (viewpoint), and a triangle icon in diagrams. It is typically the top-level package, but it can still be contained in another package. A model library is just another package with a special tag — no special semantics, but intended to model reusable model fragments.

Names, visibility and containment as rules

Three relationships are worth being able to write from memory: how a qualified name is built, how a namespace's name set is defined, and what visibility quantifies over.

1. A qualified name is the path through the nesting

Write \(N_1 \rhd N_2 \) for “\(N_1\) contains the namespace \(N_2\)”. Then the qualified name of an element \(e\) owned by \(N_k\) is the chain

\[ q(e) \;=\; N_1 :: N_2 :: \dots :: N_k :: \mathrm{name}(e) \]

Read from the outermost namespace inwards. Because \(\rhd\) is containment and not composition, \(q(e)\) describes where the element is filed, not what it is made of — which is exactly why the containment symbol is the circle-and-cross and not the filled diamond.

2. Names in a namespace need not be unique

Uniqueness is preferred, not required. The deck's two counter-examples are an overload and a collision:

\[ \mathrm{name}(op_1) = \mathrm{name}(op_2) \quad\text{with}\quad \mathrm{params}(op_1) \neq \mathrm{params}(op_2) \] \[ \mathrm{name}(attr) = \mathrm{name}(op) \quad\text{within one class} \]

Practical consequence: a bare name is not an identifier. A tool that resolves references must either use the qualified name or disambiguate using the signature, and a modeller who relies on uniqueness is relying on a convention rather than on the language.

3. Visibility is a predicate on the referencing element

Let \(E\) be the element being referenced, \(N\) the namespace that owns it, and \(R\) the element that wants to reference it. In the deck's definitions, where \(\mathrm{ext}(N)\) is the extended namespace of \(N\) (itself plus everything that extends it) and \(\mathrm{pkg}(N)\) the package that encloses \(N\):

\[ \mathrm{visible}_+(E,R) \iff R \text{ can access } N \] \[ \mathrm{visible}_-(E,R) \iff R \in N \] \[ \mathrm{visible}_\#(E,R) \iff R \in \mathrm{ext}(N) \] \[ \mathrm{visible}_\sim(E,R) \iff R \in \mathrm{pkg}(N) \]

Two things follow immediately and both are examinable. First, the four kinds are not a total order: an element in the same package but outside the inheritance hierarchy satisfies \(\sim\) and fails \(\#\), while a subclass in another package satisfies \(\#\) and fails \(\sim\). Second, the deck notes that these are general rules — a profile may constrain them further, but it cannot make a private element visible to the world.

4. A package adds one thing to a namespace

Since package, model and model library are the same machinery with different decorations, the honest way to state the difference is as a pair of optional annotations:

\[ \mathrm{Package} \;\equiv\; \mathrm{Namespace} \] \[ \mathrm{Model} \;=\; \mathrm{Package} \,+\, \langle \mathrm{viewpoint} = v \rangle \] \[ \mathrm{ModelLibrary} \;=\; \mathrm{Package} \,+\, \texttt{«modelLibrary»} \]

The second line is a real attribute that distinguishes two models of the same system; the third line is only a tag with no special semantics. Confusing the two is the most common Week 7 error.

Why the deck asks “why not the black diamond?” Because a filled diamond asserts that the whole owns its parts at run time — if the whole is destroyed, the parts go with it. Namespace containment asserts nothing of the sort: a class does not cease to exist because the package that files it is reorganised. The two symbols answer different questions, which is why the deck answers the question with “black diamond used for run-time containment” and stops there.

Worked example — resolving visibility questions with the predicates. Four queries against the same model; answer each by naming the audience, then checking membership.

1

Query A: can Order reference Customer's − creditRating from another package? The predicate is \(R \in N\), and Order is not inside the Customer class namespace. Answer: no. Private stops at the owning namespace, and no relationship — not import, not access, not merge, not inheritance — changes that.

2

Query B: can VipCustomer, a subclass in the same package, reference # creditRating? The predicate is \(R \in \mathrm{ext}(N)\). VipCustomer extends Customer, so it is in the extended namespace, and the answer is yes — the package it lives in is irrelevant here.

3

Query C: can a helper class in the same package but outside the hierarchy reference ~ creditRating? The predicate is \(R \in \mathrm{pkg}(N)\), and the helper is inside the enclosing package. Answer: yes. Package visibility is the widest of the three non-public kinds when the audience is a package-mate, and the narrowest when the audience is a subclass elsewhere.

4

Query D: an element imported from another package arrives with the alias +Y::E. Who may reference it? The local visibility governs. Declaring the import + makes the imported name part of the importing namespace's public surface, so clients of the importer may name it. Declaring it −, as in the deck's {-C} case, keeps it entirely internal.

5

What examiners look for. Quote the audience, then test membership: “it is ~, whose audience is the enclosing package, and the referencing class is in that package, therefore yes”. An answer that says “because it is accessible” earns nothing.

Import, access and merge as set operations

The deck's worked example is a set-membership question in disguise. Stating it that way makes the answer mechanical instead of memorised.

1. What a namespace contains after an import

Let \(\mathrm{Own}(X)\) be the elements owned by namespace \(X\), and \(\mathrm{Pub}(Y)\) the public elements of namespace \(Y\). After \(X \xrightarrow{\texttt{«import»}} Y\):

\[ \mathrm{Names}(X) \;=\; \mathrm{Own}(X) \;\cup\; \underbrace{\mathrm{Pub}(Y)}_{\text{nameable, not owned}} \]

Two consequences follow directly from the union. Elements of \(Y\) that collide in name with elements of \(X\) are still distinguishable, because the imported one keeps its qualified form — that is where Y::C comes from in the deck's example. And private elements never enter the union at all: \(\mathrm{Pub}(Y)\) excludes \(Y\)'s − members by definition.

2. The deck's example, computed

With \(X\) owning \(A\) and \(C\), and \(Y\) owning \(+B\), \(+C\), \(-D\) and \(+E\):

\[ \mathrm{Names}(X) \;=\; \{A, C\} \;\cup\; \{B, C, E\} \;=\; \{A,\; B,\; C,\; Y::C,\; E\} \]

The doubled \(C\) is written once as \(C\) and once as \(Y::C\) so that both are still addressable; \(D\) is absent because \(D \notin \mathrm{Pub}(Y)\). And the ownership question is answered by a different set: \(\mathrm{Own}(X)\) is still \(\{A, C\}\), so \(Y::C\) and \(E\) are nameable but not owned.

3. Import versus access

Import adds the target's public elements to the importing namespace's name set. Access adds them to the accessing namespace's visibility without adding them to what it exports:

\[ X \xrightarrow{\texttt{«import»}} Y \;\Rightarrow\; \mathrm{Pub}(X) \supseteq \mathrm{Pub}(Y) \] \[ X \xrightarrow{\texttt{«access»}} Y \;\Rightarrow\; X \text{ may name } \mathrm{Pub}(Y), \;\; \mathrm{Pub}(X) \not\supseteq \mathrm{Pub}(Y) \]

This is why the deck's access slide asks a second question about a third namespace \(H\): \(H\) sees \(X\)'s own public names and does not inherit \(X\)'s access to \(Y\). Access is a private import in the sense that matters for layering.

4. Element import: alias and local visibility

An imported element may be given a local name and a local visibility. Writing the deck's two forms as a before/after table:

\[ X \xrightarrow[\;\text{alias } B\;]{\texttt{«import»}} Y::C \;\Rightarrow\; X \text{ contains } B \text{ with local visibility } \texttt{-} \] \[ X \xrightarrow[\;\text{no alias}\;]{\texttt{«import»}} Y::E \;\Rightarrow\; X \text{ contains } Y::E \text{ with local visibility } \texttt{+} \]

The alias and the visibility are independent choices: the alias decides what the element is called inside \(X\), and the local visibility decides whether \(X\)'s own clients can see it. The deck's two “imports” differ on both.

Worked example — computing a namespace's name set after a mixed set of relationships. Namespace X owns \(A\) and \(C\), and has three relationships: it imports Y (+B, +C, −D, +E), it accesses Z (+F, −G), and it merges W (+H).

1

Start from what is owned. \(\mathrm{Own}(X) = \{A, C\}\). This set never changes; none of these relationships transfers ownership into \(X\).

2

Add the import. \(\mathrm{Pub}(Y) = \{B, C, E\}\), so the union gains \(B\), a second \(C\) written Y::C, and \(E\). \(D\) is excluded because it is private.

3

Add the access. X may name \(F\) but does not export it: \(\mathrm{Pub}(X)\) does not gain \(F\). G is excluded. And a namespace \(H\) that imports X receives \(\mathrm{Pub}(X)\) only, so \(H\) cannot reach \(F\) through \(X\).

4

Add the merge. \(H\)'s contents are combined, so \(H\) enters \(\mathrm{Names}(X)\) as an owned-looking element rather than as a qualified reference. That is the observable difference between merge and import in a name set: merge produces a plain name, import produces a qualified one when there is a collision.

5

State the answer twice. \(\mathrm{Names}(X) = \{A, B, C, Y::C, E, F, H\}\) and \(\mathrm{Own}(X) = \{A, C, H\}\). Exam answers that give only one of the two sets are answering only half of the question.

6

Then check the graph. Draw \(X \to Y\), \(X \to Z\), \(X \to W\) and \(H \to X\) as a directed graph and confirm it is acyclic. A cycle in these relationships means a qualified name has become unbounded, and tools will either reject the model or resolve it inconsistently.
