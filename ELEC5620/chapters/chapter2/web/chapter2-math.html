Foundations: the vocabulary, notation and relations of modelling

Week 2 is conceptual rather than mathematical, so this page does the equivalent job. It pins down the definitions the lecture relies on, turns UML notation into a reference card, writes the week's relationships as formulas you can reproduce, and ends with the checklist that decides whether a model is good enough.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Model

A representation of a part of the function, structure or behaviour of a system; a simplification of that system; something that can answer questions in place of the actual system (inference, prediction); built for a purpose (planning, design, risk analysis, testing).

Abstraction

Forgetting some details — deliberately, and for a reason. The deck's one-line form is abstraction is forgetting (some) details, and its engineering consequence is that raising the level of abstraction of the development technology is a basic means of guarding against accidental complexity.

Engineering model

A selective representation of some system that captures accurately and concisely all of its essential properties of interest for a given set of concerns. Every clause is load-bearing: selective, accurate, concise, essential, and relative to concerns.

Software model

An engineering model, specified using a modelling language, of some software that represents (1) design-time views: the structure and content of the software specification; and (2) run-time views: the structure and behaviour of the software in execution.

Model-based software engineering (MBSE) / model-based engineering (MBE)

An approach to system and software development in which software models play an indispensable role. It rests on two time-proven ideas: abstraction (the realm of modelling languages) and automation (the realm of tools).

Viewpoint and view

A viewpoint is a perspective together with the concerns it addresses and the language it uses to express them. A view is the model of the system produced from one viewpoint. The building metaphor is the deck's: architect, builder, designer, electrician, plumber — we do not see everything at once, and what we do see is adjusted to human understanding.

Modelling language, metamodel, stereotype

A modelling language has defined syntax and semantics for expressing models. Its metamodel defines which constructs exist (Class, Association, State, Transition), what properties they have and how they may legally be combined; a model is an instance of the metamodel. A stereotype, written «like this», is a controlled metamodel extension that brands an existing element with domain meaning — as «sc_method» and «sc_slave» do in the deck's SystemC example.

Model repository

The versioned store that holds the models and that tools read, transform and validate against. It is what makes “structured and versioned models” operational: because the model lives in a repository, it can be diffed, reviewed, transformed, generated from and traced through.

Traceability

The recorded links between model elements and the things they exist to serve — requirements, decisions, tests, code. Traceability answers two questions mechanically: why does this element exist, and if this requirement changes, what must be revisited. The tutorial lists requirements traceability among the established capabilities of MBE today.

Model quality

Fitness of the representation to its purpose: accurate (it does not contradict the system), concise (nothing incidental survives), essential (the omissions are deliberate), concern-scoped (you can name the viewpoint it serves) and usable for the purpose it was built for — understanding, prediction, communication or specification.

How to use this card

For any element you draw, be able to say three things: what it is called, what it means, and what would have to change in the system for it to be wrong. If the third answer does not exist, the element is decoration.

Abstraction, refinement and traceability as relations

The Week 2 deck is prose. The relations below are a revision aid written here so you can state the week's claims compactly — they are not lecture notation and should not be quoted as such.

1. A model is a projection of the system

Let \(S\) be the system (or the situation it comes from) and let \(A\) be the set of aspects the model keeps. Then

\[ M \;=\; \sigma_{A}(S), \qquad |A| \;<\; |S| \]

The strict inequality is the definition doing its work: a model that keeps everything is not a model. Selecting \(A\) is what the deck calls forgetting (some) details, and \(A\) is chosen by the concerns, not by convenience.

2. The engineering-model definition is a predicate

\(M\) is an engineering model of \(S\) for the concern set \(C\) when all three hold:

\[ \text{accurate}:\; M \not\models \neg S, \qquad \text{concise}:\; |M| \ll |S|, \qquad \text{relevant}:\; A = A(C) \]

Read it as a checklist rather than as mathematics. Accuracy is a claim about truth, concision about size, relevance about the choice of \(A\). A model can fail any one of the three and still look impressive.

3. Effort splits, and abstraction attacks one half

With \(\ell\) the level of abstraction of the development technology:

\[ E_{\text{total}} \;=\; E_{\text{essential}} \;+\; E_{\text{accidental}}, \qquad \frac{\partial E_{\text{accidental}}}{\partial \ell} \;<\; 0, \qquad \frac{\partial E_{\text{essential}}}{\partial \ell} \;=\; 0 \]

The two derivatives are the deck's argument in one line. Raising the level of abstraction reduces accidental complexity and does not touch essential complexity — which is why modelling is not a cure for a hard problem, only for a badly expressed one.

4. Refinement: the model can become the system

Refinement is a chain in which each step adds detail without contradicting the previous model:

\[ M_0 \;\sqsubseteq\; M_1 \;\sqsubseteq\; \cdots \;\sqsubseteq\; M_n \;\equiv\; S \]

The deck's claim is that this chain can be carried all the way: models can be refined continuously until the application is fully specified, so that the model becomes the system it was modelling. Software is the medium in which this is possible without fundamental discontinuities in expertise, tools or methods, because the model and the system share the same medium.

5. Views partition the concerns, not the system

With \(V_i\) the view produced from viewpoint \(i\) and \(C_i\) the concerns it addresses:

\[ \bigcup_i V_i \;\supseteq\; \text{the parts of } S \text{ that matter}, \qquad V_i \cap V_j \;\neq\; \emptyset \;\text{ for related } i, j \]

Views overlap, and that is not a defect: the same class appears in a structural view and in an interaction view because both need it. The requirement is consistency between overlapping views, not disjointness — which is precisely what consistency checking verifies.

6. Traceability is a relation, and it has a coverage

Let \(R\) be the requirement set and \(E\) the model-element set. Then

\[ T \;\subseteq\; R \times E, \qquad \text{coverage} \;=\; \frac{|\pi_R(T)|}{|R|}, \qquad \text{impact}(r) \;=\; \{\, e \;\mid\; (r, e) \in T \,\} \]

Coverage measures the fraction of requirements that any model element serves; impact is the set you must revisit when requirement \(r\) changes. A model whose traceability has low coverage is not wrong, it is unreviewable: you cannot tell whether a missing element was omitted deliberately.

7. The tool-generated share is a ratio with two named data points

For a codebase of \(L_{\text{total}}\) lines of which \(L_{\text{gen}}\) were produced by tools:

\[ G \;=\; \frac{L_{\text{gen}}}{L_{\text{total}}}, \qquad G_{\text{base station}} = 0.87 \;\text{ of } 2\text{M lines}, \qquad G_{\text{network controller}} = 0.80 \;\text{ of } 4.5\text{M lines} \]

These are the deck's results for a major telecom equipment manufacturer using UML, Rational Technical Developer and the Rational Unified Process. The ratio measures leverage, not correctness: the deck's own generation slide shows a bug surviving into the generated switch statement.

One sentence that ties the page together. Modelling is the deliberate choice of \(A\) for a stated \(C\), refinement is the disciplined growth of \(M\) towards \(S\), and traceability is what keeps the whole chain auditable when \(R\) changes.
A team raises the level of abstraction of its development technology: they model the appointment workflow instead of hand-writing the state handling. According to relation 3, what should happen?
Both halves of the effort fall, because the model is simpler than the code
Accidental effort falls and essential effort is unchanged
Essential effort rises because the model must be reviewed as well

Worked example — put the deck's numbers through the relations. The telecom result gives two data points; traceability gives a third quantity to compute.

1

Radio Base Station. \(L_{\text{total}} = 2{,}000{,}000\) lines and \(G = 0.87\), so \(L_{\text{gen}} = 1{,}740{,}000\) lines. The hand-written remainder is \(260{,}000\) lines — the part that carries the design decisions no transformation could make.

2

Network Controller. \(L_{\text{total}} = 4{,}500{,}000\) lines and \(G = 0.80\), so \(L_{\text{gen}} = 3{,}600{,}000\) lines, leaving \(900{,}000\) hand-written lines.

3

Combined leverage. Total lines \(= 6{,}500{,}000\); generated lines \(= 5{,}340{,}000\); so the pooled ratio is \(G = 5{,}340{,}000 / 6{,}500{,}000 \approx 0.822\), about 82%. Note that the pooled figure is a weighted average: the larger system has the lower ratio, so it pulls the combined value down.

4

Traceability coverage on a small example. Suppose the appointment service has 24 requirements and the model traces 19 of them. Then \(|\pi_R(T)| = 19\) and coverage \(= 19/24 \approx 0.79\), or 79%. The five untraced requirements are the review agenda: for each one, either a model element is missing or the requirement is out of scope. Saying which is the point of measuring coverage at all.

5

Impact analysis. If \(T\) contains \((r_7, e_2), (r_7, e_5), (r_7, e_9), (r_7, e_{14})\), then \(\text{impact}(r_7) = \{e_2, e_5, e_9, e_{14}\}\) — four elements to revisit, all of them found by lookup rather than by memory. This is the mechanical answer the definition of traceability promises.

6

What the ratio does not tell you. \(G = 0.87\) says nothing about correctness. Because generation is only as good as the model and the transformation, the reviewable artefact is the model plus its traceability — and the deck's generation slide shows a bug surviving into the generated code precisely to make that point.

Model quality checklist

The engineering-model definition is the rubric. Turn it into questions and it will tell you what is wrong with a model before a reviewer does.

AttributeQuestion to askHow it typically fails
AccurateDoes anything in the model contradict the system or the requirement?A stale diagram that was right two iterations ago and is now trusted
ConciseWhich of these elements would survive if the model had to be half its size?Every attribute of every class reproduced, so nothing stands out
EssentialWas each omission a decision, and can you say why?Omissions nobody noticed, discovered later as missing requirements
Concern-scopedWhich viewpoint does this element serve, and can you name its reader?A diagram that mixes persistence, UI and protocol concerns in one picture
ConsistentDo overlapping views still agree about the same element?A class renamed in one view and not in another; multiplicities that contradict
TraceableCan every element be traced to a requirement, and every requirement to an element?Coverage so low that nobody can tell omission from oversight
Fit for purposeDoes it do the job it was built for — understand, predict, communicate, specify?A precise model that nobody can read, or a readable one nothing can be generated from
The two questions that catch most bad models. “What does this element commit us to?” — if nothing, it is decoration. “What would have to change for this element to be wrong?” — if nothing could, it is not a claim about the system.

Worked audit — a model that looks complete. A team submits a 14-page class diagram of the one-person AI company: every entity, every attribute, every getter. Run the checklist over it.

1

Accuracy first, because everything else is worthless without it. Compare three elements against the running system. If the diagram still shows an Order.status field that the code deleted, stop: nothing downstream of an inaccurate model can be trusted.

2

Concision. Getters and setters are not design. Neither is an attribute that nothing else in the model refers to. Removing them is not losing information; it is restoring the signal-to-noise ratio that makes the diagram readable.

3

Essentiality of the omissions. The diagram has no state machine, no actor and no boundary. Are those omissions deliberate? For a structure-only view they might be — but then the model has no run-time view, and the software model is only half present.

4

Concern scope. The diagram serves no single concern: it is a persistence view and an API view and a UI view in one picture. Split it by viewpoint, and each part immediately becomes smaller and more checkable.

5

Traceability. Ask for the coverage figure. If nobody can produce one, the model cannot be reviewed for completeness — which is a stronger criticism than any individual mistake in it.

6

Verdict and the sentence to write. “The model is accurate but not concise and not concern-scoped: it reproduces implementation detail instead of the essential structure, so it supports communication weakly and specification not at all. Split it by viewpoint, drop the accessor noise, add a run-time view for the appointment workflow, and report traceability coverage.”

A model is accurate, readable and well scoped, but nothing in it can be traced to a requirement. Which criticism is the strongest?
It is inaccurate
It is not concise enough
It cannot be reviewed for completeness, because deliberate omissions cannot be distinguished from oversights

Tutorial 2 and Lab Note 2 review

Tutorial 2 is a modelling studio on two sample projects; Lab Note 2 turns the theme into project requirements. Everything below comes from those two documents.

Actors are roles

An actor is outside the system, interacts with it and has a goal. The shoe-store sample lists Customer, Store Adviser, Store Admin and an external Payment / Delivery Service. Actor ≠ person name.

The boundary defines responsibility

Inside the shoe store: collect preferences, generate recommendations, explain and compare, manage product information, create an order request. Outside: the customer who chooses, the adviser who reviews, the service that processes payment.

Write the boundary rule down

Tutorial 2's rule: the AI may recommend and explain; it does not make the final purchase decision. A boundary rule is a testable constraint, which is why it belongs in the model rather than in the pitch.

The MVP question

“Can the assistant help a customer make a better shoe choice?” Keep only the features needed to test that value; everything else — 3D try-on, social feed, voice assistant — is added later.

At least three distinct AI roles performing primary stakeholder or business functionsThree actors with different goals, not three copies of one agent. Each needs its own use cases and its own boundary.
Every group member implements at least two core features and one optional featureEach of those features is a model element traceable to a goal. The optional feature is explicitly outside the MVP and must be modelled as such.
A three-minute topic presentation: what real-world problem does it solve, and which roles should be performed or replaced by AI agents?Two sentences that are really a problem-domain model and a boundary decision — the same two artefacts the tutorial asks you to draw.
