Foundations: the notation and the rules behind agile model practice

Week 8 is about process and practice rather than mathematics, so this page does the equivalent job: it fixes the definitions, gives you the notation card for the two diagram types the tutorial puts in front of you, writes the relationships between a model, its tests and its code as compact rules, and ends with the checklist that decides whether a model is kept or dropped.

Definitions and process terms

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Agile development

A way of organising product development that is adaptive (teams and process stay flexible under rapid-fire change), iterative and incremental (working products in stages, a growing set of completed and working software) and people-oriented (the team organisation and process support good people, who are the most important ingredient to project success). Its framework asks teams to keep things small, deliver partially-completed software frequently, talk to the customer often, write more code than documentation, and learn together.

Iteration (Sprint)

A timeboxed development cycle of 2 to 4 weeks containing a list of tasks and work product outputs. It opens with iteration planning, contains development work, and closes with an iteration review; the team tracks the iteration with a burndown chart and reflects in a retrospective. Management does not add new work to a running Sprint — new items go on the Product Backlog.

Backlog, task view and estimate

The Product Backlog is the set of all features and sub-features known to be needed, in priority order by value to the customer, and items may be added at any time. Within an iteration the team divides its Product Backlog Items into individual tasks — the task view is used only inside the iteration. Every PBI carries an estimate of effort, and estimates come from the team, never from managers.

User story

The unit of work in agile: an informal, general explanation of a software feature, simpler than a use case, written from the user's perspective and used to drive collaboration. The template is “As a <role>, I want to <goal> so that <benefit>”. A user persona is a fictional but detailed representation of a typical user; an epic and a theme name the larger groupings a story belongs to.

What makes a model agile

The lecture's own tests for an agile artefact apply directly to models. These are the three questions to run before you draw anything, plus the two properties that decide whether the result was worth keeping.

1. The keep-or-drop test is a conjunction

Keep a model only when all three hold. With \(P\) for purpose, \(A\) for audience and \(L\) for a maintenance lifetime:

\[ \text{keep} \;=\; P \;\wedge\; A \;\wedge\; L \]

The conjunction is the point: a complete model with no reader is dropped, and so is a useful model nobody plans to update. This is the modelling reading of the deck's advice that a document nobody reads should be left out “because you are Agile”.

2. Value per unit of effort, not completeness

Agile modelling maximises the decisions a model settles per unit of effort spent. If a model of size \(s\) settles \(d\) decisions, and the alternative is to answer \(d\) questions in code at cost \(c\), the model earns its place when:

\[ \frac{d}{s} \;>\; \frac{d}{c} \quad\Longleftrightarrow\quad s \;<\; c \]

In words: model the question when the model is cheaper than finding out by building. That is why a two-class slice and a three-state machine are the right size for a Sprint, and a whole-system class diagram is not.

3. Executable means every transition is total

A state machine is executable when each transition \(t\) specifies all three parts — trigger, guard and effect — and the guards are exhaustive enough that the machine always knows what to do:

\[ t \;=\; \langle\, \textit{trigger},\; \textit{guard},\; \textit{effect} \,\rangle \]

A transition with a trigger but no guard is a machine that can fire when it should not; a guard with no effect is a machine that fires and leaves no evidence. Both failures are invisible in a diagram and fatal in an executable model.

4. Testable means the claim can fail

Every constraint the model asserts must map to at least one check that can fail. For a model element \(m\) with claim \(k(m)\), require:

\[ \forall\, m \in M:\; k(m) \;\Rightarrow\; \exists\, \tau \in T \text{ such that } \tau \text{ fails when } k(m) \text{ is violated} \]

Multiplicity is the clearest case: a model that says a user has 0..* preferences is asserting that a second preference is legal and a missing channel is not. If no test can fail on that, the multiplicity is decoration.

Where the requirement meets the model. The Week 8 deck advises creating acceptance tests at the same time as you write the key requirements. In this framework that is not a testing preference but a modelling constraint: the test is what makes the model's claims falsifiable, so it is part of the iteration's definition of done rather than a later phase.

Package rules worth writing down

  • A package name must be unique within a system; class names need not be.
  • Packages may contain whole diagrams, the names of components alone, or nothing at all.
  • Nested packages are hierarchical, and their atomic modules are usually class diagrams.
  • A package represents a namespace, so it is also the unit you version and review.

Deployment rules worth writing down

  • A deployment diagram describes the structure of the system at runtime: hardware configuration and how software is deployed into the network.
  • There is only one deployment diagram for a system model.
  • It is the diagram that controls performance, scalability, maintainability and portability.
  • Most UML diagrams deal with logical components; this one focuses on the hardware topology.

Model, tests and code as one system

The week's central relationship is between three artefacts that must agree: the model, the tests derived from it, and the code generated from it. Written as a relation, the round trip is a fixed point rather than a one-way street.

The consistency relation

Let \(M\) be the model, \(T\) the test suite and \(C\) the code, and let \(g\) be the generator and \(r\) the reverse step:

\[ C \;=\; g(M), \qquad M' \;=\; r(C) \]

The loop is closed when \(M' = M\), that is, when the code contains nothing that the reverse step has not already accounted for. Every difference is either a defect in the code or a discovery that belongs in the model — there is no third option, and leaving it in the code is what makes the loop a race.

Three conditions for a usable round trip

\[ \text{round trip} \;=\; \textit{deterministic}(g) \;\wedge\; \textit{generated}(C) \subseteq g(M) \;\wedge\; \forall\, e \in \textit{manual}(C):\; e \in \textit{marked}(C) \]

Deterministic transformation (same model, same output); the model is the single source for everything the generator owns; every manual edit is marked and either protected from regeneration or moved back into the model. Drop any one condition and the next regeneration silently loses work.

Traceability as a total function

Each requirement \(q\) should map to at least one model element \(m\) and one test \(\tau\):

\[ \forall\, q \in Q:\; \exists\, (m, \tau) \;\text{ with }\; q \rightarrow m \rightarrow \tau \]

This is the modelling reading of the deck's requirements advice: for key requirements, the acceptance test is created at the same time as the requirement. A requirement with no model element is unimplemented; a requirement with no test is unverifiable; a model element with neither is a candidate for the keep-or-drop test above.

Worked answer — reading a dependency graph for trouble. You are handed the Week 8 tutorial's Order Processing subsystem and asked whether the package structure is healthy. Work it through in four moves.

1

Name every package and its namespace. Track Order, Order Processing, Shipping, plus the external UI Framework. Each is a namespace, so Track Order.Status and Order Processing.Status may coexist while the package names themselves must be unique.

2

Check each arrow against the rule. Track Order takes order details from Order Processing, and Order Processing needs the tracking information the customer supplied. Both directions therefore exist, and the tutorial calls the result an «access» dual dependency. Shipping's functionality is imported by Track Order, so that arrow is «import».

3

Say what the cycle costs. A two-way dependency means the two packages cannot be understood, tested or released independently: a change to the tracking display can force a change in order processing and the reverse. It is not automatically wrong — the tutorial draws it deliberately — but naming the cost is the markable observation.

4

Propose the smallest repair, and test it. Introduce an interface the tracker publishes (TrackingQuery) that Order Processing consumes, so the dependency points one way. Then check the claim: removing the reverse arrow should not break the tracking scenario, and a change to the tracking screen should no longer be able to force a change in order processing.

The round-trip rules

The consistency relation above is easy to state and easy to break. These are the four decisions that keep it true under a two-week iteration, in the order you would explain them.

DecisionRuleSymptom when it is broken
What the generator ownsEverything the transformation emits is owned by the model; generated regions are never edited by handRegeneration overwrites a fix and the defect returns
What is hand-writtenManual code lives in marked, protected regions or in a separate file the generator does not touchThe distinction between generated and manual code is lost within two Sprints
Where discovery goesA finding in the code is folded into the model in the same changeThe model drifts into a historical sketch and reviewers stop trusting it
When the loop is checkedInside the iteration, by the tests derived from the model and the acceptance criteria“Done” means the demo worked once, and the burndown reflects hope rather than state
The exam sentence for the round trip: the model is generated forward into code, the code is read back into the model, and the loop is safe only when the transformation is deterministic, the model owns everything generated, and every manual edit is marked — which is what lets a model survive rapid-fire change instead of becoming the document the week warns about.

Keep-or-drop and tutorial review

The Week 8 tutorial asks for two diagrams and a Jira board. Use this checklist to audit what you produced before you commit it to the Sprint.

Package diagram audit

One tab per package, unique names, every arrow justified by the change-propagation rule, and each dependency stereotyped as «import» or «access» where the distinction is meaningful.

Deployment diagram audit

Exactly one diagram for the system model; nodes, node instances and artifacts distinguished; every communication path carrying its protocol; the four parameters (performance, scalability, maintainability, portability) answerable from what is drawn.

Backlog audit

Every item ordered by value to the customer, every estimate made by the team, MoSCoW applied so the Sprint holds the must-haves and should-haves, and any new request sitting on the Product Backlog rather than in the running Sprint.

Model audit

Each model names its question, its reader and its update point; each constraint maps to a check that can fail; each transition carries a trigger, a guard and an effect.

Candidate modelVerdictReason
Two-class slice for the preference storyKeepSettles the ownership decision, has a reader in the team, updated with the code
Three-state preference lifecycleKeepThe guard on the return transition is a decision the story does not make on its own
Package diagram of the whole productTrimOnly the packages the increment touches change a decision this Sprint
Deployment diagram of an environment nobody will provisionDropFails purpose and lifetime; the tutorial's own example is a clustered environment that is actually assumed
Sequence diagram of the unchanged login flowDropFails purpose and audience; the code is the clearer source of truth

Worked answer — auditing a Sprint's models in five questions. Sprint goal: “A customer can track an order from the store's order-processing screen.” The team has produced a package diagram, a deployment sketch and a preference state machine it never used.

1

Purpose. The package diagram settles where tracking logic lives and whether the two-way dependency is acceptable; the deployment sketch settles whether the cluster can serve the lookup. The preference state machine settles nothing in this Sprint. Verdict on the third: drop it, and note in the retrospective that it was written before the story was understood.

2

Audience. Both kept diagrams are read by the whole team during the Sprint, and the deployment sketch is read again at the review when performance is discussed. Name a reader for each or the artefact goes.

3

Lifetime. Both are updated in the same change as the code and both are re-examined at the review. Without that commitment they become the stale artefacts the week warns about, and the correct decision is to delete them rather than keep them “just in case”.

4

Falsifiability. Every constraint gets a check: the dual «access» dependency is reviewed against the rule that a change in one package can force a change in the other; the tracking state machine's guard “serial number is well formed” is tested with a malformed serial that must never leave the submitted state; the lookup timeout has a test that fails when the status never resolves.

5

Cheaper place to answer. The unknown-serial message was modelled, then dropped: one line of code answers it faster than a diagram. That is the trade the week is asking you to make deliberately, not a failure of rigour.
