Foundations: the definitions and notation of architectural modelling

Week 4 is a modelling week, so the foundations page is a notation page. It pins down the definitions the lecture relies on, draws the UML notation you are expected to read and produce, states the relationships between design space, viewpoints, patterns and V&V as compact expressions, and ends with the checklist that turns a vague architecture answer into a markable one.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Architecture — ISO/IEC/IEEE 42010

“[the] fundamental concepts or properties of a system in its environment embodied in its elements, relationships, and in the principles of its design and evolution”. An architecture description is “[a] work product used to express an architecture”.

Architectural principle

A general design principle or invariant that holds across the system — for example “there shall be no single point of failure in components deemed critical”. Principles are what make a proposed change decidable: they are the rules the detailed design must not break.

Viewpoint and view — IEEE 1471

A viewpoint identifies the set of concerns and the representation techniques used to describe the architecture to address those concerns. A view is a representation of a whole system from the perspective of a related set of concerns: the result of applying a viewpoint to a particular system.

Model of computation (MoC)

The rules governing how computational components execute, communicate, synchronise and exchange data, which explain how the behaviour of the whole system is the result of the behaviour of each of its components. Two families: structure-dominant, and behaviour-dominant — the latter splitting into procedural (control-flow based) and data flow.

Control in architecture

The set of (additional) mechanisms and actions required to bring a system into the desired operational state and to maintain it in that state in the face of various planned and unplanned disruptions: start-up and shut-down, failure detection/reporting/recovery, administration, maintenance and provisioning, and on-line software upgrade.

Architectural design pattern

Defines types of elements and relationships that work together in order to solve a particular problem from some perspective (viewpoint). It is composed of a context (a recurring common situation), a problem arising in that context, and a reused solution to that recurring design problem. Its value is abstraction, minimal change and a general structure.

Design space, views and V&V as relationships

Five relationships are worth being able to write from memory. They are revision notation: compact statements of what the lecture says in prose.

1. An architecture is a projection of the solution space

Let \(R\) be the requirement set, \(S_0\) the set of solutions that satisfy \(R\), and \(A\) an architecture for \(R\). Then

\[ S_A \;=\; \{\, s \in S_0 \;:\; s \text{ conforms to } A \,\}, \qquad S_A \subset S_0 \]

The point is not the set theory but the asymmetry: \(S_A\) is much smaller than \(S_0\), and every later decision is taken inside \(S_A\). An architecture that does not shrink \(S_0\) has not decided anything.

2. The full specification is a union of views

With \(L\) logical, \(D\) development, \(P\) process and \(Ph\) physical, and a scenario \(u\) drawn from the use-case view:

\[ \text{Spec} \;=\; L \cup D \cup P \cup Ph, \qquad \text{slice}(u) \;=\; \bigl(L_u,\; D_u,\; P_u,\; Ph_u\bigr) \]

Each view describes different aspects of the system, so no view is complete and none is redundant. The scenario is a vertical slice through all four, which is why it is the “+1” and not a fifth competing view. Consistency is a separate obligation: the views must agree where they overlap.

3. Coupling is a counting argument

For \(n\) participants, a fully connected point-to-point architecture needs

\[ E_{\text{p2p}} \;=\; \frac{n(n-1)}{2} \;=\; O(n^2), \qquad E_{\text{mediator}} \;=\; n \;=\; O(n) \]

At \(n = 6\) that is 15 links against 6; at \(n = 20\), 190 against 20. The saving is bought with a new critical component: the mediator is now a single point of failure and a potential bottleneck, which is exactly the kind of statement an architectural principle has to rule on.

4. Control predicates function

Let \(\mathrm{op}(t)\) mean the system is in its operational state at time \(t\), and \(\mathrm{fn}(t)\) mean it is performing its primary function. Then

\[ \mathrm{fn}(t) \;\Longrightarrow\; \exists\, t_0 < t \;:\; \mathrm{op}(t_0) \;\wedge\; \text{maintained}(t_0, t) \]

Control is a precondition, not a feature. The deck's second observation is the engineering consequence: the process by which a system reaches its operational state is often the same regardless of the component's functionality, so control can be designed once — provided it is separated from function and centralised rather than retrofitted into a framework built for functionality.

5. Verification and validation test different things

Write \(I\) for the implementation, \(Sp\) for the specification and \(N\) for what the user actually needs:

\[ \text{verification}: \quad I \models Sp \qquad\qquad \text{validation}: \quad Sp \models N \]

The two are independent. \(I \models Sp\) can hold perfectly while \(Sp \models N\) fails, which is the failure the deck's joke is about: nothing works and nobody knows why. A pattern, similarly, is a triple

\[ \Pi \;=\; \langle\, C,\; Pr,\; So \,\rangle \]

context, problem and solution — and quoting \(So\) without \(C\) is quoting a solution to a problem nobody has.

Why these ten pairs. Each one is a distinction that a single word hides: shared versus exclusive ownership, mandatory versus optional inclusion, ordering versus structure, specification versus instances, and conformance versus adequacy. Exam questions in this unit are usually built from exactly these contrasts.
A team proves that their implementation conforms to the specification, and separately proves that the specification satisfies every recorded stakeholder requirement. What have they established?
Verification only, because the second proof is also about the specification
Verification and validation: conformance of the artefact to the specification, and adequacy of the specification to the needs
Neither, because only formal methods were used

Worked example — putting numbers on the design-space and coupling arguments. A team must connect six clinical subsystems: triage, records, scheduling, notification, knowledge base and audit.

1

Count the point-to-point case. \(E_{\text{p2p}} = n(n-1)/2 = 6 \times 5 / 2 = 15\) links between six subsystems. Every subsystem must know five peers' protocols, and every change to one protocol is potentially five edits.

2

Count the mediator case. \(E_{\text{mediator}} = n = 6\) links. Each subsystem knows one interface; adding a seventh subsystem is one new connection, not six.

3

Price the saving. The mediator is now on every path, so it is a single point of failure and a throughput ceiling. That directly contradicts the principle “there shall be no single point of failure in components deemed critical” unless the mediator is replicated or the clinical paths that must survive it are routed around it.

4

Express the design-space claim. Before the decision, the requirement set admits both the fully connected design and the mediated one plus hybrid variants: \(S_0\) contains all of them. After choosing mediation, \(S_A\) contains only the mediated family with different replication strategies. That reduction is the architecture's contribution — and it is also the reason the decision is expensive to reverse later.

5

Write it as a principle, not a preference. “All inter-subsystem communication passes through the integration mediator; critical clinical paths have a declared direct fallback.” Now the next team can decide whether a proposed shortcut is admissible, which is the whole purpose of recording principles.

Classification checklist

Most Week 4 questions reduce to “which viewpoint, which model of computation, which pattern — and why?”. Run the system through these steps in order and the justification writes itself.

DecisionLook forMarks are lost when…
1. Quality attributesSafety, privacy, security, reliability, availability, performance, scalability, auditability, maintainability, explainabilityYou list features instead of the properties the architecture must guarantee
2. Locus of computationOne node or many; what the choice eliminates from the solution spaceYou describe a deployment without saying what it ruled out
3. Model of computationStructure-dominant, procedural or data flow — and the trigger that starts a componentYou confuse an agent's reasoning loop with the system's MoC
4. Control structureStart-up, failure detection and recovery, administration, on-line upgrade; policies versus mechanismsYou treat control as error handling bolted on afterwards
5. PatternContext, problem, solution — and the published disadvantageYou name a pattern without the context that makes it valid
6. ViewpointsWhich concerns each view addresses, in which notation, and where the views must agreeYou draw one diagram and call it the architecture
7. RationaleThe principles, and the alternatives that were rejectedYou leave the next team to reconstruct intent from the code — the road to decay
A system reads a stream of claims, validates each one, enriches it from a shared reference database and writes it to a queue. Which pair of decisions is most defensible?
Data-flow model of computation with the pipe-and-filter pattern; shared-data for the reference database
Structure-dominant model of computation with the blackboard pattern
Model-View-Controller with a layered decomposition

Worked classification — the agentic healthcare consultation, run through the checklist.

1

Quality attributes. Safety (can unsafe agent actions be prevented or escalated?), privacy (which agents can access patient information?), auditability (can we reconstruct why an action occurred?), availability (can patients reach critical services during failures?), explainability (can important decisions be traced?). Five attributes, each already phrased as an architecture question.

2

Locus of computation. Identifiable data stays in a private environment; de-identified context may reach an external LLM. That one decision eliminates every solution in which a single general-purpose model sees the full record — including some that would have been cheaper and more capable.

3

Model of computation. Agents are components that hold state and react to stimuli and messages, so the system-level MoC is structure-dominant; the chaining of retrieval, reasoning and action inside one agent is a data-flow pattern at the agent level. Say both, and say which level each belongs to.

4

Control. Separate control from function: the guardrails, approval rules and escalation policies live in the control components; the mechanisms live inside each agent. Centralise the decision to escalate. If the required behaviour is a fixed collect–assess–book order, choose workflow control, which is predictable and auditable; if the order must adapt, choose supervisor control and accept that the supervisor becomes the component to test.

5

Pattern. The intake is data-flow; the knowledge base is shared-data; the clinician's review screen is MVC; the LLM workflow is preprocess–construct–infer. State the disadvantage you have accepted for each: limited interactivity in the pipeline, scalability at the shared store, extra indirection in MVC.

6

Viewpoints and rationale. Logical for responsibilities, development for the prompt and policy artefacts, process for concurrency and the coordination problem, physical for data and model placement, scenario for a vertical slice. Then record the principles — no identifiable data in an external call, high-impact actions require approval — so that the next team can tell a violation from a change.

Tutorial 4 and Lab 4 review

Tutorial 4 recaps the lecture and then asks how viewpoint analysis is actually performed and documented. Lab 4 asks you to do it on your own project. Use this page to audit the result.

Define objectives and scope

Clarify the analysis goals, define the scope and the relevant viewpoints, identify the stakeholders who are affected or interested, and define viewpoints aligned with their concerns.

Select viewpoints

Choose by system complexity and requirements, and fix the focus of each viewpoint. “4+1” is the model the unit expects unless you can justify another.

Collect and organise

Gather requirements documents and design specifications, and organise them into analysable formats — diagrams, using proper tools such as UML.

Analyse and integrate

Analyse each viewpoint in detail, identify the interactions and dependencies between them, then summarise everything into one architecture description — consistent, without contradictions or conflicts.

What the report must contain

Organise the results: compile the findings from all viewpoints, including identified issues and improvement suggestions. Structure the report: introduction (purpose and scope of the analysis), viewpoint analysis (results for each viewpoint), issues and recommendations (problems and suggested improvements), conclusion (key findings and next steps). Use visual aids: diagrams and models that visualise complex structures and interactions, kept simple and focused on key information. Purpose: clear guidance for development and maintenance, and a long-term reference for understanding the system.

Tutorial-style worked answer — a viewpoint analysis report outline for the agentic healthcare consultation.

1

Introduction — purpose and scope. “This analysis documents the architecture of the patient consultation service so that the clinical safety and privacy requirements can be reviewed against a single description. In scope: triage, clinical knowledge retrieval, appointment scheduling and notification, plus the clinician review step. Out of scope: billing and the hospital's appointment system internals, which are treated as an external tool.” Stakeholders named: patient, clinician, hospital privacy officer, operations.

2

Viewpoint analysis — one subsection per view. Logical: the agents and shared services, with the responsibilities of each drawn as a class or sequence diagram. Development: the package structure, including where prompts, guardrails, policies and schemas live — this is where an agentic system stops looking like an ordinary codebase. Process: concurrent agent execution and the coordination problem, drawn as an activity diagram with the communication service that prevents two agents speaking to the patient at once. Physical: the private node and the external model endpoints, with the artefact placement that enforces the data boundary. Scenario: “patient reports headache and fever”, traced through all four.

3

Issues and recommendations. Issue: the follow-up and appointment agents can both initiate patient contact, which is a coordination defect visible only in the process view. Recommendation: route all patient-facing messages through the communication service and record the decision as a control policy. Issue: the development view does not yet place the prompt templates under version control. Recommendation: treat them as artefacts with the same review process as code.

4

Consistency check across views. Every logical component must appear in the development view as an owned artefact, every concurrently executing agent must appear in the process view, and every process entity must be mapped to a node in the physical view. A component that appears in the logical view and nowhere else is either undocumented or unwanted — either way the description is inconsistent.

5

Conclusion and next steps. Summarise the findings, state which principles the architecture now commits to, and list what still has to be decided. The report's stated purpose is to give clear guidance for development and maintenance and to serve as a long-term reference — which is the same objective as avoiding architectural decay.
