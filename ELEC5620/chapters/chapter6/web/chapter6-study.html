How Things Happen in UML

Week 5 modelled what a system is. Week 6 models what it does: the deck calls the underlying story UML's model of causality.

The model of causality from the lecture: UML is a discrete, event-driven model of computation built from a network of communicating objects. All behaviour stems from objects — an action is always executed by some object, on some object.

Individual object behaviour

The behaviour specification attached to one class or object: which actions it performs, in what order, and how it reacts to the events it receives. A state machine is the canonical notation for this view.

Inter-object (system) behaviour

The emergent behaviour of the network: objects invoking operations on each other and sending signals. This is what an interaction (sequence or communication diagram) or an activity diagram captures.

Action, in the deck's words

An action is a named element which represents a single atomic step within an activity, i.e. that is not further decomposed within the activity. An action is executed by an object and may change the contents of one or more variables or slots. If it is a communication action it may invoke an operation on another object or send a signal to another object. Its successor actions are determined either by control flow or by data flow.

FormalismModel of computationAnswers the question

ActivitiesControl and data flowIn what order do the steps run, and who performs them?

What if the user cancels mid-booking? How do you distinguish a failed booking from a successful booking whose response was lost? What if an older symptom summary finishes processing after a newer one? Models give the developer and the coding agent a shared place to resolve these questions before they become inconsistent code — and the modelling effort should stay proportional to the uncertainty.

Actions: The Atomic Step

Every behaviour in UML is ultimately a combination of actions. Getting the granularity right is what makes a model checkable rather than decorative.

Action vs activity

Action — a named element representing a single atomic step within an activity, not further decomposed inside that activity. Activity — a behaviour composed of individual elements that are actions, represented as a coordinated flow of them. Actions are drawn as round-cornered rectangles, and the name is usually an action verb or a noun with a short explanation.

What actions are for

Modelling fine-grained behavioural phenomena that manipulate and access UML entities — objects, links, attributes, operations. The deck's examples are exactly this granularity: create link, write attribute, destroy object.

What the standard fixes

The UML standard defines both a set of actions with their semantics (what happens when each is executed) and a method for combining actions into more complex behaviours. Two modellers using the same action vocabulary must get the same run-time meaning.

Objectcreate, destroy, reclassify, startStarting an active object; the initial node of a workflow creating its first object
Linkcreate, destroy, read, writeCreating the association between a booking and a slot

The tutorial's framing: actions and activities cover micro-level behaviour, while state machines and interactions capture macro-level behaviour. A model that mixes the two levels in one diagram is a model nobody can check.

Run Time: Active Objects and Run-to-Completion

Actions need a scheduler. The deck's answer is the distinction between passive and active objects, and the run-to-completion rule that keeps concurrent events from tearing an object apart.

Active object, in the deck's words

An active object is an object that, as a direct consequence of its creation, commences to execute its classifier behaviour, and does not cease until either the complete behaviour is executed or the object is terminated by some external object. The points at which it responds to messages received from other objects are determined solely by its own behaviour specification. Notation: the class box carries parallel lines on its left edge to distinguish it from a passive class.

Passive objects

  • Respond whenever one of their operations (or receptions) is invoked
  • Invocation is not scheduled by the object itself
  • Concurrent invocations are possible, so conflicts are possible
  • Reading getA() while another caller runs setA(1) is the classic hazard

Active objects

  • Run concurrently with everything else in the system
  • Respond only when they execute a receive action
  • Incoming messages wait in a message queue
  • Which queued event is taken is decided by the chosen scheduling policy
Run-to-completion (RTC)

Any messages arriving between successive receive actions are queued and only considered for handling on the next receive action. The object handles one thing at a time: the current step always finishes before the next event is looked at. This is what avoids concurrency conflicts inside one object.

RuleStatement in the deckConsequence for design
QueuingEvents arriving mid-step are queued, not deliveredNo state is observed half-updated — but latency is bounded by the longest step
PriorityIn some systems (for example real-time systems) messages carry different prioritiesHigh-priority events can jump the queue and interrupt handling of low-priority ones
Priority inversionA high-priority message has to wait for a low-priority messageRTC is susceptible to it — but only where the high- and low-priority events are handled by the same object, not by the system as a whole
InterruptionIf a high-priority event arrives for an object that is ready to receive it, processing of low-priority events by other active objects can be interruptedPriority is a cross-object scheduling property, not a private one
Communication typeMottoWhat happens
SynchronousCall and waitObject1 calls opX(); Object2 executes the method; Object1 blocks until the reply returns
AsynchronousSend and continueObject1 sends sigX() to a reception, or makes an asynchronous operation call whose replies are discarded; Object2 executes the method while Object1 continues
RTC in agentic software. The deck's example: an agent receives a plan from an LLM and then validates the proposed tool action, records the tool request identifier, arranges asynchronous tool execution, and enters WaitingForTool. If the user sends Cancel during those updates, what could happen if the cancellation were processed halfway through updating the agent's state? The design rules that follow: keep reactions short, treat LLM output as input to validate, and define the boundary of what one reaction may change.

Activities: Control Flow, Object Flow and Swimlanes

An activity is where UML lets you draw a workflow: what happens, in what order, and who is responsible for each step.

Definition

An activity is a parameterised behaviour represented as a coordinated flow of actions. It contains activity nodes — which may be action, object or control nodes — and the flow of execution is modelled as activity nodes connected by activity edges.

Activity partitioning (swimlanes)

An activity partition is an activity group for actions that have some common characteristic. Partitions often correspond to organisational units or business actors in a business model, and the partitioning criteria are the modeller's choice: geography, department, role or system boundary are all legitimate, as long as the criterion is stated.

Worked example — an activity diagram for the smart health agent. The deck draws the booking scenario with three swimlanes: Patient, Agent and Scheduling System. Rebuild the reasoning step by step.

1

Fix the boundary. The activity is one booking, not the whole agent. Entry point: the patient requests an appointment. Exit points: self-care advice delivered, or booking confirmed with the doctor system.

2

Choose the partitions. The obvious common characteristic is who performs the step. Patient: Request appointment, Select preferred time slot. Agent: Analyze symptoms, Suggest self-care advice, Present options to patient, Notify patient. Scheduling System: Retrieve doctor availability, Return available slots, Send confirmation, Confirm booking with doctor system.

3

Draw the backbone as control flow. Request appointment → Analyze symptoms → a choice. One guard leads to If mild → Suggest self-care advice (a flow final: this path is over, but the activity is not). The other leads to If need doctor → Retrieve doctor availability.

4

Make the data explicit with object nodes. “Return available slots” produces a slot list that “Present options to patient” consumes; “Select preferred time slot” produces a chosen slot that the confirmation step consumes. Those nodes are the parts of the workflow a reader can actually check.

5

Add the exception path, not just the happy path. Wrap the confirmation steps in an interruptible region and let a “Cancel booking” accept-event action fire inside it. This is the diagram-level answer to the deck's question “what happens if the user cancels while booking is underway?”

6

Say what the model still does not decide. An activity shows order and responsibility, not the reaction to a duplicate confirmation or a lost response. Those need a state machine (for the agent's own lifecycle) and an interaction (for the message traffic with the scheduling system).

Interactions: Sequence, Communication and Overview

An interaction is the system-level view: collaborating instances exchanging messages. The deck gives three concrete notational forms for the same idea.

Definition and precondition

Interactions focus on the communications between collaborating instances communicating via messages. They require a prior definition of a collaboration structure, which defines the context for the interaction. Multiple concrete notational forms exist: the sequence diagram, the communication diagram and the interaction overview diagram.

Communication diagram

Shows interactions between objects using sequenced messages: the objects are drawn as nodes and the messages are numbered — 1: query, then 2b: get — so the numbering carries the ordering that the sequence diagram carries with vertical position. The connectors follow the structure of the collaboration, so a communication diagram is the natural bridge from an object diagram: an association connects classes, a link connects instances, and the sequenced messages travel along those links.

Interaction overview diagram

Provides an overview of the flow of control where the nodes of the flow are interactions. It contains the activity-diagram node set: initial node, flow final node, activity final node, decision node, merge node, fork node and join node — with ref nodes holding the interactions. Use it when the question is “which interaction happens next, and under which condition?” rather than “what is the message order inside one interaction?”

State Machines: Events, Guards and Actions

A state machine is the notation for one object's event-driven life. The examinable detail is the anatomy of a transition and the exact order in which its actions run.

The role of statecharts

Statecharts show the discrete behaviour of a part of a designed system through finite state transitions. They are used to describe event-driven behaviour: what the object does when something happens, rather than what it computes.

Event and event occurrence

An event is an instantaneous change of state in the system. The deck names three kinds:

  • Message event — the receipt by an object of either a call of an operation or a signal.
  • Change event — a change in the system configuration.
  • Time event — occurs at the specified time.

An event occurrence is an instance of an event: it occurs at a particular time instant and has no duration.

Anatomy of a transition

trigger [guard] / effect — for example bid [value < 100] /reject. The trigger is the event that makes the transition eligible; the guard is a Boolean predicate that must hold; the effect is the behaviour executed when the transition is taken.

The rule about guards

Guards are for conditional execution of transitions and must be side-effect free. A guard may read the system; it may not change it. Anything that must be computed belongs in the transition's effect, which is why the deck's choice example computes gain in the effect rather than in a guard.

TransitionActions executed, in orderWhy
LampOn —off/ printf(“to off”)→ LampOffprintf(“exiting”) → printf(“to off”) → lamp.off()Exit of LampOn prefixes the effect; entry of LampOff postfixes it
LampOff —off/ printf(“needless”)→ LampOff (self-transition)printf(“exiting”) → printf(“needless”) → lamp.off()The state does not change, but it is still exited and re-entered — hence the deck's name for it
Entry and exit actions are a dynamic assertion mechanism. They let a state guarantee something about the world while it is active: LampOn asserts the lamp is on when entered and unconditionally restores the invariant on the way out, whatever transition caused the exit.

The guard may update value so that later guards see the new figure

The guard is the trigger, so the transition fires whenever the guard changes

Branching, Hierarchy and Completion

Real state machines do not stay flat. The deck's answer to complexity is a graduated one: first branch precisely, then nest, then let nested machines hand control back on their own.

ConstructWhen the guards are evaluatedDeck example
Junction pseudostate — static conditional branching Before the transition is taken. The junction is merely a graphical shortcut for convenient rendering of decision trees. Selling —bid [value < 100] /reject→ Unhappy; [value ≥ 200] /sell; [(value ≥ 100) & (value < 200)] /sell
Choice pseudostate — dynamic conditional branching At the point when the choice point is reached, after the incoming transition's effect has run. Selling —bid /gain := calculatePotentialGain(value)→ ♦ then [gain ≥ 200] /sell, [gain < 100] /reject, [(gain ≥ 100) & (gain < 200)] /sell
The distinction that earns marks: a junction decides with the values the system had before the transition; a choice decides with the values the transition just produced. If the branch condition depends on a computation, you need a choice — and the computation must sit in the effect of the incoming transition.

Hierarchical state machines

The deck's phrase is a graduated attack on complexity: states are decomposed into state machines. LampFlashing contains FlashOn and FlashOff, each with its own entry action and its own timed transitions (1sec/), and a default transition to the initial pseudostate decides which substate is entered first.

Group transitions and triggering rules

A group transition is a higher-level transition drawn on a composite state: it applies whatever the active substate is. Two or more transitions may share the same event trigger — when they do, the innermost one wins, so on/ on FlashOn pre-empts the group-level on/.

Completion transitions

A completion transition is triggered by a completion event: an event generated automatically when an immediately nested state machine terminates. It has an implicit trigger — nothing is written before the slash — so the deck's committing example runs Phase1 → Phase2 → CommitDone without any external event being involved.

Worked answer — the deck's complex order-of-actions exercise. Two nested machines: S1 (entry en1, exit exS1) contains S11 (entry en11, exit exS11); S2 (entry enS2) contains S21 (entry enS21, exit exS21) with an initial pseudostate H*. The transitions are E1/act1 from S1 to S2, and E3/act3 from S21 to S2.

1

The rule. Exits run from the innermost active state outwards, up to but not including the transition's least common ancestor. Then the transition action runs. Then entries run from the least common ancestor inwards, down to the target state.

2

Question 1: in S1::S11, event E1 occurs. The transition leaves S1 altogether, so the least common ancestor is above both S1 and S2. Everything active is exited: exS11 then exS1. Then the effect act1. Then the target is entered from the outside in: enS2, and because S2's default transition leads to S21, enS21.

Sequence: exS11 → exS1 → act1 → enS2 → enS21.

3

Question 2: in S2::S21, event E3 occurs. The target is S2 itself and the source S21 is inside it, so the least common ancestor is S2 — a state that is not exited. Only exS21 runs. Then act3. Then S2's default transition enters S2 again through its initial pseudostate: enS2, then enS21.

Sequence: exS21 → act3 → enS2 → enS21.

4

Why the two answers differ. The number of exit actions is decided entirely by whether the transition crosses the boundary of the composite state. Crossing it (E1) destroys the nested configuration and rebuilds it; staying inside it (E3) resets only the region below the boundary. This is the same LCA reasoning that makes group transitions cheap to write and expensive to get wrong.

Selling receives bid, computes gain := calculatePotentialGain(value), and then branches on [gain ≥ 200], [gain < 100] and the middle case. Which pseudostate is that, and why?
A junction, because three guards leave one point
A choice pseudostate, because the guards are evaluated when the choice point is reached
A completion transition, because the effect ran first

Orthogonal Regions: Concurrent Viewpoints

The last piece of the state-machine vocabulary is also the most misused. Orthogonality is about simultaneous descriptions of one entity, not about several entities running at once.

Definition

Orthogonality should be used to capture different concurrent views of the same entity. Orthogonal regions of a state combine multiple simultaneous descriptions: the deck's example splits one person into an age region (Child, Adult, Retiree) and a financialStatus region (Poor, Rich), so the object is always in exactly one state of each region at the same time.

Semantic ruleWhat it meansConsequence for the model
Regions execute concurrentlyAll mutually orthogonal regions detect the same events and respond to them simultaneouslyIn practice this usually reduces to some type of interleaving, and the order of the two responses is not specified
A state is a combinationThe object's situation is the tuple of its region statesChild × Rich is a different situation from Child × Poor, and both are legal
The same event can hit every regionrobBank/ moves LawAbiding → Outlaw in one region and Poor → Rich in the otherOne event, two independent effects, no sequencing between them
Do not fall into this trap. The concurrency of orthogonal regions is the concurrency of different viewpoints. It should not be used to model concurrent objects: object concurrency has different semantics from region concurrency, and the deck names this as the way most modellers misuse regions. If you have two objects that run at the same time and exchange messages, you want active objects with message queues — not two regions of one state machine.
A modeller models a web server and its three worker processes as four orthogonal regions of one state machine. According to the deck, what is wrong with that?
Region concurrency models different viewpoints of one entity, not concurrent objects
Nothing: orthogonal regions are the standard notation for concurrent objects
It is wrong because each region must respond to a different event

Smart health agent — the three models

  • Activity: swimlanes Patient, Agent, Scheduling System; If mild → self-care advice, If need doctor → retrieve availability, present options, select slot, confirm.
  • Sequence: sd Book appointment with an alt on [chk = need doctor] referencing sd Make booking, and [chk = mild] giving self-care advice; sd Make booking runs request slots → return slots → present slots → select slot → confirm booking → send confirmation → notify patient.
  • State machine: Idle → Analysing → (If mild) Advising Self-care, or (If need doctor) Make Booking → QueSchedule → Slot received → PresOptions → Choice received → Booking confirmed.

The RTC design rules the deck derives

  • Keep reactions short — a long reaction is a long window in which nothing else is observed.
  • Treat LLM output as input to validate — the plan is a proposal, not a command.
  • Define the boundary — say exactly which state one reaction may change before it completes.
  • Validate, record, arrange, wait — the four updates before WaitingForTool are one completion unit; a Cancel arriving halfway through is the failure the model exists to prevent.
What the deck says to produce for the financial-advisor scenario: an activity diagram with swimlanes Client, Smart Financial Advisor Agent, Market Data API and Brokerage System, actions such as Analyze client profile, Get market data and Present options to client, and an explicit condition on whether the client approves; a sequence diagram with four participants using alt and loop; and a state machine whose first job is to define the correct states.

Worked answer — the cancel-during-booking question, modelled three ways. The brief-sentence is “if the user cancels while booking is underway, the agent must stop”. Here is what each model contributes, and what each one cannot say.

1

Activity view. Draw the booking steps inside an interruptible region and add an Accept event action for “Cancel requested”. The region gives you the answer to “may this happen while that is running?” in one visual grouping — and it forces you to say what happens to the partially completed booking.

2

Interaction view. A sequence diagram with a par-like alternative is not enough on its own: you must draw the cancel message arriving between two booking messages and add the reply that the scheduling system sends for the already-issued request. That reply is precisely the message that is otherwise lost.

3

State machine view. The agent's states decide the outcome: MakeBooking has exit notifyPatient(); a Cancelling state that records “a request is in flight” is what lets the agent distinguish an orphaned confirmation from a fresh one. Without a state for that situation, the model cannot express the difference at all.

4

RTC view. All of this only works if each reaction is short and the boundary of one reaction is defined: validate the plan, record the request identifier, arrange execution, enter WaitingForTool. If Cancel is processed halfway through those updates, the agent can hold a request identifier for a tool call it believes was never made. Run-to-completion is what makes “halfway through” impossible.

5

The sentence that earns the mark. “The activity diagram shows where cancellation may interrupt the workflow; the interaction shows which reply can be lost; the state machine gives the agent a state in which a late reply can be recognised as stale; and run-to-completion guarantees that the cancellation is handled either before or after the update sequence, never inside it.”

Week 6 Recap

All behaviour stems from objects

UML's causality is a discrete, event-driven model of computation over a network of communicating objects. An action is a single atomic step executed by an object.

Foundation

Four formalisms, one semantic base

Actions for fine-grained manipulation, activities for control and data flow, interactions for message ordering, state machines for event-driven reactions.

Vocabulary

Exit prefixes, entry postfixes

On a transition: exit actions of the source, then the transition's effect, then entry actions of the target — and the whole thing runs to completion.

Semantics

Regions are viewpoints, not objects

Orthogonal regions give concurrent descriptions of one entity. Concurrent objects need active objects, message queues and RTC — different semantics.

Trap

Check yourself

Can you state what makes an object active, write the action sequence for a transition between nested states, and say exactly when a choice pseudostate evaluates its guards?

Prepare for the tutorial and lab

Bring one scenario from your project and say which behaviour model answers which open question. The laboratory continues the modelling work — the runtime view of your classes is what your behaviour models must be consistent with.
