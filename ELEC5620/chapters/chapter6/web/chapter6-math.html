Foundations: the notation and semantics of behaviour models

Week 6 is notation-heavy rather than algebraic, so this page does the equivalent job: it fixes the definitions the lecture relies on, collects every notation element into a reference card, writes the transition and run-to-completion semantics as relationships you can reproduce under exam pressure, and ends with the checklist that picks the right model for a scenario.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Action

A named element representing a single atomic step within an activity, not further decomposed within that activity. An action is executed by an object, may change variables or slots, and — if it is a communication action — may invoke an operation on another object or send a signal. Its successors are determined by control flow or by data flow.

Activity

A parameterised behaviour represented as a coordinated flow of actions. It contains activity nodes (action, object or control) connected by activity edges. Partitions (swimlanes) group actions that share a common characteristic, and the partitioning criterion is the modeller's choice.

Interaction

A behaviour that focuses on communications between collaborating instances communicating via messages. An interaction requires a prior definition of a collaboration structure, which is its context. Its concrete notational forms are the sequence diagram, the communication diagram and the interaction overview diagram.

State machine and event

A statechart shows the discrete behaviour of part of a designed system through finite state transitions, and describes event-driven behaviour. An event is an instantaneous change of state in the system: a message event (receipt of an operation call or a signal), a change event (a change in the system configuration) or a time event (occurs at the specified time). An event occurrence is an instance of an event: it occurs at a particular time instant and has no duration.

Active object and run-to-completion

An active object commences to execute its classifier behaviour as a direct consequence of its creation and does not cease until that behaviour completes or an external object terminates it; the points at which it responds to messages are determined solely by its own behaviour specification. Run-to-completion is the rule that messages arriving between successive receive actions are queued and only considered on the next receive action.

Rules you can write from memory

Six relationships carry most of the marks in this topic. The notation below is a revision aid introduced on this page; it is not lecture notation and should not be quoted as such.

1. When does a transition fire?

A transition \(t\) with source state \(s\) is enabled by event \(e\) when the trigger matches and the guard holds on the current values:

\[ t \text{ enabled by } e \iff \operatorname{trigger}(t) = e \;\wedge\; \operatorname{guard}(t)(v) = \text{true} \]

What fires is the innermost enabled transition, so a nested state's transition pre-empts the group transition on the state that contains it:

\[ t^{*} \;=\; \arg\max_{t \in E(e)} \operatorname{depth}\big(\operatorname{source}(t)\big) \]

If two transitions at the same depth are enabled by the same event, the model is underspecified: the deck's rule is simply that two or more transitions may share a trigger, and the innermost wins.

2. In what order do the actions run?

Let \(L = \operatorname{LCA}(s_{src}, s_{tgt})\) be the least common ancestor of the source and target states, and let \(\uparrow\) mean “outwards” and \(\downarrow\) “inwards”:

\[ \operatorname{seq}(t) \;=\; \operatorname{exit}\big(s_{src} \uparrow L\big) \;\cdot\; \operatorname{effect}(t) \;\cdot\; \operatorname{entry}\big(L \downarrow s_{tgt}\big) \]

Exit actions run from the innermost active state outwards, stopping below \(L\); entry actions run from \(L\) inwards to the target. For a flat machine \(L\) is the enclosing region, so the sequence collapses to the deck's simple case: exit actions prefix the transition action, entry actions postfix it.

3. Run-to-completion as a queue discipline

With \(Q_k\) the queue before step \(k\) and \(A_k\) the events that arrive while step \(k\) executes:

\[ Q_{k+1} = Q_k \cup A_k, \qquad e_{k+1} = \sigma\big(Q_{k+1}\big) \]

where \(\sigma\) is the chosen scheduling policy. The consequence is the point: no event is ever handled inside another, so no observer can see a half-updated state. Priority inversion appears when \(\sigma\) can select a low-priority event ahead of a high-priority one that has already arrived at the same object.

4. Junction decides before, choice decides after

For a guard \(g\) over the system's values \(v\):

\[ \text{junction: } g\big(v_{\text{before}}\big) \qquad\qquad \text{choice: } g\big(v_{\text{after effect}}\big) \]

A junction is a graphical shortcut for rendering a decision tree; a choice is genuine dynamic branching. If the branch condition depends on something the transition itself computes — the deck's gain := calculatePotentialGain(value) — only a choice can express it.

5. Orthogonal regions multiply the state space

A state with regions \(R_1 \dots R_n\) is in exactly one state of every region at once, so its configurations are the cartesian product:

\[ S = R_1 \times R_2 \times \dots \times R_n, \qquad |S| = \prod_{i=1}^{n} |R_i| \]

Two regions of three and two states give six simultaneous situations (Child × Poor, Child × Rich, …). Every region receives the same event and responds to it simultaneously, which in practice reduces to some interleaving whose order is not specified.

Message ordering in an interaction. On a single lifeline \(l\) the message occurrences are totally ordered by vertical position: \(m_1 \prec_l m_2 \prec_l \dots\). Between different lifelines only the send–receive causality of each message is fixed, which is why a sequence diagram can show genuine concurrency that a numbered communication diagram has to flatten into a single numbering.

Worked cases: count the actions, then justify them

The deck's complex exercise is the cleanest way to test rule 2. Both cases end in the same nested configuration — the difference is entirely in how much of the machine had to be torn down.

Read the two charts together: the entry count is identical because both transitions finish by entering S2 through its default transition into S21. The exit count differs because only the first transition leaves S1. Whenever an exam question gives you a nested machine, locate the least common ancestor first — everything else follows from it.

Worked derivation — which transition fires when two share a trigger? The deck's lamp example has LampFlashing with substates FlashOn (entry lamp.on()) and FlashOff (entry lamp.off()), timed transitions 1sec/ between them, and an on/ transition drawn both on the substates and on the composite state. The group also has an off/ transition.

1

Collect the candidates. For an event \(e\), \(E(e)\) is every transition whose trigger matches and whose guard holds. With the machine in LampFlashing::FlashOn and event on arriving, \(E(\texttt{on})\) contains the on/ transition on FlashOn and the group-level on/ transition on LampFlashing.

2

Apply the depth rule. \(t^{*} = \arg\max_{t \in E(e)} \operatorname{depth}(\operatorname{source}(t))\). FlashOn is deeper than LampFlashing, so the substate's transition wins and the group transition is never taken.

3

Write the action sequence. \(L = \operatorname{LCA}(\texttt{FlashOn}, \texttt{FlashOn}) = \texttt{FlashOn}\) for a self-transition, so the sequence is exit(FlashOn), then the effect, then entry(FlashOn) — the lamp is switched off and straight back on. For off/ the group transition does fire, because no nested state has a transition on off.

4

State the design consequence. Group transitions are a convenience: they let you write one reaction for a whole composite state. The moment one substate needs different behaviour for the same event, you add the substate transition and the group transition quietly stops applying there — no editing of the group transition required.

Worked classification — junction or choice? Five transition fragments from the deck's auction example. Decide each one with rule 4, in one sentence.

1

bid [value < 100] /reject leaving Selling to Unhappy. A single guarded transition: no pseudostate at all, and value is read as it stands. The guard is evaluated when the event bid is dispatched.

2

Selling —bid→ ♦ —[value ≥ 200] /sell→ Happy and its two siblings. This is a junction: the incoming transition carries no effect, and the three guards are evaluated before the transition is taken. It is a decision tree drawn compactly.

3

Selling —bid /gain := calculatePotentialGain(value)→ ♦ followed by [gain ≥ 200] /sell, [gain < 100] /reject and the middle case. This is a choice: the guards mention gain, which does not exist until the incoming transition's effect has run, so they can only be evaluated at the choice point.

4

The discriminating question. “Does the branch condition depend on something this transition computes?” Yes → choice. No → a junction, or simply guards on the transitions. A guard that assigns a value is not a guard at all: guards must be side-effect free.

5

Why the distinction is examinable. The two notations draw as the same diamond. Only the position of the effect — on the incoming transition or after the pseudostate — tells you which semantics apply, and the action order changes accordingly.

Model-selection checklist

Most Week 6 exam questions reduce to “which model, and why?”. Run the scenario through these steps in order and the justification writes itself.

StepLook forMarks are lost when…
1. The open questionA decision the code cannot make consistently todayYou draw a diagram without saying what it decides
2. Subject: object or systemOne lifetime, or message traffic between instancesYou model a workflow as a state machine for the whole system
3. Interaction formTime order (sequence) vs structure and coupling (communication)You use a communication diagram to prove a timing property
4. State machine formEvents, guards, entry and exit actions, nestingYou list activities as states, or forget the final state
5. Activity formPartitions, object nodes, fork and join, finalsYou draw a flow with no start, no end, or no responsibility
6. Edge casesAlternatives, loops, interruption, reused interactionsYou model only the happy path
7. What is still openThe questions the model deliberately leaves to another modelYou claim the model answers everything
