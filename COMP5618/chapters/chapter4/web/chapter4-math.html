Foundations: the vocabulary and notation behind web application security

Week 4 is conceptual, so this page does the equivalent of a formula sheet. It pins down the definitions the lecture relies on, gives compact notation for sessions, authorisation and caching, builds a status-code and layer taxonomy you can be examined on, and ends with the threat-model checklist that turns “this app is vulnerable” into a markable answer.

Definitions verified against the Week 4 lecture deck Notation is a revision aid, not lecture notation Threat-model checklist for exam answers

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Web application

A software application accessed through a web browser or web-enabled device, hosted on a remote server and reached over a network, delivering its functionality through web technologies such as HTML, CSS and JavaScript. It receives HTTP requests and generates HTTP responses, and it is a complex system with multiple layers and dependencies.

Web server

A software application that handles the delivery of web content over the internet. It receives and processes HTTP requests from clients, returns HTTP responses containing the requested content, and acts as the intermediary between clients and the hosted application — listening on a port and either serving a resource or forwarding the request.

Application server

The component that handles the actual processing of HTTP requests: executing the back-end code, implementing the business logic, accessing the database through its interface methods, and managing caching layers. It is where the dynamic page is generated.

Web application firewall (WAF)

A security solution designed to protect web applications from various types of attacks and vulnerabilities. It acts as a shield between the application and the client, analysing and filtering incoming requests and responses, and is typically positioned in front of the web server, on-premises or in the cloud.

Worked answer — assigning a finding to a layer. Given a description of a flaw, the first markable step is naming the component that owns it, because that is what determines who fixes it and which control counts.

1

“The vendor's sample admin page is reachable on the production host.” Nothing was programmed wrongly and no user input is involved. The deployment kept a default: web server layer, security misconfiguration. Control: configure to OWASP and NIST guidance and remove sample content.

2

“A search parameter changes which rows a product query returns.” User input reaches a query parser: application server layer, SQL injection. Controls: fix the query's structure, validate the expected format, give the database account least privilege, and log the queries executed.

3

“A review containing markup executes for everyone who views the page.” Stored data reaches an HTML parser at render time: the failure is at the output position, even though the data was accepted at the application layer. Controls: encode or escape on output through an anti-XSS library; validate and sanitise on input as the second layer.

4

“Two users see the same personalised page after a cache warm-up.” The cache returned a response computed for somebody else: cache layer. Control: key stored responses on the identity and authorisation state entitled to see them, never on the URL alone.

5

The sentence to reuse. “The flaw is X at the Y layer, reached through Z, and it survives because no control at that layer evaluates it — the fix belongs at Y, not at the edge.”

The request was rejected but the body was returned anyway
The server treated the request as valid and authorised, so no authorisation check stopped it
The response was served from cache rather than from the database

Sessions, authorisation and caching in notation

Three relationships are worth being able to write from memory: how identity is reconstructed, how access is decided, and what a cache actually saves.

1. Identity is reconstructed, not remembered

HTTP is stateless, so the server holds no memory of the previous request. Each request carries a session token, and the server maps that token to an identity and a set of permissions:

\[ \operatorname{session} : \operatorname{token} \;\longmapsto\; (\operatorname{identity},\ \operatorname{permissions}) \]

Consequence: the token is the credential. Possession is sufficient, which is why stolen tokens, passwords or keys are described in the lecture as a stolen identity.

2. Access requires authentication and authorisation

Two independent predicates have to hold before a function may run. Let \(a\) be authentication (is the caller who they claim to be?) and \(z\) be authorisation (is that identity permitted to perform this action?):

\[ \operatorname{grant} \;=\; a \;\land\; z \]

Missing function-level access control is the case \(a = \text{true}\) and \(z\) never evaluated. Insecure direct object access is the same shape one level down: the object identifier is used before \(z\) is asked about that object.

3. A session that can be forged is an identity that can be forged

Write \(u_{\text{apparent}}\) for the identity the application believes it is serving and \(u_{\text{actual}}\) for the human at the browser. When authentication material is captured, the two separate:

\[ \operatorname{token}_{\text{stolen}} \;\Rightarrow\; u_{\text{apparent}} = u_{\text{victim}} \;\neq\; u_{\text{actual}} \]

The defence chain from the deck attacks the left-hand side: a strong unique password makes the credential harder to obtain, and a second verification step means a stolen password alone does not complete the login. Neither control helps once the token has already been issued.

4. What a cache buys, and what it costs

With \(h\) the hit ratio, \(t_{\text{hit}} \approx 1\text{–}2\) ms and \(t_{\text{miss}} \approx 50\text{–}100\) ms from the deck:

\[ t_{\text{avg}} \;=\; h\,t_{\text{hit}} + (1-h)\,t_{\text{miss}} \]

At \(h = 0.9\) that is roughly 6–12 ms against 50–100 ms uncached — a large win, which is exactly why caching survives review. The security condition is the part that gets skipped: a cached response is only safe if it was keyed on the identity and authorisation state entitled to see it.

Threat-model checklist for a web application

Most Week 4 exam questions reduce to “given this application, where would you look and what would you report?”. Run the checklist in order and the answer writes itself.

StepLook forMarks are lost when…
1. ComponentsWhich of the four layers the flaw belongs to, and whether a WAF sits in frontYou describe a flaw without saying where it lives or who must fix it
2. Entry pointsParameters, bodies, headers, cookies and methods the interface never usesYou assume the form's own validation is a control
3. Data flowThe interpreter that consumes user input: query parser, HTML parser, filesystemYou name the flaw without naming the interpreter it abuses
4. Session flowHow the token is issued, carried, stored, expired and revokedYou treat 2FA as protection for a session that was already issued
5. AuthorisationA server-side check on every function and every objectYou accept a hidden link or a disabled button as an access control
6. Response evidenceStatus codes, stack traces, version banners, redirect targetsYou claim an impact you have no response evidence for
7. Control pairingValidation and structural safety and least privilegeYou answer “validate input” and stop, when the flaw is structural
Validation versus structure. The lecture's stated solution for SQL injection is input validation: ensure user input is the correct format and length before it reaches the query, and reject or sanitise what does not match. That is necessary. It is not sufficient, because it requires predicting every dangerous input. The structural control — keeping the query's shape fixed and binding data into it — removes the class rather than the instance. A complete answer names both, then adds least-privilege credentials and logging.
Which answer best explains why “validate the input” alone is an incomplete response to an injection finding?
Validation is not a real security control and should not be mentioned
Validation reduces instances of a flaw but does not remove the class, because it depends on predicting every dangerous input
Validation only works on the client side, so the server never sees it

Worked classification. Place three findings using the checklist, two sentences each.

1

A search page returns every product when the query contains a quotation mark. Data flow: user text is assembled into the database query, so it can occupy an instruction position. Verdict: SQL injection at the application server. Controls: fix the query's structure, validate the expected format and length, run the database account with least privilege, and log the queries actually executed. Response evidence: a result set larger than any legitimate search, and often a 500 once the malformed statement reaches the parser.

2

A product review is displayed to every visitor, and the review contains script. Data flow: stored untrusted data is rendered into HTML without escaping. Verdict: stored XSS at the output position. Controls: encode or escape on output using an anti-XSS library, validate and sanitise on input, and remember that script in the origin can read CSRF tokens and act with the user's session.

3

A normal account reaches the admin console by editing one path segment. Authorisation: \(a = \text{true}\) but \(z\) was never evaluated for that function. Verdict: missing function-level access control. Control: a server-side privilege check before the function executes, applied to every entry point, not just the link in the menu. Response evidence: a 200 where a 403 is expected.

4

The sentence that earns the mark. “The flaw is X at layer Y, reached through entry point Z, with impact I, and the control belongs at layer Y as well — input validation reduces the instances, but only fixing the structure removes the class.” Every clause in that sentence is checkable, which is why it scores.

Tutorial walkthrough: hosting, then filtering

The Week 4 tutorial builds an application-layer firewall in front of a deliberately vulnerable application. Each step produces an observable checkpoint, and the last step is the one that matters: the same attack, blocked and allowed, with the code unchanged.

Host it first

Host the vulnerable application on NginX rather than Apache. Because NginX has no built-in PHP support, PHP-FPM provides the CGI bridge between the server and the application.

Contain it

Put the vulnerable host on a NAT network with the attack VM, then switch it to a host-only adapter so the deliberately vulnerable application is not exposed to any other host.

Filter it

Compile NginX with the filter module, point the denied-URL page in its rules file, and reference that rules file from the site configuration so it is applied.

Then try to break it

Send attack requests from the command line and from the application's own interface, and read /var/log/nginx/error.log to see what the filter recorded about each one.

1

Why learning mode exists. Enabling the filter in learning mode prevents it from taking any action except logging suspicious requests to the Nginx error log. On a real site the first rule set will flag legitimate traffic; learning mode is how you find those requests before they become blocked users.

2

What you do with the log. By examining the log lines generated from legitimate, non-attack requests, exceptions can be made to the built-in or custom rules so that legitimate requests are not blocked. The log is the input to the configuration, not just evidence.

3

What the tutorial warns about. Properly configuring and implementing a WAF on a high-traffic website can require a lot of effort, and it is usually a good idea to give legitimate users who land on the “request denied” page a route to contact the webmaster.

4

The checkpoint sequence. Start and stop the services and show the server running; show the PHP configuration page from the host, proving the request path; use curl to send a suspicious request and show it recorded in error.log; log in to the vulnerable application from the host browser; then demonstrate XSS and SQLi both blocked and, with learning mode on, allowed.

Worked answer — what the difference between the two modes proves.

1

Observation, enforcing. The request is refused before the application sees it, the browser shows a different response code, and the event appears in the error log. Nothing about the application changed.

2

Observation, learning mode. The identical request reaches the application and produces the vulnerable behaviour, and all the filter produces is a log line. Again, nothing about the application changed.

3

Inference. The difference between the two runs is entirely the filter's mode. Therefore the filter is the only thing preventing exploitation, and the underlying defect is untouched — which is exactly why the deck describes WAF protection as shielding known weaknesses until a proper patch is deployed.

4

Report wording. “SQL injection remains present in the application and is currently only mitigated at the edge; the mitigating rule set must be maintained and the application code must still be fixed. Evidence: identical requests produce different outcomes when filter mode changes.”

5

Scope. All of this was performed against a deliberately vulnerable application in a host-only lab network. The same requests aimed at a system you do not own or have written permission to test are an offence, not an exercise.
