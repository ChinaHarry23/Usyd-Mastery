What a Web Application Is

A web application is a software application accessed through a browser or web-enabled device. That single sentence is the whole reason this week exists: the attacker's entry point is the same interface the user gets.

Definition

A web application is a software application accessed through a web browser or web-enabled device. Unlike a traditional desktop application it is hosted on a remote server and reached over a network, and it delivers its functionality through web technologies — HTML, CSS and JavaScript — rather than through an installed binary.

The lecture breaks the thing into three simultaneous descriptions, and all three matter for security work:

The code and assets

Server and client scripts, images, stylesheets and templates define what the application does. Every one of those artefacts is reachable by URL unless something stops it, which is why directory listing, backup files and unreferenced endpoints are a recurring finding.

The request/response machine

The application receives HTTP requests and generates HTTP responses. It has no other way to be talked to. Anything an attacker can express as a request is therefore in scope — including requests the user interface would never send.

Third description: a complex system with layers and dependencies. A web server, a database, an API and third-party services all sit behind one page load. Each dependency is another component whose trust assumptions can be wrong, and each one widens the blast radius of a single injection flaw.

Those three properties are also what makes it attackable from anywhere.

The Request Stack: Web Server, App Server, Database

One click travels through four components. Knowing which component is responsible for what is how you decide where a defence belongs — and which findings belong to which layer of a report.

Web server

A web server is a software application that handles the delivery of web content: it receives and processes HTTP requests from clients and returns HTTP responses containing the requested content. It is the intermediary between clients and the hosted application, listening on a port and either serving a resource directly or passing the request on.

The deck lists five responsibilities a web server carries: serving static content, processing dynamic content, handling HTTP methods, managing connections, and implementing security measures. The last one is where TLS termination, request-size limits and — in this week's tutorial — the WAF plugin live.

Application server

An application server handles the actual processing of HTTP requests that the web server forwards to it. It executes the back-end code, implements the business logic, accesses databases and manages caching.

SQL versus NoSQL — the exam contrast

  • SQL: structured data with a predefined schema, relationships enforced between tables, one query language, suited to complex joins
  • NoSQL: flexible or schema-less model, minimal relationship enforcement, a query language that depends on the data model, suited to large volumes of unstructured or semi-structured data

Where the database sits changes the blast radius

The deck notes that databases can reside on the same host as the app server or on a separate host. Co-location makes the database reachable from a compromised application host with no network boundary in between; separation adds a boundary but not an authorisation control, because the application still holds working credentials.

Approaches to dependencies: Putting it all together

1

The user sends a request to the web server.

2

The web server forwards it to the application server, which holds the business logic and talks to the database.

3

The application server updates the database and, once the update completes, generates a response.

4

The response goes back through the web server to the client, which renders the updated information or a message.

HTTP, Statelessness and Sessions

HTTP has no memory. The application has to rebuild the idea of “you” on every single request, and it does that with a cookie. Almost every web flaw in this unit is a failure of that reconstruction.

Piece of a requestWhat it carriesWhy an attacker cares
Method and pathWhat action is requested and on which resource, e.g. a GET of a page or a POST of a formThe web server's method handling is a listed responsibility; methods the UI never uses are still usually accepted
Query stringParameters appended to the URLFully attacker-controlled, appears in logs and history, and is the easiest place to test an injection
BodyForm fields and uploaded contentWhere file upload and direct object access flaws usually arrive
HeadersMetadata: host, user agent, content type, refererSome applications trust headers for decisions they should make themselves
CookiesThe session identifierPossession of the cookie is the authenticated identity — the root of broken authentication
Statelessness and the session

HTTP is stateless: each request is independent and the server keeps no memory of the previous one. A session is the application's workaround — after login the server issues a token, the browser stores it in a cookie and returns it automatically with every subsequent request, and the server uses it to look up who you are. The cookie is therefore a bearer credential: whoever holds it is treated as the user.

What a session cookie buys the application

  • Identity across stateless requests
  • A place to store authorisation decisions
  • A single artefact to expire on logout

What it costs

  • Theft of the cookie is theft of the session
  • The browser attaches it to requests the user never intended to make — the CSRF precondition
  • In an intercepting proxy it is visible, editable and replayable
Same-origin policy. The browser's core containment rule: script served from one origin cannot read the responses of another origin. The origin is the scheme, host and port together. It is what stops a page on an attacker's site from silently reading your bank's pages — and it is why XSS and CSRF matter so much, since both find ways to act as the trusted origin instead of reading across origins.
Where to look in an exam question: the interesting failure is rarely at step 1 or step 6. Ask which of steps 2–5 can be made to happen with a token that belongs to somebody else, or without the check at step 4 ever running.
Why does a session cookie make CSRF possible at all?
Because cookies can be read by JavaScript on the page
Because the browser attaches the cookie automatically to any request for that origin, however that request was triggered
Because sessions never expire on the server side

Broken Authentication: Sessions, Tokens and 2FA

Broken authentication is what the lecture calls hijacking a session by stealing tokens, passwords or keys. The lecture's one-line summary is worth memorising: stolen credentials are a stolen identity.

The attack chain in the deck: credential theft → the attacker steals credentials → the attacker impersonates the user → the attacker hijacks the session. Shoulder surfing and social engineering are the named entry points.

The defence chain in the deck: stop impersonation → a complex, unique password policy → a second verification step → stolen credentials alone fail and the session stays secure. The bottom line the deck draws: even if a password leaks, 2FA stops an attacker from completing the login.

Why a strong password policy is not enough

A unique, complex password defeats guessing and credential stuffing, but it does nothing against a credential that is stolen directly — phishing, keylogging, shoulder surfing or a breach at another service where the same password was reused.

Why 2FA is not enough on its own

A second factor protects the login. It does not protect a session token that was already issued: if the cookie is stolen after authentication, the second factor has already been satisfied and is not consulted again.

FailureHow it happens in a web applicationControl the deck names
Credentials stolenShoulder surfing, social engineering, phishing, re-use after another breachComplex, unique passwords
Credential used successfullyNothing further is demanded, so the attacker is now the userTwo-factor authentication
Session hijackedToken, password or key captured and replayed; the server sees a valid sessionRe-authentication for sensitive actions; short session lifetimes
Session forged from another siteThe cookie is attached automatically to a request the user did not intendCSRF tokens; re-authentication
Exam framing: authentication answers “who are you?”, authorisation answers “what may you do?” and session management answers “how do I know it is still you on the next request?”. Broken authentication is a failure of the first and the third together, which is why it undermines every authorisation check that follows.
An application enforces complex passwords and 2FA at login. An attacker still reaches another user's data. Which explanation fits the lecture's broken-authentication material?
The password policy was too weak, so the password was guessed
The session token was stolen after login and replayed, so the second factor never came into play
2FA is not a real defence because attackers can always bypass it

Injection: When Input Becomes Code

SQL injection is the lecture's Part I vulnerability: a malicious user injects a string into a field to manipulate the application's actions or reveal unauthorised data. Everything else about the class follows from one sentence — user input is treated as part of an instruction instead of as data.

SQL injection

A flaw in which a user-supplied string is inserted into a database query in a way that changes the query's meaning, letting the attacker manipulate the application's actions or reveal unauthorised data. The deck's impact statement: the attacker can view all records in a table — including sensitive data such as credit card numbers or personal information.

The deck's three-frame story is the one to reproduce: a vulnerable input field receives a payload, the query is manipulated, and data is exposed — unauthorised records returned. The payload shown in the deck is a condition that is simply true, which is why the filter the developer wrote stops filtering anything.

Why input validation alone is a weak answer. The deck's solution to SQL injection is input validation — ensure user input is the correct format and length before it reaches the query, and reject or sanitise anything that does not match. That is necessary but incomplete: it depends on predicting every dangerous input. The durable fix is structural — keep the query's structure fixed and bind the user's data into it as data, so no input can be a clause.

Insecure direct object access (Part V)

The application allows direct access to an internal object, such as a file, without proper access controls. The deck's example is a file upload feature that does not validate the file type and therefore accepts any file, including a malicious one. Solution: implement access controls and properly validate and sanitise all user input.

Why this is the same flaw in another costume

Both injection and direct object access are missing-authorisation bugs on a user-controlled identifier. The identifier is a query fragment in one case and a file or record reference in the other; in both cases the application acts on what the user supplied without asking whether the user is allowed to reach it.

Worked example — reading an injection bug from a page's behaviour (conceptual, using the lecture's own description rather than a runnable payload).

1

Find the seam between data and instruction. A product search sends the text you type into a database query. If the query is assembled by concatenating that text into the statement, the seam is the point where user data joins the instruction.

2

Ask what the developer assumed. The assumption is that the field contains a product name. An input that contains a quotation mark and a condition breaks that assumption, and the deck's example is exactly a condition that always evaluates true.

3

Notice what changed in the result, not just the error. The manipulated statement no longer selects a product; it selects the whole table. The observable symptom is a result set larger than any product search could legitimately return.

4

State the impact in the deck's terms. Unauthorised records returned: the attacker can now view all records in the products table, including sensitive data such as credit card numbers or personal information.

5

Write the layered fix. Input validation with an expected format and length, rejection or sanitisation of anything that does not match, and a query structure in which user data can never become a clause. Then add least-privilege database credentials so a successful injection reaches as little as possible, and log the queries the application actually runs.

Scope and ethics: every example on this page is a description of a defect class from the lecture, exercised only against the deliberately vulnerable application in your own tutorial virtual machine, which is why that tutorial insists the machine sits on a host-only adapter.
Which statement best captures why SQL injection works?
The database's authentication can be bypassed by a specially formed string
User input is assembled into the query text, so it can occupy an instruction position rather than a data position
The application stores passwords in plain text

XSS, CSRF and the Same-Origin Policy

The next two flaws move the attack into the victim's browser. Both abuse the trust the browser places in the site's own origin, and both are defeated by making the browser able to distinguish content the site wrote from content an attacker wrote.

Cross-site scripting (XSS)

An application allows untrusted data to be included in a web page without proper validation or escaping, so attacker-supplied script executes in the victim's browser in the context of the trusted site. The deck gives two types:

  • Reflected — the untrusted data comes back in the immediate response to the request that carried it.
  • Stored — the untrusted data is persisted by the application and served later to other users.

Solutions from the deck: validate and sanitise all user input so malicious code cannot be included in the application, and use anti-XSS libraries that automatically encode or escape user input.

Reflected XSS

A search page echoes your query back to you. If that echo is inserted into the HTML without escaping, the page will execute what you searched for. Delivery needs a victim to follow a crafted link, and the payload lives only for that one response.

Stored XSS

A comment, profile field or product review is saved and rendered to everyone who views the page. One submission executes for every later visitor, with no crafted link required — which is why stored XSS is the more serious of the two.

Why the same-origin policy raises the stakes. Because script running on the trusted origin can read that origin's pages and act with the user's session, an XSS flaw does not just affect the page it appears on: it converts a script injection into full control of the user's authenticated session on that site.
Cross-site request forgery (CSRF)

An attack that performs actions on behalf of the victim without their knowledge or consent. The deck's example: when a victim visits an attacker's malicious website, the script automatically submits a hidden form to the vulnerable website, using the victim's authentication information and cookies so that the request appears legitimate.

Solutions from the deck: reauthentication, and CSRF tokens.

Worked example — classifying an XSS finding through the tutorial's exercises. The Week 4 tutorial has you attack the XSS section of the vulnerable application with the filter first learning and then enforcing. Turn that into a finding.

1

Decide which type it is. If the submitted value is echoed back only in the response to your own request, the flaw is reflected: it needs a victim to follow a crafted link. If it is stored and shown to other visitors, it is stored XSS, and its reach is every later viewer with no crafted link at all.

2

Name the interpreter. The value is being consumed by the browser's HTML parser in a position that can carry executable content. That is the data-flow statement of the finding, and it belongs in the report.

3

State the impact in the same-origin terms. Script running in the site's origin can read that origin's pages, so it can act with the victim's session and read material such as CSRF tokens. An XSS flaw is therefore a full compromise of the user's session on that site, not a cosmetic page defect.

4

Separate the two controls. Input validation and sanitisation reduce what can be stored; output encoding or escaping through an anti-XSS library is what makes the value render as text. Fixing only the input leaves stored data that was written before the fix — which is why output encoding is the control that must hold for every render path.

5

Say what the filter changed. The tutorial's requests are refused before the application sees them, so the response no longer carries the script. That is a mitigation at the edge: the page still renders untrusted data unescaped, and any encoding difference between the filter and the browser is the gap an attacker works in. The library fix and the rule-based fix are not interchangeable.

Access Control and Misconfiguration

The remaining lecture vulnerabilities share a theme: the application knows who you are but does not check what you are allowed to do — or it was deployed with the developer's defaults still switched on.

Security misconfigurations (Part VI)

Applications that are not properly configured are left vulnerable to attack. The deck's example is human error: leaving default passwords in place, or misconfiguring firewalls. Solution: configure according to security best practices and standards, such as OWASP and NIST guidelines.

Missing function-level access control (Part VII)

The application fails to verify user access privileges before allowing access to a particular function or feature. The deck's example: the user modifies the URL, or follows a direct link, and reaches the administrative panel without being challenged for proper credentials or permissions. Solution: implement access controls and verify user access privileges before granting access to any function or feature.

Invalidated redirects and forwards (Part VIII)

When an application uses a redirect or forward feature to send users to a different page, an attacker can use it to send them to a malicious site or to steal sensitive information. The deck's example: modifying the redirect URL so that it points at the attacker's site. Solutions: validate every redirect and forward request before it is executed, and avoid using user-supplied data — input fields or query parameters — in redirect or forward requests at all.

The reportable sentence for each flaw

Cause, then impact, then control. “The application fails to verify access privileges before loading the admin function, so any authenticated user who edits the URL reaches administrative functionality; the fix is an authorisation check on the server for every function, not a hidden link in the interface.”

Why hiding a link is not a control

Missing function-level access control is exactly the case where the interface is the only thing standing between a user and a feature. If the check lives in the menu that renders the link, removing the link from the request removes the check.

A user who is logged in as a normal account changes one path segment in the URL and reaches the admin console. Which vulnerability is this, and where must the fix live?
SQL injection; the fix belongs in the query builder
Invalidated redirect; the fix belongs in the redirect handler
Missing function-level access control; the fix belongs in a server-side authorisation check on the function

Intercepting Proxies and Web Application Firewalls

Two pieces of tooling bracket this week. A proxy sits on the attacker's side and shows you what the application actually receives; a WAF sits on the defender's side and decides what the application is allowed to receive.

Intercepting proxy

A tool that sits between the browser and the server so that every HTTP request and response can be inspected, paused, edited and replayed. Because the application's whole interface is HTTP, editing a request in a proxy is how you reach states the user interface would never produce: parameters the form does not send, values outside the form's own validation, and methods the page never uses.

Why the browser's developer tools come first

The tutorial begins by opening the browser's developer tools so the requests can be watched while the attack is attempted. That establishes the baseline: which request carries the parameter, what the server answers when the input is well behaved, and what changes when it is not.

Why disabling client-side validation proves nothing

A form's length checks and input types are conveniences. If removing them in the proxy produces a request the server accepts, the server never validated the input at all — which is the finding, expressed as a single edited request.

Web application firewall (WAF)

A security solution designed to protect web applications from various types of attacks and vulnerabilities. It acts as a shield between the web application and the client, analysing and filtering incoming requests and responses. It is typically placed in front of the application, on-premises or in the cloud — positioned between the client and the web server, intercepting and inspecting all traffic that passes through it.

Learning mode. NAXSI's learning mode prevents the filter from taking any action except logging suspicious requests to the Nginx error log. Those logged lines are then used to write exceptions so that legitimate requests are not blocked. Without that step, a WAF's first day in production is a denial-of-service against your own users — which is why the tutorial has you observe blocked and allowed requests in /var/log/nginx/error.log before trusting the rules.

Tutorial exercise walked through — demonstrating that NAXSI is filtering, not fixing. The Week 4 tutorial asks for a screencast in which the same XSS and SQLi attempts are shown both blocked and allowed.

1

Establish that the stack is up. Stop the PHP-FPM and NginX services, start them again, and show the services running. This is the checkpoint the tutorial asks for first, and it matters because every later observation depends on the same configuration being live.

2

Prove the application is reachable through the server, not around it. Load the PHP configuration page and log in to DVWA from the host through the browser. NginX does not have built-in PHP support, so PHP-FPM is the CGI bridge between the server and the application — showing both working proves the request path is real.

3

Send a suspicious request from the command line. Using curl rather than a browser removes the interface from the picture, so the response you get is the filter's decision and nothing else. Then show the corresponding line in /var/log/nginx/error.log: the request was detected.

4

Attempt XSS and SQLi with learning mode on. The attack reaches the application and only a log line appears, because learning mode takes no action other than logging. Record the log lines: they are the evidence used to write exceptions for legitimate traffic.

5

Disable learning mode and repeat the identical requests. Now the response changes — the tutorial has you watch the response code in the browser's developer tools — and the request never reaches the application. Turn learning mode back on afterwards.

6

State the conclusion in the report. The filter changed what reached the application without changing the application. The underlying flaws are still present, so the correct framing is mitigated pending patching, and the log is the artefact that proves both the detection and the gap.

A WAF blocks your injection attempt while it is enforcing, and the same request succeeds once learning mode is enabled. What is the correct conclusion?
The application was patched, and learning mode temporarily disabled the patch
The filter is a mitigation layer, not a fix: the vulnerable code is unchanged and the request succeeds whenever the filter is not enforcing
NAXSI is ineffective because it was compiled rather than installed from a package

Week 4 Recap

Five ideas carry the whole week. If you can state them and attach one control to each, the exam question is answerable.

HTTP is the entire interface

Requests in, responses out. Anything expressible as a request is in scope, including the requests the UI never sends.

Attack surface

State is rebuilt from a cookie

HTTP is stateless; the session token is the identity. Steal the token and you have stolen the identity, second factor included.

Broken authentication

Input must never become instruction

SQL injection, XSS and path-style object access are the same failure at three different interpreters.

Injection class

Authorise on the server, every time

Hidden links, client-side checks and unvalidated redirects are not controls. The check belongs on the function, server-side.

Access control

A WAF buys time, it does not fix

Inspect, filter, log — and shield known weaknesses until a proper patch is deployed.
