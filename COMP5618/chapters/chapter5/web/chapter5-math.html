COMP5618 — Week 5 supplement

Foundations: measuring what a scanner actually finds

Week 5 is a tooling week, so this page does the equivalent of a formula sheet: it pins down the definitions the lecture leans on, builds a taxonomy of scanner classes, and gives you the arithmetic that decides whether a scan was worth running — detection probability, coverage, precision and recall, and the risk score that orders the backlog.

Definitions verified against the Week 5 deck Formulas are standard practice, not lecture notation Triage arithmetic you can reproduce in the exam

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Vulnerability scanner

A tool that maps a target, sends safe tests for known weakness patterns, matches the responses against risk indicators, and reports prioritised evidence for remediation — output that still needs validation, ownership and remediation tracking.

White box / black box / grey box

White box examines source code, configuration files and internal messages, giving full visibility into internal workings. Black box scans over the network with no source access, identifying flaws from external observation and response analysis. Grey box combines both, with visibility that varies according to configuration and capabilities.

Fuzzing

A technique used by some vulnerability scanners to test the robustness and security of a web application by providing it with invalid, unexpected or random data as input.

Authenticated scanning

Configuring a scanner with a valid authentication cookie, obtained from a real login, so that its requests are treated as authenticated and can reach fields and functionality that are only available to logged-in users.

False positive, false negative, severity

A false positive is a flaw the scanner reports that is not present or not exploitable. A false negative is a real flaw the scan did not report. Severity is how much harm exploitation could cause; risk adds how likely and how exposed that exploitation is.

Axis 3 — what the finding is about

Security flaws

Injection, script execution and authentication gaps: input reaches an interpreter or a browser without the right control in between. These need confirmation, because the indicator is a response difference rather than a proof.

Misconfigurations and weak areas

Headers, TLS settings and exposed services are configurable facts, so a scanner can judge them with far higher confidence than it can judge an injection indicator. Weak areas are the prioritised issues handed to developers.

The arithmetic of scanning

Five relationships explain almost every practical question about scanners: how likely a probe set is to find a flaw, why exhaustive fuzzing is impossible, how good the alert queue is, how much of the app was reached, and how to order the work.

1. Detection is a sampling problem

If each probe independently reveals a given flaw with probability \(p\), then after \(n\) probes to the same input slot:

\[ P(\text{detected}) \;=\; 1 - (1-p)^{n} \]

Consequence: raising \(n\) is what fuzzing does, and it has diminishing returns; raising \(p\) is what better probe design does — a payload set that understands the context of the parameter. Both matter, and neither can rescue a slot the crawler never discovered.

Probes per slot \(n\)\(P(\text{detected})\) at \(p = 0.05\)Reading
10\(1 - 0.95^{10} \approx 0.40\)A short payload list misses most flaws
20\(1 - 0.95^{20} \approx 0.64\)Still more than a third missed
60\(1 - 0.95^{60} \approx 0.95\)The usual operating point of a real scan
90\(1 - 0.95^{90} \approx 0.99\)Diminishing returns: 50% more requests, 4 points more detection

2. Exhaustive fuzzing is not an option

For a field of length at most \(L\) over an alphabet of size \(|\Sigma|\), the number of distinct inputs is

\[ \left|\Sigma^{\le L}\right| \;=\; \sum_{k=1}^{L} |\Sigma|^{k} \;\approx\; \frac{|\Sigma|^{L+1}}{|\Sigma|-1} \]

A six-character field over the 95 printable ASCII characters has about \(7.4 \times 10^{11}\) candidates. At 100 requests per second that is roughly 233 years for one parameter. This is precisely why scanners ship curated payload sets and heuristics instead of brute force — and why understanding the vulnerability (the deck's emphasis on manual expertise) beats enumerating inputs.

3. The alert queue has a quality, and it is measurable

Once a human has triaged a scan, the ground truth is known and the scanner can be scored:

\[ \Pr \;=\; \frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FP}}, \qquad \mathrm{Re} \;=\; \frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FN}}, \qquad F_1 \;=\; \frac{2\,\Pr\,\mathrm{Re}}{\Pr+\mathrm{Re}} \]

A false-positive rate in the strict sense, \(\mathrm{FP}/(\mathrm{FP}+\mathrm{TN})\), needs the number of true negatives — which a scan does not enumerate. Report the false discovery rate \(\mathrm{FP}/(\mathrm{TP}+\mathrm{FP})\) instead, and recall separately, because the two failure modes have different costs: precision costs analyst hours, recall costs missed vulnerabilities.

4. Coverage explains most silent failures

With \(D\) endpoints discovered and \(P\) actually probed:

\[ C \;=\; \frac{P}{D} \]

A scan without a session cookie typically reports \(C\) near zero for the authenticated part of the application, because every protected request returns a redirect instead of content. State coverage next to every result: a scan that reached 18% of the surface and found nothing has told you almost nothing.

5. Priority is risk, not severity

Severity is impact; the ordering key for the backlog multiplies it by likelihood and exposure:

\[ R \;=\; L \times I, \qquad \mathbb{E}[\text{loss}] \;=\; P(\text{exploit}) \times \text{impact} \]

Two findings with the same impact can differ by a factor of four in risk once likelihood is counted, which is why the lifecycle's prioritize stage ranks by risk context after the assess stage scores severity and impact.

Where the severity number comes from. The deck requires severity scoring but gives no formula. Industry practice is a composite such as CVSS: exploitability (attack vector, complexity, privileges required, user interaction) plus impact (confidentiality, integrity, availability), combined and rounded up to one decimal, \( \text{Base} = \operatorname{roundup}\!\big(\min(\text{Impact} + \text{Exploitability},\,10)\big) \) with \( \text{Exploitability} = 8.22 \times AV \times AC \times PR \times UI \) and \( \text{Impact} = 6.42 \times \mathrm{ISS} \) for an unchanged scope, where \( \mathrm{ISS} = 1-(1-C)(1-I)(1-A) \). Everything weighted maximum for a network-reachable flaw gives \( \mathrm{ISS} = 1-0.44^{3} = 0.9148 \), \( \text{Impact} = 5.87 \), \( \text{Exploitability} = 3.89 \) and a base score of 9.8 — the familiar critical rating. Cite it as standard practice, not as lecture content.

Worked triage arithmetic

One scan of the lab application, worked end to end: coverage, precision, recall, the cost of the alert queue, and the effect of tuning the probe set.

What the crawler found

\(D = 400\) endpoints, parameters and forms across the public and authenticated parts of the application.

What the prober reached

\(P = 260\) of them, because part of the application needed a session the scan did not have.

What came out

30 alerts: 18 confirmed findings and 12 false positives. Manual review added 4 real flaws the scanner never reported.

What it cost

15 minutes of analyst time per alert, before a single fix was written.

Step 1 — coverage

\[ C = \frac{P}{D} = \frac{260}{400} = 0.65 \]

Two thirds of the discovered surface was tested. The missing third is the authenticated area, which is exactly where the manual review later found the extra flaws.

Step 2 — precision, recall and their balance

\[ \mathrm{TP} = 18, \quad \mathrm{FP} = 12, \quad \mathrm{FN} = 4 \] \[ \Pr = \frac{18}{30} = 0.600, \qquad \mathrm{Re} = \frac{18}{22} \approx 0.818 \] \[ F_1 = \frac{2(0.600)(0.818)}{0.600+0.818} \approx 0.692 \]

The false discovery rate is \(12/30 = 0.40\): two alerts in five are wasted work. Recall is 82%, so roughly one real flaw in five was never surfaced by the tool.

Step 3 — the cost of the queue, and the cost of tuning

At 15 minutes per alert, triage costs \(30 \times 15 = 450\) minutes, or 7.5 analyst-hours, of which \(12 \times 15 = 180\) minutes are spent on findings that turn out not to be real.

Now suppose the probe set is tightened and nine alerts disappear: eight false positives and one true positive. Then \(\mathrm{TP} = 17\), \(\mathrm{FP} = 4\) and the queue is 21 alerts long, so

\[ \Pr = \frac{17}{21} \approx 0.810, \qquad \mathrm{Re} = \frac{17}{22} \approx 0.773, \qquad F_1 \approx 0.791 \] \[ T_{\text{triage}} = 21 \times 15 = 315\ \text{minutes} \]

Precision improves by 21 points and triage falls from 7.5 to 5.25 analyst-hours, at the price of one missed flaw. Whether that trade is acceptable is a risk decision, not a tooling decision — which is why the lifecycle keeps prioritisation and ownership with people.

Step 4 — ranking the backlog by risk

Three confirmed findings, each scored with a likelihood \(L \in [0,1] \) and an impact \(I \in [1,5] \):

\[ R_1 = 0.8 \times 5 = 4.0, \qquad R_2 = 0.5 \times 5 = 2.5, \qquad R_3 = 0.9 \times 2 = 1.8 \]

Order: \(F_1 \succ F_2 \succ F_3\). Ranking on impact alone would tie the first two and might promote the third, whose impact is lower but whose likelihood is the highest of the three. That difference is the whole point of the prioritize stage.

Sanity check on the numbers: precision and recall are only meaningful once the ground truth is known, so they are always computed after manual confirmation. Reporting them from scanner output alone would be circular — the scanner would be marking its own homework.

The scan is useful but incomplete and noisy, with the authenticated area as a known blind spot
The alert queue is healthy, because only a third of the alerts were wasted effort

Worked solution — how many probes are enough? A payload set detects a given flaw in one parameter with per-probe probability \(p = 0.04\).

1

Write the model. \(P(\text{detected}) = 1-(1-p)^{n}\), with \(1-p = 0.96\).

2

Ask for 90% detection. \(0.96^{n} \le 0.10 \Rightarrow n \ln 0.96 \le \ln 0.10 \Rightarrow n \ge \frac{-2.3026}{-0.04082} \approx 56.4\). So 57 probes are needed.

3

Check the doubling claim. Halving \(p\) to 0.02 needs \(n \ge \frac{-2.3026}{\ln 0.98} \approx 114.5\), so 115 probes: improving the payload set is worth as much as doubling the request count.

4

State the caveat. The model assumes independence and a uniform \(p\). Real probes are correlated (the same payload family is tried in sequence) and \(p\) varies by parameter type, so treat the answer as an order of magnitude and validate it by measuring detection on the lab application.

Worked solution — scoring and ranking an injection finding. A confirmed SQL injection on a network-reachable search parameter: no authentication required, no user interaction, low complexity, and full loss of confidentiality, integrity and availability on the database tier. Scope is unchanged.

1

Impact. \(\mathrm{ISS} = 1-(1-0.56)^{3} = 0.9148\), so \(\text{Impact} = 6.42 \times 0.9148 = 5.873\).

2

Exploitability. \(8.22 \times 0.85\,(AV{:}N) \times 0.77\,(AC{:}L) \times 0.85\,(PR{:}N) \times 0.85\,(UI{:}N) = 3.887\).

3

Base score. \(\operatorname{roundup}(\min(5.873+3.887,\,10)) = \operatorname{roundup}(9.76) = 9.8\) — critical.

4

Turn the score into priority. Severity is one input. If this endpoint is internet-facing and holds customer records, \(L\) is high and \(R = L \times I\) puts it at the top of the backlog; the same 9.8 on an internal, single-user test instance would be ranked below it despite the identical score.

5

Say what the score does not cover. It does not measure whether the flaw is reachable in your deployment, whether compensating controls exist, or what the data is worth. Those are the risk-context factors the lifecycle's prioritisation stage adds.

Tutorial lab review

Tutorial 5 is a tooling lab: content discovery, a proxy, a DAST scan with a report, an injection-specific scanner, and manual confirmation of everything the tools claimed. Use the checklist below to audit what you produced.

Content discovery

Point a dictionary-based content scanner at your own DVWA host from the Kali VM and compare the output of two tools. Record which files and folders each one reports — and which one the other missed.

Proxy and request control

Configure Burp Suite as the browser's proxy, log into DVWA, and capture the request to the brute-force page. Identify the session cookie, the parameters, and how a dictionary attack would differ from a manual attempt.

Scan and report

Run ZAP (or OpenVAS) against DVWA and save the report. Group findings by mechanism and pick one representative SQLi, one XSS and one CSRF for manual confirmation.

Confirm and explain

For each representative finding, reproduce it in the DVWA interface, state why it was detected, and name the control that is missing. That is the analysis step the deck describes.

Worked answer — triaging one scanner alert with the numbers attached. Alert: “possible SQL injection” on a search parameter of the lab application. Scanner confidence: medium. Time budgeted: 15 minutes.

1

Start from the evidence pair, not the title. Read the stored baseline and probe responses. If the difference is a status code alone, the alert is probably robustness; if the boolean pair returns different result sets, the indicator is strong.

2

Reproduce deterministically. Replay the exact request three times. Variation in the response by itself tells you the indicator is unstable and the alert needs more work before it can be scored.

3

Classify. Confirmed true positive: the parameter reaches a query and the response changes with the injected condition. Dismissed false positive: the string is escaped, or the difference is explained by dynamic content. Either way the decision is recorded with its evidence.

4

Score and rank. Score severity from impact, then compute \(R = L \times I\) using the exposure of this endpoint. One confirmed SQLi on an authenticated admin route outranks a dozen low-impact header findings, even though header findings are almost never false positives.

5

Feed the result back. A confirmed flaw belongs in the remediation backlog with an owner; a dismissed one is a data point for tuning the payload set. Both outcomes improve the next scan, and both are needed for precision and recall to be computed honestly.
