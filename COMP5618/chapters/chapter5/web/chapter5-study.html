How a Web Application Scanner Works

The deck opens with the four-stage engine that every scanner shares, and with the caveat that matters most in the exam: automated discovery produces candidates, not confirmed vulnerabilities.

Lecture framing: automated scanners help teams discover common web weaknesses early, then turn findings into risk-based remediation work. Scanner output still needs validation, ownership and remediation tracking.

StageWhat the scanner does (deck)Evidence it recordsWhere it fails
CrawlMaps pages, APIs, forms and linksURL inventory, parameter names, form fields, route listMisses routes that are only reachable after login, from JavaScript, or from a sitemap that is not linked
ProbeSends safe tests for known weakness patternsThe exact request sent, including headers, cookies and bodyA destructive or rate-limited test can change state, lock accounts or corrupt lab data
AnalyseMatches responses to risk indicatorsBaseline and test response: status, length, timing, error text, reflectionsSignature matching cannot reason about business logic, so it produces both false positives and false negatives
ReportPrioritises evidence for remediationFinding, severity, affected endpoint, reproduction steps, suggested fixA report nobody owns or retests is a document, not a control

What scanners help detect

  • Security flaws — injection, XSS, authentication gaps
  • Misconfigurations — headers, TLS, exposed services
  • Weak areas — prioritised issues for developer fixes

Why teams still run them

  • Identify security weaknesses at scale and repeatedly
  • Protect sensitive data and reduce financial loss
  • Meet compliance and regulatory requirements
  • Enhance user trust through evidence of testing
Exam framing: automation buys coverage and repetition, not judgement. The deck is explicit that scanners have limitations in deep system inspection, that understanding a vulnerability and crafting a manual exploit remains crucial, and that automated tools should complement manual processes rather than replace them.
A scanner reports “possible SQL injection” on a search parameter because the response contained a database error string. What is the most accurate description of that output?
A confirmed vulnerability with a known impact
A candidate finding that still needs validation, ownership and remediation tracking
A misconfiguration of the web server error handler

Worked example — tracing one finding through the four stages. Scope: your own DVWA virtual machine on the isolated lab network. The scanner is pointed at the lab host, never at a system you do not own.

1

Crawl. The crawler starts from the seed URL, follows the menu links, and parses every form it reaches. It records /dvwa/vulnerabilities/sqli/ with one GET parameter (id) and one session cookie. Two links it never follows are behind the login form, so the site model is already incomplete.

2

Probe. For the id slot the prober first sends the normal value and stores the response as the baseline. It then substitutes one test string at a time — syntax-breaking characters, boolean-true and boolean-false variants, timing variants — and never touches more than one slot per request, so the cause of any change stays attributable.

3

Analyse. The boolean pair returns the same page with different result rows: a difference the crawler can attribute to the injected condition rather than to page noise. A syntax-breaking string returns a database error signature. Two independent indicators raise confidence; a single odd status code would not.

4

Report. The finding leaves with the request/response pair as evidence, the affected endpoint, a severity estimate and a suggested remediation. Because it is an error-based indicator, it may still be a false positive if the application sanitises the value elsewhere — so the first action on the ticket is manual reproduction, not a patch.

5

Close the loop. A human reproduces it, a developer fixes it (parameterised queries), the scanner is re-run to verify, and the ticket records who owns the residual risk if the fix is deferred. Those three words — validate, own, track — are the deck's own caveat about scanner output.

Black Box, White Box and Grey Box

The deck names three main categories of web application vulnerability scanner. Each follows a different approach, and each brings its own advantages and limitations.

White box

A scanner that examines the source code or internal structure of a web application. It provides a deeper level of analysis by inspecting the application's code, configuration files and internal messages. Key characteristics from the deck: source code analysis, internal message analysis, in-depth coverage, customisation and configuration, and code review with recommendations.

Black box

A scanner that operates from the outside, without access to the internal structure or source code. It simulates real-world attack scenarios and identifies vulnerabilities by interacting with the application as an external user would. Key characteristics: network scanning, attack payloads, pattern recognition, vulnerability detection and web application crawling.

Grey box

Combines elements of white and black box scanning. Visibility varies with the configuration and capabilities granted to the tool; it mixes code analysis and response analysis, may require source access depending on the level of analysis, and can incorporate an external perspective to some extent.

DimensionWhite box scannersBlack box scannersGrey box scanners
ApproachExamines source code and internal structureScans via the network and analyses responsesCombines elements of white and black box scanners
VisibilityFull visibility into the application's internal workingsLimited visibility into the internal workingsVariable visibility depending on configuration and capabilities
Vulnerability detectionComprehensive analysis of code and configurationIdentifies vulnerabilities from external observation and response analysisMixes code analysis and response analysis
False positives / negativesMay arise from misinterpretation of codeMay arise from limited visibility and response analysisMay arise depending on the level of analysis performed

Benefits of white box scanning

  • Early detection — issues found during development, before deployment
  • Deeper analysis — flaws that are hard to detect from outside
  • Compliance and best practice — coding standards and industry guidelines
  • Secure coding education — insights developers can act on immediately

Benefits of black box scanning

  • Real-world simulation — how an external attacker actually sees the app
  • Comprehensive coverage — probing many parts and functions
  • Quick deployment — no source or internal structure required
  • Third-party perspective — flaws that internal developers cannot see
  • Continuous monitoring — regular scans that catch emerging threats
Downsides worth quoting: black box scanners suffer limited visibility, false positives and false negatives, and dependence on response analysis. White box scanners suffer source code availability, complexity and false positives, and a limited external perspective. Neither list is a reason to skip the other class — they fail in different directions.
A team has the source repository and CI pipeline but no running production instance to scan. Which class of scanner can still be used, and what does it cost them?
White box scanning, at the cost of the external attacker's perspective
Black box scanning, at the cost of source code access
Grey box scanning, because it needs neither source nor a running target

Fuzzing and Probe Design

Fuzzing is the technique underneath the probe stage. Understanding what it does — and what it cannot do — explains both the value and the noise of scanner output.

Fuzzing (deck definition)

A technique used by some vulnerability scanners to test the robustness and security of a web application. It involves providing the application with various types of invalid, unexpected or random data as input in order to identify vulnerabilities.

Input classWhat it stressesWhat the scanner compares
InvalidParsing, validation and error handlingStatus code changes, stack traces, database error signatures, generic error pages
UnexpectedType assumptions, boundary conditions, encoding and canonicalisationResponse length and structure against the baseline, reflected characters, boolean-true vs boolean-false differences
RandomRobustness and crash resistanceTiming outliers, connection resets, repeated-content fingerprints, rate-limit responses

Two design decisions make the difference between a useful probe set and a noisy one. The first is one variable at a time: change a single parameter or header per request so that any change in the response is attributable. The second is the baseline: the same request with a benign value, stored before any test is sent, is the only thing that makes a diff meaningful.

# Conceptual exchange only — sent by a scanner to your own lab VM, never to a third party.
# 1. Baseline: the benign request, stored for comparison.
GET /dvwa/vulnerabilities/sqli/?id=1&Submit=Submit HTTP/1.1
Host: <your-lab-vm>
Cookie: PHPSESSID=<session-copied-from-your-own-lab-browser>; security=low
--> 200 OK, 4 812 bytes, one data row, no error text

# 2. Probe: exactly one slot changed. The scanner records the pair, not a verdict.
GET /dvwa/vulnerabilities/sqli/?id=<single-test-string>&Submit=Submit HTTP/1.1
Host: <your-lab-vm>
Cookie: PHPSESSID=<same-session>; security=low
--> 500 Internal Server Error, 1 290 bytes, database error signature present

Why fuzzing finds real flaws

Attackers also send malformed input. A parser that assumes well-formed data fails in ways the developer never tested: unhandled exceptions, verbose errors that leak structure, and code paths that skip validation entirely.

Why fuzzing produces noise

A 500 response may be a handled error with no security consequence, and an input echoed into the page may already be encoded. Pattern matching sees the symptom, never the root cause — which is exactly why the analyse stage needs a human afterwards.

Safe testing in the lab: the deck specifies safe tests for the probe stage. In the tutorial this means a deliberately vulnerable application (DVWA) running on your own virtual machines, non-destructive checks, and awareness that state-changing requests, account lockouts and rate limits can distort both the target and the result.
A scanner sends one request per parameter and keeps a benign baseline of each. Which property of good probe design does this describe?
Randomising the order of tests to avoid caching effects
Isolating one variable per request and comparing against a stored baseline
Maximising the number of requests per second to finish the scan faster

Content Discovery and Intercepting Proxies

The tutorial puts the scanner toolkit into practice against DVWA. Its first lesson is a distinction the exam likes: a content scanner is not a vulnerability scanner, but it finds the entry points a vulnerability scanner needs.

Web content scanner (tutorial)

Where nmap scans a host for ports, services, versions and operating-system information, a web content scanner looks for web objects, hidden or otherwise. It usually works by launching a dictionary-based attack against a web server and analysing the response. These tools are not vulnerability scanners, but they can find useful pages that contain possible entry points. Example tools: dirb, dirbuster, gobuster.

Authenticated Scanning and Session Cookies

Half of a typical application is behind a login form. The deck's answer is the authentication cookie — and the tutorial's answer is DVWA, which requires a login before a scanner can reach the interesting fields.

Authentication and cookies (deck)

In web applications, certain fields or functionalities may only be accessible to logged-in users. Users obtain an authentication cookie by providing correct login credentials; the cookie is stored in the browser and included in subsequent HTTP requests. The presence of a valid cookie is what authenticates the browser.

# Conceptual exchange only, against your own DVWA VM on the lab network.
# Before: the scanner has no session, so protected routes bounce it.
GET /dvwa/vulnerabilities/brute/ HTTP/1.1
Host: <your-lab-vm>
--> 302 Found, Location: /dvwa/login.php
    (the body is the login form, so the scanner learns nothing about the protected page)

# After: the tester logs in with the lab credentials and copies the session cookie
# from their own browser's cookie store into the scanner configuration.
GET /dvwa/vulnerabilities/brute/ HTTP/1.1
Host: <your-lab-vm>
Cookie: PHPSESSID=<value-from-your-own-lab-session>; security=low
--> 200 OK, the protected form is returned and can now be probed
Without a valid session cookieWith a valid session cookie
Protected requests are answered with a redirect to the login pageRequests are treated as authenticated and reach the requested fields
The crawl model contains only public routes and the login formThe crawl model contains the full authenticated navigation, forms and API routes
Findings cluster on pre-authentication surfaces: headers, TLS, error handling, login formFindings appear in privileged functionality, including injection, access-control and session flaws
False negatives dominate: absence of a finding says nothing about the protected areaCoverage improves, but cookie expiry, CSRF tokens and lockouts now shape the result
Operational details that decide whether an authenticated scan works: retrieve the cookie from your own lab session rather than guessing it; expect it to expire mid-scan, and re-authenticate when the redirect count spikes; check whether the application also requires a per-request anti-CSRF token; avoid brute-force style tests that lock the account you are using; and keep the cookie out of the report, because a session identifier is a credential.
A scanner configured without a session cookie reports almost nothing on an application whose interesting features are all behind a login. What is the correct reading of that report?
The authenticated area of the application is secure
The scan is dominated by false negatives because the scanner never reached the protected functionality
The scanner is misconfigured at the network layer and cannot reach the host

Worked answer — planning an authenticated scan of a lab application. Target: DVWA on your own Ubuntu VM, reached from the Kali VM over the isolated lab network.

1

Confirm the login contract first. Log in through the browser with the proxy recording. The exchange shows the method, the parameter names, the credential fields and the Set-Cookie response that issues the session. That one exchange defines everything the scanner needs.

2

Copy the session cookie, not the password. The deck's method is to retrieve the authentication cookie from the browser's cookie store and enter it into the scanner. The scanner then sends requests that are treated as authenticated, without storing credentials in a tool configuration.

3

Prove the cookie works before scanning. Request one protected page with and without the cookie. A 200 with the cookie and a 302 without it is the evidence that the scan will actually see the protected area — and it is the baseline for detecting expiry later.

4

Plan for session lifecycle. Sessions expire, may be invalidated by concurrent logins, and may be tied to an anti-CSRF token or a security level setting such as DVWA's difficulty. Re-authenticate on redirect spikes and note the session's lifetime as a limitation of the scan.

5

Scan safely and report honestly. Exclude destructive or lockout-prone tests, record the cookie in the evidence but redact it from the report, and state plainly which parts of the application the session could and could not reach. A coverage statement is what turns a scan into a defensible assessment.

Triage: False Positives, False Negatives and Severity

Scanner output is a work queue, not a verdict. Triage is the manual stage that decides which findings are real, how bad they are, and who fixes them.

Three terms to keep apart

False positive — the scanner reports a flaw that is not present or not exploitable. False negative — a real flaw the scan did not report. Severity — how much harm the flaw could cause if it were exploited, which is what prioritisation ranks.

Where false positives come from

  • A pattern matched text that is already encoded or escaped downstream
  • A 500 response from unhandled input that has no security consequence
  • An error string in a page that is never influenced by user input
  • Duplicate reporting of one flaw across many parameters

Where false negatives come from

  • The crawler never found the route: unlinked pages, multi-step forms, JavaScript-built URLs
  • No session cookie, so protected functionality was never probed
  • The flaw is logic or workflow abuse, with no signature to match
  • Rate limiting, lockouts or WAF responses stopped the probes early
Signal in the reportCould be a false positive because…How a human confirms it (lab)
Database error signature in a responseThe message may be static text or a decoy, not caused by the injected valueSend a benign value, then a syntax-breaking value; confirm the error appears only with the second, and only in that parameter
Reflected input in the response bodyThe value may be encoded, or reflected in a context where it cannot executeInspect the exact bytes around the reflection and test the encoding in the lab browser
Status code changed from 200 to 500Any malformed input may produce an unhandled error with no security impactRepeat with several malformed values; if all fail identically, the finding is robustness, not injection
Response length changed materiallyDynamic content, timestamps or A/B rendering change length without any injectionRequest the baseline several times to measure normal variation before attributing the change
Longer response time on a test requestServer load, caching or network jitter explain most outliersRepeat the timing test and compare against several baseline samples, not one

What handcrafted exploits still do better

  • Exploration of edge cases the payload set does not contain
  • Customisation for the specific system under test
  • Detection of complex vulnerabilities that span several requests
  • Real-world simulation of a motivated attacker

What automation does better

  • Repetition: the same checks on every build, without boredom
  • Coverage: every discovered parameter, every time
  • Efficiency: repetitive tasks take minutes, not days
  • Baselines: consistent evidence that a regression has appeared
The deck's position, stated plainly: scanners are useful but have limitations in deep system inspection; understanding a vulnerability and crafting an exploit manually remains crucial; automation should streamline and expedite existing manual processes. Manual expertise plus automated tools is what produces comprehensive identification.
A report lists the same reflected-input finding against six parameters of one page. The reflection is HTML-encoded in every case. What is the correct triage outcome?
Six confirmed vulnerabilities, because the input is reflected each time
Dismiss the alerts as false positives, recording the encoding evidence once and noting the duplicate pattern
Leave all six open and unresolved until the next scan

The Vulnerability Management Lifecycle

A scan is one turn of a continuous cycle. The deck frames this as DevSecOps practice: find, risk-rank, fix, validate and monitor weaknesses across applications and systems.

StageQuestion it answersArtifact that proves it happenedOwnership
DiscoverWhat do we have, and what is exposed?Asset and endpoint inventory, scan scope statementSecurity and platform teams
AssessIs it real, and how bad is it?Reproduced evidence pair, severity and confidenceSecurity analyst
PrioritizeWhat gets fixed first?Risk-ranked backlog with justificationSecurity with product owners
RemediateWhat changes, and who changes it?Patch or configuration change, linked to the findingEngineering team
VerifyIs it actually gone, and did the fix break anything?Retest result plus regression test evidenceSecurity review
MonitorIs it coming back, and are we meeting our commitments?Trend of recurrence and SLA attainmentSecurity leadership
Where AI fits, according to the deck: AI can cluster duplicate findings, enrich exploit context and suggest fixes — it strengthens triage. Accountability stays with engineering teams, security review and measurable SLAs. A model may draft the ticket; it does not own the risk.
Regression testing (deck)

Retesting the modified or updated parts of the application to ensure that the changes do not introduce new vulnerabilities or impact existing functionality. After fixing a known vulnerability, regression testing verifies that the fix does not break features or open a new hole.

Mitigation strategies (deck)

Measures that reduce the risk or impact of vulnerabilities: applying patches, implementing security controls, or modifying system configurations. Examples: input validation and output encoding to mitigate XSS; secure communication protocols such as HTTPS to protect against data interception and tampering.

Why the cycle, not the scan, is the unit of work

A one-off scan produces a snapshot. The lifecycle produces a trend: recurrence, mean time to remediate, and evidence that verification actually happened.

What makes a report actionable

Affected endpoint, evidence pair, severity with justification, suggested remediation, owner, and a verification step. Without the last two it is documentation rather than a control.

Defending Web Applications

The deck closes the loop from offence to defence with four defensive practices and a layered architecture in which each layer owns a different control.

Data layer

Defensive software architecture

Designing and implementing software systems with security in mind: incorporating security controls such as access controls, input validation, encryption and error handling at various layers of the application architecture, rather than bolting them onto one layer.

Comprehensive code reviews

Thorough examination of the source code to find vulnerabilities and insecure practice, which also surfaces coding errors and deviations from standards. Manual or automated, experienced developers or security analysts review the codebase line by line, looking for flaws such as SQL injection, XSS and insecure data storage.

Vulnerability discovery and analysis

Discovery is actively searching for weaknesses: manual inspection, automated scanning tools, fuzzing or penetration testing. Analysis is evaluating the impact and severity of what was found — the underlying cause, the attack vectors, and the consequences, such as how much access an injection flaw would grant and what damage it could cause.

Tutorial self-assessment — turning a scan report into a confirmed set of findings. The tutorial asks you to scan DVWA with OWASP ZAP (or OpenVAS), save the report, and then, for each important finding, confirm it manually, explain why it was detected and what caused it, and repeat for one SQLi, one XSS and one CSRF.

1

Scope and evidence first. Confirm that the target is your own DVWA instance on the lab network and that the difficulty is set to low. Record the tool, its version, the start and end time, and the session state — an unauthenticated scan and an authenticated scan of the same host are different assessments.

2

Group the report by finding type. Scanners repeat one root cause across many parameters. Cluster by the mechanism (injection, script execution, request forgery), then pick one representative endpoint per cluster to confirm — the tutorial's requirement of one SQLi, one XSS and one CSRF is exactly this move.

3

Confirm each one manually in the lab interface. Reproduce the flaw through the DVWA pages themselves, with the proxy recording, and capture the request, the response and the visible effect. State in one sentence why the scanner flagged it: which input reached which component and produced which observable difference.

4

Explain the cause, not the symptom. For each confirmed flaw, name the missing control: absent parameterisation for the injection, unencoded output for the script execution, a state-changing request with no anti-CSRF token for the forgery. That is what makes the finding remediable, and it is what the deck's vulnerability-analysis step asks for.

5

Write the remediation and the retest. For each flaw, give the control that fixes it, then say how you would verify the fix: re-run the scan, re-attempt the manual reproduction, and regression test the pages that changed. A finding without a verification step is not closed.

6

Respect the scope. Everything above happens against a deliberately vulnerable application on your own virtual machines. The same techniques pointed at a system you do not own are an offence, not an exercise — which is why the unit treats ethics and authorisation as part of the tooling, not as an afterthought.

A team fixes a cross-site scripting flaw by encoding output on the affected page. What does the deck's lifecycle require next?
Close the finding, because the control that addresses XSS has been applied
Retest the finding and run regression tests on the modified components before closing it
Re-scan the whole application and ignore the changed pages, since the scanner covers them
