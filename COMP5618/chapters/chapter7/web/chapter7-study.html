The Mobile OS Landscape, and Why Android

The smartphone operating-system market is effectively a duopoly. The lecture spends its first slides explaining why a security unit studies the open one.

iOS

  • Closed-source operating system
  • Kernel based on Unix (Darwin)
  • Apps developed in Swift
  • Native app development historically in Objective-C

Android

  • Open-source operating system based on Linux (by Google)
  • Native apps developed in Java
  • Many other toolchains allow development in other languages
Also-rans named in the deck

The lecture lists the platforms that never reached the same scale: Windows, BlackBerry OS, Symbian OS, Sailfish OS, Fire OS and Tizen. The exam-relevant point is not the list but the concentration: two platforms define the mobile attack surface, and one of them is open.

Why the unit focuses on Android

  • The open-source nature of the OS lets you learn mobile OS concepts rather than guess at them
  • Apple's app signing process makes it difficult to publish vulnerable apps or reverse engineer them
  • Device availability — emulators and cheap hardware are both easy to obtain

What follows from that

  • You can read the platform, the manifest and the bytecode yourself
  • You can build, disassemble, modify and re-sign an app end to end
  • Every one of those steps is also what an attacker does
Framing for the exam: the choice of Android is methodological, not a claim that Android is less secure. An open platform is one whose security model you can inspect — which is exactly what the rest of this week does.
Which pair of reasons does the Week 8 deck give for studying Android rather than iOS?
Open source so the concepts are inspectable, and Apple's signing process makes vulnerable or reverse-engineered apps hard to publish
Android has a larger market share and therefore a larger attack surface
Android apps cannot be reverse engineered, so the material stays theoretical

Android Architecture: A Stack of Trust Boundaries

Android is a Linux kernel with a managed application runtime stacked on top of it. Read as a security document, the stack is a series of levels that each enforce a different kind of control.

Reading the stack

The lecture presents the Android OS architecture as a layered diagram. Memorise it as five bands and one vertical column: the Linux kernel at the bottom, then the HAL, then native C/C++ libraries beside the Android runtime, then the Java API framework, and finally the system apps. Everything above the kernel runs as ordinary Linux processes, which is what makes one mechanism — the UID — the backbone of the whole security model.

LayerRepresentative componentsSecurity role
System appsDialer, Email, Camera, Calendar, third-party appsUntrusted from the platform's point of view; holds only what its manifest declares
Java API frameworkActivityManager, PackageManager, Content ProvidersMediates app requests; resolves intents and performs permission checks
Libraries + runtimelibc, media, SQLite, WebKit; ARTLarge native parsing surface; one isolated runtime per app process
HALCamera, audio, Bluetooth, sensorsHardware reachable only through permission-gated framework calls
Linux kernelUID/GID, DAC, SELinux, binder, driversThe actual enforcement layer: isolation is a kernel property
The one-sentence summary: Android's security architecture is a userspace permission framework sitting on top of a kernel-level user-isolation mechanism. Break the kernel or the framework and both halves fall together — which is precisely what the landmark vulnerabilities in this week's deck did.
Where is an Android app's isolation actually enforced?
In the Android runtime, because each app executes its own DEX bytecode
In the app manifest, because it declares the app's permissions
In the Linux kernel, through the per-app UID and the kernel's access-control checks

The Application Sandbox

The whole of Android's application security rests on three sentences from the lecture. Everything else in the week is a consequence of them.

The lecture's three claims:

  1. Android's sandbox is a user-based protection model in Linux.
  2. Apps cannot talk to each other and have only limited access to the operating system.
  3. Apps must share resources and actions by declaring permissions.
Property of the sandboxMechanismWhat it stops
One identity per appA distinct Linux UID assigned at installOne app reading or writing another app's files
Private storageApp data directory owned by that UIDCross-app credential and database theft
Separate executionOwn process and own ART instanceShared in-memory state between apps
Mediated accessFramework APIs backed by permission checksDirect reach into the OS, hardware and user data
Explicit sharingIntents, content providers, bound servicesSilent data exchange — sharing must be declared and can be permission-guarded

Why user-based isolation was the right choice

Linux already had a mature, well-tested notion of a user. Reusing it gave Android per-app isolation, file ownership and the chmod-style semantics for free, and it runs at kernel speed rather than inside a language interpreter.

What the sandbox deliberately does not do

It does not judge intent, it does not stop an app from being malicious with the permissions it legitimately holds, and it does not protect data the app chooses to publish. Sandboxing bounds reach, not behaviour.

Two apps are installed on the same device. What does the sandbox guarantee about them by default?
Neither can read the other's private files, and they cannot talk to each other except through declared mechanisms such as intents or content providers
They share one sandbox so their combined permissions can be audited together
A malicious app cannot cause harm because the sandbox blocks malicious behaviour

The Permission Model

The sandbox denies everything by default. Permissions are the declared exceptions — the mechanism by which an app asks for a capability it was not born with.

Three things a permission actually is

1. A declaration. The app states the capability it needs in AndroidManifest.xml. 2. A grant. The platform (or the user, at runtime) decides whether the app receives it. 3. A mapping onto a kernel identity. A granted low-level permission can be expressed as group membership, so the kernel check that follows is an ordinary Unix check.

Permission categoryMechanismApp store behaviour
Kernel-level permissionsEnforced at the kernel by GID membership; read by the low-level system servicesNot user-visible; part of the platform contract
Application-level permissionsEnforced by the framework when an API for sensitive data or hardware is calledRequested at install; since Android 6.0 requested and granted at runtime
Install-time (normal) permissionsLow-risk, granted automatically on installShown as a summary rather than a prompt
Runtime (dangerous) permissionsA dialog is shown at the moment of first useUser can approve to save time, or deny and review later
Runtime permissions changed the security question. Before Android 6.0, a permission prompt happened once, at install, in a batch, when the user was least able to judge it. After the change the user is asked in context, at the moment the capability is used, when they can judge whether it makes sense. The attacker's question moved with it: not “will the user notice this permission?” but “can I get the capability used while the grant is in force?”
Auditing an app's reach: read the manifest, list the declared permissions, and for each one ask three questions — does the app's stated purpose require it, does the code path that uses it actually exist, and is the permission used for the narrowest possible job? A torch app with contact access fails all three.
An app declares only android.permission.INTERNET. What can it do?
Read the user's contacts, because it can upload them over the network
Open network connections, and nothing beyond what its manifest declares
It must prompt the user at runtime before it can use the network at all

Worked example — auditing a permission list before you trust an APK. Given a decompiled app whose manifest declares INTERNET, CAMERA, READ_CONTACTS, ACCESS_FINE_LOCATION and RECEIVE_BOOT_COMPLETED, decide whether to install it. The app claims to be a QR-code scanner.

1

State the claimed purpose. A QR scanner needs the camera and, to resolve a scanned URL, the network. Two permissions are justified before any code is read: CAMERA and INTERNET.

2

Flag the unexplained ones. Contact access and precise location have no stated relationship to reading a barcode. RECEIVE_BOOT_COMPLETED means the app wants to start itself without being launched — a persistence primitive, not a scanning feature.

3

Look for the code path, not just the declaration. Disassemble with apktool and search the smali for the API calls those permissions gate. A declared permission with no calling code is either dead weight or a capability reserved for later; both are reasons to ask why.

4

Check the reachable components. If the app also declares a BOOT_COMPLETED receiver that starts a background service which reads and uploads contacts, the permissions stop being suspicious and start being a described design.

5

Write the verdict as a trade-off, not a verdict. “The camera and network grants are proportionate to the stated purpose; the contacts, location and boot-start grants are not, and there is no need for the app to run before the user launches it. On a lab device this is a finding; on a personal device it is a reason not to install.”

Intents and IPC: the Controlled Hole in the Sandbox

A sandbox with no exits is useless. Android's exits are explicit: an app publishes components, other apps send intents, and the framework decides whether the message may be delivered.

Vocabulary you must be able to use precisely

Intent — a message describing an operation to perform. Explicit intent — names the target component, so only that component can receive it. Implicit intent — names an action and data, and lets the system resolve a handler. Intent filter — the declaration by which a component advertises which implicit intents it accepts. Exported component — a component other apps may reach; unexported components are private to the app.

Four component types

  • Activity — a screen the user interacts with
  • Service — background work with no UI
  • Broadcast receiver — reacts to system-wide or app-sent announcements
  • Content provider — a structured data interface other apps can query

Where IPC goes wrong

  • An exported component without a permission guard is a public API nobody designed
  • Trusting the caller's identity or the extras it supplies
  • A provider whose queries are not constrained by the caller's identity
  • Implicit intents whose resolution can be claimed by another app
The design rule: every exported component is an interface contract with every other app on the device. Treat it the way you would treat a public web endpoint — authenticate the caller where the operation is sensitive, validate everything that crosses the boundary, and export only what has to be exported.
An app declares a broadcast receiver that is exported and not protected by a permission. What is the security consequence?
Any other app on the device can send it a broadcast and reach whatever logic the receiver runs
Nothing, because the sandbox prevents apps from communicating with one another
The receiver is safe as long as it is exported rather than unexported

APK Internals: a Signed ZIP You Can Dismantle

The code written in Android Studio is built into an Android Application Package. Understanding what is inside it is the prerequisite for every analysis task in this unit.

From source to package

The code you write is built to an Android Application Package (APK). An APK is a packaging format — in practice a ZIP archive with a defined layout. Unzip it and you get something that is mostly in binary and unreadable; that is expected, not a sign that something went wrong. The readable view comes from a disassembler.

EntryHoldsTool that makes it readable
AndroidManifest.xmlPackage identity, permissions, components, export statusapktool (decodes binary XML)
classes.dexCompiled application bytecodeapktool → smali
META-INF/Digests and the signing certificatekeytool, jarsigner, apksigner, openssl
resources.arsc, res/Compiled resource table and resource filesapktool (decoded resources)
lib/, assets/Native libraries and bundled raw filesFile and disassembly tools
The consequence of “just a ZIP”: if the package is an archive and the code inside it is bytecode, then anyone holding the package can read the code, change a resource, edit the smali, rebuild and re-sign. That is the tutorial's whole workflow — and it is also the attacker's workflow for advertisement hijacking and malware redistribution.

Worked example — the tutorial's repackaging loop, end to end. Task: an app shows a greyscale USYD logo, and two buttons switch it to colour and back. Change the behaviour so the buttons are swapped, then prove it on the emulator.

1

Establish the baseline. Install the original with ./adb install task2.apk on a running Android Virtual Device and confirm which button does what. Without a baseline you cannot claim the change worked.

2

Disassemble. Decompile the APK with apktool. The output is a directory tree: a readable manifest, decoded resources, and a smali/ tree of the bytecode.

3

Make the smallest change that produces the behaviour. For a resource-level change, swap the image file names so each button now loads the other asset. Nothing in the code changes; the mapping from button to asset does.

4

Rebuild with apktool. Repackaging disassembled sources into a new APK is what apktool b is for. The result is a valid package with an invalid signature — Android will refuse to install it as it stands.

5

Sign with a key you control. Generate a keystore with keytool (the tutorial's example uses RSA with SHA1withRSA, which is illustrative rather than current best practice) and sign the rebuilt APK with jarsigner. The signature now vouches for you, not for the original developer — which is exactly why an unexpected signer is a finding.

6

Install and verify. Install the rebuilt package on the emulator and demonstrate the swapped behaviour. In the tutorial deliverable, this demonstration is the evidence; the tool output alone is not.

7

State what changed and why it mattered. One resource mapping changed, so the app's behaviour changed without a code edit. That is the security lesson: signing authenticates the packager, not the behaviour, so an app whose signer you do not recognise is an app whose behaviour you have not verified.

Why acquisition choice is a security decision

An APK obtained from a mirror may not be the artefact the developer published. If you analyse the mirror's copy you may be analysing an already-repackaged app — and if you install it you may be running one. The certificate tells you who signed what you are holding; comparing it against the official signer is the check.

Anti-reverse-engineering as a response

Developers can raise the cost of exactly this workflow. ProGuard ships with Android Studio and obfuscates; DexGuard and DashO add encryption. The lecture is explicit that there is a trade-off — obfuscation and encryption also cost debuggability, crash-report quality and developer time.

Copy it from the ADB shell; ADB lives in the Android SDK platform-tools and the device must have developer mode / USB debugging enabled
Download it from an alternative app store, because those allow direct APK downloads
Download it from Google with a Play CLI client, because vendor signing guarantees fidelity

Static Analysis: the Week 8 Lab Workflow

The tutorial defines the task precisely: inspect the code of a program and understand its purpose without executing it. The same techniques are applied to malware analysis.

Static vs dynamic

Static analysis reads the artefact — manifest, resources, bytecode, certificate — and reasons about what it would do. Dynamic analysis runs it and observes. Static analysis is safer (nothing executes), cheaper (no instrumented device needed) and better at finding dormant capabilities; dynamic analysis is better at finding what actually happens at runtime. A serious review uses both, starting static.

StepCommand-line toolWhat you are looking for
DisassembleapktoolReadable smali, decoded manifest and resources — and a tree that can be rebuilt
Inspect the certificatekeytool, jarsigner, apksigner, opensslCertificate owner/distinguished name, validity dates, key and signature algorithm
Attribute to a developerThe same certificate tools on a second APKIdentical signer identity across two packages — the tutorial's “same developer” question
Create a signing keykeytool -genkeyA keystore and alias you control, so the rebuilt APK can be installed at all
Sign the rebuildjarsigner (or apksigner)A valid signature over the repackaged artefact — under your identity, not the original's
Install and observeadb installThe package running on the emulator, with the modified behaviour visible
The certificate question, answered properly. Two APKs come from the same developer when their signing certificates identify the same owner — not when the file names, icons or package-name prefixes look similar. The tutorial's first task is deliberately built so that appearances are not the answer: you have to read the certificate and compare identity, validity period and key details.

From resource edits to logic edits

  • Renaming resource files changes which asset a button loads — behaviour with no code change
  • Editing smali changes program logic itself
  • The order matters pedagogically: the easy change proves the toolchain, the hard one proves you can read bytecode

Why this is a security lesson and not just a lab

  • The identical workflow produces advertisement hijacking and malware redistribution
  • Nothing in it requires the original developer's cooperation or key
  • The only thing standing between a rebuild and a user is the signer identity the user never checks
Lab scope: every technique on this page is performed against locally provided sample APKs and an emulator you control. Repackaging, re-signing or redistributing someone else's application without authorisation is not a lab exercise — it is the offence the unit spends Week 1 warning about.

Worked example — the certificate question from Task 1. Given a set of decompiled sample APKs, decide which two came from the same developer, and justify it in a way that would survive scrutiny.

1

Decompile first, but do not start there. Run apktool over each sample to get readable manifests and resources. This tells you what each app claims to be; it does not tell you who built it.

2

Extract the signer identity. Use a certificate tool — keytool, jarsigner -verify -verbose -certs, apksigner verify --print-certs, or openssl over the certificate — and record the certificate owner, the validity period, and the key and signature algorithms for every sample.

3

Compare the identities, not the packaging. The decisive evidence is that two packages carry a certificate naming the same owner with the same validity period and key material. Shared icons, similar package names or a common vendor prefix are circumstantial at best and are exactly the cues a repackaged app can fake.

4

Check what the signature does and does not prove. It proves the two packages were signed with the same private key, so the same party controlled both releases. It does not prove the code is safe, and it does not prove the signer is who the certificate claims to be unless the trust chain is verified.

5

Answer in the form the tutorial asks for. “Apps 2 and 4 share a developer: their signing certificates report the same owner and validity period, and the signature algorithms match. App 1 differs in owner and validity, so it is a different signer — and a difference in signer is the first thing to explain when a package claims to be an update of another.”

Reverse-engineering exploits

What repackaging buys an attacker, in the deck's own list: advertisement hijacking (take a popular application and change the advertisement ID, then publish it in a different app market), distribution of malware (incorporate malware code segments and redistribute), harvesting credentials in bad implementations, and — for fun — changing scores in games or skipping levels.

Why the smartphone is a harder target than it looks

The sandbox, the permission gate and the signature check are three independent obstacles. Every incident above defeated exactly one of them — which is why the deck's closing instruction is defence in depth: no single control is asked to carry the whole load.

What made Janus (2017) significant?
A crafted MMS could trigger code execution during media parsing
A flaw in a remote support tool let an attacker control the device remotely
APK/DEX bytes could be added to a package without changing its signature, allowing an app to be updated without the developer knowing

Rooting, Jailbreaking and Privilege Escalation

The sandbox is a boundary around the app. Rooting is what happens when something — the owner or an attacker — gets past it.

“Jail breaking” iOS devices

  • Gets you the ability to download apps that are not in the App Store, use themes, and extensions Apple does not support
  • Involves no changes to the iOS operating system
  • Apple signs the source code of every App Store app; iOS carries Apple's public key and verifies that apps are signed
  • Unsigned apps cannot be executed — and jailbreaking removes that check

“Rooting” Android devices

  • Unlike iOS, Android is open source and already allows installing apps from outside the official store
  • Rooting means obtaining superuser access to the system
  • It also allows replacing the existing operating system with custom ROMs
  • The goal is the same as jailbreaking, but on Android the sideloading objection does not apply — only the privilege escalation does
The distinction to write down

On iOS, jailbreaking is fundamentally about removing a signature check so unsigned code can run; the OS itself is unchanged. On Android, rooting is about obtaining superuser access, which then permits replacing the OS entirely. Both end with an unconfined user, but they defeat different controls — code-signing enforcement in one case, the privilege model in the other.

Why rooting matters defensively

A rooted device has no meaningful sandbox left. Every app on it can potentially reach every other app's data, and the permission model becomes advisory. This is why the deck's user guidance is unambiguous: do not root or jailbreak unless it is absolutely necessary, and why enterprise deployments care about device integrity at all.

Why rooting matters offensively

Privilege escalation turns a foothold into ownership: an app's worth of access becomes the ability to read everything, persist across reboots and defeat the platform's own verification. The chain below is the conceptual shape of every such path — note that it starts with a reachable component, not with a bug in the kernel.

Which statement correctly separates jailbreaking iOS from rooting Android?
Jailbreaking removes iOS's signature check so unsigned apps can run, with no change to the OS; rooting Android obtains superuser access and can go as far as replacing the OS with a custom ROM
Both are needed only to install apps from outside the official store
Jailbreaking rewrites the iOS kernel, while rooting only installs extra apps

Defences: Raising the Cost of Reverse Engineering

If repackaging is cheap, the developer's options are to make the artefact harder to understand and to make the user harder to convince. The deck gives both halves.

ProGuard — comes with Android Studio

Obfuscation. Class, method and field names are renamed and unused code is stripped, so a disassembled listing no longer reads like the original source. It raises the cost of understanding what the bytecode does.

Other methods & tools: DexGuard, DashO

Encryption on top of obfuscation. The lecture names the trade-off explicitly: would Google prefer all of its developers to use code obfuscation and encryption? Harder artefacts are also harder to debug, profile and support.

The general principle

Anti-reverse-engineering controls do not make an app unreadable; they make reading it expensive. That is a valid security goal as long as you are honest about it: the control buys time and deters casual repackaging, while a determined analyst with enough budget is not stopped. Layering it with signature verification and integrity checks is what makes it hold.

Protecting mobile devices: do and do not

Do

  • Install apps only from official or otherwise trusted sources
  • Read the permissions when installing and granting them — ask whether this app really needs this permission
  • Run mobile antivirus software (recommended)
  • Always update the operating system
  • For enterprises: use MDM software and VPNs

Do not

  • Install apps from unofficial app sources
  • Root or jailbreak unless it is absolutely necessary
  • Be careless with suspicious SMS/MMS containing links or attachments
A colleague argues that adding ProGuard obfuscation makes an app safe from repackaging. What is the correct correction?
Obfuscation raises the cost of understanding the code but does not stop repackaging — the package can still be rebuilt and signed with a different key
ProGuard encrypts the DEX, so no disassembler can read the bytecode at all
ProGuard is unavailable to most developers, so the argument is moot in practice

Week 8 Recap

Isolation is a Linux UID

The sandbox is the user-based protection model: one app, one UID, one data directory, one process. Apps cannot talk to each other and have limited OS access.

Core mechanism

Permissions are the declared exceptions

Declared in the manifest, granted at install or at runtime, and mapped onto kernel identities for low-level capabilities. Audit them against the app's stated purpose.

Sharing model

An APK is a signed ZIP

Manifest, DEX bytecode, resources and a signature block. Unzip gives binaries; apktool gives readable smali and decoded resources that can be rebuilt and re-signed.

Artefact

Signature verifies the packager, not the behaviour

Janus showed what happens when verification can be added around. Certificate identity is how you attribute a package to a developer — and how you notice that you cannot.
