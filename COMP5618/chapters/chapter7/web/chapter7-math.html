COMP5618 — Week 8 supplement

Foundations: the Android security model, stated precisely

Week 8 is a systems week, not a mathematics week, so this page does the equivalent job. It fixes the definitions the lecture relies on, reads the architecture diagram as a sequence of trust boundaries, states the sandbox and permission model as relationships you can reason with, writes down what a package signature actually guarantees, and ends with the checklist that turns “I looked at the APK” into a defensible finding.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Android sandbox

A user-based protection model in Linux: each application is assigned its own user identity, so the kernel confines it to its own files and process. Apps therefore cannot talk to each other and have only limited access to the operating system.

Permission

The declared and granted capability by which an app steps outside its sandbox. In the lecture's phrasing: apps must share resources and actions by declaring permissions. A permission is simultaneously a manifest declaration, a grant decision, and — for low-level capabilities — a mapping onto a kernel identity.

APK (Android Application Package)

The build output of an Android application: a ZIP-format package containing the manifest, DEX bytecode, the resource table and resources, and a signature block. Unzipped it is mostly binary and unreadable; apktool disassembles it into readable smali and decoded resources and can reassemble it.

Static analysis

Inspecting the code of a program to understand its purpose without executing it. The Week 8 tutorial applies it to Android apps and notes that the same techniques are applied to malware analysis.

Rooting vs jailbreaking

Jailbreaking iOS removes the check that refuses to execute apps not signed with Apple's key; the deck is explicit that no changes are made to the iOS operating system. Rooting Android obtains superuser access; because Android is open source and already allows installing apps from outside the official store, rooting's distinctive consequence is that it lets you replace the OS with custom ROMs.

The architecture diagram as trust boundaries

The lecture's Android architecture slide is usually read as plumbing. Read as a security document it is a list of levels, each of which enforces a different kind of control and each of which has been defeated at least once.

The structural claim worth memorising: every layer above the kernel is a convenience and policy layer; the kernel is the enforcement layer. That is why the escalation chain on this page always ends at kernel privilege — until then, an attacker has merely borrowed someone else's policy.

The sandbox and permissions as a containment invariant

Four relationships are worth being able to write from memory: what confines an app, what a capability is, how a request is gated, and what the whole model guarantees.

1. The sandbox is a UID predicate, not a feature

Isolation is exactly the statement that one app's identity does not satisfy another app's ownership check:

\[ \forall A \neq B,\; \forall r : \mathrm{own}(r) = \mathrm{uid}(B) \;\Longrightarrow\; \lnot\,\mathrm{allow}\big(\mathrm{uid}(A), r\big) \]

Practical consequence: the sandbox is only as strong as the kernel's decision. It says nothing about behaviour within your own identity, which is why a malicious app with legitimate permissions is inside the rules rather than outside them.

2. Capability is an intersection, not a declaration

An app can do what it declared and was granted — nothing more:

\[ \mathrm{cap}(A) \;=\; M_A \;\cap\; G_A \]

Two immediate corollaries. A permission that was declared but denied contributes nothing, so a runtime denial is a real reduction in reach. And a permission that is granted but unnecessary is pure attack surface: the intersection is only as small as the grant you agreed to.

3. Every IPC request is a conjunction of checks

A component \(c\) owned by \(B\) accepts a request from \(A\) only if the component is reachable and the caller satisfies the guard:

\[ \mathrm{accept}(A \to c) \;=\; \mathrm{exp}(c) \;\wedge\; \big(\mathrm{guard}(c) = \bot \;\vee\; \mathrm{guard}(c) \in \mathrm{cap}(A)\big) \]

Read the second clause carefully, because it is where reviews go wrong. An exported component with no guard accepts every app on the device. Exported with a guard is a contract; exported without one is a public API nobody designed.

4. What the model guarantees, and what it does not

Sandboxing bounds reach; it does not bound behaviour. Formally, the model constrains which \(r\) an app may touch, but places no constraint on what the app does with the resources it legitimately holds. The lecture's three claims — user-based protection, no app-to-app access, sharing by declared permissions — are all reach claims. Keep that distinction and the exam answers write themselves.

An app declares READ_CONTACTS and CAMERA, and the user grants only CAMERA at the runtime prompt. What is \(\mathrm{cap}(A)\) with respect to these two?
The app can use the camera; contact access is not in its capability set because the declaration alone grants nothing
The app can use both, because both were declared in the manifest
The app can use neither, because a denial invalidates the whole permission set

Signature, integrity and what Janus broke

The lecture's Janus slide makes one claim: signature verification matters. This section writes down what a package signature actually computes, so the claim has a mechanism behind it.

1. What signing computes

A signer hashes the package's content and signs the digest with a private key; a verifier recomputes the digest from the artefact it holds and checks the signature against the public key in the certificate:

\[ \sigma \;=\; \mathrm{Sign}_{K_{\text{priv}}}\big(H(\text{content})\big), \qquad \text{accept} \iff \mathrm{Verify}_{K_{\text{pub}}}\big(\sigma,\, H(\text{content})\big) \]

Two things follow. Verification detects a change in the hashed content. And verification tells you who packaged the artefact — it says nothing at all about whether the code is safe.

2. Entry-wise verification leaves room to append

A scheme that verifies the digests of the archive's entries constrains each entry while leaving the surrounding archive unconstrained. If the verifier never binds the set of entries, content can be added:

\[ \text{Verify}\big(\sigma, H(\text{entries})\big) = \top \;\;\not\Rightarrow\;\; \text{artefact} = \text{signed artefact} \]

This is the structure of Janus (2017): APK/DEX bytes added to the package without changing its signature, so the app could be updated without the developer's knowledge. The lesson is not “hashing is broken” but “verify the whole artefact, not the parts you happened to enumerate”.

Why the certificate answers the tutorial's question

The certificate carries the signer's identity, validity period and key details. Two packages from the same developer carry matching signer identity because the same private key signed both. That is evidence, and it is checkable — unlike icons, names or vendor prefixes, which a repackager can copy.

Why a different signer is the finding

If a package claiming to update another was signed by a different key, then whoever built it did not hold the original signing key. The signature has done its job: it has not stopped the rebuild, but it has made the substitution visible to anyone who checks.

An APK passes signature verification. What has been established?
The app is safe to install, because a valid signature means the code was reviewed
That the artefact matches what was signed by the holder of the signing key — nothing about what the code does, and nothing about integrity if the scheme only checks entries
That the code has been obfuscated, which is why the signature is required

The escalation chain

Rooting is the endpoint of a path, not a single event. Writing the path as a chain of prerequisites makes it clear which control removes which step.

1. Escalation is reachability plus transferred trust

An unprivileged app \(A\) gains privilege \(P\) if there is a component that \(A\) can reach, that runs with privilege at least \(P\), and that acts on what \(A\) supplies:

\[ \exists\, c : \mathrm{accept}(A \to c) \;\wedge\; \mathrm{priv}(c) \succeq P \;\wedge\; c \text{ acts on } A\text{'s input} \;\Longrightarrow\; A \rightsquigarrow P \]

Note what is absent: no kernel bug is required. The cheapest escalations are components that were trusted more than the callers they accept — which is exactly the Certifi-Gate shape.

2. Kernel privilege is the terminal state

Once the path reaches kernel-level privilege, every userspace control above it becomes advisory, because those controls are themselves userspace policy evaluated by code that now runs at the attacker's privilege:

\[ \mathrm{priv}(A) = \text{root} \;\Longrightarrow\; \forall\, \text{control } C \text{ above the kernel},\; C \text{ no longer constrains } A \]

This is why rooting is described as removing the model rather than defeating one control: the sandbox, the permission gate and the signature check all sit above the kernel.

3. Each control removes one conjunct

Read the chain as a conjunction and the defences map onto it one for one:

\[ \underbrace{\text{reachable}}_{\text{unexport / guard}} \;\wedge\; \underbrace{\text{privileged component}}_{\text{least privilege, review pre-installed apps}} \;\wedge\; \underbrace{\text{acts on input}}_{\text{validate, authenticate the caller}} \;\wedge\; \underbrace{\text{carries the data out}}_{\text{egress control, no unnecessary permissions}} \]

A chain is only as strong as its weakest conjunct, and removing any one of the four breaks the path. That is the concrete meaning of the deck's instruction to design defence in depth.

Cost, not impossibility. Anti-reverse-engineering controls (ProGuard, DexGuard, DashO) follow the same logic. They do not make an app unreadable; they make reading it expensive enough that casual repackaging stops being worth it. State that trade-off explicitly — the lecture does, and it is the honest answer.

Attack-surface checklist for APK review

Run any sample through these steps in order. Each one maps to something the Week 8 lecture or tutorial actually asks you to do.

A package declares no dangerous permissions, but exports a receiver with no permission guard that writes caller-supplied values into its own database. Which conclusion is best supported?
The package has a real finding: an exported, unguarded receiver is reachable by any app, and it lets a caller write into this app's private storage without needing any permission
There is no finding, because the app declares no dangerous permissions and therefore cannot reach sensitive data
The finding is that the app is malware, because exported receivers are always a sign of malicious intent

Worked example — writing up one APK review as a finding. Sample: a decompiled app whose manifest declares INTERNET, CAMERA, READ_CONTACTS and ACCESS_FINE_LOCATION, exports one activity and one receiver, and whose certificate owner differs from the vendor's published signer.

1

State the artefact. “Sample app-x.apk, acquired by pulling from the test device with the ADB shell, SHA-256 recorded at acquisition, decompiled with apktool.” Every later claim is about these bytes and these bytes only.

2

Separate justified from unjustified capability. Camera and network follow from the stated purpose. Contacts and precise location do not — and in terms of the model, they are two permission sets inside \(M_A\) whose value to the app is unexplained.

3

Establish reach. The exported receiver with no guard satisfies \(\mathrm{accept}(A \to c)\) for any app on the device. It is not a hypothetical entry point; it is one the platform will deliver to on request.

4

Trace the consequence. Follow the receiver's smali to whatever it does with the caller's extras. If it writes them to the app's own storage or forwards them to a privileged operation, the reach converts into capability the caller never had.

5

Report the signer discrepancy as its own item. A certificate that does not match the vendor's published signer means this build was not produced by the party the user believes produced it. That is a separate finding from the exported receiver, and it is the first thing to check when a package claims to be an update.

6

Write the finding in the three-part form. “Reach: any installed app can deliver an intent to the exported, unguarded receiver. Consequence: caller-supplied values reach the app's private write path, so data inside the sandbox can be modified without holding any permission. Control that removes it: mark the receiver unexported, or give it a signature-level permission guard.”

The lab, modelled

The Week 8 tutorial is a static-analysis lab with three deliverables. Treat each as a claim you must be able to evidence, not a command you must run.

Setup is part of the task

apktool installed, JDK and Android SDK available, and an Android Virtual Device created. A second device image is what makes an install-and-verify step possible at all.

Certificates are evidence

Decompile the samples, read each certificate with the certificate tooling, and decide which apps share a developer — then justify it from certificate identity, not from appearances.

Change the behaviour, prove the change

Swap the resource mapping, rebuild with apktool, sign with a key you created with keytool, install with adb, and demonstrate the app behaving differently on the emulator.

Then change the logic

The final task edits smali rather than resources. The resource edit proves the toolchain; the smali edit proves you can read the bytecode.

Worked answer — why a rebuilt package will not install, and what that proves. After apktool b you have a structurally valid APK that the device refuses. Explain the refusal.

1

Name the check that failed. Installation verifies the signature over the package. Rebuilding changed the content while the old signature block no longer matches it, so verification fails and the install is refused.

2

Say what this demonstrates. It demonstrates that signature verification is a real gate on the path from a modified artefact to an installed app. Repackaging is easy; getting the result installed is the part the platform actually defends.

3

Explain the remedy and why it is not a loophole. Creating your own key with keytool and signing with jarsigner produces a valid package — under your signer identity. The app now installs; what it no longer has is the original developer's certificate, which is precisely the evidence a user or a store would use to detect the substitution.

4

Connect it to the week's lesson. These are the same steps as the tutorial: rebuild, re-sign, install, observe. Against a sample you were given they are analysis. Against an application you do not own they are repackaging — advertisement hijacking, malware redistribution, credential harvesting — and the only thing standing between the two is authorisation.

Worked answer — “Compare jailbreaking iOS with rooting Android.” A short comparison question that is easy to answer superficially and easy to answer well.

1

Name the control each one defeats. Jailbreaking defeats code-signing enforcement: Apple signs the source code of App Store apps, iOS holds Apple's public key and verifies signatures, unsigned apps cannot execute, and jailbreaking removes that check. Rooting defeats the privilege model: it obtains superuser access.

2

State the structural difference. On iOS the deck is explicit that no changes are made to the operating system — the check is what moves. On Android, obtaining superuser access is what then permits replacing the operating system with a custom ROM.

3

Dispose of the usual red herring. The motivation people cite for jailbreaking — installing apps from outside the store — does not transfer to Android, because Android is open source and already allows installation from outside the official store. So on Android the distinctive consequence of rooting really is privilege, not sideloading.

4

Close on the security consequence. Both end states remove the platform's ability to constrain what runs. On a rooted device the sandbox, the permission gate and the signature check all sit above the kernel, so all three become advisory — which is why the deck's user guidance is not to root or jailbreak unless it is absolutely necessary.
