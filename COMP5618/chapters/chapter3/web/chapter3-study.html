Networks Aren't Flat: Routes Between Subnets

Week 2 ended at the data-link layer, where everything in one broadcast domain can hear everything else. Week 3 starts where that stops being true: the moment a router sits between two subnets, reachability becomes a policy decision.

The deck's opening claim: not all subnets are equal — a router's rules decide who can talk to whom, and in which direction. Reachability is not symmetric, and the asymmetry is deliberate.

Definition

Firewalking is the technique used to discover how routes and Access Control Lists (ACLs) are configured on the routers between you and a target. It matters because the same host can be reachable from one subnet and invisible from another.

Route in the deckWhat is permittedWhat is deliberately not permitted
Admin → everywhereThe admin subnet may initiate connections to any other subnetThat does not automatically mean responses can traverse back — the reverse direction is its own rule
Finance → PrinterFinance may open new connections to the printer networkNothing: replies from printer back to finance are allowed, but only as replies, never as new connections
Printer → anythingNothing — connections cannot originate in the printer network at allThis prevents a rogue or compromised printer from initiating connections and scanning hosts in the finance network
Read the direction, not the diagram. “Finance can reach the printer” and “the printer can reach finance” are two different rules. A stateful firewall can grant the first and still refuse the second, because the reply is matched against the connection it belongs to rather than treated as a new flow.
A router permits the finance subnet to reach the printer subnet and permits printer → finance traffic only as replies. What does this configuration achieve?
The printer network is completely isolated from finance
A compromised printer cannot originate connections into finance, so it cannot scan those hosts
It prevents attackers from using firewalking against the router

IP Addressing, TCP and UDP

Traversal happens inside packets. Before the offensive technique makes sense, be precise about what a TCP connection is, because almost every scan result is an inference drawn from how a handshake ended.

Definition

An IPv4 address is split into a network part and a host part by its prefix length (for example 10.0.3.5/24). Hosts inside one prefix reach each other at layer 2; hosts in different prefixes need a router, and the router's rules — not the address — decide whether the traffic is allowed through.

PropertyTCPUDP
ConnectionConnection-oriented: state is established by a handshake and torn down explicitlyConnectionless: each datagram stands alone
Header20 bytes minimum, plus options (MSS, window scaling, SACK)8 bytes: ports, length, checksum
ReliabilitySequence numbers, cumulative acknowledgements, retransmission, flow and congestion controlNone: loss is silent unless the application adds its own logic
Scan evidenceA reply proves a listener; a RST proves the host is up and the port is closed; silence means filteredNo reply is ambiguous — open and filtered look identical from outside
Typical use hereSSH, HTTP, MySQL, and therefore every tunnel in this week's materialDNS, DHCP, SNMP, streaming — and the UDP forwarding that SOCKS5 can carry
Why the handshake is an offensive topic. Every frame above produces a different observable. SYN, ACK means open; RST means closed but alive; nothing at all means something in the path dropped it. A port scan is not magic — it is a table of inferences from those three outcomes.
A scanner sends a SYN to a host and receives nothing back, even after the timeout. Which conclusion is defensible?
The port is closed, because no service replied
The port is open but the service is slow to respond
The port is filtered or open — a drop is indistinguishable from a listener that never answers

Port Scanning and What a Firewall Reveals

The deck puts a full-range scan (nmap -p1-65535) at the top of active information gathering: it should be detected by the target, and it is suspicious by definition. Scanning is therefore a trade between how much you learn and how loudly you learn it.

TechniqueWhat is sentWhat comes backNoise and privilege
TCP connectA full handshake per portReal connection, so the service logs an ordinary clientNo special privilege; slowest; the application sees you
TCP SYN (“half-open”)SYN only; the handshake is never completedSYN, ACK = open; RST = closed; silence = filteredNeeds raw sockets; the application is never notified, but the stack and any IDS still see it
UDPA datagram per port, sometimes service-specificICMP port-unreachable = closed; anything else, or nothing, is inconclusiveSlow and unreliable; useful for DNS, DHCP and SNMP
FIN / NULL / XmasFlag combinations a normal stack would never open withRST = closed (RFC-compliant stacks); silence = open or filteredHistorical bypass of simple stateless filters; modern stacks and firewalls see through it

What the scanner can report

  • open — a listener answered
  • closed — the host answered, the port did not
  • filtered — a rule dropped the probe
  • unfiltered — reachable, but open/closed was not determined
  • open|filtered — honest ambiguity, mostly on UDP and silent drops

What the defender sees

  • Many SYNs to sequential ports from one source, in a very short window
  • SYNs that are never completed — connections with no follow-up data
  • IDS alerts on the interface inside the segment, which is exactly what Snort is installed to do in Tutorial 3
  • Egress from a host that has no business talking to that segment at all

Worked example — planning a scan in the Tutorial 3 topology. Kali sits in the developer network (192.168.56.0/24) and DVWA sits in the server network behind pfSense. Work out what to scan, in what order, and what the lab will show you.

1

Fix the map before the scan. pfSense is the DHCP server for the server network with a pool such as .100–.200, and the tutorial's screenshot shows DVWA receiving 10.0.3.5. So the target range is the server prefix, and your own host is in 192.168.56.0/24. Because the two prefixes differ, every packet to DVWA goes through the router — which is the whole point of the exercise.

2

Host discovery first, ports second. Find which addresses answer before spending time on 65,535 ports each. This is also where the tutorial's Snort rule is instructive: the custom rule alert ip any any -> any any with the message “ICMP packet detected!” exists precisely to make a ping visible in the Alerts page.

3

Then the full-range scan. The deck's example of active information gathering is nmap -p1-65535: all ports on the discovered host, which is slow but leaves nothing to inference. A targeted scan of the handful of ports DVWA actually needs would be quieter — and would tell you less.

4

Read the result as a firewall map. If a port answers with SYN, ACK, the rule set passed you and something is listening. If it answers with RST, the ACL passed you and the host refused. If nothing comes back, you have learned that a rule dropped you — which is information about the router, not about the host.

5

Confirm from the other side. The tutorial has you run tcpdump on DVWA and watch the Snort Alerts page at the same time. That comparison is the lesson: the same packets are “just traffic” on the wire and an alert in the IDS, and blocking ICMP in the firewall rule set makes both views go quiet at once.

You scan a host behind a firewall and every port reports filtered. What have you actually established?
That the host is running no services on those ports
That a filtering device is dropping your probes, so you have mapped policy rather than services
That the scan was too fast for the host to keep up with

NAT, VPN and Where a Tunnel Terminates

The tutorial builds exactly this situation: two VirtualBox NAT networks with DHCP switched off, pfSense providing addresses, and the host needing an explicit route before it can reach the server subnet. NAT and tunnels are the two mechanisms that make that layout work.

Definitions

NAT rewrites the source address and port of outbound packets to a shared public address and keeps a translation entry so replies can be mapped back. Outbound traffic creates the state; inbound traffic has no entry to match, which is why an unsolicited connection from outside simply fails.

A VPN securely tunnels network traffic across another network. The deck's framing: it lets you “plug into” a remote network as if you were physically plugged in, and you end up with an additional virtual interface that is a direct tunnel to the far side.

InterfaceLayerUnit carriedConsequence in practice
TUNLayer 3 network tunnelPacketsThe deck's recommendation: almost all protocols already run on top of IP, so a TUN interface is enough for nearly everything.
TAPLayer 2 network tapFramesBehaves like plugging into a local switch: you join the remote broadcast domain, receive ARP requests and other chatter, and burn bandwidth on traffic you did not ask for.
NAT is not a security control. It blocks unsolicited inbound connections as a side effect of having no translation entry, but it does nothing about outbound traffic — which is exactly why a tunnel that starts outbound (SSH, SOCKS, a VPN client) crosses it without difficulty.
Why does the Week 3 deck recommend a TUN interface over TAP for most tunnelling work?
TUN carries more protocol detail than TAP, so fewer things break
TUN carries packets at layer 3, which is enough for almost every protocol, while TAP makes you part of the remote broadcast domain and wastes bandwidth
TUN authenticates the tunnel while TAP does not

Proxies and SSH Port Forwarding

The deck's pivoting premise: the first computer compromised is usually a workstation, not the domain controller, and it is often segregated from the valuable machines. To move anyway, attackers pivot — and SSH, proxies and VPNs are the standard ways to do it.

Definitions

A proxy server acts as an intermediary for requests. Proxies are usually considered to live at layer 5 of the OSI model, the session layer, though the deck notes this is not always the case. A web proxy (for example Squid on Linux) handles HTTP(S) and can add authentication and caching; the university's network is the deck's example, where firewall rules block outbound port 80 unless the traffic goes via the proxy.

A SOCKS proxy is different: it provides a generic intermediary for any TCP connection, and SOCKS5 can also add authentication and forward UDP. Install one on a compromised host and your traffic leaves as if it originated there.

ForwardWho connects to whomThe deck's example
Local (-L)
“bring a remote service to me”		A TCP port on your localhost is forwarded through the SSH server to a remote TCP service.ssh -L 33306:mysql-server:3306 dev@web-server — the developer network can SSH to the web server on 22 but cannot reach the MySQL host on 3306, so 33306 locally becomes the MySQL port.
Reverse (-R)
“send the remote server to my service”		A TCP port on the remote SSH server allows a connection back to a local TCP service.ssh -R 22222:web-server:22 dev@home — no port has to be opened on the company's public address, because the connection is started outbound from inside.
 
# local forward: a port on MY machine reaches a service the SSH server can see
ssh -L 33306:mysql-server:3306 dev@web-server

# reverse forward: a port on the REMOTE machine reaches a service I can see
ssh -R 22222:web-server:22 dev@home

# the same idea, one hop further: reach a bastion, then tunnel again from there
ssh -J dev@web-server dev@mysql-server   # ProxyJump (administrative use, in scope only)

Why SSH forwards are so common

The deck is explicit: due to its simplicity and ease of set-up, SSH port forwarding is very handy and used frequently. It needs only one permitted outbound port — the 22 the ACL already allows — and it multiplexes arbitrary TCP traffic inside a session that looks entirely ordinary.

What defenders can still see

The inner protocol is opaque, but the session is not: one long-lived SSH connection to a jump host, followed by traffic volumes and destinations that do not match that host's role, is the pattern worth alerting on. Log the jump host, the account and the duration.

Worked example — reaching a service the ACL will not route. From the developer network you can SSH to web-server (port 22) but a connection to mysql-server:3306 is dropped by the router. Explain the tunnel you would set up, field by field, and what each side observes.

1

Name the permitted hop. The only thing the ACL allows is SSH from the developer network to web-server. That host is the pivot, and the tunnel must fit inside that one permitted flow.

2

Write the forward and read every field. ssh -L 33306:mysql-server:3306 dev@web-server. The first number is the local listening port on your machine; mysql-server:3306 is the destination as resolved and dialled by the SSH server; dev@web-server is the permitted hop that does the dialling.

3

Explain why the ACL never sees MySQL. Your client connects to 127.0.0.1:33306. The MySQL protocol travels inside the encrypted SSH session, so on the wire between the developer network and the server network there is only SSH traffic to port 22 — a flow that was already permitted.

4

State the limits. The forward lives only as long as the SSH session, it reaches only what the SSH server itself can reach, and it needs a valid account on the pivot. Kill the session and the local port closes.

5

Say what the defender would see. One long-lived SSH session from a developer workstation to the web server, and a MySQL connection to the database whose source address is the web server — not the workstation. The log on the database is accurate about the pivot and silent about you.

Scope reminder. Every technique on this page is a legitimate administrative mechanism. In this unit it is exercised only against the VMs you built yourself in the tutorial — tunnelling or scanning a system you do not have written authorisation for is the line the Week 1 material draws, and the Week 3 pre-engagement stage exists to make that authorisation explicit.
You need a service that sits behind a jump host to appear on your own laptop's loopback interface. Which forward, and why?
Local forward: a local port is mapped through the SSH server to the remote service
Reverse forward: a remote port is mapped back to your local service
Web proxy: it caches the responses so the service appears locally

Principles of Secure Network Design

The second half of the deck flips to defence. These six principles are the design answer to everything the first half demonstrated: if traversal is easy, the network was designed to make it easy.

Definitions from the deck

Defense in depth (“the castle approach”) deploys multiple layers of security controls throughout the environment so there is redundancy in case of an incident. It takes the weight off any single control by having multiple independent controls at different layers.

Network segregation splits a network into sub-networks to reduce the attack surface and group systems by security need. Least privilege comes from the military need-to-know idea: an entity should only have the access needed to do its job and nothing beyond, with everything else denied by default.

PrincipleWhat it doesHow it limits traversalWhere you meet it
Defense in depthIndependent controls at different layers, so one failure is not a breachEven a permitted hop does not hand over the whole network; each segment re-checksThe pfSense router plus the Snort rules on the server interface
Network segregationSplits the network by security need — the deck's power-plant example keeps the control system network away from the IT networkA flat network is why pivoting works; segments give the pivot somewhere to stopDeveloper (LAN) and server (OPT1) networks on separate adapters; achieved with firewalls, VLANs or SDN
Least privilegeGrant only what the job needs; deny the rest by defaultA compromised service account cannot reach beyond its own function“A web server must not run as a root user”
Soft targets and choke pointsFind the bottlenecks and single points of failure, then monitor and harden themChoke points are where traffic must pass, so they are where inspection is cheapestA firewall in front of an internet-facing site; a load balancer that reroutes under DDoS
Zero trustStrict identity verification and access control for every person and device, wherever they sit relative to the perimeterRemoves the “inside means trusted” assumption that makes one breach catastrophicIAM and MFA; ACLs and segmentation applied internally as well as at the edge
Continuous monitoringSecurity as an ongoing process: hunt for unauthorised devices, watch for suspicious activity, verify that deployments behave as intendedDetects the pivot that got through the rules — the only control that helps once prevention failsSnort alerts and tcpdump captures during the tutorial; NOC/SOC continuous improvement
A team adds a second firewall, but both firewalls are administered with the same credential and the same rules. Which principle have they actually improved?
Defense in depth, because there are now two layers of control
Neither redundancy nor depth has improved; the duplication added cost without adding an independent control
Zero trust, because traffic now crosses two enforcement points

Penetration Testing: Scope and Stages

The deck's second half is the professional frame around the techniques: penetration testing simulates real attacks to assess the risk associated with potential security breaches. It goes further than a vulnerability assessment, which discovers vulnerabilities that could be used — a pentest also exploits them, where possible, to assess what an attacker might actually gain.

Scope typeWhat the tester doesWhat it tests
ExternalSimulates an attack via the internetThe perimeter: exposed services, filtering and the rules that govern them
InternalActs as an insider, or as an attacker who has already breached the perimeterSegmentation and least privilege — whether one foothold becomes many
Social engineeringClient-side attacks to gain access to the internal networkPeople and process, which no firewall rule can address
Wireless / physicalTests wireless security or physical access controlsThe layer before the network: can someone simply get in?
StageKey outputWhat goes wrong if it is skipped
1. Pre-engagementSigned scope, testing window, contact details, contract and NDAUnlimited liability: the deck's bottom line is that no scanning, exploiting or reporting starts until scope, contract and NDA are signed
2. Information gatheringA map of hosts, services, names and relationshipsFewer attack vectors — the more information gathered here, the more vectors are available later
3. Threat modellingA plan of attack grounded in the business, not in a tool listTime spent on targets that do not matter to the client's actual risk
4. Vulnerability analysisA ranked list of weaknesses with evidenceBlind exploitation: failed exploits can crash services, set off intrusion-detection alerts and ruin the engagement
5. ExploitationProof of access, and evidence of what it was worthFindings that remain theoretical: the client is told a risk exists but never sees its consequence
6. Post-exploitationPrivilege level reached, systems reached, data reachableThe real impact is understated — one workstation looks harmless until you can show what it can reach
7. ReportingSummary, methodology, findings, recommendations, conclusionThe work has no business value: nothing is fixed, and nothing is defensible if the client is later breached
Pre-engagement in the deck's own words. Understand the client (learn why they need the test, what exposures worry them, which fragile devices need care), set the terms (scope, testing window, contact information, payment, contract) and protect both sides (NDA, a “get-out-of-jail-free” card, signed authorisation kept on hand).
During an engagement, a tester finds an unpatched service on a host that was not included in the agreed scope. What is the correct action?
Exploit it quietly to measure impact, then report it as a bonus finding
Record the observation, stop testing that host, and raise it with the client contact before going further
Say nothing, because out-of-scope systems are the client's own responsibility

Information Gathering and Threat Modelling

The deck describes intelligence gathering as reconnaissance against a target to gather as much information as possible for use during the vulnerability assessment and exploitation phases. The trade-off is always the same: more information, more vectors — and more chance of being noticed.

The three levels from the deck

Level 1 is mainly a click-button process: the information can be obtained almost entirely by automated tools. Level 2 adds some manual analysis and a good understanding of the business — physical location, business relationships, org chart. Level 3 adds a great deal of manual analysis plus cultivating relationships on social networks and a deep understanding of business relationships.

ModeDefinitionTypical activityDetectable?
PassiveGathering that is never detected by the target; only archived or stored information is usedReading caches, archives, public registries and published documentsNo — the target never sees a packet
Semi-passiveMethods that look like normal internet traffic and behaviourQuerying only the published name servers, with no in-depth reverse lookups and no brute-force DNS requestsIn principle, but it blends into ordinary traffic
ActiveActivity that should be detected as suspicious or maliciousMapping infrastructure (the deck's example: a full port scan nmap -p1-65535), enumerating and vulnerability-scanning open services, searching for unpublished directories, files and serversYes — by design, this is the noisy phase
Threat modelling is the bridge. Here you think like attackers and develop plans of attack from the information gathered. The deck's example: if the client develops proprietary software, an attacker could devastate the organisation by reaching the internal development systems where the source is written and tested, then selling the trade secrets to a competitor. The route matters less than what sits at the end of it.

What a defender can do about each mode

  • Passive: nothing directly — assume it happened and reduce what is published
  • Semi-passive: keep records accurate and minimal; split authoritative DNS from internal naming
  • Active: this is where IDS rules, alerting and continuous monitoring earn their place

What the tester owes the client

  • Stay inside the agreed scope and testing window
  • Keep a record of when the noisy phases ran, so alerts can be correlated afterwards
  • Report what was learned passively as well — it is often the finding the client can act on cheapest

From Vulnerability Analysis to the Report

The last four stages are where the engagement becomes evidence. Vulnerability analysis decides how successful an exploit strategy might be; exploitation proves it; post-exploitation measures what it was worth; reporting turns the whole thing into something the client can act on.

StageWhat happensThe risk of doing it carelessly
Vulnerability analysisActively discover vulnerabilities to judge how successful the exploit strategies might be. Vulnerability scanners use vulnerability databases and a series of active checks to make a best guess about what is present.Failed exploits can crash services, set off intrusion-detection alerts and otherwise ruin your chances of successful exploitation.
ExploitationUse techniques, tools and exploits — pre-built frameworks, custom-developed code, or manual methods — chosen to suit the specific vulnerability, the target environment and the goals of the test. The aim is unauthorised access: bypassing authentication, executing code remotely, or leveraging a weakness to take control.Loud, unstable, and destructive if the wrong technique is used on a fragile service. This is why scope and the pre-agreed fragile-device list exist.
Post-exploitationFurther exploration, activity and analysis inside the compromised environment: investigate the system, map its architecture, identify additional vulnerabilities, and gather information on the system and its users.Stopping at the first shell overstates safety: the point is what that foothold can reach next.
ReportingThe findings, observations and recommendations are compiled into a comprehensive report that documents the engagement and communicates results to the client or stakeholders: identified vulnerabilities, their potential impact, and recommendations for mitigating the risks.A report without impact and remediation is a list, not an assessment. The deck's structure is Summary, Methodology, Findings, Recommendation, Conclusion.

Post-exploitation, part 1 — explore the system

  • Investigate the system in more depth
  • Map out its architecture
  • Identify additional vulnerabilities
  • Gather information on the system and its users

Post-exploitation, part 2 — escalate and move

  • Escalate privileges for higher-level access
  • Pivot to other systems on the network
  • Compromise additional hosts
  • Expand the scope of control across the environment

Worked example — writing up one foothold as impact. In a lab engagement you obtain a normal user shell on a workstation in the finance subnet of the topology earlier on this page. The workstation can reach the printer network but not the database. Turn that into a post-exploitation plan and a reportable finding. Keep every step inside the authorised scope.

1

Explore before you move. Identify the interfaces, the routes and the reachable prefixes. The interesting output is not the shell prompt — it is the list of networks this host can talk to that your own host cannot.

2

Establish the direction of the rules. The finance workstation may open connections to the printer network, and the printer network cannot originate anything. That single sentence tells you which way traffic can be tunnelled and which way it cannot.

3

Choose the pivot that fits the permitted flow. If SSH outbound is allowed, a local forward reaches a service the pivot can see; if only HTTP is allowed, a generic TCP intermediary on the pivot is the alternative. Choose by what the ACL permits, not by what is most convenient.

4

Escalate only as far as the finding requires. Post-exploitation escalates privileges for higher-level access, but the report needs the minimum proof of impact. Escalating further than necessary increases the risk of crashing a service and adds nothing to the recommendation.

5

Write the finding so it maps to a control. “A workstation in the finance subnet reaches the printer segment, and a local forward through it exposes the printer web interface to the developer network.” The recommendation writes itself: restrict outbound initiation from the finance segment, keep the printer segment non-initiating, and alert on long-lived sessions to management interfaces. Impact, then remediation — in that order.

Everything here is lab-scoped. The techniques on this page are described so you can recognise and defend against them. Nothing in this unit authorises testing a system you do not own or have written permission to test.

Week 3 Recap

Reachability is directional

A router's ACLs decide who may initiate and who may only reply. Firewalking is how you discover those rules; segmentation is how a defender sets them.

Core idea

The handshake is the evidence

SYN, ACK means open; RST means closed but alive; silence means a rule dropped you. Every port state is an inference from those three outcomes.

Scanning

Tunnels follow the permitted flow

VPN (TUN vs TAP), web proxies at the session layer, SOCKS for arbitrary TCP, and SSH -L / -R forwards all fit inside a connection the rules already allow.

Pivoting

Seven stages, one deliverable

Pre-engagement, information gathering, threat modelling, vulnerability analysis, exploitation, post-exploitation, reporting — ending in Summary, Methodology, Findings, Recommendation, Conclusion.
