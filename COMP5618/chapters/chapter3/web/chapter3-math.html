This page fixes all four, then ends with the checklist that diagnoses a broken pfSense lab.

Addressing & subnet arithmetic

A prefix length is the only thing that tells you which addresses are neighbours and which need a router. Get it wrong and every reachability conclusion after it is wrong too.

Definitions that must be exact

An IPv4 address is 32 bits. A prefix length \(p\) (“/24”) takes the leftmost \(p\) bits as the network part and leaves \(32-p\) bits as the host part. The all-zero host part is the network address and the all-ones host part is the broadcast address; neither can be assigned to a host.

Hosts in the same prefix reach each other at layer 2 (which is Week 2's territory: ARP and Ethernet). Hosts in different prefixes must send to a router, and the router's ACLs — not the address — decide whether that traffic is allowed.

1. How many hosts fit in a prefix

With prefix length \(p\), the prefix contains

\[ N_{\text{addresses}} \;=\; 2^{\,32-p}, \qquad N_{\text{usable}} \;=\; 2^{\,32-p} - 2 \]

The subtraction removes the network address and the broadcast address. The wider the prefix (the smaller \(32-p\)), the fewer hosts — a /30 is two hosts on a point-to-point link, a /24 is 254 hosts on a LAN.

Prefix and mask. \(p = 24\), so the host part is \(32 - 24 = 8\) bits and the mask is 255.255.255.0. The network part is the first three octets: 10.0.3.

2

Network address. Zero the host bits: \(10.0.3.5 \wedge \text{mask} = 10.0.3.0\). That is the address that identifies the segment.

3

Broadcast address. Set every host bit: \(10.0.3.5 \vee \lnot\text{mask} = 10.0.3.255\). Everything sent there is delivered to every host in the segment.

Usable range. \(2^{8} - 2 = 254\) addresses, from 10.0.3.1 to 10.0.3.254. DVWA sits at .5, comfortably below the tutorial's suggested .100–.200 DHCP pool.

5

Why the gateway must not be .1 or .2. The tutorial warns explicitly: do not set pfSense's gateway for either network to *.*.*.1 or *.*.*.2, because in a VirtualBox NAT network those low addresses are used by the hypervisor to forward the host's loopback interface. Point the gateway there and the router's own traffic disappears into the hypervisor instead of reaching the segment.

TCP states & handshake numbers

Every port state a scanner reports is a conclusion about a conversation it can only partly see. These are the numbers and states that conversation is built from.

1. The handshake, written out

With \(x\) the client's initial sequence number and \(y\) the server's:

\[ \underbrace{\text{SYN}(seq=x)}_{\text{client} \to \text{server}} \;\longrightarrow\; \underbrace{\text{SYN,ACK}(seq=y,\; ack=x+1)}_{\text{server} \to \text{client}} \;\longrightarrow\; \underbrace{\text{ACK}(seq=x+1,\; ack=y+1)}_{\text{client} \to \text{server}} \]

The acknowledgements are \(x+1\) and \(y+1\) rather than \(x\) and \(y\) because a SYN consumes one sequence number even though it carries no data.

2. What an acknowledgement counts

Every later segment acknowledges the peer's next expected byte:

\[ ack \;=\; seq_{\text{peer}} \;+\; len(\text{data}) \;+\; \bigl[\, \text{SYN or FIN present} \,\bigr] \]

Practical reading: if a segment carries \(n\) bytes starting at \(seq = x+1\), the reply acknowledges \(x+1+n\). A FIN, like a SYN, advances the counter by one even when no data is carried — which is why teardown sequence numbers look off by one until you remember the rule.

3. Why the handshake sets the cost of a scan

A full connect scan completes the handshake on every port; a SYN scan sends one segment and abandons the conversation. With \(n\) ports probed and round-trip time \(\mathrm{RTT}\):

\[ T_{\text{connect}} \;\approx\; n \cdot 2\,\mathrm{RTT}, \qquad T_{\text{SYN}} \;\approx\; n \cdot \mathrm{RTT} \]

Segment count per port follows the same reasoning. An open port costs three segments on a connect scan (SYN, SYN-ACK, ACK) and two on a SYN scan (SYN, SYN-ACK, RST); a closed port costs two either way (SYN, RST). The formula is a lower bound: it ignores retransmission, and it says nothing about ports that never answer at all.

1

Worked example. Probe \(n = 1000\) ports on one host with \(\mathrm{RTT} = 10\ \text{ms}\). Connect scan: \(T \approx 1000 \times 2 \times 10\ \text{ms} = 20\ \text{s}\). SYN scan: \(T \approx 1000 \times 10\ \text{ms} = 10\ \text{s}\).

2

Scale it to a segment. A /24 has 254 usable addresses. The same 1000-port probe across all of them is \(254 \times 1000 = 254{,}000\) ports: about 84 minutes with a SYN scan at that RTT, and about 2.8 hours with a connect scan — before any filtering timeouts.

3

Add the filtered case. A dropped probe produces no reply, so the scanner waits for a timeout \(t_{\text{out}}\) instead of one RTT. If every port is filtered, \(T \approx n \cdot t_{\text{out}}\) — the arithmetic reason a full-range scan against a well-filtered host is measured in hours, and the reason “filtered” is a finding about the firewall rather than the host.

4

State the assumption. Both approximations assume one probe in flight at a time. Real scanners pipeline or parallelise, which is why they finish sooner — and why they generate the burst of SYNs that any IDS is looking for.

ACL, NAT & tunnel notation

The direction rules on the study page are written in prose in the deck. Here is the same content as something you can evaluate packet by packet.

Notation used on this page

The lecture is written in prose and shows commands, not algebra. The symbols below are a revision aid introduced here so the rules can be reasoned about compactly; they are not lecture notation and should not be quoted as such.

1. An ACL is an ordered list with a first match and an implicit deny

Let the rule list be \(r_1, r_2, \dots, r_m\), each rule a predicate over the packet's source, destination, protocol and port, paired with an action:

\[ \text{action}(pkt) \;=\; \text{action}\bigl(r_{i}\bigr) \quad\text{where}\quad i \;=\; \min\{\, j \;:\; pkt \models r_j \,\}, \qquad \text{default} = \text{deny} \]

Two consequences follow immediately. First, order is semantic: a broad permit placed above a narrow deny makes the deny unreachable. Second, the implicit deny at the end is what makes “everything else is denied by default” true — the deny rule is usually invisible because it is not written down.

2. Stateless and stateful rules treat replies differently

A stateless list sees each packet alone, so a reply needs its own rule. A stateful device maintains a connection table and admits a reply because it belongs to a flow it already permitted:

\[ \text{admit}(pkt) = \begin{cases} \text{match}(pkt, R) & \text{stateless} \\[2pt] \text{match}(pkt, R) \;\lor\; \text{tracked}(pkt) & \text{stateful} \end{cases} \]

This is exactly the deck's printer case: finance may initiate to the printer, and the printer's replies are admitted as replies — but a new connection originating at the printer matches neither branch and is dropped.

3. NAT is a mapping with a lifetime

For each outbound flow the translator stores

\[ M:\; (ip_{\text{priv}},\, port_{\text{priv}}) \;\longleftrightarrow\; (ip_{\text{pub}},\, port_{\text{pub}}) \]

The entry exists only while the flow is alive; when it expires, replies have nothing to match and are dropped. That is why an unsolicited inbound connection fails by construction rather than by policy, and why reaching an internal service from outside needs a static mapping that does not depend on an outbound flow having created it.

Worked evaluation — four packets against one policy. The router holds these rules in order, and everything else is denied:

1  permit  finance  -> printer     tcp  any
2  permit  printer  -> finance     tcp  established
3  permit  admin    -> any         tcp  any
4  deny    printer  -> any         ip   any        (explicit, for logging)

Evaluate each packet and say which rule decides it.

1

Finance → printer, new connection (SYN, no ACK). Rule 1 matches and the SYN has no ACK flag, so it is a new connection. Verdict: permitted by rule 1.

2

Printer → finance, reply to that connection (ACK set, matches the tracked flow). Rule 2 is written to match replies on an established flow. Verdict: permitted by rule 2 — note that on a stateful device this rule is implicit, and writing it explicitly is how a stateless list is made to behave.

3

Printer → finance, new connection (SYN, no ACK). Rule 2 does not match, because there is no established flow. Rule 3 requires the source to be admin. Rule 4 matches. Verdict: denied by rule 4 — this is the rogue printer case, and it is logged.

4

Finance → admin, any port. Rules 1 and 2 do not match the destination, rule 3 requires the source to be admin. Nothing matches, so the implicit deny applies. Verdict: denied — and this is the one that catches people out: the admin subnet may initiate everywhere, but that does not grant everyone a path into admin.

5

Why order matters, in one line. Swap rules 3 and 4 and the printer's denial disappears, because “admin → any” is unaffected but a hypothetical broad permit above rule 4 would shadow it. First match wins: the rule you meant to apply is not necessarily the rule that applies.

An ACL contains, in this order: (1) deny printer → finance, (2) permit finance → printer established. A reply from printer to finance on an established connection arrives. What happens?
It is denied by rule 1, because deny rules are evaluated first
It is permitted by rule 2, because the reply matches the established-flow rule before rule 1 is reached
It is denied by the implicit deny at the end of the list

Depth & least privilege, written as relationships

The design half of the deck is qualitative, but two of its claims behave like formulas — and writing them down exposes the assumption that usually breaks them.

1. Defense in depth multiplies, and only under independence

If control \(i\) is defeated with probability \(p_i\), and the controls are independent, the probability that all of them are defeated is

\[ P(\text{breach}) \;=\; \prod_{i=1}^{n} p_i, \qquad P(\text{breach}) = p^{\,n} \ \text{ when every } p_i = p \]

With \(p = 0.5\): one control gives \(0.5\), two give \(0.25\), three give \(0.125\), four give \(0.0625\).

Independent controls \(n\)\(p = 0.5\)\(p = 0.2\)Reading

Where the model fails. The product is only valid under independence. Two firewalls administered with one credential, or two layers that both trust the same unverified identity, have \(P(\text{breach}) \approx p\), not \(p^2\). When you argue for depth in an exam answer, name the failure mode each layer catches separately — that is the evidence of independence.

2. Least privilege is a subset relation

Write \(A_{\text{required}}\) for the actions a role actually needs and \(A_{\text{granted}}\) for what it is allowed. Least privilege is the requirement

\[ A_{\text{granted}} \;\subseteq\; A_{\text{required}}, \qquad \text{everything in } \complement A_{\text{granted}} \text{ is denied by default} \]

The deck's example is the concrete form of it: a web server must not run as a root user, so the compromise of that service does not hand over the host. The over-privileged service is the pivot the week keeps coming back to.

3. Zero trust re-evaluates the decision per request

Traditional models treat the perimeter as the trust boundary, so a decision is made once and inherited. Zero trust makes the decision a function of the request itself:

\[ d \;=\; f\bigl(\text{identity},\ \text{device},\ \text{resource},\ \text{context}\bigr) \]

The deck's examples — IAM with MFA, and ACLs with network segmentation — are two ways of feeding those arguments. The defining property is that \(d\) is recomputed for every access, whether the request arrives from inside or outside the perimeter, because “inside” is no longer treated as evidence.

Two independent controls each stop an attack with probability 0.8. Under the product model, what is the breach probability, and what is the assumption?
0.4, because the failure probabilities add
0.04, assuming the two controls fail independently
0.2, because the stronger control dominates the average

Before the lab

Two VirtualBox NAT networks with DHCP disabled; pfSense with WAN bridged, LAN on the developer network and OPT1 renamed to Server; no IPv6; the router's LAN address outside the addresses your host already holds.

Routing and DHCP

DHCP enabled on the interfaces whose pools you defined, with the gateway set to the router's address in that network — never *.*.*.1 or *.*.*.2 in a VirtualBox NAT network.

Detection

Snort installed and running on the server interface with the custom rule enabled, and tcpdump running on the target so the same packets can be seen from both ends.

Engagement

Scope, testing window, contacts, contract and NDA agreed before anything is scanned; fragile devices identified; authorisation kept on hand throughout.

Worked diagnosis — DVWA never receives an address. The tutorial's checkpoint is blunt: if the server host cannot get an IP address in the server network via DHCP, something is wrong. Work through it in the order that eliminates the most possibilities per step.

1

Is it a link problem or a service problem? Check that the DVWA virtual machine's adapter is attached to the server NAT network at all. No interface on the segment means no DHCP conversation is possible, whatever the router is configured to do.

2

Is the interface assigned and enabled? In the pfSense console, OPT1 must be assigned and enabled; in the web interface it must be renamed to Server and set to static IPv4 with an address chosen from the server prefix.

3

Does a rule allow the request? The tutorial's step is to create a firewall rule on the server network that passes traffic from any source to “this firewall”. Without it, the DHCP request reaches the router and is dropped by the implicit deny — a perfect illustration of the first-match/deny-by-default model earlier on this page.

4

Is the DHCP service configured with a sane scope? Range inside the prefix, gateway set to the router's address in that network, and not pointed at the hypervisor's reserved low addresses. A pool that overlaps the router's own address produces the same symptom from the other direction.

5

Can the client reach the router at all? From the developer side, add the route to the server network via pfSense's LAN address, then ping. If the ping works but DHCP does not, the problem is in the service, not the path; if neither works, go back to step 1.

6

Confirm the outcome, not the intention. The final check is the one the tutorial asks you to record: the lease appears on the server host, the address is inside the pool you configured, and a ping from the other network shows up in both the Snort Alerts page and the tcpdump output. When the firewall rule blocking ICMP is enabled, both views go quiet — that is continuous monitoring working as designed.
