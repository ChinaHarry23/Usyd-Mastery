What Linux Is

Week 6 opens at the bottom of the stack. Before you can escalate privileges on a Linux host you need to know what the operating system is made of, because every escalation path in this week runs through one of those components.

Definition

Linux is an open-source operating system based on UNIX, known for its powerful and versatile features. Its core component is the kernel, created by Linus Torvalds and released in 1991. The kernel plus the surrounding userland gives a robust and stable platform for running applications and services.

UNIX-like, not UNIX

Linux is called a UNIX-like operating system because it shares design principles with the original UNIX of the 1970s: a hierarchical file system, multiuser support, and a command-line interface. UNIX is the original; Linux is the modern, actively developed descendant.

The three shared principles

  • Hierarchical file system — files organised in a tree of nested directories.
  • Multiuser support — multiple users access the system concurrently.
  • Command-line interface — a shell for direct, scriptable control of the system.
Why the lecture starts here. Every mechanism later in this week — permissions, setuid, sudoers, cron — is a feature of one of those three principles. The multiuser design is what makes privilege a meaningful concept at all: without separate identities there would be nothing to escalate from.

A distribution is a bundle, not a kernel

A Linux distribution is a collection of software bundled together to form a complete operating system. The lecture's five-part breakdown is worth memorising as a list, because each part is also an attack surface.

ComponentWhat it doesSecurity relevance
KernelSchedules processes, enforces permissions, talks to hardwareKernel bugs let an unprivileged local user reach root (see the CVE section below)
Package managerInstalls, updates and removes softwareThe patch pipeline: what you use to apply the fixes that close escalation bugs
Window managerDraws and controls the graphical desktopExtra daemons and services listening on the host
Text editorEdits configuration files such as /etc/sudoersEditing sudoers by hand instead of with visudo is a classic way to break the host
Web browserClient software most users spend their day inA large, network-facing, frequently patched attack surface

Popular examples named in the lecture: Ubuntu, Debian, Fedora, Arch and Kali. The distributions provide a ready-to-use environment with pre-installed software and utilities — which is exactly why the choice of distribution changes the default attack surface you inherit.

Linux is widely used across servers, embedded systems, mobile devices and desktop computers, and it powers a significant portion of the internet as the operating system behind web servers, cloud infrastructure and networking devices. Its stability, security and flexibility make it a popular choice for both personal and enterprise use — and, for the same reasons, a popular target and a popular attacker platform.

The Filesystem Hierarchy and Permission Bits

Everything in Linux is a path. The directory a file lives in tells you what it is for; the ten characters in front of it tell you who may do what with it.

Reading the ten characters

PositionSymbolMeaning
1- / d / lFile type: regular file, directory, symbolic link
2–4rwxWhat the owner may do: read, write, execute
5–7r-xWhat the group may do. A missing permission is shown as -
8–10r-xWhat everyone else may do
owner's execute slots instead of xSUID: the file runs with the privileges of its owner
group's execute slots instead of xSGID: the file runs with the privileges of its group
others' execute slott instead of xSticky bit: only a file's owner may delete it from the directory
ls -la /bin | grep ping
-rwsr-xr-x 1 root root 44168 May 8 2014 ping

Worked example — reading one ls -l line field by field. Take the lecture's line and decode every column before deciding whether it is a risk.

1

-rwsr-xr-x — the mode. Leading -: a regular file, not a directory. Owner triad rws: root may read, write and execute it, and the s in place of the owner's x means the setuid bit is set. Group triad r-x and other triad r-x: everyone else may read and execute, but not write.

2

1 — the hard link count. One name points at this inode. Low link counts on system binaries are normal; a binary with many hard links in unexpected places deserves a second look.

3

root root — owner and group. This is the decisive column. Because the owner is root and the setuid bit is set, executing the file gives the process root's effective identity. A setuid bit on a binary owned by an unprivileged user changes nothing that matters.

4

44168 May 8 2014 — size and timestamp. The date is a patch-latency signal: a system binary whose timestamp is years behind the rest of the system is either unpatched or replaced. The correct response is to compare it against the package manager's record, not to trust the file.

5

ping — the verdict. A legitimate setuid binary: ping needs to send and receive raw network packets, a privileged operation, so it ships with the SUID bit set. It is not very useful for escalation because it does not let you execute arbitrary commands — which is exactly the distinction the tutorial draws when it says to look for SUID files that can run commands.

A file on a lab host shows -rwsr-xr-x 1 root root. What does the s actually change?
It lets every user write to the file as well as execute it
It makes the program run with the privileges of the file's owner, which here is root
It marks the file as a script rather than a compiled binary

Users, Groups and Program-Specific Accounts

Linux is multiuser by design, and the single most important defensive decision on the host is which account each program runs as.

Definition

A program-specific user is a dedicated account created for one program during its installation or configuration. In Linux systems it is common practice for programs to run under a different user account rather than with root access, because this provides an additional layer of security by limiting the scope of damage in case of a compromise.

Program compromised
→
Confined to user privileges
→
Rest of system protected

The lecture's chain is the whole argument in three boxes: an attacker gains a foothold, their access is limited to that account, and the damage does not spread. Web servers like nginx commonly run as the user www-data, and the MySQL database daemon mysqld runs as the user mysql. Linux systems also often include an account called nobody, designed to run services that require minimal privileges: it has limited access rights and is typically used for services that do not need special permissions.

Security benefits

  • Running programs under dedicated accounts enhances the overall security posture.
  • It follows the principle of least privilege: programs hold only the privileges needed for their intended function.
  • A smaller privilege set means a smaller attack surface and a smaller blast radius.

Operational benefits

  • Easier monitoring and management — administrators can track the activity and resource usage of each program separately.
  • Improved control over file permissions — each program can be given access only to the files and directories it needs.
The Windows contrast from the deck: in Windows, programs typically run with the privileges of the user account executing them. By default users have more elevated privileges and many programs run under that user's account, so a compromise can be far more damaging — the attacker inherits everything the user could do.
Exam framing: the program-specific user is not an administrative convenience, it is a containment mechanism. It converts one catastrophic compromise (root) into one contained compromise (a single service account) — and it is precisely that containment that Week 6 then tries to break with privilege escalation.

Privilege Escalation, Part 1: The Setuid Bit

A foothold is not a compromise. Escalation is the step that turns a confined process into administrative control, and the setuid bit is the first mechanism the lecture gives you.

Definitions

Privilege escalation is the process of gaining higher privileges or access rights than originally granted to a user or a running process. When an attacker gains access to a shell through a running program, the privileges of that shell are limited to the user under which the program is running — so to take the system, they must escalate.

The setuid (SUID) permission on a file allows it to be executed with the privileges of the file owner, rather than the user executing it. It is identified by the letter s in the permission string.

Setuid exists for legitimate reasons. It enables certain applications to be run by all users as privileged users, providing access to restricted operations or resources. The lecture's example is ping, which needs to send and receive network packets — a privileged operation — and therefore ships with the SUID bit set by default.

TechniqueWhat it usesWhy it works
Setuid bitA program that executes with the privileges of its owner, typically a privileged userThe identity change comes from the file, not from a password
Kernel vulnerabilitiesSecurity flaws or weaknesses in the kernel itselfThe kernel enforces privilege, so a bug in it can be turned into privilege
sudoers entriesThe permissions granted to users or groups to run commands with elevated privilegesA permitted command may itself be able to spawn a shell or write a root-owned file
Cron jobsScheduled tasks that run automatically at specified timesA task scheduled under root's crontab executes whatever its script contains — as root
The three ways a setuid program becomes an escalation path: (1) the program can be made to execute arbitrary commands, as with tools that expose an interactive or shell-escape feature; (2) the program has an exploitable memory-safety or input-validation flaw, so controlling its input controls its behaviour; (3) the program loads or runs something the attacker can write to — a script, a library or a configuration file. The lecture's warning is that attackers can exploit vulnerabilities in setuid-enabled programs to execute arbitrary commands with elevated privileges.

Why most kernels ignore SUID on scripts. Setting the setuid bit on a shell script (a file starting with #!) is ignored on most operating systems, because a script interpreter is a general-purpose program: honouring the bit would hand every user a trivially scriptable root shell. The Week 6 tutorial turns this into a design constraint — if the escalation helper must be setuid, it has to be a compiled binary that then invokes the interpreter.

The lecture's seven best practices for setuid usage

Design and code

  1. Limit setuid-enabled programs — the fewer there are, the smaller the surface.
  2. Implement strict input validation and access control.
  3. Follow the principle of least privilege.

Operate and watch

  1. Regularly update and patch setuid-enabled programs.
  2. Conduct periodic security audits and vulnerability assessments.
  3. Monitor system logs.
  4. Perform real-time monitoring.

Tutorial walkthrough — the lab escalation chain, described as a defender would log it. The Week 6 tutorial builds a SUID-to-root path inside your own Ubuntu VM using the DVWA host you configured earlier. The steps below are the reasoning at each stage; no exploit code is reproduced here.

1

The foothold is a service account. The shell obtained through the web application's SQL injection runs as www-data. Running whoami in that shell confirms the ceiling: everything the attacker does now inherits that account's privileges, and reading /etc/shadow or /root is refused.

2

The escalation file must be chosen or created. The first thing needed is a file owned by root with the SUID bit set — ideally one that can be leveraged to execute arbitrary commands, which is why the lecture notes that ping is not very useful here while some versions of nmap, with an interactive mode that allows commands to be executed, could be. In the tutorial you instead create your own helper.

3

Why it must be a compiled binary. Because most operating systems ignore the SUID flag on script files, the helper has to be a small compiled program whose only job is to drop to the file owner's identity and hand control to a shell script. That single design decision — a binary that runs an interpreter — is what converts a writable path into a root shell.

4

The file is placed where the service account can reach it. The helper sits in /tmp, is made executable, is owned by root with the service group as its group, and is given the SUID and SGID bits. Each of those four attributes is individually unremarkable; together they are the vulnerability.

5

The script provides the payload. The helper invokes a second file, also in /tmp, which connects a shell back to a netcat listener already waiting on the attacker-controlled host. Because the helper's effective UID is 0, that shell is a root shell — and the attacker never needed the root password.

6

Verification and consequence. Running whoami in the listening session returns root, and anything placed in the script now runs as root. That is full control of the machine.

7

The defender's reading of the same chain. Five detection opportunities exist and each maps to a control: a SUID binary appearing in a world-writable directory (find / -perm -4000 -type f), a new root-owned executable outside the package manager's records (integrity checking with Tripwire or AIDE), the web server spawning a shell (application logs and process monitoring), an outbound connection from a server that should never dial out (network monitoring with Snort or Suricata), and a setuid binary that has no business existing (the limit setuid-enabled programs practice).

You have a shell as www-data on a lab host. Why does a root-owned setuid binary in /tmp change your situation so dramatically?
Because it lets you read files in /tmp that are otherwise hidden
Because executing it runs the process with root's effective identity instead of www-data's
Because the SUID bit requires the root password to be supplied at run time

Kernel Vulnerabilities as an Escalation Path

The kernel decides who may do what. A bug in that decision is therefore a bug in the privilege model itself — and it needs no misconfiguration to exploit.

The Linux kernel, despite its complexity, has experienced vulnerabilities in the past that allowed regular users to escalate their privileges. When exploited, these vulnerabilities can lead to unauthorised actions and potential compromise of the system's security. It is important to stay informed about privilege-escalation vulnerabilities and mitigation techniques to protect Linux systems.

Resource

CVE Details is a resource that provides information on publicly disclosed vulnerabilities, including those related to Linux kernel privilege escalation. Visiting the CVE Details page gives access to a comprehensive listing of known published vulnerabilities for the Linux kernel, and it serves as a valuable reference for understanding the historical landscape of privilege-escalation vulnerabilities.

FieldValue for the lecture's worked CVE
CVE IDCVE-2016-0728
YearDiscovered in 2016
SubsystemThe keyring facility of the Linux kernel
Root causeThe keyring facility failed to properly validate certain operations
Who can trigger itAn attacker with local access — a regular user on the host
ImpactEscalation from a regular user to root, gaining complete control of the system; potentially unauthorised access, data theft or malicious actions
MitigationPatched in the Linux kernel; users were advised to update to the latest patched version
What makes kernel bugs distinctive. A setuid flaw or a sudoers mistake is a configuration problem that a careful administrator can avoid. A kernel privilege-escalation bug is present on a perfectly configured host running an unpatched kernel, it requires only local access, and it grants root directly. The only controls that apply are keeping the kernel patched, monitoring for new vulnerabilities, and limiting who can get a local shell in the first place.

Triage questions for any claimed kernel escalation

  • Vector: local or remote? The lecture's example is local only.
  • Precondition: does it need a specific kernel version, feature or configuration?
  • Impact: does it reach root, or only leak information?
  • Fix: is there a patched version, and how far behind is this host?

Why the fix is the only real control

Applying security updates and regularly monitoring for new vulnerabilities are essential to protect against privilege-escalation attacks. On a virtual machine you can snapshot between steps — on a production host, the equivalent action is a tested patch window, not an improvised one.

Privilege Escalation, Part 2: The sudoers File

Delegation is necessary and dangerous in the same way setuid is: it hands out pieces of root on purpose, and every piece is a potential escalation path.

Definition

The /etc/sudoers file in Linux contains directives that define how and when users are permitted to run the sudo command. It provides a way to control and restrict user access to specific commands or command categories, and its directives can be used to grant or revoke sudo privileges for individual users or user groups.

User1 ALL=(ALL) /usr/bin/reboot
User2 ALL=(ALL) /usr/bin/apt-get update
FieldMeaningIn the example
User1Who the rule applies to — a user or, better, a groupUser1 is allowed to run the reboot command using sudo
ALL (host)Which hosts the rule applies toAny host reading this file
(ALL)The target identity the command may run asAny user, including root
/usr/bin/rebootThe command, given as an absolute pathOnly reboot — and nothing else, in principle
Why the absolute path is not enough. A delegated command is only as narrow as that command's own capabilities. Some programs can spawn a shell, read or write arbitrary files, or load attacker-controlled configuration; granting any of those through sudoers is equivalent to granting root, even though the directive looks tightly scoped. When you audit a sudoers entry, the question is never “which command?” but “what else can that command be made to do?”

Edit it with visudo, never by hand. It is important to exercise caution when editing the sudoers file to prevent granting excessive privileges. Improper configuration can inadvertently give users more access than intended, potentially compromising system security. The visudo command should be used because it performs syntax checks before saving any changes — a single malformed line can lock every administrator out of the host.

The lecture's five best practices

PracticeWhat it means in practice
Limit sudo access to only necessary commandsGrant users access only to the specific commands they require for their tasks
Regularly review and update the sudoers fileKeep the file up to date by removing unnecessary privileges and modifying access as needed
Use groups to manage privilegesAssign sudo access to user groups instead of individual users for easier management and control
Test configuration changesThoroughly test a new sudoers configuration in a controlled setting before deploying it to production
Implement logging and monitoringEnable logging of sudo activities to track and identify suspicious or unauthorised command executions

Worked example — reviewing a sudoers entry for over-granting. A colleague proposes: deploy ALL=(ALL) /usr/bin/apt-get, so the deployment account can install packages.

1

State the task. The account has to install and upgrade packages from the distribution's repositories. Nothing in the task requires reading arbitrary files or running a shell.

2

Check the command's own power. The lecture's own example scopes the grant to /usr/bin/apt-get update. Granting all of apt-get is broader than it looks: package handling can execute maintainer scripts as root, so a crafted package turns the grant into arbitrary root code execution. Verdict: over-granted.

3

Narrow to the smallest sufficient command. If the requirement is refreshing package metadata, the entry should name apt-get update exactly, matching the pattern of the lecture's User2 line. If full installation is genuinely required, that is a decision to record and review, not to leave implicit.

4

Use a group, not a person. Replace deploy with a group such as %deployers so that the privilege follows the role and leaves with it when someone changes teams.

5

Test, save, log. Rehearse the entry in a throwaway VM, apply it with visudo so the syntax is validated before saving, and make sure sudo activity is logged so that the first use of the new grant leaves a trace.

6

The sentence that earns the mark. “The entry is valid sudoers syntax but grants more than the task requires, because apt-get can execute package scripts as root; least privilege requires naming the narrowest command, delegating to a group, validating with visudo, and logging the result.”

What does the directive User2 ALL=(ALL) /usr/bin/apt-get update actually grant?
Full sudo rights on every command, for User2 only
Only the command /usr/bin/apt-get update, which User2 may run as any user on any host
Nothing, because a password is still required for every sudo command

Cron Jobs and Scheduled Tasks

Automation runs with privileges and without supervision. That combination is why cron is the fourth classic escalation path.

Definition

Cron jobs are scheduled tasks on a Linux system that are executed automatically at specified times or intervals. Administrators commonly use them to run software regularly, such as cleanup or keep-alive scripts. These scripts are often scheduled to run under the root user's crontab, which allows them to have the necessary privileges to perform certain operations.

The legitimate example from the lecture

An administrator sets up a cron job to run a script every night at 2:00 AM that performs system cleanup tasks, such as deleting temporary files and optimising disk space.

0 2 * * * /usr/local/bin/cleanup.sh

Managing the root crontab

The sudo crontab -e command is used to view and edit the list of tasks scheduled to run as the root user. Running it with sudo privileges lets administrators access and modify the root user's crontab, adjusting execution times or updating the commands to be executed.

0 12 * * 0 /usr/local/bin/backup.sh

The lecture's second example: a backup script every Sunday at 12:00 PM.

Why this is worse than a one-off escalation. Modifying scheduled scripts in the root user's crontab can lead to unauthorized access, manipulation of system files, or even complete control over the system — and because the task repeats, the access repeats too. The lecture's example is an attacker who gains persistent control by making a root-owned backup script run their commands.
RiskWhy it existsDefensive response
Script writable by a non-root accountCron executes the file's current contents as rootRoot-owned, mode 0700, in a root-owned directory with no world-writable ancestors
Directory writable, script replaceableWrite access to the directory is enough to swap the fileEnumerate writable directories with find / -writable -type d 2>/dev/null
Script reads attacker-controlled inputCron runs the interpreter, which trusts the input fileValidate input inside the script; never source configuration from a writable path
Task unscheduled under a service accountA compromised service account inherits the schedule's privilegesRun maintenance tasks as the least-privileged account that can do the job
A nightly root cron job executes /opt/backup/run.sh, and the directory /opt/backup is writable by the www-data account. What is the escalation?
A compromised www-data shell can change what executes as root, and the change repeats on every run
The www-data account can read the backup contents
Cron will refuse to run because the directory ownership is inconsistent

Detection: Finding Escalation Vectors and Rootkits

Privilege-escalation attacks can be challenging to detect, so the practical answer is to enumerate the host systematically — and then to look for the software that hides after it succeeds.

The lecture's tool

unix-privesc-check is an automated script that identifies potential issues: it performs various checks on the Linux system and helps system administrators identify and address security weaknesses proactively. In the tutorial it is run as root with the detailed argument and the output is paged and searched for the string WARNING.

sudo ./unix-privesc-check detailed | less
# then search the pager for WARNING with /WARNING
The lecture's cheat sheet

g0tmi1k's blog post “Basic Linux Privilege Escalation” provides a comprehensive cheat sheet for detecting privilege-escalation vulnerabilities. It covers a wide range of areas, and it lets system administrators conduct thorough assessments of their own Linux systems and stay proactive in identifying escalation risks.

What to checkThe lecture's commandWhy it matters
SUID / SGID filesfind / -perm -4000 -type f -exec ls -l {} \;Searches for files with the setuid or setgid permissions, which can potentially lead to privilege escalation if misused
Writable directoriesfind / -writable -type d 2>/dev/nullIdentifies directories with writable permissions, which can be exploited to plant malicious files or gain unauthorised access
World-writable filesfind / -perm -2 -type f -exec ls -l {} \;Finds files with world-writable permissions — a potential security risk if sensitive data or system files are accessible to unauthorised users
Community knowledge is part of the method. The lecture also points at the SANS Institute forum discussion on privilege-escalation flaws in Linux. Sharing information about these flaws, learning from others' experiences, and engaging in discussion within the cybersecurity community improves overall awareness and preparedness against such threats.

Rootkits: escalation that hides

Definition

Rootkits are malicious software that grants unauthorised access to a Linux system while evading detection. They provide attackers with privileged control over the compromised system and remain hidden from traditional security measures. Two examples from the lecture: RootkitX, which uses kernel-level hooks and backdoor access, and the Adore Rootkit, which modifies system binaries and kernel modules, providing remote access and hiding its presence.

Why detection is hard

  • Kernel-level manipulation — the tool that would report the truth is itself compromised
  • Stealth techniques — the rootkit hides its own files and processes
  • Anti-antivirus techniques — it interferes with the tools looking for it
  • Evolving techniques — signatures age out quickly
  • Advanced Persistent Threats — patient adversaries who are not in a hurry

Where you would look on the host

The week's filesystem walkthrough pays off here: /var/log holds syslog and application logs, process state is visible under /proc, and the binaries a rootkit would replace live under /bin, /usr/bin and the kernel module tree. Comparing those against known-good copies is the point of integrity checking.

The pattern to remember. The lecture's detection techniques fall into five families: signature-based (rkhunter, chkrootkit, plus integrity checks with Tripwire or AIDE), behavioural (OSSEC or Samhain, plus analysis of syslog, application logs and network logs), memory forensics (Volatility or LiME), network traffic analysis (Snort or Suricata as NIDS; Bro or Argus for flow analysis), and advanced techniques (XenServer or KVM-based hypervisor detection; live forensics with GRR or the Volatility Framework). If you can name the family as well as the tool, you can answer any question the exam asks about this slide.

Linux Hardening and SSH

Since Linux distributions offer a diverse range of tools and features, there is no one-size-fits-all approach to protecting Linux systems — but a small number of measures raise the security bar considerably.

Week 6 Recap

Linux is a bundle, and every part is surface

UNIX-like by design: hierarchical filesystem, multiuser support, command-line interface. A distribution adds a package manager, window manager, editor and browser on top of the kernel.

Foundations

Identity is the security model

Programs run as dedicated low-privilege accounts — www-data, mysql, nobody — so a compromise is contained instead of total. Least privilege is the through-line of the week.

Containment

Four escape routes from a confined shell

Setuid binaries, kernel vulnerabilities, sudoers entries and cron jobs. Each one is a legitimate mechanism that hands out a piece of root — and therefore a privilege boundary to cross.

Escalation

Detection is enumerate, then compare

find for SUID files, writable directories and world-writable files; unix-privesc-check for a systematic audit; integrity checks, log analysis and memory forensics for the rootkit that hides afterwards.
