Foundations: permissions, identity and the escalation equation

Week 6 is a systems week, so the foundations page does three jobs: it pins down the definitions the lecture relies on, turns the permission string into arithmetic you can compute with, and states privilege escalation as a small state model — a process cannot manufacture privilege for itself, so escalation always means finding a mechanism that hands it an identity. The notation here is a revision aid built from the lecture's examples, not lecture notation.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these in one sentence, with the consequence included.

Linux and the kernel

Linux is an open-source operating system based on UNIX, known for its powerful and versatile features. Its core component, the kernel, was created by Linus Torvalds and released in 1991. It is a UNIX-like system because it shares UNIX's design principles: a hierarchical file system, multiuser support and a command-line interface.

Linux distribution

A collection of software bundled together to form a complete operating system — kernel, package manager, window manager, text editor and web browser — giving users a ready-to-use environment with pre-installed software and utilities.

Program-specific user

A dedicated account under which a single program runs, created during that program's installation or configuration and granted only the privileges it needs. Because the program does not run with root access, a compromise is confined to that account's privileges instead of spreading across the system.

Setuid (SUID) permission

A per-file permission that allows the file to be executed with the privileges of its owner rather than those of the user executing it. It is identified by the letter s in the permission string, in place of the owner's x. SGID does the same for the file's group.

Privilege escalation

The process of gaining higher privileges or access rights than were originally granted to a user or a running process. The four techniques the lecture names are the setuid bit, kernel vulnerabilities, sudoers entries and cron jobs.

Rootkit

Malicious software that grants unauthorised access to a Linux system while evading detection, providing privileged control and remaining hidden from traditional security measures — through kernel-level hooks and backdoor access, or by modifying system binaries and kernel modules.

Permission arithmetic

The lecture's example line is enough to derive the whole notation. Ten characters, three triads, one special letter.

1. One triad is a three-bit number

Each of the three permission triads — owner, group, other — is a three-bit value in the order read, write, execute:

\[ d \;=\; 4\,r \;+\; 2\,w \;+\; x, \qquad r, w, x \in \{0, 1\} \]

So rwx is \(4+2+1=7\), r-x is \(4+0+1=5\), r-- is \(4\), and --- is \(0\). That is why -rwsr-xr-x and 4755 describe the same file.

2. The special bits are the leading octal digit

Writing \(S = 4\,s_u + 2\,s_g + t\) for the setuid, setgid and sticky flags, and \(d_u, d_g, d_o\) for the three triads:

\[ M \;=\; 4096\,S \;+\; 64\,d_u \;+\; 8\,d_g \;+\; d_o \]

Check it on the lecture's ping: setuid only, so \(S = 4\); the triads are \(7, 5, 5\), giving \(4096 \cdot 4 + 64 \cdot 7 + 8 \cdot 5 + 5 = 16877\), which is 040755 in octal — the 4 in 4755 is exactly the setuid flag.

3. The setuid equation: identity changes at exec

A process carries a real and an effective identity. Executing a file leaves the real identity alone and may change the effective one:

\[ \text{euid} \;=\; \begin{cases} \text{owner}(f), & \text{SUID}(f) = 1 \\ \text{ruid}, & \text{otherwise} \end{cases} \qquad\qquad \text{egid} \;=\; \begin{cases} \text{group}(f), & \text{SGID}(f) = 1 \\ \text{rgid}, & \text{otherwise} \end{cases} \]

The kernel then authorises file access against the effective identity and the supplementary groups. Two consequences follow, and both are examinable:

  • Permission is decided by who the process is, never by who launched it or what they typed. There is no password inside exec.
  • If \(\text{euid} = 0\) the identity is root, and root is not subject to the ordinary permission check at all. This is why one wrong s bit outweighs a careful rwxr-x--- everywhere else.

Capital S and capital T are warnings, not equivalents. A lowercase s means setuid and execute; an uppercase S means setuid is set but the execute bit is not, so the flag is currently inert. The same applies to t versus T for the sticky bit. When you audit a host, an uppercase letter is a finding worth explaining: the intent is there but the effect is not.

Worked example — converting between the two notations, and deciding what is dangerous. Six modes appear in the week's material; decode each one and classify it.

1

-rwsr-xr-x → ? Special: the owner's slot holds s, so \(S = 4\). Triads: rwx \(= 7\), r-x \(= 5\), r-x \(= 5\). Mode \(= 4755\). Classification: a setuid binary executable by everyone — safe only if the program cannot be made to run arbitrary commands.

2

4755 → which file? \(4096 \cdot 4 = 16384\), \(64 \cdot 7 = 448\), \(8 \cdot 5 = 40\), \(5\) → \(16877 = \text{0o40755}\), the lecture's ping. Classification: legitimate — raw sockets are privileged, and ping offers no command execution.

3

-rwxrwxrwt on a directory. Special: t in the others' slot, so \(S = 1\). Triads 7-7-7, but the leading d marks a directory. Mode \(= 1777\). Classification: expected for /tmp — everyone may create files, the sticky bit stops them deleting each other's.

4

-rwSr--r--. The capital S is the trap: setuid is set but no execute bit is present on the owner's triad, so the flag has no effect until someone adds x. Mode \(= 4644\). Classification: inert today, a one-character change away from being dangerous. Report it as a latent finding.

5

Why the enumeration commands are written the way they are. find / -perm -4000 -type f uses a dash before the mode, which means “all of these bits are set” rather than “exactly this mode”. That is why it finds 4711 and 6755 as well, and why it is the right command for an audit: you want every file with setuid, whatever else it has. The matching world-writable check, find / -perm -2 -type f, asks for bit 2 — the write bit in the others' triad.

Privilege escalation as a state model

All four of the lecture's techniques are the same idea wearing different clothes. State the invariant first, then the mechanisms become a lookup table instead of a list to memorise.

4. The invariant: a process cannot create privilege

A process inherits its identities from its parent and can only change them through a kernel-mediated mechanism:

\[ \text{priv}(\text{child}) \;\subseteq\; \text{priv}(\text{parent}) \quad\text{unless a mechanism } m \text{ applies} \]

This is why “I have a shell” and “I have the system” are different statements. A shell spawned by a web server carries the web server's identity, and the only way out is to find an \(m\) that supplies another one. Every technique in Week 6 is such an \(m\).

SGID file\(\text{group}(f)\)The group's execute slot holding sSame audit as SUID; group membership is privileges too

5. An escalation path is a chain of identity changes

Write a path as a sequence of identities joined by the mechanism that moves between them. The Week 6 tutorial is one instance:

\[ \text{www-data} \;\xrightarrow{\;\text{SUID binary owned by root}\;}\; \text{root} \]

The same notation handles the other three techniques without modification: alice --[sudoers: apt-get update]--> root, www-data --[writable cron script]--> root, and local user --[CVE-2016-0728 keyring flaw]--> root. When a question asks you to “explain the escalation”, it is asking for the middle arrow: which mechanism, where it is configured, and why it confers the identity.

Why the mechanism matters more than the payload. Once the identity changes, the payload is trivial — anything the script or command contains now runs as root. That is why the lecture's defences are all about the mechanism: fewer setuid binaries, narrower sudoers entries, unwritable scheduled scripts, and a patched kernel.

Worked example — triaging an enumeration report. You run an audit on a lab host and collect five findings. Rank them by how directly each one reaches root, and give the control that closes each.

1

/usr/local/bin/backup-helper is mode 4755, owned by root. \(S = 4\), triads 7-5-5. Direct SUID path: any account that can execute it runs as root. Rank 1. Control: establish whether the helper needs the bit at all; if it does, it must validate its input and must not hand control to an interpreter the caller can influence.

2

/etc/cron.d/cleanup runs /opt/cleanup/nightly.sh as root, and /opt/cleanup is writable by the www-data group. Directory write access is enough to replace the script. Rank 2, because it needs no exploit at all — the schedule supplies the privilege and the persistence. Control: root-owned directory and script (0700), and re-check with find / -writable -type d.

3

Sudoers contains %support ALL=(ALL) /usr/bin/less. A pager that can open a shell is a root shell with extra steps. Rank 3. Control: remove the delegation or replace the command with one that has no escape, and remember that sudoers risk is a property of what the command can do, not of how narrow the path looks.

4

The kernel is three minor versions behind the distribution's current package. No misconfiguration, but every locally reachable kernel escalation applies — CVE-2016-0728 was exactly this shape. Rank 4 only because it needs a known working exploit; in impact it is rank 1. Control: patch, and track \(W\), the window between disclosure and deployment.

5

/var/log/secure is world-readable. No escalation by itself, but it leaks accounts, schedules and failure patterns. Rank 5. Control: tighten permissions and treat log exposure as reconnaissance, not as a finding to dismiss.

6

The sentence that earns the mark. “Ranked by directness: the root-owned setuid binary and the writable root cron script each give an immediate identity change; the sudo delegation gives one if the permitted command can escape; the stale kernel gives one only where a working local exploit exists; the readable log gives reconnaissance rather than privilege.”

crontab and sudoers notation

Two mini-languages carry most of the delegation on a Linux host. Both are worth being able to read at a glance, because both are where privilege is handed out.

6. A crontab line is five fields and a command

\[ \underbrace{m}_{\text{0–59}}\;\; \underbrace{h}_{\text{0–23}}\;\; \underbrace{dom}_{\text{1–31}}\;\; \underbrace{mon}_{\text{1–12}}\;\; \underbrace{dow}_{\text{0–7}}\;\; \underbrace{\text{command}}_{\text{run as the crontab's owner}} \]

Each field accepts * (any value), a list (1,15), a range (9-17) or a step (*/5). Day-of-week accepts both 0 and 7 for Sunday.

LineWhen it runsWhere it comes from
0 2 * * * /usr/local/bin/cleanup.shEvery night at 02:00The lecture's cleanup example — deletes temporary files and optimises disk space
0 12 * * 0 /usr/local/bin/backup.shEvery Sunday at 12:00The lecture's second example, added with sudo crontab -e to root's crontab
*/5 * * * * /opt/health/ping.shEvery five minutesStep syntax, the shape of a keep-alive script

7. A sudoers directive is four fields

\[ \underbrace{\text{who}}_{\text{user or } \%\text{group}}\;\; \underbrace{\text{where}}_{\text{host}}\;=\;(\underbrace{\text{as whom}}_{\text{RunAs}})\;\; \underbrace{\text{which command}}_{\text{absolute path}} \]

The lecture's two lines instantiate it exactly: User1 ALL=(ALL) /usr/bin/reboot permits User1 to run the reboot command as any user on any host, and User2 ALL=(ALL) /usr/bin/apt-get update does the same for one apt-get subcommand. Both the what and the as whom are part of the grant; narrowing either one narrows the privilege.

A crontab line reads 0 2 * * * /opt/cleanup.sh and lives in root's crontab. What happens, and as whom?
It runs at 02:00 on the second day of every month, as the user who owns the script file
It runs every day at 02:00, as root, because that is whose crontab it is
It runs every two hours, as root, because the 2 is a step value

Hardening as exposure arithmetic

Since distributions differ so widely, there is no one-size-fits-all approach to protecting Linux systems. What the lecture does give you is a list of measures, and each one can be read as a subtraction from something an attacker could otherwise reach.

8. Patch exposure is a time window

For a vulnerability disclosed at \(t_0\) and patched on a host at \(t_1\):

\[ W \;=\; t_1 - t_0 \]

\(W\) is the period during which the host is exploitable and the fix is already public. CVE-2016-0728 is the lecture's case study: the keyring facility failed to properly validate certain operations, local users could escalate to root, and the mitigation was to update to the latest patched kernel. Applying security updates and regularly monitoring for new vulnerabilities is what drives \(W\) down.

9. Attack surface is a sum; hardening is a subtraction

Write the reachable surface as a count of the things that accept input or confer identity:

\[ S \;=\; \#\{\text{listening services}\} \;+\; \#\{\text{setuid binaries}\} \;+\; \#\{\text{accounts with sudo}\} \;+\; \#\{\text{root-run scheduled tasks}\} \]

Every recommendation on this page lowers one term without removing a capability anyone needs: the firewall removes listening services, limit setuid-enabled programs removes the second term, limit sudo access to only necessary commands and use groups shrink the third, and least-privilege scheduling shrinks the fourth.

10. Least privilege bounds the blast radius

When a program is compromised, the impact is bounded by the identity it was running as:

\[ \text{impact} \;\le\; \text{priv}(\text{compromised account}) \;\ll\; \text{priv}(\text{root}) \]

This single inequality is the reason nginx runs as www-data, mysqld runs as mysql, and services that need nothing special run as nobody. It is also why Week 6 spends the second half of the lecture trying to break the inequality — and why every escalation path is a way of restoring \(\text{priv}(\text{compromised}) = \text{priv}(\text{root})\).

A host is patched on a monthly schedule. A critical kernel escalation is disclosed on day 3 of the cycle and patched on day 30. What is the exposure window \(W\), and what does it mean?
27 days, during which the host is exploitable and the fix is already public
30 days, because that is the length of the patch cycle
0 days, because the monthly patch closed the vulnerability

Tutorial triage review

The Week 6 tutorial is an escalation exercise in your own VM: get a www-data shell through the web application, escalate through a setuid helper you control, then run an automated audit and read its warnings. Use the checklist below to audit what you produced.

Establish the ceiling first

Run whoami in the web shell. If it does not say www-data, you have not established the boundary you are about to cross — and you cannot describe the escalation afterwards.

Name the mechanism, not the payload

The reportable fact is “a root-owned setuid binary executed an interpreter I could write to”, not “I ran a listener and got a shell”. The mechanism is the finding; the payload is the demonstration.

Explain the script rule

Be ready to say why the helper has to be a compiled binary: most kernels ignore the SUID flag on #! scripts, because honouring it would hand every user a scriptable root shell.

Run the audit as root, and read it

sudo ./unix-privesc-check detailed | less, then search for WARNING. The value is in the triage: which warning corresponds to the path you actually used, and which are noise on this host.

Worked answer — writing up the tutorial as a finding. The tutorial asks for a screencast demonstrating the escalation and the audit script. A markable write-up has five parts; here is the skeleton with the Week 6 material filled in.

1

Scope and precondition. Lab VM only, attacker host on the same host-only network. The precondition is a web application reachable from the attacker and vulnerable to SQL injection, plus the ability to run commands on the VM as an administrator while setting up.

2

Initial access and identity. The injection yields an operating-system-level shell through the database service. whoami returns www-data: the shell is confined to the web server's program-specific account, which is exactly what the least-privilege design intends.

3

The escalation mechanism. A root-owned executable with the setuid bit set runs an interpreter. By the setuid equation, \(\text{euid} = \text{owner}(f) = 0\), so the interpreter and everything it starts run as root. The identity change came from the file's mode bits, not from any credential the attacker held.

4

Evidence and verification. The reverse connection is received on the attacker host, and whoami in that session returns root. The controlled script contents run with root privileges, which demonstrates full control of the machine without knowing the root password.

5

Detection and remediation, as the defender. Detection: a SUID binary outside the package manager's records in a world-writable directory (find / -perm -4000 -type f -exec ls -l {} \;), the web server process spawning bash, and an outbound connection from a server that should never initiate one. Remediation: remove the setuid bit and the helper, keep the web application patched so the initial injection fails, run the web and database services under accounts with no write access outside their own directories, and audit remaining setuid binaries against the seven best practices from the lecture.
