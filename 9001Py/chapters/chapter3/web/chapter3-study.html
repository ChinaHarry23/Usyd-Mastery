Why Programs Need Decisions

The lecture opens with the claim that we make about 35,000 decisions each day, then asks where decisions appear in the software you already use — and why the programs we wrote so far cannot make any.

Decisions in real software

  • Canvas shows a Teacher View or a Student View depending on who logged in
  • Kmart applies free delivery only to eligible orders over $65
  • Self-driving cars react to detected traffic lights
  • Gmail routes a message to Inbox or Spam

What our code could not do yet

  • The lecture revisits tailor4.py from Week 2
  • Every line always runs, top to bottom
  • Its flowchart is one straight line with no branches
  • It cannot respond differently to different inputs

The Akvan story: the lecture frames conditionals with the Epic of Kings. Akvan the beast asks Rostam whether he wants to be thrown into the sea or the mountains — and plans the opposite of whatever he answers: if he answers “mountains”, then I will throw him into the sea; if he answers “sea”, then I will throw him into mountains. That pair of if-sentences is exactly the structure this lecture turns into Python.

Recap from the lecture: the boolean values are True and False. A comparison is a mixed type operator — it takes operands of one type and returns another type (a Boolean).

The if Statement

Programs with decisions: a selection statement instructs the computer to perform a set of actions depending on whether a condition is fulfilled. The lecture names three: conditional execution (if), alternative execution (if-else) and chained conditionals (if-elif).

if <Boolean_expression>: Statement

In the flowchart, the boolean expression sits in a diamond: the True path runs the indented statement, while the False path skips around it and execution continues below.

This is enough to model Akvan the beast. The lecture’s akvan.py uses two independent if statements:

# Akvan the beast model rostam_answer = input("wakey wakey,\nwhere do you want me to throw you, sea or mountains? ") if rostam_answer == "sea": print("I'm throwing you into MOUNTAINS! Ha Ha Ha!") if rostam_answer == "mountains": print("I'm throwing you into the SEA! Ha Ha Ha!")
1

The two if statements only cover the exact strings "sea" and "mountains". String comparison with == is an exact match — case and spelling included.

2

Answer "Sea", "SEA", "ocean" or anything else: both conditions evaluate to False, no branch runs, and the beast prints nothing at all.

3

This sets up a point the lecture returns to later: it is safest to list out all the possibilities a condition can take, because being human, we easily miss a case.

if … else

The pass-or-fail slide states two rules: if you get 50 or above, you will pass; if you get less than 50, you will fail. Then it asks: can we do better? Can you be more efficient? The improved phrasing — if you get 50 or above you will pass, otherwise you will fail — is exactly if … else.

if <Boolean expression>: Statement 1 else: Statement 2

Two separate ifs

Both checked

With two plain if statements, both conditions are evaluated every time, and you must write two complementary conditions yourself — and keep them consistent.

if … else

Exactly one branch

The condition is evaluated once. If it is True, Statement 1 runs; in every other case, Statement 2 runs. Exactly one of the two branches is guaranteed to execute.

Warning from the slide: DO NOT put expressions after the keyword else. An else takes no condition — it simply catches every case where the if condition was False.

Chained Conditionals: if … elif

elif is an abbreviation of else-if. The lecture introduces it for situations with more than two possibilities that need more than two branches — like turning a mark into one of the five USyd grades (HD 85–100, DI 75–84, CR 65–74, PS 50–64, FA 0–49).

The elif rules from the slide

  1. There is no limit on the number of elif statements
  2. If there is an else clause, it has to be at the end — but it is not syntactically required
  3. Conditions are checked in order of appearance: if the first is false, the next is checked, and so on
  4. Only the first true branch runs
checked in order first true wins else last & optional

The lecture’s worked example computes a speeding fine:

if speed <= 60: fine = 0 elif speed <= 70: fine = 109 elif speed <= 80: fine = 254 elif speed <= 90: fine = 835 else: fine = 2252

Nested if and Good Habits

An if can contain other ifs. The lecture’s nested example — introduced with the Inception poster — checks a driver’s speed and sets ticket:

if speed > 0: if speed < 40: ticket = False if speed > 100: ticket = True
Lecture activity: predict ticket when speed starts at 5, 40, 80 and 100. Only speed = 5 assigns False. For 40, 80 and 100 neither inner branch runs, so ticket is never assigned at all — which is exactly why the next slide’s advice matters.

Initialize, then cover every case

The “some good points” slide says: remember to initialize all variables to a useful value, and it is safest to list out all the possibilities a condition can take. It is not an issue in a simple case — but being human, we can easily make a mistake and miss a case.

The pass statement

pass is a null statement, i.e. do nothing. It is a placeholder for when a statement is syntactically required but no code needs to be executed — the lecture uses it to spell out the “do nothing” case explicitly.

print('Enter an integer:') num = int(input()) if num > 0: print('Positive') if not(num > 0): pass

Multiple ifs vs elifs

The lecture compares three versions of a grade program for the USyd scale and labels two of them bad. The point: knowing when to use multiple ifs and when to use if … elifs is itself a skill.

VersionApproachVerdict
bad_kylie.pyPlain ifs with one-sided conditions (mark >= 85, mark >= 75, …)Broken: a mark of 90 satisfies every condition, so later branches keep overwriting grade until it ends as “FA”
still_bad_kylie.pyPlain ifs with two-sided conditions (mark >= 85 and mark < 100, …)Bad: it works, but every condition is always checked and the hand-written range bounds are easy to get wrong
kylie.pyif … elif … elseGood: each mark lands in exactly one branch, and the chain stops at the first true condition
mark = int(input("Please enter the mark: ")) name = input("Please enter the name: ") grade = "undefined" if mark >= 85: grade = "HD" elif mark >= 75: grade = "DI" elif mark >= 65: grade = "CR" elif mark >= 50: grade = "PS" else: grade = "FA"

One last output-prediction trap from the lecture, the “checking a, b, c” example:

char = 'a' if char == 'a': print('a') elif char == 'b': print('b') elif char == 'c': print('c') print('Unknown')

With char = 'a' this prints a and then Unknown, because the final print('Unknown') is not part of the chain — it is unindented and always runs. With char = 'z', only Unknown is printed.

Lecture Summary

Selection statements allow the flow of execution to follow a specific branch depending on the condition. The closing slides show the four branching shapes side by side, as flowcharts and as code.

if

Run a block only when the boolean expression is True; otherwise skip straight past it.

Conditional execution

if … else

Exactly one of two branches runs. The else takes no condition of its own.

Alternative execution

if … elif … else

Conditions are checked in order and only the first true branch runs; an optional else catches the rest.

Chained conditionals

Nested ifs

A decision inside a decision — the inner check only happens once the outer condition is True.

Decisions within decisions
