### 1.2 `chapter5-study.html#sec-why` — Beyond Confidentiality: What Encryption Cannot Do
- Section lead: "Week 4 ended with confidentiality. This week starts from the two attacks that confidentiality alone does not stop — and from the question that organises everything that follows: *what guarantee is missing?*" (the table actually lists three attacks; the lead says "two attacks", a page-internal wording quirk worth knowing).
- One-time-pad recap with four strict conditions: the key is "truly random, as long as the message, used exactly once, and kept secret"; a 1 GB message therefore needs a fresh 1 GB key, and "the hard part was never the XOR, it was managing the key".
- Semantic security is quoted as the Week 4 target: "no efficient attacker should learn significant information from the ciphertext."
- Attack table row 1 — **Message modification**: attacker "Flips bits or splices ciphertext so that C becomes C′. The receiver decrypts to a different message and never notices." Missing guarantee: "Integrity — detecting unauthorised modification".
- Attack table row 2 — **Replay**: attacker "Records a valid encrypted message — 'extend the assignment deadline by 1 day' — and sends exactly the same bytes again later. No understanding and no modification is required." Missing guarantee: "Freshness — proof that the message is new and not stale".
- Attack table row 3 — **Forgery / imitation**: attacker "Creates a message that appears to come from Alice, without Alice ever sending it." Missing guarantee: "Authenticity — proof of who created the message".
- The gap, quoted in the def-box: "Encryption gives **confidentiality**: it hides the content. It does not prove that a message is *unchanged* (integrity) or *new* (freshness), and it does not prove who sent it (authenticity). Confidentiality hides content; integrity, freshness and authenticity make a message trustworthy."
- Four-node flow diagram: "1. Hide the message → 2. Detect changes → 3. Prove origin → 4. Trust the key", captioned "Confidentiality (encryption / AEAD) → integrity (hash / MAC / AEAD) → authenticity (MAC / digital signature) → identity binding (certificates / fingerprints)."
- Method callout (the lecture instruction used as an exam method): "when you meet a security problem, do not reach for an algorithm. Ask first *which guarantee is missing*, then choose the primitive that provides exactly that guarantee."
- Quick-check (replay scenario: Eve re-sends an identical decrypted-by-the-bank $100 transfer): correct answer is "Freshness: the bank cannot tell a new message from a recorded one"; the feedback adds that freshness "needs a nonce, timestamp or sequence number", and the two distractors explain that confidentiality was not broken (Eve read nothing) and integrity checks would pass (the bytes are identical).

### 1.3 `chapter5-study.html#sec-hash` — Hash Functions: A Fingerprint, Not a Secret
- Lead: a hash turns "an input of any practical length into a fixed-length digest. It answers one question very well — *has this data changed?* — and says nothing about who produced it."
- Definition quoted (def-box "Cryptographic hash function"): maps "an input of any practical length to a fixed-length **digest**"; **deterministic** ("the same input always gives the same digest"), **fixed-length** ("a short and a huge input produce the same output size"), **one-way** ("recovering the input from the digest should be hard"), efficient to compute, and exhibits the **avalanche effect** ("a tiny input change produces a widespread, unpredictable output change"); explicit warning: "Hashing is *not* encryption — there is no key and no decryption."
- Resistance table: **pre-image resistance** (given a digest h(x), find x) ≈ 2^n work; **second-pre-image resistance** (given a specific x, find x′ ≠ x with the same digest) ≈ 2^n work; **collision resistance** (find *any* pair x ≠ y with h(x) = h(y)) ≈ 2^(n/2) "the birthday effect, so collisions are the cheapest attack".
- Avalanche demo (code block, digests truncated for display as in the lecture demo): `SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e…`, `SHA-256("hell0") = 04a6f55face2f46be8c23f627d539827…`, `SHA-256("password123") = ef92b778bafe771e89245b89ecbc08a4…`, with the note "one character in, about half of the 256 output bits change".
- Uses table (where hashes are used / what is checked / typical modern choice): file integrity → "Recompute the digest and compare it with the expected value" → SHA-256/SHA-3; password storage → "A password-hashing function or KDF with a tunable cost — never raw SHA-256, and never an unsalted hash" → Argon2id / scrypt / bcrypt / PBKDF2; signatures and MACs → "The digest (or a keyed construction over it) is what gets authenticated" → HMAC / digital signatures; content addressing → "Content is named or identified by its digest" → Git, package verification, deduplication; proof of work → "Find an input whose digest has a required prefix — expensive to find, cheap to verify" → hash-based puzzles.
- "Which hash would you choose today?" list: MD5 "do not choose: collision resistance is broken"; SHA-1 "do not choose: collision resistance is broken"; SHA-256 "good default, widely supported"; SHA-3 "good alternative from a different design family; it is a standardised modern option, not merely a future one".
- "Hashing a password does not create a key": SHA-256("password123") "looks random, but *looks random is not high entropy*. A hash can spread the bits of its input; it cannot create unpredictability that was never there." A human-chosen password has "far fewer than 256 bits of entropy, so its digest is guessable at the same cost as the password itself. For cryptographic keys, generate randomness with a CSPRNG."
- Proof-of-work insight box: find a number x such that `hash("send email" || x)` starts with `000000`; the sender must try many x, the verifier checks a single hash; "Asymmetry — expensive to find, cheap to verify — is the whole point, and it exists only because hashing is one-way."
- Quick-check: Alice sends M with SHA-256(M); Eve replaces both with her own consistent pair and Bob's recomputation matches — Bob has verified "Only that the message is consistent with the digest — not who created it"; feedback notes a hash has no key and anyone can recompute it.

### 1.4 `chapter5-study.html#sec-mac` — MAC and HMAC: A Digest With a Secret Key
- Lead: "A plain hash is a fingerprint anyone can recompute. Add a shared secret and the fingerprint becomes a tag that only a key holder can produce."
- Definition quoted: "A keyed tag over a message. Three operations: **KeyGen** produces a shared key K; **Tag(K, M) → T** produces the tag; **Verify(K, M, T) → {0,1}** accepts only when the recomputed tag matches. **HMAC** is the standardised hash-based MAC construction (NIST FIPS 198-1). A MAC provides integrity *and* sender authenticity — but only for parties who share the secret key."
- Decision table — Case A: M and T arrive unchanged → Accept, "The recomputed tag matches under the shared key K"; Case B: M changed, old T replayed → Reject, "The tag no longer matches the message"; Case C: "A new fake M with a new fake T, created without K" → Reject, "Eve cannot compute a valid tag without the key".
- Attacker's goal is stated exactly: "to **pass verification without K**" — either *modifying* an existing valid pair (change the amount or the deadline) or *forging* a completely new one; "Even after observing many valid message–tag pairs, Eve still cannot produce a new pair that verifies."
- HMAC construction (def-box, "The HMAC construction (FIPS 198-1)", interactive anchor `#ix-hmac`): `HMAC(K, m) = H( (K₀ ⊕ opad) ‖ H( (K₀ ⊕ ipad) ‖ m ) )`. K is turned into a block-sized key K₀ — "hashed first if it is longer than the block, zero-padded if it is shorter"; **ipad** is "the byte 0x36 repeated B times" and **opad** is "0x5c repeated B times", where B is the hash block size ("64 bytes for SHA-256"); "The nested inner/outer structure is the point: a naive keyed hash such as H(K ‖ m) inherits structural weaknesses from the underlying hash."
- What a MAC cannot do (list): no public verification ("a MAC proves authenticity only while K stays secret from attackers"); anyone with K can forge ("if many people share one key, every one of them can create a valid tag"); no replay protection by itself ("a recorded message and tag still verify tomorrow — add a nonce, timestamp or sequence number").
- Where MAC fits in a modern stack (list): Encryption — confidentiality only; MAC/HMAC — integrity and authenticity between key holders; AEAD — both together (AES-GCM, ChaCha20-Poly1305); Secure channel — TLS/HTTPS, "which is where you actually meet all of this".
- Boundary callout motivating signatures: "A MAC says 'whoever made this tag knew K'. If millions of users must verify a software update, sharing K with all of them means any single user can forge an update that everyone else accepts. Public verification breaks the shared-secret model — which is exactly why digital signatures exist."
- Interactive `#ix-hmac` (stepper, captions in `chapter5-study.js`): six frames — preprocess key into block-sized K₀; mix with inner pad (0x36 × B, "so the key never appears directly in the hash input"); hash inner block with the message (32-byte inner digest for SHA-256); mix with outer pad (0x5c × B, "never combined with the message directly"); hash once more (tag is "32 bytes for HMAC-SHA-256, 64 for HMAC-SHA-512"); verify and remember that "a genuine message-and-tag pair replayed tomorrow still passes, so freshness needs a nonce, timestamp or sequence number".
- Quick-check: Eve changes one byte and replays the original tag → verification fails because the recomputed tag over the modified message no longer matches; HMAC is not encryption and has no decryption step.

### 1.5 `chapter5-study.html#sec-signatures` — Digital Signatures: Private Signing, Public Verification
- Lead: "Hash detects change; a MAC adds a shared secret; a signature solves the remaining problem — many verifiers, one signer, and no secret handed out."
- MAC/HMAC card: one shared secret key K; "If many people know K, any of them can create a valid tag"; good for closed groups that already share a secret; "Cannot support public verification".
- Digital signature card: "One private signing key SK_A, many public verification keys PK_A"; only the owner can sign, anyone with the public key can verify; "Designed for public verification at scale"; "This is why software updates, app packages and certificates use signatures".
- Scenario insight box: a publisher ships an update to millions of users; if it shared one MAC key, "any malicious user would hold K, could publish a fake update with a perfectly valid tag, and every other user would accept it. A MAC proves authenticity only while its key is secret from attackers — so it cannot be used for public verification."
- Ordering exercise `#ix-sig-seq` ("Order the digital signature process"), five steps in the deck's order: (1) "Hash the message to create a digest of M"; (2) "Sign that digest with the sender's private key to produce S"; (3) "Send the message M together with the signature S"; (4) "Recompute the digest and verify the signature with the sender's public key"; (5) "Accept only if M and S match under the sender's public key".
- What digital signatures provide (table): **Integrity** — "The signed content cannot be changed unnoticed — change either the message or the signature and verification fails"; **Origin authentication** — "The signature is tied to the signer's private key, so a valid signature proves control of that key"; **Public verifiability** — "Anyone who has the public key can check the signature, without being able to create one"; **Non-repudiation support** — "Only when identity, key ownership and audit evidence are established — the signature alone is not a legal conclusion".
- What signatures do *not* provide (table, with the "precise wording to use instead"): **Confidentiality** — "Signing does not encrypt the message; anyone who receives it can still read it unless encryption is also used" → say "Encrypt to hide; sign to prove origin and detect changes."; **A raw mathematical guarantee of identity** — "A valid signature proves control of a private key — connecting that key to a person or domain is a separate trust problem" → "A valid signature proves control of a private key; the certificate says whose key it is."; **Safety from a badly built scheme** — "Raw textbook RSA signatures are malleable; approved schemes apply an encoding such as PSS (RSA-PSS, ECDSA and EdDSA are the FIPS 186-5 options)" → "Hash, then sign with an approved padding scheme — never raw RSA."
- Callout: "**Never describe signing as 'encrypting with the private key'.** The two operations use the same mathematics in RSA, but they carry different guarantees: encryption hides content for one recipient; signing proves origin and detects change for anyone. The lecture is explicit that signing does not hide the message."
- Worked example `#sol-1` ("a secure software update, end to end"), six steps: (1) **Publish** — the package is M plus S, and "The private signing key SK_dev never leaves the developer"; (2) **Hash** — "H = H(M) reduces the update to a fixed-length digest, so the signature only has to cover a short value"; (3) **Sign** — "S = Sign(SK_dev, H(M)). Only the holder of SK_dev can produce S."; (4) **Verify** — the device recomputes H(M′) and checks Verify(PK_dev, M, S); "A single changed byte changes the digest and breaks verification; a fake update signed with somebody else's key fails under PK_dev"; (5) **Decide** — "Valid signature → install. Modified or fake update → reject *before* install."; (6) **Name the remaining gap** — "Everything above assumes the device holds the *right* PK_dev… That is the certificate and PKI problem."
- Quick-check: vendor signs an installer → correct statement is "Users verify with the vendor's public key, and the installer remains readable to anyone"; distributing the private key would let anyone sign, and signing does not encrypt.

### 1.6 `chapter5-study.html#sec-pubkey` — Public-Key Cryptography: RSA
- Lead: "Symmetric cryptography assumes both sides already share a key. Public-key cryptography splits the key in two, so one half can be published and the other never leaves its owner."
- Definition quoted: "A key pair whose two halves are mathematically linked: a **public key** that may be shared widely, and a **private key** that must remain with its owner. The pair performs three different jobs — **encrypt** (public key encrypts, private key decrypts: RSA-OAEP), **sign** (private key signs, public key verifies: RSA-PSS, ECDSA, EdDSA) and **agree** (each side combines its own private value with the peer's public value: Diffie-Hellman, ECDH)."
- One-way-function SVG figure (three boxes + arrows): left "private: x / a random exponent a" → middle "y = g^x mod p / easy: repeated squaring" → right "public: y / published, safe to share"; a grey dashed arrow runs backwards labelled "hard: recover x from y (discrete logarithm) — for RSA the hard direction is factoring n = p · q"; headline inside the figure: "Publish y — not x. This one-way gap is what makes public-key cryptography possible."
- Figure caption: "Multiplying two large primes is easy; factoring their product is believed hard. Raising g to a power modulo p is easy; inverting it is the discrete logarithm problem. Everything in this section is built on one of those two gaps."
- RSA key-generation table, six steps with the page's toy values: (1) choose two distinct large primes p = 61, q = 53; (2) n = p·q = 3233, "its bit length is the 'key size'"; (3) φ(n) = (p−1)(q−1) = 3120; (4) choose e with 1 < e < φ(n) and gcd(e, φ(n)) = 1, e = 17; (5) d ≡ e⁻¹ (mod φ(n)), d = 2753; (6) publish (n, e), keep (n, d) secret — "p, q and φ(n) must never be published"; the page's key lines read "public (3233, 17) · private (3233, 2753)".
- Why decryption recovers the message: because e·d ≡ 1 (mod φ(n)), "raising a ciphertext to the power d undoes raising the message to the power e: m^(e·d) ≡ m (mod n). That is Euler's theorem, and it is also why φ(n) must stay secret — anyone who learns p and q can compute d in moments."
- Three rules that matter in practice: **Never use raw RSA** ("Textbook RSA is deterministic and malleable; approved schemes apply OAEP for encryption and PSS for signatures"); **One key pair, one job** ("NIST FIPS 186-5 states that an RSA signature key pair shall not be used for other purposes such as key establishment"); **Respect the minimum size** ("The standard requires a modulus of at least 2048 bits, with p and q of equal bit length and 2^16 < e < 2^256").
- Hybrid-encryption callout: "Modular exponentiation with a 2048-bit modulus is orders of magnitude slower than AES. Real systems therefore use public-key cryptography only to protect a short secret — encrypt a random session key with RSA-OAEP, or agree one with Diffie-Hellman — and then protect the bulk data with AES-GCM or ChaCha20-Poly1305. The asymmetric step is the short setup, not the payload."
- Worked example `#sol-2` (p = 61, q = 53, e = 17, m = 65), six steps: n = 61 × 53 = 3233 ("about 12 bits" — real keys are 2048 bits or more); φ(n) = 60 × 52 = 3120; gcd(17, 3120) = 1 shown as "3120 = 17 × 183 + 9, then 17 = 9 + 8, then 9 = 8 + 1"; private exponent via "1 = 2 × 3120 − 367 × 17, so d ≡ −367 ≡ 2753 (mod 3120). Check: 17 × 2753 = 46 801 = 15 × 3120 + 1. ✓"; encrypt "c = m^e mod n = 65^17 mod 3233 = 2790, computed with repeated squaring rather than 17 multiplications"; decrypt "m = c^d mod n = 2790^2753 mod 3233 = 65"; the step-6 note: "what makes it safe is that computing d needs the factorisation of n, and nothing published reveals it."
- Interactive `#ix-rsa` (stepper "RSA: from two primes to a working key pair", toy parameters so every value can be checked by hand, "the structure is identical at 2048 bits"), eight frames: choose primes (p and q are secret material); multiply to get n (bit length of n is the key size, n is published); compute φ(n) and never publish it ("Anyone who learns it can compute the private key"); choose e coprime to φ(n) (standard constrains the range, "65537 is the usual choice"); compute d with the extended Euclidean algorithm (e·d ≡ 1 mod φ(n)); two keys, two jobs; encrypt/decrypt/sign/verify ("Signing swaps the roles: s = H(m)^d mod n, verified by s^e mod n = H(m)"); closing frame "Why the toy numbers are only a teaching device" — "A 12-bit modulus can be factored by hand… even then RSA is only used for the short asymmetric step of a hybrid scheme."
- Quick-check: publishing n and e "lets anyone encrypt or verify, while only d can decrypt or sign"; recovering d from (n, e) requires factoring n, and RSA does not replace AES for bulk data.

### 1.7 `chapter5-study.html#sec-dh` — Diffie-Hellman: Agreeing on a Secret in Public
- Lead: "Diffie-Hellman solves key establishment, not bulk encryption: two parties who have never met derive the same secret while an observer sees every value they exchange."
- Five-step exchange table: (1) Public — "Agree on a large prime p and a generator g. Eve can see both."; (2) Alice — pick secret exponent a, "compute A = g^a mod p, send A to Bob. Keep a private."; (3) Bob — pick secret exponent b, "compute B = g^b mod p, send B to Alice. Keep b private."; (4) Both — "Alice computes B^a mod p; Bob computes A^b mod p. Both equal g^(ab) mod p — the shared secret."; (5) Both — "Run the shared value through a key-derivation function to obtain fresh session keys, then protect the traffic with an AEAD cipher."
- What Diffie-Hellman alone does not give: "Nothing about *who* is on the other end. Eve can sit in the middle, replace Alice's public value with her own when talking to Bob (and vice versa), and end up sharing one secret with Alice and a different one with Bob. Diffie-Hellman creates a shared secret; authentication is what tells you who shares it — a certificate or signature binds the public values to a verified identity."
- Why ephemeral keys are the default: "If each session generates a fresh exponent and discards it afterwards, then compromising a long-term key later does not reveal past session keys. Ephemeral Diffie-Hellman over elliptic curves (ECDHE) is the usual choice, and approved group parameters matter: bad primes or unvalidated public values enable small-subgroup attacks that leak the private exponent."
- Four-node flow: "1. Authenticate → 2. Agree (ECDHE) → 3. Derive (KDF) → 4. Protect (AEAD)", captioned "Key agreement is one layer, not the whole protocol: a certificate or signature verifies the peer, ECDHE produces the shared secret, a KDF creates fresh session keys, and an AEAD cipher protects the traffic."
- Key-strength chart `#ix-key-race` ("Relative security strength of common choices", max 128, "Figures follow NIST SP 800-57 and FIPS 186-5 guidance"): AES-128 (symmetric) = 128-bit security; ECDH/ECDSA with P-256 = "about 128-bit security"; RSA-3072 = "about 128-bit security"; RSA-2048 = "about 112-bit security"; SHA-256 collision resistance = "about 2^128 work". Its subtitle says "Comparable security strength in bits, not key length: a 2048-bit RSA key gives roughly the protection of a 128-bit symmetric key" — note this subtitle conflicts with the chart's own RSA-2048 row (112) and with the insight box; the row values and the insight box agree with the math page's table, so treat ≈112 bits as the page's operative assessment.
- Insight box "Read the key sizes correctly": "Key length is not security level. A 2048-bit RSA modulus is assessed at roughly 112 bits of security because the best known attack is factoring, not brute force; a 256-bit elliptic curve gives about 128 bits because the best known attack is the discrete logarithm in a much smaller group. Matching a primitive to a required security level is a lookup in the standards, not a guess."
- Interactive `#ix-dh` (stepper "The Diffie-Hellman exchange", toy group p = 23, g = 5, "the mechanism is what matters, not the size"): six frames — public parameters; Alice publishes only A; Bob publishes only B; both derive the same shared secret; "What Eve would have to solve" ("In this toy group there are 22 candidates; with real parameters the search space is astronomically larger"); "Agreement is one layer, not the whole protocol" (MITM requires authentication).
- Quick-check: after an unauthenticated DH exchange over a channel Eve can read and write, Alice and Bob know "That they share a secret with *somebody* who knows a matching exponent — not who that somebody is"; the exchanged values were never confidential, and identity is not established.
- Worked example `#sol-3` (p = 23, g = 5, a = 6, b = 15), six steps: public parameters p = 23, g = 5 ("23 would be breakable by hand"); Alice A = 5^6 mod 23 = 8 ("5^2 = 25 ≡ 2, 5^3 ≡ 10, so 5^6 = (5^3)^2 ≡ 100 ≡ 100 − 92 = 8"), keeps a = 6; Bob B = 5^15 mod 23 = 19 ("From 5^12 ≡ 18 and 5^3 ≡ 10, B ≡ 18 × 10 = 180 ≡ 180 − 161 = 19"), keeps b = 15; Alice K = 19^6 mod 23 = "5^90 mod 23; the order of 5 modulo 23 is 22, and 90 ≡ 2 (mod 22), so K = 5^2 mod 23 = 2"; Bob K = 8^15 mod 23 = (5^6)^15 = 5^90 ≡ 5^2 = 2; step 6: Eve sees p = 23, g = 5, A = 8, B = 19 and "would only have to search 22 exponents here. With a real group of about 256 bits the search space is around 2^256, and no efficient classical method for the discrete logarithm is known. The toy numbers show the mechanism, not the security."

### 1.8 `chapter5-study.html#sec-trust` — Whose Key Is It? Certificates and PKI
- Lead: "A valid signature proves control of a private key. It does not prove whose key it is. If Eve swaps in her own public key, every signature check still succeeds — for the wrong person."
- Key-substitution SVG figure: box "Alice / sends PK_A" → box "Eve / substitutes PK_A → PK_E" → box "Bob / accepts the wrong key", with dashed grey transfer lines; figure text: "A valid signature proves control of a private key. It does not prove whose key it is."; "Eve never breaks the algorithm. She replaces the key — and every mathematical check still passes."; "The real question is not only 'is the signature valid?' but 'whose key verified it?'" Caption: "Trust is a binding problem, not only a mathematics problem. Something outside the signature has to connect a public key to an identity."
- Trust-binding table: "This is Alice" / "This is example.com" → **Certificates** ("a CA signs a public key for a domain or organisation") → "A key bound to a name by a party you already trust"; Web PKI → **Certificate authorities** ("trusted third parties whose roots ship with the operating system or browser") → "You trust a small set of roots instead of every key you meet"; Directory lookup → **Public-key directories** ("a trusted service publishes identity–key mappings") → "Scalable lookup, but the directory itself must be trusted"; Server identity in SSH → **Known host keys** ("the client remembers the server key after first trust") → "Trust on first use; a changed key becomes a loud warning"; Out-of-band check → **Key fingerprints** ("humans compare a short representation of the key") → "Verification that does not depend on any infrastructure".
- Trust spectrum `#ix-trust-spectrum` ("Ways to bind a public key to an identity", "A spectrum from fully automated to human-verified, not a chronology"): **Fingerprint** ("No infrastructure required, but it only scales to a handful of keys… read the digest aloud, or compare it in person"); **Known host key** ("Trust on first use… Convenient and unauthenticated at that first moment; a later change is treated as a possible man-in-the-middle"); **Directory** ("Central and scalable, but the security now depends on the directory: whoever can write to it can substitute keys"); **Certificate** ("A CA signs the public key together with the identity… verification needs no online lookup and no prior contact — only trust in the issuing CA"); **Web PKI** ("Roots, intermediates and revocation… a small trusted root set, delegated intermediates, validity windows, name checks and revocation status. Automated, revocable, and only as trustworthy as the CAs in the chain").
- X.509 field table (field / why it exists): **Version and serial number** — "Identifies the certificate uniquely so it can be referenced, renewed and revoked"; **Issuer** — "Names the CA that signed this certificate — the next link in the chain"; **Validity (not before / not after)** — "A bounded lifetime; an expired certificate is invalid even if every signature checks out"; **Subject** — "The identity being bound: a domain name for a server certificate, or an organisation"; **Subject public key info** — "The algorithm and the public key itself — the thing being certified"; **Extensions** — "Subject alternative names, key usage, and basic constraints such as 'this key may sign other certificates'"; **Signature algorithm and value** — "The CA's signature over all of the fields above; changing any of them breaks it".
- Chain-validation insight box, "in the order a client should do it": "Build a chain from the server certificate to a locally trusted root; verify each signature up the chain; check that every certificate is inside its validity window; check that the name you asked for appears in the subject or the subject alternative names; and check revocation (CRL or OCSP) and key usage. Only then is the public key 'the server's key' in any meaningful sense."
- Quick-check: verifying a signature with a handed-over public key establishes "That whoever produced the signature holds the matching private key — the key's owner still depends on the certificate"; the other statements are the substitution attack and a confusion of signatures with confidentiality.

### 1.9 `chapter5-study.html#sec-tools` — Choosing a Primitive: Guarantee First
- Lead: "Four tools, four key models. Choosing between them is a question about the guarantee you need — confidentiality, integrity, authenticity, or public verification — not about which one sounds strongest."
- Four-tool comparison table (tool / key model / confidentiality / integrity–authenticity / public verification): **Hash** — no key / No / "Change detection only" / "Anyone can recalculate it"; **MAC / HMAC** — shared secret / No / "Yes — between key holders" / No; **Digital signature** — private/public key pair / No / Yes / Yes; **AEAD** — shared secret / Yes / "Yes — between key holders" / No.
- Matcher `#ix-tool-match` ("Match the requirement to the primitive"), six pairs: "Did the downloaded file change in transit?" → "A cryptographic hash compared against a published digest"; "Did someone who holds the shared secret create this tag?" → "A MAC / HMAC verified with the shared key"; "Does this update verify under the publisher's public key?" → "A digital signature checked with the publisher's public key"; "Whose public key is this, really?" → "A certificate, a trusted directory or a compared fingerprint"; "Are the contents hidden and authenticated at the same time?" → "An AEAD cipher such as AES-GCM or ChaCha20-Poly1305"; "Can two strangers derive the same key over an open channel?" → "Diffie-Hellman key agreement, authenticated by a certificate".
- Verification pipeline `#ix-update-pipeline` ("Secure software update: the verification path", "Any failure ends the sequence with a rejection"), six nodes: **Download** — "Fetch the update file M and its detached signature S over an untrusted network"; **Recompute the digest** — "Hash the downloaded bytes: H(M′). One changed byte changes the digest completely"; **Verify the signature** — "Check Verify(PK_dev, M, S) with the developer's trusted public key"; **Check the digest** — "Confirm the signed digest matches the recomputed one, so the signature really covers these bytes"; **Check the certificate** — "Confirm PK_dev is bound to the expected publisher by a valid chain to a trusted root"; **Install or reject** — "Install only if every check passed; otherwise refuse before anything is written to the system".
- Question-to-primitive table: "Did the data change?" → Hash (SHA-256 / SHA-3); "Did someone with the shared secret create this valid tag?" → MAC / HMAC; "Does this message verify under this public key?" → Digital signature (RSA-PSS, ECDSA, EdDSA); "Whose public key is this?" → Certificates, trusted directories, fingerprints; "Are the contents protected and authenticated together?" → AEAD (AES-GCM, ChaCha20-Poly1305).
- Takeaway insight box: "**hash = fingerprint. MAC = shared-key authenticity. Signature = public verification. AEAD = encryption and integrity together.** Modern systems combine these blocks rather than asking one tool to do every job — and getting the combination wrong is a design failure, not a mathematical one."
- Common misuses card (red): "Using a MAC where millions must verify — any key holder can forge"; "Using a plain hash as proof of origin — anyone can recompute it"; "Describing a signature as encryption — it hides nothing"; "Trusting a valid signature without checking whose key it is".
- What good practice looks like card: "AEAD by default for traffic; AES-GCM or ChaCha20-Poly1305"; "Hash, then sign with an approved scheme — never raw RSA"; "Bind public values to identities with certificates or signatures"; "Add a nonce, timestamp or sequence number wherever replay matters".

### 1.10 `chapter5-study.html#sec-recap` — Week 5 Recap
- Toolkit card 1 — "Hash = fingerprint": "Any practical input becomes a fixed-length digest. It detects change, scales to many files, and proves nothing about who created the data." Flip hint: "Integrity only".
- Toolkit card 2 — "MAC = shared-key authenticity": "Add a secret to the digest and only key holders can produce a valid tag. Great inside a closed group; useless for public verification." Flip hint: "Integrity + authenticity".

- Toolkit card 4 — "Trust = binding, not mathematics": "Certificates, CAs, directories and fingerprints are what connect a public key to an identity. A valid signature only proves control of a key." Flip hint: "PKI".

### 1.12 `chapter5-math.html#sec-m-mod` — Modular arithmetic and the one-way gap
- Notation def-box: "\(a \bmod n\) is the remainder of \(a\) on division by \(n\). Two integers are **congruent** modulo \(n\), written \(a \equiv b \pmod{n}\), when \(n\) divides their difference. The integers modulo \(n\) form a set written \(\mathbb{Z}_n\); the values coprime to \(n\) form a group of size \(\varphi(n)\), Euler's totient."
- Theorem 1 (modular inverse and the totient): "A value \(a\) has a multiplicative inverse modulo \(n\) exactly when it is coprime to \(n\), and that inverse is what the extended Euclidean algorithm computes: \(a a^{-1} \equiv 1 \pmod n \iff \gcd(a,n)=1\)." For an RSA modulus n = pq with distinct primes, "counting the values that are *not* coprime to \(n\)" gives φ(n) = (p−1)(q−1).
- Theorem 1 practical consequence (quoted): "anyone who learns \(p\) and \(q\) can compute \(\varphi(n)\), then \(d\), and then read every message. The security of RSA is the secrecy of the factorisation, not the secrecy of the algorithm."
- Theorem 2 (Fermat and Euler): "\(a^{\,p-1} \equiv 1 \pmod{p}, \qquad a^{\,\varphi(n)} \equiv 1 \pmod{n}\)" — "This is what makes exponentiation a permutation of \(\mathbb{Z}_n^{*}\): the exponents wrap around with period \(\varphi(n)\), which is exactly why \(e d \equiv 1 \pmod{\varphi(n)}\) lets decryption undo encryption."
- Theorem 3 (easy forward, hard backward): repeated squaring costs "about \(O(\log x)\) modular multiplications"; "\(y = g^{\,x} \bmod p\) (easy)" and "\(x = \log_g y \bmod p\) (hard)". "The backward problem is the **discrete logarithm problem**. Its sibling is **integer factorisation**: computing \(n = p q\) is easy, and recovering \(p\) and \(q\) from \(n\) is not. Diffie-Hellman rests on the first, RSA on the second."
- Interactive `#ix-modexp` ("Easy forward, hard backward", "Modular exponentiation in the toy group p = 23, g = 5 — and what changes when the group is real"), three frames: (1) forward repeated squaring shown as a table — 5^1 mod 23 = 5 (start); 5^2 mod 23 = "25 mod 23 = 2" (square); 5^4 mod 23 = "2 x 2 = 4" (square the square); 5^6 mod 23 = "4 x 2 = 8" (6 = 4 + 2, combine) — "Three multiplications instead of five", and "Cost grows with log x, so a 256-bit exponent is still fast."; (2) backward exhaustive search — candidate list "x=1 → 5, x=2 → 2, x=3 → 10, x=4 → 4, x=5 → 20, x=6 → 8 ✓", "22 candidates, found by hand. The attacker's work is the size of the exponent space.", and "With a 256-bit group the same search is about 2^256 attempts — no efficient classical method is known."; (3) the same asymmetry at real sizes — card A "factoring: n = p · q easy / recover p, q from n hard / used by: RSA", card B "discrete log: g^x mod p easy / recover x hard / used by: Diffie-Hellman, ECDH", footer "Publish the parameters and the public value; keep the exponent and the primes."
- Quick-check: the one-way function works "Because computing y is cheap with repeated squaring, while recovering x is the discrete logarithm problem"; the distractors state that g and p must be kept secret (they are public) and that inversion is impossible even for p = 23 (there the 22 exponents can simply be tried).

### 1.13 `chapter5-math.html#sec-m-rsa` — RSA: key generation, encryption and signatures
- Key-generation theorem box: "\(n = p\,q, \qquad \varphi(n) = (p-1)(q-1), \qquad e\,d \equiv 1 \pmod{\varphi(n)}\)"; "Public key \((n, e)\); private key \((n, d)\); \(p\), \(q\) and \(\varphi(n)\) destroyed or stored as secret material."
- Size and parameter rules (quoted): "NIST FIPS 186-5 requires a modulus of at least 2048 bits, primes \(p\) and \(q\) of equal bit length, and a public exponent in the range \(2^{16} < e < 2^{256}\) (typically \(e = 65537\))."
- Encryption/decryption box: "\(c = m^{\,e} \bmod n\)" and "\(m = c^{\,d} \bmod n\)"; correctness from Euler: since "\(ed = 1 + k\varphi(n)\)", "\(m^{\,ed} = m^{\,1 + k\varphi(n)} = m \cdot (m^{\varphi(n)})^{k} \equiv m \pmod{n}\)"; note that this "holds for messages coprime to \(n\); the Chinese Remainder Theorem covers the remaining cases", and "the exponent pair is what ties the two keys together."
- Signature box: "\(s = H(m)^{\,d} \bmod n\), verified by \(s^{\,e} \bmod n \overset{?}{=} H(m)\)"; "Anyone can verify with \((n,e)\); only the holder of \(d\) can produce \(s\)." Two warnings: "a signature key pair shall not be reused for encryption or key establishment, and raw textbook RSA must never be deployed — without an encoding such as PSS, the multiplicative structure of RSA makes signatures forgeable."
- Toy-value table (quantity / toy value / how obtained): p, q = 61, 53 ("Random primes of equal bit length"); n = pq = 3233 ("Multiplication — published as part of the public key"); φ(n) = (p−1)(q−1) = 3120 ("Secret; reveals \(d\) if leaked"); e = 17 ("Chosen coprime to \(\varphi(n)\); published"); d ≡ e⁻¹ (mod φ(n)) = 2753 ("Extended Euclidean algorithm; secret"); Check = "17 × 2753 = 46 801 = 15 × 3120 + 1"; m → c = "65 → 2790"; c → m = "2790 → 65".
- RSA modulus strength table: 1024 bits — "No longer acceptable in new designs" (comparable symmetric key "—"); 2048 bits — "About 112 bits" ("3DES-class strength; still allowed, not generous"); 3072 bits — "About 128 bits" ("AES-128"); 7680 bits — "About 192 bits" ("AES-192"); 15360 bits — "About 256 bits" ("AES-256").
- Quick-check: "φ(n) … must never be published, and why?" — correct answer "φ(n), because with e it yields the private exponent d immediately"; the distractors are n (published deliberately) and e (public exponent, not the inverse of d).
- Worked example `#sol-m1` (p = 61, q = 53, e = 17, m = 65), six steps: n = 61 × 53 = 3233 "so len(n) = 12 bits. Real deployments require len(n) ≥ 2048."; φ(n) = 60 × 52 = 3120; validity of e via Euclid "3120 = 17 × 183 + 9, 17 = 9 + 8, 9 = 8 + 1, so gcd(17, 3120) = 1 and the inverse exists."; private exponent "1 = 2 × 3120 − 367 × 17, so d ≡ −367 ≡ 2753 (mod 3120). Check: 17 × 2753 mod 3120 = 1. ✓"; encryption by repeated squaring "65^2 ≡ 992, 65^4 ≡ 1232, 65^8 ≡ 1547, 65^16 ≡ 789 (mod 3233), so c = 789 × 65 = 51 285 ≡ 2790 (mod 3233). Only five multiplications were needed rather than sixteen."; decryption "2790^2753 mod 3233 = 65 by the same route. Anyone can reproduce step 5 from the public key; only the holder of d can run this step."

### 1.14 `chapter5-math.html#sec-m-dh` — Diffie-Hellman: the shared secret equation
- Exchange theorem box: "Public parameters: a large prime \(p\) and a generator \(g\). Alice chooses \(a\), Bob chooses \(b\), both uniformly at random from \(\{1, \dots, p-2\}\)"; "\(A = g^{\,a} \bmod p, \qquad B = g^{\,b} \bmod p, \qquad K = B^{\,a} \bmod p = A^{\,b} \bmod p\)"; the agreement proof "\(B^{\,a} = (g^{\,b})^{a} = g^{\,ab} = (g^{\,a})^{b} = A^{\,b} \pmod{p}\)".
- Computational Diffie-Hellman assumption (quoted): "Anyone who can solve the discrete logarithm recovers \(a\) from \(A\) or \(b\) from \(B\), and therefore \(K\). That is the **computational Diffie-Hellman** assumption: \(g^{ab}\) is hard to compute from \(g^{a}\) and \(g^{b}\) alone."
- Toy exchange table (step / Alice / Bob / Eve sees): Parameters — p = 23, g = 5 (Eve sees both); Private choice — a = 6, b = 15 (Eve sees nothing); Public value — A = 5^6 mod 23 = 8, B = 5^15 mod 23 = 19 (Eve sees 8 and 19); Combine — K = 19^6 mod 23 = 2, K = 8^15 mod 23 = 2; Why it matches — "19^6 = (5^15)^6 = 5^90 ≡ 5^2 = 2 (mod 23) because the order of 5 modulo 23 is 22 and 90 ≡ 2 (mod 22)".
- Why the parameters matter: "The hardness assumption only holds for good groups: a large prime-order subgroup, safe primes or approved elliptic curves, and validation of every received public value." Contrast pair: "secure: ord(g) is a large prime" / "insecure: ord(g) has small factors". Mechanism of the attack (quoted): "If the order has a small factor, an attacker can test candidate values of \(a\) in that small subgroup and learn \(a\) modulo that factor. Send an invalid public value, repeat, and the private exponent leaks. This is why the standards fix the groups (NIST SP 800-186 for curves) and require public-value validation."
- Classical DH vs ECDH cards: Classical — "Modular arithmetic in \(\mathbb{Z}_p^{*}\)"; "Needs a large prime \(p\) and a generator of large prime order"; "Bigger values on the wire for the same security level"; "Vulnerable to small-subgroup attacks if parameters are weak". ECDH — "Same structure with points on a curve instead of integers"; "A 256-bit curve gives roughly the security of a 3072-bit RSA modulus"; "Smaller keys and faster operations; this is what TLS deploys"; "Ephemeral use (ECDHE) gives forward secrecy for past sessions".
- Quick-check: DH does *not* provide "Assurance about who is on the other end of the exchange"; it does provide agreement between honest parties and secrecy against a passive eavesdropper.
- Worked example `#sol-m2` (p = 23, g = 5, a = 6, b = 15), five steps: Alice "5^2 = 25 ≡ 2, 5^3 ≡ 2 × 5 = 10, so \(A = 5^{6} = (5^{3})^{2} \equiv 100 \equiv 100 - 4 \times 23 = 8 \pmod{23}\)"; Bob "5^12 = (5^6)^2 ≡ 64 ≡ 18, so \(B = 5^{15} = 5^{12} \cdot 5^{3} \equiv 18 \times 10 = 180 \equiv 180 - 7 \times 23 = 19 \pmod{23}\)"; Alice computes "K = 19^6 (mod 23)… The order of 5 modulo 23 is 22, and 90 = 4 × 22 + 2, so K ≡ 5^2 = 25 ≡ 2"; Bob computes the same via 8 ≡ 5^6; conclusion "Both sides hold K = 2, which was never transmitted. Eve would have to solve \(5^{a} \equiv 8 \pmod{23}\) — 22 candidates here, infeasible for an approved group — and even then she would only have a shared secret with someone she has not authenticated."

### 1.15 `chapter5-math.html#sec-m-hash` — Hash sizes, the birthday bound and HMAC
- Hash-size table (algorithm / block bits / digest bits / collision work / use): SHA-1 — 512 / 160 / "about 2^80 — broken in practice" / "Legacy only; do not choose"; SHA-224 — 512 / 224 / about 2^112 / "Compatible with 112-bit security targets"; SHA-256 — 512 / 256 / about 2^128 / "The default choice"; SHA-384 — 1024 / 384 / about 2^192 / "Higher security targets"; SHA-512 — 1024 / 512 / about 2^256 / "Higher security targets, 64-bit platforms".
- Birthday bound box: "A collision attack does not need to hit a fixed digest; it needs any two inputs that agree. Comparing all pairs makes the expected work \(q \approx 1.177\,\sqrt{2^{n}} \approx 2^{\,n/2}\)." Consequence: "an \(n\)-bit digest gives about \(n\) bits of pre-image resistance but only about \(n/2\) bits of collision resistance. That is why MD5 and SHA-1 fell first: their collision margins were the smallest, and collision resistance is the property signatures and certificates depend on."
- HMAC box: "From NIST FIPS 198-1, with \(K_0\) the key padded (or hashed then padded) to the hash block size \(B\), and ipad/opad the bytes 0x36 and 0x5c repeated \(B\) times: \(\mathrm{HMAC}(K, m) = H((K_0 \oplus \mathrm{opad}) \,\|\, H((K_0 \oplus \mathrm{ipad}) \,\|\, m))\)". Two consequences: "the tag length equals the digest length (\(L\) bits), and the key is never fed to the hash directly, which is what a naive construction such as \(H(K \| m)\) gets wrong. Because the same construction works with any approved hash, HMAC-SHA-256 is the common modern default."
- Entropy box: "For a key drawn uniformly from \(N\) possibilities, the entropy is \(H_{\text{key}} = \log_2 N\) bits." Example: "A 128-bit key drawn from a CSPRNG has 128 bits of entropy. A human-chosen password has far less, and hashing it does not add any: SHA-256 of a password with 30 bits of entropy still has 30 bits of guessability, even though the digest is 256 bits long. Password storage therefore uses a deliberately slow KDF with a salt (Argon2id, scrypt, bcrypt, PBKDF2), and keys come from a CSPRNG."
- Attack-race chart `#ix-attack-race` ("Attacker work against a 256-bit digest", "Collision resistance is always the cheapest target, which is why it is the property that gets broken first"): pre-image "about 2^256 work"; second pre-image "about 2^256 work"; collision "about 2^128 work"; "Brute force an HMAC key drawn from 128 bits" = "about 2^128 guesses".
- Quick-check: "A system needs 128-bit security and uses SHA-256 in a digital signature. Is that consistent?" — "Yes: SHA-256 supplies about 128 bits of collision resistance, which matches a 128-bit target"; the distractors wrongly treat the digest length as the security level and wrongly claim SHA-256 provides no confidentiality (it never does, and that is irrelevant).
- Worked example `#sol-m3` ("compute HMAC-SHA-256 by hand, at the level of the algorithm"; key K 20 bytes, B = 64 bytes, L = 32 bytes), six steps: (1) normalise the key — "|K| = 20 < B = 64, so \(K_0 = K \| 0^{44}\): append 44 zero bytes. If the key had been longer than 64 bytes, the rule would be \(K_0 = H(K) \| 0^{32}\) instead — hash first, then pad."; (2) inner block "\(K_0 \oplus \mathrm{ipad}\) where ipad is 0x36 repeated 64 times. XOR is byte-wise and self-inverse, so the verifier derives the identical block from the same key."; (3) inner hash "\(h_{\text{in}} = H((K_0 \oplus \mathrm{ipad}) \| m)\), a 32-byte value. Every byte of both the key and the message now influences it."; (4) outer block "\(K_0 \oplus \mathrm{opad}\) where opad is 0x5c repeated 64 times. Note that the message is *not* concatenated here — only the inner digest is."; (5) tag "\(T = H((K_0 \oplus \mathrm{opad}) \| h_{\text{in}})\), 32 bytes for HMAC-SHA-256. Two hash computations over at least two blocks each, no matter how short the message."; (6) verify "The verifier recomputes \(T' = \mathrm{HMAC}(K, m')\) and compares. A modified \(m'\) yields a different \(T'\); a forged tag needs \(K\). But a valid pair recorded yesterday still verifies today, so freshness requires a nonce, timestamp or sequence number on top."

### 1.16 `chapter5-math.html#sec-m-sign` — Signatures and trust binding, in notation
- Hash-then-sign box: "A signature is computed over a digest, never over an arbitrarily long message directly: \(s = \mathrm{Sign}_{SK}(H(m)), \qquad \mathrm{Verify}_{PK}(m, s) = 1 \iff \mathrm{check}(PK, H(m), s) = 1\)". "Three reasons for hashing first: the signed object has a fixed size whatever the message length; the asymmetric operation is slow and is applied once to a short value; and the digest binds the signature to the exact bytes. Verification recomputes \(H(m)\), so changing a single byte of either \(m\) or \(s\) makes the check fail."
- Raw-textbook-RSA box: "Without an encoding, RSA signatures are multiplicatively malleable: if \(s_1\) verifies \(m_1\) and \(s_2\) verifies \(m_2\), then \((s_1 s_2)^{e} \equiv m_1 m_2 \pmod{n}\) so \(s_1 s_2 \bmod n\) is a valid signature on the product \(m_1 m_2\), which the attacker never had signed. Approved schemes prevent this by encoding the digest with a randomised, structured padding (RSA-PSS) or by using a different construction entirely. FIPS 186-5 approves RSA, ECDSA and EdDSA, and requires the hash strength to be at least that of the key."
- ECDSA box: "With domain parameters \((q, G, n)\), private key \(d\), per-message secret \(k\), and \(e\) the leftmost bits of \(H(m)\) interpreted as an integer: \(R = [k]G, \qquad r = x_R \bmod n, \qquad s = k^{-1}(e + r\,d) \bmod n\)"; "The signature is the pair \((r, s)\). \(k\) must be unique per signature and secret: reuse it and the private key falls out of two signatures by simple algebra, which is exactly why the standard requires a fresh \(k\) at every invocation and allows deterministic generation to remove the temptation."
- Certificate box: "A certificate is a signed statement binding a public key to a subject, issued by a CA whose own key is trusted: \(\mathrm{Cert} = \langle \text{subject},\ PK,\ \text{issuer},\ [\text{notBefore}, \text{notAfter}],\ \text{extensions},\ \sigma_{CA} \rangle\), \(\sigma_{CA} = \mathrm{Sign}_{SK_{CA}}(H(\text{certificate fields}))\)". "Validation therefore checks more than one equation: the CA signature over the fields, a chain from the subject through any intermediates to a locally trusted root, the validity window, the name you asked for, key usage, and revocation status. A valid signature proves control of a private key; the chain is what turns that key into an identity."
- Interactive `#ix-cert-hotspot` ("Anatomy of an X.509 certificate"): an SVG of an X.509 v3 certificate labelled `tbsCertificate`, with eight clickable markers — **Version and serial number** ("A unique identifier for this certificate. It is what a revocation list names, and it is how a renewal is distinguished from the certificate it replaces."); **Signature algorithm** ("The algorithm the issuer used to sign these fields — here ECDSA with SHA-256. A validator must trust this choice, not just the signature bytes."); **Issuer** ("The CA that signed the certificate. Validation uses this to find the next certificate up the chain, and continues until it reaches a locally trusted root."); **Validity** ("A bounded lifetime. An expired certificate is invalid even when every signature checks out, which is why renewal is an operational process rather than an optional one."); **Subject** ("The identity being bound — a domain name for a server certificate, or an organisation for a client or code-signing certificate."); **Subject public key info** ("The algorithm and the public key itself: the object being certified. This is the value an application will use to verify signatures or to run a key exchange."); **Extensions** ("Subject alternative names, key usage, and basic constraints such as whether this key may sign other certificates. A validator must enforce these; ignoring key usage is a real vulnerability class."); **Signature value** ("The CA's signature over every field above. Change any field and this no longer verifies — but a valid signature still only proves control of the CA's private key; the chain is what makes it an identity.").
- The same SVG's example field values (useful for question stems): version/serial "v3, 04:9a:1c:... (unique)"; signatureAlgorithm "ecdsa-with-SHA256"; issuer "CN = Example Intermediate CA"; validity "2026-03-01 to 2027-03-01"; subject "CN = www.example.com"; subjectPublicKeyInfo "id-ecPublicKey, P-256, 04:3b:..."; extensions "SAN, keyUsage, basicConstraints"; signatureValue "the CA signature over every field above".
- Quick-check: hash-then-sign does not lose security "Because a collision-resistant digest commits to the whole message in a fixed length, so one signature covers all of it"; hashing does not hide the message and is not done to fit a packet.

### 1.17 `chapter5-math.html#sec-m-tools` — Decision table, notation and self-checks
- Lead: "The exam question is almost always 'which primitive, and why?'. This is the table to reconstruct, and the symbols you need in order to read it."
- Decision table (guarantee needed / primitive / key model / fails when): "Detect that data changed" → Hash (SHA-256, SHA-3) → "No key" → "An attacker replaces the message *and* the digest"; "Prove a key holder created the tag" → MAC / HMAC → "Shared secret" → "The key leaks, or one of many holders forges"; "Let anyone verify one signer" → Digital signature → "Private / public pair" → "The public key is substituted, or the scheme is raw RSA"; "Hide and authenticate traffic" → AEAD (AES-GCM, ChaCha20-Poly1305) → "Shared secret" → "The nonce is reused"; "Agree a key over an open channel" → Diffie-Hellman / ECDHE → "Ephemeral key pairs" → "The exchange is unauthenticated, or parameters are weak"; "Bind a key to a name" → X.509 certificate, PKI → "Trust anchors" → "A trusted CA is compromised, or validation is skipped".
- Notation matcher `#ix-m-notation` (twelve pairs): "n = p·q" → "The RSA modulus; its bit length is the key size"; "(n, e)" → "The RSA public key, used to encrypt and to verify"; "(n, d)" → "The RSA private key, used to decrypt and to sign"; "φ(n) = (p−1)(q−1)" → "Euler's totient — secret, because it yields d"; "g, p" → "Public Diffie-Hellman parameters: generator and prime"; "A = g^a mod p" → "Alice's public value; a itself stays private"; "K = g^(ab) mod p" → "The shared secret both sides derive and never transmit"; "H(m)" → "The digest that a signature or MAC actually covers"; "K0 ⊕ ipad / opad" → "HMAC's inner and outer key blocks (0x36 and 0x5c)"; "2^(n/2)" → "The birthday bound on collision attacks against an n-bit digest"; "σ_CA" → "The certificate authority's signature over the certificate fields"; "Verify(PK, H(m), s)" → "The check a verifier runs using the signer's public key".

## 2. FORMULAS AND NUMERIC DRILLS (every formula, worked, with arithmetic shown)

### 2.1 Modular arithmetic foundations (`#sec-m-mod`)
- **Congruence**: a ≡ b (mod n) when n divides (a − b); a mod n is the remainder of a on division by n; Z_n is the set of integers mod n; the values coprime to n form a group of size φ(n).
- **Modular inverse exists iff coprime**: a·a⁻¹ ≡ 1 (mod n) ⟺ gcd(a, n) = 1; computed by the extended Euclidean algorithm.
- **Totient of an RSA modulus**: φ(n) = (p−1)(q−1). Drill: p = 61, q = 53 → φ = 60 × 52 = **3120**.
- **Fermat**: a^(p−1) ≡ 1 (mod p) for prime p and p ∤ a. **Euler**: a^φ(n) ≡ 1 (mod n) for gcd(a, n) = 1. Consequence: exponentiation is a permutation with period φ(n), so e·d ≡ 1 (mod φ(n)) makes decryption undo encryption.
- **Repeated squaring cost**: about O(log x) modular multiplications. Drill (from `#ix-modexp`): 5^6 mod 23 → 5^1 = 5; 5^2 = 25 ≡ **2**; 5^4 = 2 × 2 = **4**; 5^6 = 4 × 2 = **8**; three multiplications instead of five. Independent check: 5^6 = 15625; 23 × 679 = 15617; 15625 − 15617 = 8 ✓.
- **One-way pair**: forward y = g^x mod p is easy; backward x = log_g y mod p is the discrete logarithm problem (hard). Sibling: n = p·q easy, recovering p and q hard — "Diffie-Hellman rests on the first, RSA on the second." Toy search space at p = 23: p − 1 = **22** candidate exponents; a ~256-bit group gives ~2^256.

### 2.2 RSA (`#sec-m-rsa`, study `#sec-pubkey`, `#sol-2`, `#sol-m1`)
- **Key generation**: n = p·q; φ(n) = (p−1)(q−1); e·d ≡ 1 (mod φ(n)). Public key (n, e); private key (n, d); p, q, φ(n) secret/destroyed.
- **Encryption/decryption**: c = m^e mod n; m = c^d mod n. Correctness: ed = 1 + kφ(n) ⟹ m^(ed) = m·(m^φ(n))^k ≡ m (mod n) (CRT covers non-coprime m).
- **Signature**: s = H(m)^d mod n; verification s^e mod n =? H(m); never raw — PSS encoding required.
- **Sizes (FIPS 186-5)**: modulus ≥ 2048 bits; p and q equal bit length; 2^16 < e < 2^256 (2^16 = 65 536), typically e = 65537.
- **Full toy drill (all values recomputed)**:
  - n = 61 × 53 = **3233**; bit length ⌈log2 3233⌉ = **12 bits** (2^11 = 2048 ≤ 3233 < 4096 = 2^12).
  - φ(n) = 60 × 52 = **3120**.
  - gcd check: 3120 = 17 × 183 + 9 (17 × 183 = 3111, remainder 9); 17 = 1 × 9 + 8; 9 = 1 × 8 + 1; so gcd(17, 3120) = 1 ✓.
  - Back-substitution: 1 = 2 × 3120 − 367 × 17; check 2 × 3120 = 6240 and 367 × 17 = 6239, difference 1 ✓.
  - d ≡ −367 ≡ 3120 − 367 = **2753** (mod 3120).
  - Check: 17 × 2753 = **46 801** = 15 × 3120 + 1 = 46 800 + 1 ✓ (and (17 × 2753) mod 3120 = 1 ✓).
  - Encrypt m = 65: 65^2 = 4225; 4225 − 3233 = **992**; 65^4 = 992^2 = 984 064; 984 064 − 304 × 3233 = 984 064 − 982 832 = **1232**; 65^8 = 1232^2 = 1 517 824; 1 517 824 − 469 × 3233 = 1 517 824 − 1 516 277 = **1547**; 65^16 = 1547^2 = 2 393 209; 2 393 209 − 740 × 3233 = 2 393 209 − 2 392 420 = **789**; c = 789 × 65 = **51 285**; 51 285 − 15 × 3233 = 51 285 − 48 495 = **2790**. Five multiplications (four squarings + one multiply) instead of sixteen.
  - Decrypt: 2790^2753 mod 3233 = **65** (verified independently).
- **RSA strength table**: 1024 bits → not acceptable in new designs; 2048 → ≈112 bits (3DES-class, "still allowed, not generous"); 3072 → ≈128 (AES-128); 7680 → ≈192 (AES-192); 15360 → ≈256 (AES-256). Study-page race chart adds: AES-128 = 128; ECDH/ECDSA P-256 ≈ 128; RSA-3072 ≈ 128; RSA-2048 ≈ 112; SHA-256 collision ≈ 2^128.
- **Signature malleability drill**: (s1·s2)^e ≡ m1·m2 (mod n); so s1·s2 mod n verifies the product m1·m2 that the signer never signed. Example with the toy key: if s1 verifies m1 and s2 verifies m2 under (3233, 17), then s1·s2 mod 3233 verifies m1·m2 mod 3233 — the attacker obtains a "valid" signature on a message of their choosing only if they can make m1·m2 equal the target; the structural point is that raw RSA has multiplicative homomorphism and therefore needs PSS.

### 2.3 Diffie-Hellman (`#sec-m-dh`, study `#sec-dh`, `#sol-3`, `#sol-m2`)
- **Equations**: A = g^a mod p; B = g^b mod p; K = B^a mod p = A^b mod p = g^(ab) mod p; a, b uniform in {1, …, p−2}.
- **Agreement proof**: B^a = (g^b)^a = g^(ab) = (g^a)^b = A^b (mod p).
- **Full toy drill (all values recomputed)**:
  - p = 23, g = 5; a = 6, b = 15.
  - 5^2 = 25 ≡ **2** (25 − 23); 5^3 ≡ 2 × 5 = **10**; 5^6 = (5^3)^2 ≡ 100; 100 − 4 × 23 = 100 − 92 = **8** ⇒ A = 8.
  - 5^6 ≡ 8; 5^12 = 8^2 = 64; 64 − 2 × 23 = 64 − 46 = **18**; B = 5^15 = 5^12 × 5^3 ≡ 18 × 10 = 180; 180 − 7 × 23 = 180 − 161 = **19** ⇒ B = 19.
  - ord(5) mod 23 = **22** (verified: the least x > 0 with 5^x ≡ 1 is 22).
  - 90 = 4 × 22 + 2, so 5^90 ≡ 5^2 = 25 ≡ **2** (mod 23).
  - Alice: K = B^a = 19^6 ≡ (5^15)^6 = 5^90 ≡ **2**. Bob: K = A^b = 8^15 ≡ (5^6)^15 = 5^90 ≡ **2**. Independent checks: 19^6 mod 23 = 2 ✓; 8^15 mod 23 = 2 ✓; 5^90 mod 23 = 2 ✓.
  - Eve's search space here: 22 candidates; a real ~256-bit group ≈ 2^256.
- **Parameter rule**: secure iff ord(g) is a large prime; insecure iff ord(g) has small factors (small-subgroup attack learns a mod that factor; invalid public values + repetition leak the private exponent). Standards fix groups (NIST SP 800-186 for curves) and require public-value validation.
- **Curve equivalence**: a 256-bit curve gives roughly the security of a 3072-bit RSA modulus; ECDHE gives forward secrecy.

### 2.4 Hash sizes, birthday bound, HMAC, entropy (`#sec-m-hash`, study `#sec-hash`, `#sec-mac`)
- **Resistance costs for an n-bit digest**: pre-image ≈ 2^n; second pre-image ≈ 2^n; collision ≈ 2^(n/2) — birthday bound q ≈ 1.177·√(2^n) ≈ 2^(n/2). Verified: 1.177 × 2^128 = 2^128.235 ≈ 2^128.
- **Table drill**: SHA-1 (160-bit digest) → 160/2 = **2^80** collision; SHA-224 → 224/2 = **2^112**; SHA-256 → 256/2 = **2^128** (pre-image 2^256); SHA-384 → 384/2 = **2^192**; SHA-512 → 512/2 = **2^256**. Block sizes: SHA-1/224/256 = 512 bits (64 bytes); SHA-384/512 = 1024 bits (128 bytes).
- **Attack race on a 256-bit digest**: pre-image 2^256; second pre-image 2^256; collision 2^128 (the cheapest target); brute-forcing a 128-bit HMAC key = 2^128 guesses.
- **HMAC formula**: HMAC(K, m) = H( (K₀ ⊕ opad) ‖ H( (K₀ ⊕ ipad) ‖ m ) ); ipad = 0x36 repeated B times; opad = 0x5c repeated B times; K₀ = K padded to B with zeros if |K| ≤ B, K₀ = H(K) padded to B if |K| > B; output length = digest length L.
- **HMAC numeric drill (SHA-256: B = 64 bytes, L = 32 bytes; |K| = 20 bytes)**: |K| = 20 < 64 → append 64 − 20 = **44 zero bytes** (K₀ = K ‖ 0^44); long-key rule would be K₀ = H(K) ‖ 0^(64−32) = H(K) ‖ 0^32; inner digest h_in = 32 bytes; tag T = 32 bytes; two hash computations over at least two blocks each. XOR drill: 0xFF ⊕ 0x36 = **0xC9** (1111 1111 ⊕ 0011 0110 = 1100 1001); 0xFF ⊕ 0x5C = **0xA3** (1111 1111 ⊕ 0101 1100 = 1010 0011); XOR is its own inverse (0x36 ⊕ 0x36 = 0x00, 0x5C ⊕ 0x5C = 0x00), which is why the verifier can rebuild the identical blocks.
- **Entropy rule**: H_key = log₂ N bits. Drills: N = 2^30 possibilities → 30 bits (and SHA-256 of a 30-bit-entropy password still has **30 bits of guessability** despite a 256-bit digest); N = 2^128 → 128 bits for a CSPRNG key; 8 lowercase letters = 26^8 = 208 827 064 576 ≈ 2^37.6 possibilities → ≈37.6 bits (this last one is a standard illustration, not printed on the page).
- **Password storage rule**: deliberate slow KDF with a salt — Argon2id, scrypt, bcrypt, PBKDF2 — never raw SHA-256, never unsalted.
- **Avalanche numeric statement**: "one character in, about half of the 256 output bits change" (≈128 of 256 bits).

### 2.5 Signatures and certificates (`#sec-m-sign`, study `#sec-signatures`, `#sec-trust`)
- **Hash-then-sign**: s = Sign_SK(H(m)); Verify_PK(m, s) = 1 ⟺ check(PK, H(m), s) = 1. Three reasons: fixed signed size; one slow asymmetric operation on a short value; the digest binds the signature to the exact bytes.
- **ECDSA**: R = [k]G; r = x_R mod n; s = k⁻¹(e + r·d) mod n, where e = leftmost bits of H(m) as an integer, domain parameters (q, G, n); signature = (r, s); k unique per signature and secret (reuse leaks d by algebra).
- **Certificate notation**: Cert = ⟨subject, PK, issuer, [notBefore, notAfter], extensions, σ_CA⟩; σ_CA = Sign_{SK_CA}(H(certificate fields)).
- **Validation equation set**: CA signature over the fields; chain from subject through intermediates to a locally trusted root; validity window; requested name in subject or SAN; key usage; revocation status (CRL or OCSP).
- **FIPS 186-5 rule**: approves RSA, ECDSA and EdDSA, and requires the hash strength to be at least that of the key (so SHA-256 collision ≈128 bits supports a 128-bit target but not a 256-bit one).
- **Strength pairing drill for questions**: RSA-2048 ↔ ≈112-bit / 3DES-class; RSA-3072 ↔ AES-128; RSA-7680 ↔ AES-192; RSA-15360 ↔ AES-256; P-256 ECDH/ECDSA ↔ ≈128; SHA-256 collision ↔ 2^128.

## 3. PITFALLS (8–12 warnings/contrasts from the pages)

1. **"Hashing a password produces a strong key" is wrong because a hash cannot create entropy; the page says** "looks random is not high entropy. A hash can spread the bits of its input; it cannot create unpredictability that was never there", and "SHA-256 of a password with 30 bits of entropy still has 30 bits of guessability, even though the digest is 256 bits long." Keys must come from a CSPRNG; storage uses a slow salted KDF (Argon2id, scrypt, bcrypt, PBKDF2).
2. **"A matching hash proves who sent the message" is wrong because a hash has no key; the page says** a plain hash gives "Change detection only" and "anyone can recompute a hash, so Bob has learned nothing about who created it" — the match proves "Only that the message is consistent with the digest".
3. **"A MAC can protect a software update that millions of users must verify" is wrong because any key holder can forge; the page says** "Anyone with K can forge: if many people share one key, every one of them can create a valid tag", and "Public verification breaks the shared-secret model — which is exactly why digital signatures exist."
4. **"Signing is encrypting with the private key" is wrong because signing hides nothing; the page says** "Never describe signing as 'encrypting with the private key'", the signatures table lists confidentiality under what signatures do *not* provide, and the wording to use is "Encrypt to hide; sign to prove origin and detect changes."
5. **"A valid signature proves identity / non-repudiation automatically" is wrong because the binding is a separate problem; the page says** "A valid signature proves control of a private key; the certificate says whose key it is", and non-repudiation holds "Only when identity, key ownership and audit evidence are established — the signature alone is not a legal conclusion."
6. **"Raw textbook RSA signatures are fine, or can replace a padding scheme" is wrong because raw RSA is malleable; the page says** "Raw textbook RSA signatures are malleable; approved schemes apply an encoding such as PSS", and without encoding "(s1 s2)^e ≡ m1 m2 (mod n) so s1 s2 mod n is a valid signature on the product m1 m2, which the attacker never had signed."
7. **"Reusing the per-message ECDSA secret k is harmless" is wrong because it destroys the private key; the page says** "k must be unique per signature and secret: reuse it and the private key falls out of two signatures by simple algebra, which is exactly why the standard requires a fresh k at every invocation."
8. **"Key length equals security level (a 2048-bit RSA key is 2048-bit secure)" is wrong because the best attack is factoring, not brute force; the page says** "Key length is not security level. A 2048-bit RSA modulus is assessed at roughly 112 bits of security because the best known attack is factoring, not brute force." (Watch the page's own inconsistency: the `#ix-key-race` subtitle equates a 2048-bit RSA key with a 128-bit symmetric key, while its own RSA-2048 row and insight box say ≈112 bits and the math table says 2048 ↔ "About 112 bits" / 3DES-class. Use 112.)
9. **"A 256-bit digest gives 256-bit security in a signature" is wrong because collision resistance is the binding property and it halves; the page says** "an n-bit digest gives about n bits of pre-image resistance but only about n/2 bits of collision resistance", so SHA-256 supplies "about 128 bits of collision resistance, which matches a 128-bit target" but not a 256-bit one.
10. **"Encryption (even AEAD) prevents replay" is wrong because freshness is a separate guarantee; the page says** a replay attack "needs neither reading nor modifying the message; encryption cannot tell a fresh message from a recorded one", a MAC "still verify[s] tomorrow", and the fix is "a nonce, timestamp or sequence number".
11. **"Diffie-Hellman authenticated the peer" is wrong because DH only agrees on a value; the page says** "Nothing about who is on the other end… Eve can sit in the middle, replace Alice's public value with her own when talking to Bob (and vice versa)", and "bad primes or unvalidated public values enable small-subgroup attacks that leak the private exponent."
12. **"One RSA key pair can encrypt and also sign, or validating a chain is just checking one signature" is wrong on both counts; the page says** "NIST FIPS 186-5 states that an RSA signature key pair shall not be used for other purposes such as key establishment" ("One key pair, one job"), and chain validation must also check validity windows, the requested name in subject/SAN, key usage and revocation — "an expired certificate is invalid even if every signature checks out" and "ignoring key usage is a real vulnerability class."

## 4. TESTABLE CLAIMS (each tagged with its anchor)

1. Encryption provides confidentiality only: it does not prove a message is unchanged (integrity), new (freshness), or sent by a claimed party (authenticity). — `chapter5-study.html#sec-why`
2. A replay attack requires neither understanding nor modification: the identical ciphertext bytes are re-sent later and still decrypt correctly, so the missing guarantee is freshness, fixed with a nonce, timestamp or sequence number. — `chapter5-study.html#sec-why`
3. A cryptographic hash is deterministic, fixed-length, one-way, efficient, and shows the avalanche effect; it has no key and no decryption, so it is not encryption. — `chapter5-study.html#sec-hash`
4. Expected classical work is about 2^n for pre-image and second-pre-image resistance but only about 2^(n/2) for collision resistance, making collisions the cheapest attack (the birthday effect). — `chapter5-study.html#sec-hash`
5. Password storage must use a tunable-cost password-hashing function or KDF (Argon2id, scrypt, bcrypt, PBKDF2) with a salt, never raw SHA-256 and never an unsalted hash. — `chapter5-study.html#sec-hash`
6. A MAC is a keyed tag with three operations — KeyGen produces K, Tag(K, M) → T, Verify(K, M, T) → {0,1} — and it gives integrity plus sender authenticity only between parties who share K. — `chapter5-study.html#sec-mac`
7. HMAC(K, m) = H((K₀ ⊕ opad) ‖ H((K₀ ⊕ ipad) ‖ m)) with ipad = 0x36 and opad = 0x5c repeated B times (B = 64 bytes for SHA-256); the nested structure avoids the weaknesses of a naive H(K ‖ m). — `chapter5-study.html#sec-mac`
8. A MAC cannot support public verification and gives no replay protection by itself; sharing K with millions of verifiers lets any one of them forge a tag everyone accepts. — `chapter5-study.html#sec-mac`
9. A digital signature uses one private signing key and many public verification keys; it provides integrity, origin authentication and public verifiability but no confidentiality. — `chapter5-study.html#sec-signatures`
10. Raw textbook RSA signatures are malleable and must be replaced by an approved encoding such as PSS; RSA-PSS, ECDSA and EdDSA are the FIPS 186-5 options. — `chapter5-study.html#sec-signatures`
11. RSA keys: n = p·q, φ(n) = (p−1)(q−1), e·d ≡ 1 (mod φ(n)); publish (n, e) and keep (n, d), p, q and φ(n) secret; FIPS 186-5 requires a modulus of at least 2048 bits, p and q of equal bit length, and 2^16 < e < 2^256. — `chapter5-study.html#sec-pubkey`
12. RSA is not used for bulk data: its asymmetric step is "orders of magnitude slower than AES", so hybrid encryption wraps a short session key with RSA-OAEP and protects the payload with AES-GCM or ChaCha20-Poly1305. — `chapter5-study.html#sec-pubkey`
13. Diffie-Hellman exchanges A = g^a mod p and B = g^b mod p so both sides compute K = g^(ab) mod p through a KDF, then protect traffic with an AEAD cipher. — `chapter5-study.html#sec-dh`
14. Unauthenticated Diffie-Hellman establishes a shared secret with an unknown party; an active attacker runs two exchanges and sits in the middle, so identity needs a certificate or signature. — `chapter5-study.html#sec-dh`
15. Ephemeral Diffie-Hellman (ECDHE) is the default because discarding per-session exponents means a later long-term key compromise does not reveal past session keys (forward secrecy). — `chapter5-study.html#sec-dh`
16. Key length is not security level: RSA-2048 is assessed at about 112 bits, RSA-3072 at about 128 bits, and a 256-bit elliptic curve at about 128 bits, because the best known attacks are factoring and discrete logarithm, not brute force. — `chapter5-study.html#sec-dh`
17. A valid signature proves control of a private key, not whose key it is; without a trusted binding an attacker can substitute her own public key and every mathematical check still passes. — `chapter5-study.html#sec-trust`
18. Chain validation must build a path to a locally trusted root, verify each signature, check each validity window, check the requested name in the subject or SAN, and check revocation (CRL or OCSP) and key usage. — `chapter5-study.html#sec-trust`
19. Primitive selection follows the guarantee: hash = change detection with no key; MAC/HMAC = shared-key integrity and authenticity; signature = public verification by anyone; AEAD = confidentiality plus integrity under a shared secret. — `chapter5-study.html#sec-tools`
20. Modular exponentiation is easy forward by repeated squaring (about O(log x) multiplications) and hard backward: the discrete logarithm problem for Diffie-Hellman and integer factorisation for RSA. — `chapter5-math.html#sec-m-mod`
21. The birthday bound q ≈ 1.177·√(2^n) ≈ 2^(n/2) explains why MD5 and SHA-1 fell first: their collision margins were the smallest and collision resistance is what signatures and certificates depend on. — `chapter5-math.html#sec-m-hash`
22. Entropy is H_key = log₂ N bits; hashing adds none, so a 30-bit-entropy password hashed with SHA-256 still has 30 bits of guessability. — `chapter5-math.html#sec-m-hash`
23. Hash-then-sign is secure and necessary: a collision-resistant fixed-length digest commits to the whole message, keeps the slow asymmetric operation to one short input, and binds the signature to the exact bytes. — `chapter5-math.html#sec-m-sign`
24. ECDSA's per-message secret k must be fresh and secret; reuse lets the private key be recovered from two signatures by algebra, so FIPS 186-5 requires a new k (deterministic generation is permitted). — `chapter5-math.html#sec-m-sign`
25. The decision table's failure modes are precise: a hash fails when the attacker replaces the message *and* the digest; a MAC fails when the key leaks or a co-holder forges; a signature fails when the public key is substituted or the scheme is raw RSA; AEAD fails when the nonce is reused; DH fails when it is unauthenticated or its parameters are weak; a certificate fails when a trusted CA is compromised or validation is skipped. — `chapter5-math.html#sec-m-tools`

## 7. FLASHCARD SEEDS (7 front/back pairs)

1. **Front:** What does encryption guarantee, and what three guarantees does it not provide? **Back:** It gives confidentiality — it hides the content. It does not prove the message is unchanged (integrity), new (freshness), or created by the claimed sender (authenticity). *(sec-why)*
2. **Front:** Name the three hash-security properties and their expected classical work for an n-bit digest. **Back:** Pre-image resistance ≈ 2^n (find the input from a digest); second-pre-image resistance ≈ 2^n (find another input matching a given one); collision resistance ≈ 2^(n/2) by the birthday effect — collisions are the cheapest attack. *(sec-hash, sec-m-hash)*
3. **Front:** Write the HMAC construction and say what K₀, ipad and opad are. **Back:** HMAC(K, m) = H((K₀ ⊕ opad) ‖ H((K₀ ⊕ ipad) ‖ m)); K₀ is the key zero-padded to block size B (or hashed first if longer); ipad is 0x36 repeated B times and opad is 0x5c repeated B times — B = 64 bytes for SHA-256. *(sec-mac, sec-m-hash)*
4. **Front:** Why does a MAC fail for a software update that millions of users must verify, and what replaces it? **Back:** Every user would hold the shared key K, and "anyone holding K can forge a valid tag for a fake update"; public verification requires a digital signature, where one private key signs and anyone with the public key verifies. *(sec-mac, sec-signatures)*
5. **Front:** What does a digital signature prove, and what does it not prove? **Back:** It proves integrity, control of the signer's private key (origin authentication), and it can be verified publicly by anyone — it does not hide the message, and it does not by itself prove identity or non-repudiation: "A valid signature proves control of a private key; the certificate says whose key it is." *(sec-signatures, sec-trust)*
6. **Front:** Trace RSA with p = 61, q = 53, e = 17, m = 65. **Back:** n = 61 × 53 = 3233 (12 bits); φ(n) = 60 × 52 = 3120; gcd(17, 3120) = 1; d = 17⁻¹ mod 3120 = 2753 because 17 × 2753 = 46 801 = 15 × 3120 + 1; c = 65^17 mod 3233 = 2790 (65^16 ≡ 789, 789 × 65 = 51 285 ≡ 2790); decrypt 2790^2753 mod 3233 = 65. *(sec-pubkey, sec-m-rsa)*
7. **Front:** Trace Diffie-Hellman with p = 23, g = 5, a = 6, b = 15. **Back:** A = 5^6 mod 23 = 8; B = 5^15 mod 23 = 19 (5^12 ≡ 18, 18 × 10 = 180 ≡ 19); ord(5) mod 23 = 22 and 90 = 4 × 22 + 2, so K = 19^6 = 8^15 = 5^90 ≡ 5^2 = 2 (mod 23); Eve sees p, g, A, B and faces a 22-candidate search here, about 2^256 in a real 256-bit group. *(sec-dh, sec-m-dh)*

## 8. INCONSISTENCIES / AUTHORING CAUTIONS OBSERVED

- `#sec-why` lead says "the two attacks that confidentiality alone does not stop", while its own table lists three (message modification, replay, forgery). All three are testable; treat "two" as loose prose.
- The `#ix-key-race` subtitle says "a 2048-bit RSA key gives roughly the protection of a 128-bit symmetric key", but its own row for RSA-2048 is 112 bits, the `#sec-dh` insight box says "roughly 112 bits", and the math table (`chapter5-math.html#sec-m-rsa`) says 2048 ↔ "About 112 bits" / "3DES-class strength". Author questions against 112 (and 3072 ↔ AES-128); avoid the subtitle wording.
- The study-page DH step 3 arithmetic writes "B ≡ 18 × 10 = 180 ≡ 180 − 161 = 19" (161 = 7 × 23) while the math page writes "180 ≡ 180 − 7 × 23 = 19"; both are the same reduction. Similarly "100 − 92 = 8" vs "100 − 4 × 23 = 8". No numeric conflict.
- `#sec-hash` says MD5 and SHA-1 are "do not choose: collision resistance is broken", while `#sec-m-hash` labels SHA-1 "Legacy only; do not choose" with collision work "about 2^80 — broken in practice". Consistent.
- The math page is explicit that the toy DH example's search space (22 candidates) shows "the mechanism, not the security"; do not present toy parameters as secure parameters.
