#### `#sec-software` — What Software Security Is
- The deck's working definition, quoted: "security is an engineering property across the complete software lifecycle — *design, develop, test and maintain software so it resists attack and protects users' data*".
- Definition box (quote): "The set of engineering practices that keep a system trustworthy while it is under attack, applied continuously from requirements to maintenance. It has two halves that the deck keeps together: **prevent vulnerabilities before deployment**, and **continue protecting the system after deployment**."
- CIA triad applied at the software layer: Confidentiality = "Prevent unauthorised disclosure of the data the system stores, moves or logs" (controls: authentication, authorisation, encryption in transit and at rest, masking, least privilege); Integrity = "Prevent unauthorised change to data, to configuration and to the code path that processes them" (constraints, transactions, input validation, signed artefacts, audit logs); Availability = "Sustain dependable access for authorised workloads" (replication, capacity planning, rate limiting, graceful degradation, DoS resistance).
- The security mindset, three bullets: "Assume the input is hostile, the dependency is stale and the default is unsafe." / "Ask what the system *trusts*, then ask why it should." / "Treat security as a property of the process, not a feature to be added late."
- Why secure systems still get hacked: "a **software weakness**, a **configuration issue** or a **dependency** gave the attacker a way in. Many major breaches exploit software vulnerabilities rather than breaking cryptography — so 'we use TLS' is not a security answer."
- Exam framing callout: "never answer 'software security is encryption and penetration testing'. The markable version names the lifecycle scope and the two halves — prevent before deployment, detect and respond after it — and then gives one example of each."
- Quick-check answer: the correct statement is "An engineering property maintained across the complete lifecycle, before and after deployment"; the distractors are "encrypting data at rest and in transit" (cryptography is one control among many; the deck's incidents were exploited through software and dependency weaknesses, not by breaking encryption) and "the final penetration test that certifies a release" (a pen test is one layer of defence in depth, "far too late to be the definition").

#### `#sec-lifecycle` — Where Vulnerabilities Come From
- Lead: "The deck's central diagram: a vulnerability can be introduced — or removed — at every lifecycle stage, and each stage has a characteristic defect."
- Six stages (numbered 0–5) and their characteristic defects / running-system appearance:
  - 0. Requirements — "Abuse case omitted" — "Nobody specified how the system must behave when a user lies, replays or escalates, so 'undefined' becomes the behaviour."
  - 1. Design — "Trust boundary missed" — "A component accepts data from a zone it was never meant to trust; privilege sits in the wrong tier."
  - 2. Implementation — "Unsafe data handling" — "Input is concatenated into a command, or content is written into a page unencoded."
  - 3. Testing — "Adversarial path skipped" — "Tests prove the happy path works; nobody tried to make the system fail in an interesting way."
  - 4. Deployment — "Insecure default" — "A debug endpoint, sample account or permissive rule ships enabled because it was convenient in development."
  - 5. Maintenance — "Patch delayed" — "A known vulnerability stays unpatched while a working exploit is public and scanning for it is automated."
- Cost argument (quote): "the later a defect is discovered, the more architecture, data and operations may already depend on it." A missing trust boundary found in design costs a conversation; the same defect found in production costs "an incident, a migration and a disclosure".
- Quick-check answer: a sample administrator account left enabled and reachable is an **insecure default at the deployment stage** (not unsafe data handling at implementation, not patch delayed at maintenance).

#### `#ix-sdlc` (interactive sequence) — "Order the secure development lifecycle"
- Six ordered steps: (1) "Elicit security requirements, including abuse cases and misuse scenarios"; (2) "Model the threats and draw the trust boundaries between components"; (3) "Implement against secure coding standards: separate data from code, fail safely"; (4) "Test the adversarial paths, not only the happy path; review the risky code"; (5) "Deploy hardened defaults with every unnecessary capability switched off"; (6) "Maintain: patch, monitor, re-assess and feed findings back into requirements".

#### `#sec-owasp` — Common Weaknesses and the OWASP Top 10
- Five headline weaknesses with their OWASP (2021) mapping and the trust mistake:
  - SQL injection — "Data becomes a database command" — **A03: Injection** — "User input is trusted as SQL syntax".
  - Cross-site scripting — "Content becomes browser code" — **A03: Injection** — "User content is trusted as markup and script".
  - Broken access control — "Identity is mistaken for authority" — **A01: Broken Access Control** — "A valid session is trusted as a permission".
  - Security misconfiguration — "Unsafe capability is exposed" — **A05: Security Misconfiguration** — "Defaults are trusted to be safe".
  - Vulnerable components — "Inherited supply-chain risk" — **A06: Vulnerable and Outdated Components** — "A dependency is trusted to be current and benign".
- Shared root cause, in the deck's words (quote): "the system trusts data, identity, configuration or dependencies more than it should."
- Full 2021 list A01–A10 with the deck's marks (Illustrated = A01, A03, A04, A05, A06; Related = A02, A07, A08, A09, A10):
  - A01 Broken Access Control — "Users act outside their intended permissions: missing checks, insecure direct object references, privilege escalation" (Illustrated).
  - A02 Cryptographic Failures — "Sensitive data exposed through weak, missing or misapplied cryptography and poor key handling" (Related).
  - A03 Injection — "Untrusted data is interpreted as part of a command or query: SQL, NoSQL, OS command, template, and XSS in the browser" (Illustrated).
  - A04 Insecure Design — "The design itself misses abuse cases, trust boundaries or business-logic limits — no amount of correct code fixes it" (Illustrated).
  - A05 Security Misconfiguration — "Unnecessary features, default accounts, verbose errors, missing hardening and permissive cloud or CORS settings" (Illustrated).
  - A06 Vulnerable and Outdated Components — "Libraries, frameworks and platforms with known vulnerabilities that nobody tracked or patched" (Illustrated).
  - A07 Identification and Authentication Failures — "Weak credential handling, absent MFA, session fixation and reusable credentials" (Related).
  - A08 Software and Data Integrity Failures — "Code and data accepted without verifying provenance: unsigned updates, insecure deserialisation, CI/CD supply chain" (Related).
  - A09 Security Logging and Monitoring Failures — "Breaches go undetected because nothing is logged, retained or alerted on — the run-time half of the week" (Related).
  - A10 Server-Side Request Forgery — "The server is tricked into making requests on the attacker's behalf, reaching internal services" (Related).
- Quick-check answer: the root cause is "The system trusts data, identity, configuration or dependencies more than it should"; wrong distractors are "attackers always find a way around weak cryptography" (A02 is a real category but the deck's five are not cryptographic failures) and "developers are not trained to write secure code" (a cause of individual bugs, not the structural explanation).

#### `#ix-rootcause` (interactive matcher) — "Match the weakness to what the system wrongly trusts"
- Seven pairs: SQL injection → "User input trusted as SQL syntax"; Cross-site scripting → "User content trusted as browser code"; Broken access control → "A valid session trusted as an authorisation decision"; Security misconfiguration → "A default setting trusted to be safe"; Vulnerable components → "A dependency trusted to be current and benign"; Insecure design → "An abuse case or trust boundary that was never modelled"; Logging and monitoring failures → "An attack trusted to announce itself".

#### `#sec-defence` — Defence in Depth: Build Time and Run Time
- Lead: "six layers of controls that work together across the lifecycle. Layered controls stop one missed defect from becoming a successful attack."
- Six layers with their one-word role (`#ix-layers`): Secure coding — **PREVENT** ("write code that keeps data separate from commands and fails safely"); Testing — **CHALLENGE** ("attack your own assumptions with adversarial tests"); Static analysis — **INSPECT** ("read code and data flow without running it (SAST)"); Dynamic analysis — **PROBE** ("exercise the running system and its dependencies (DAST, fuzzing, scanning)"); Monitoring — **OBSERVE** ("logs, metrics and traces; the evidence that something changed"); IDS / IPS — **DETECT / BLOCK** ("signatures and anomalies, alerting or intervening inline").
- Layer table (when / strongest against / blind to): Secure coding (Build; whole classes of injection, encoding and authorisation mistakes; "The mistakes you did not notice making"); Testing (Build; logic, specification and integration errors on the paths you thought of; "The paths nobody thought to test"); Static analysis (Build; tainted data flow, unsafe APIs, known-bad patterns across the whole codebase; "Configuration, runtime state; it also produces false positives that must be triaged"); Dynamic analysis (Build / pre-release; real behaviour: authorisation gaps, dependency versions, runtime errors; "Code paths that the probe never reaches"); Monitoring (Run; knowing that something happened at all, and reconstructing it afterwards; "Attacks that look like ordinary traffic"); IDS / IPS (Run; known attack patterns, and inline blocking of them; "Novel behaviour; false positives that cost availability").
- Caveat quoted: "defence in depth only pays off when the layers are genuinely independent. If the same vulnerable library sits in the web tier, the job runner and the report generator, one supply-chain defect defeats three 'layers' at once. That is why vulnerability management (later in this page) is a security control and not just housekeeping."
- Quick-check answer: the layer that reports an attack happening "right now" is "Monitoring plus IDS/IPS, the run-time half of the deck's bar"; secure coding and static analysis are build-time and produce no signal about the running system.

#### `#sec-database` — Database Security: Crown-Jewel Data
- Definition (quote): a database is "A managed system for **storing, relating, querying and updating persistent data**" — "more than files: it enforces structure, relationships, transactions, concurrency and controlled access to shared state."
- Relational: "Tables, rows, columns and constraints. Structure is declared up front and enforced by the engine; queries are expressed in SQL." Named: PostgreSQL, MySQL.
- Non-relational: "Documents, key-value pairs, graphs or wide columns. Structure is often carried by the application, which moves part of the validation burden into code." Named: MongoDB, Redis, Neo4j.
- Security implication (quote): "a compromise affects not only the stored records, but *every application and decision that depends on them*. The database is where the consequences of a small software defect become population-scale."
- Four crown-jewel data classes (`metric-grid`): Personal data ("Identity, contact and behavioural records — the material of identity theft and surveillance"); Financial data ("Payments, transactions and account history, which are also regulated"); Credentials ("Passwords, tokens and access secrets — stealing these converts one breach into many"); Intellectual property ("Research, source data and commercial knowledge, where the loss cannot be undone by reissuing a card").
- Data-layer goals, in the deck's wording: Confidentiality — "Only authorised subjects can view specific data" (authentication, least privilege, encryption, masking); Integrity — "Data remains accurate, valid and traceable" (constraints, transactions, validation, audit logs); Availability — "Authorised workloads can access data when required" (replication, backup, recovery, capacity and DoS resistance).
- Objective (quote): "controlled, correct and dependable use of data — not merely keeping attackers outside. A database that nobody can query is not secure; it is unavailable."
- `#ix-db-map` (interactive hotspot over an SVG) — title "One request, seven places to get it wrong" (the JSON actually lists **nine** hotspots — see §2b). The SVG shows: User / browser ("untrusted input") → Web application tier (three boxes: "input handling and validation", "query construction", "session and identity store") → Database server (service accounts, crown-jewel tables, audit log) plus Backups and replicas ("a second copy of everything"), Operations and admin path ("migrations, exports, support access … legitimate access that can be abused … and is rarely monitored as closely"), and Monitoring and IDS ("log collection, alerting … and detection of what prevention missed").
- The nine hotspots and their controls: (1) Untrusted input at the browser boundary — "Everything arriving from the client is attacker-controlled: form fields, headers, cookies, file names, JSON bodies… never treat client-side checks as a control." (2) Query construction — "if the statement string is assembled from user data, input can become syntax. Fix the structure first and bind the data into it." (3) Session and identity store — "Identity is not authority. A valid session says who the caller is; an authorisation check on every object is what says what they may do. Confusing the two is broken access control (OWASP A01)." (4) Database service accounts — "least privilege … a read-only account for reporting, no schema-changing rights for the web tier, no shared administrator credential." (5) Crown-jewel tables — encryption at rest, column-level masking for non-production copies, row-level access rules. (6) Audit log — "who read or changed what, when, and under which identity … somewhere an attacker with application access cannot rewrite." (7) Backups and replicas — "often with weaker controls … Encrypt them, restrict who can restore them, and test the restore — an untested backup is a claim, not a control." (8) Operations and admin path — "Insider misuse lives here: least privilege, separation of duties, just-in-time access and the same logging standard as the application." (9) Monitoring and IDS sensor — "Centralised logging plus host and network intrusion detection is what turns a quiet compromise into an alert."

#### `#sec-injection` — SQL Injection: When Data Becomes a Command
- Mechanism (quote): "malicious input changes the SQL query executed by an application. The attack succeeds when user-controlled text is interpreted as SQL syntax."
- Key message (quote): "attackers exploit insecure *application code* — not the database itself. The database faithfully executes the statement it was given; the application built the wrong statement."
- Four-stage walkthrough: (1) Normal input — "Username: alice" — "A username that matches one row"; (2) Malicious input — "the lecture's canonical illustration is the tautology `alice' OR '1'='1`" — "Still just text in a form field"; (3) Executed query — "The application concatenates the value into the statement, so the appended text is parsed as SQL rather than as data" — "A `WHERE` clause that is true for every row"; (4) Result — "Authentication bypass, unauthorised data access".
- The page notes the illustration "is the classic teaching example used in the deck and in the OWASP guidance it cites… the control that removes the mechanism is parameter binding".
- Structural fix contrast: string concatenation `"SELECT * FROM users WHERE username='" + username + "'"` — "The statement is a function of user input. Nothing separates the two." versus the prepared statement `cursor.execute("SELECT * FROM users WHERE username=?", (username,))` — "The statement is a constant. Only the parameter varies, and it can never be parsed as SQL."
- Four controls paired with binding: **Prepared statements** ("the structural defence; use them everywhere, including in reporting and admin tooling"); **Input validation** ("constrain what the field may contain (type, range, syntax)"); **Least privilege** ("limit what the database account can do; a reporting account that cannot modify schema is not a route to mass deletion"); **ORM frameworks** ("safe query APIs by default, but only when they are used correctly: raw fragments and string-built filters reintroduce the flaw").
- What is *not* the fix: "Escaping quotes by hand — encoding context varies and denylists are famously incomplete"; "Client-side validation alone — the attacker simply does not use your form"; "A web application firewall alone — a useful additional layer, but the code still trusts input as syntax"; "Hiding error messages — it reduces information leakage, not the injection".
- Input-handling table: Username → "Letters and numbers only" → "Reject characters outside the allowlist"; Age → "Integer from 0 to 120" → "Parse as a number; enforce the range"; Email → "Valid email structure" → "Use a trusted email validator"; Comments → "Text, not executable markup" → "Encode HTML output; sanitise only if HTML is genuinely allowed".
- Two rules kept separate (quote): "Validation decides *what a field may contain*; parameter binding decides *how the statement is assembled*. Only the second removes the injection class, because validation can be bypassed by any path that reaches the query builder — an internal API, a batch job, a support tool. The deck's motto covers both: *separate user input from SQL commands*, and *validate input before processing, encode before output*."
- Quick-check answer: a team blocking single quotes and the word `OR` is not fixed "because denylists are incomplete and bypassable, while parameter binding makes the statement structure independent of input". Not performance, and not "hide error messages".
- `#sol-1` — "Worked example — triaging a suspected injection defect" (search field "returns rows that do not match what I typed"), five steps: (1) "Find the construction, not the payload… the question is not 'what did they type?' but 'is the statement string a constant?'"; (2) "Check every route to that code… Injection is fixed per query builder, not per screen"; (3) "Fix structurally… Where dynamic identifiers are genuinely required (a sort column, for example), map them through an allowlist rather than binding them — parameters carry values, never structure."; (4) "Add the layers the deck lists… least privilege on the database account (the web tier rarely needs `DROP` or unrestricted `SELECT` across schemas), ORM query APIs used correctly, and a regression test that asserts the structure is constant."; (5) "Assume it was used, then verify… review the audit log for unusual query patterns and volumes… confirm the fix in the deployed environment rather than only in the branch."

#### `#sec-inference` — Inference Attacks and Privacy Leakage
- Definition (quote): "An attack in which the adversary does **not bypass access control** but learns sensitive information indirectly, by combining answers to legitimate queries. The deck classifies it as an *indirect* database threat, next to SQL injection's direct manipulation of the query."
- Minimal example: "a permitted query filters on a secret it never returns: a query of the form `... WHERE username = 'alice' AND salary > 100000` produces either a row or no row… The salary is never disclosed. The *existence of a result* answers the question anyway."
- Why "no result" is still an answer: "Each answer carries little information — at most one bit. But a sequence of low-information answers can reveal a high-value secret, because the attacker chooses the questions and keeps the ones that narrow the space." Hence "the mitigation is about what the system is willing to answer, not only about who may ask."
- Design consequence (quote): "aggregation and filtering are themselves disclosure decisions. If a view can isolate a group small enough to be identified, it is an inference channel even when every field in it is legitimate."
- Conference-reviewing case study: three privacy rules were already in place — "reviewers are anonymised, authors must not see discussion of their own submission, and reviewer identities are visible only to co-reviewers of the same paper" — and the system still leaks once it "publishes a procrastination chart of progress over time".
- Four leakage channels: Named progress lines → "Identity signal: the chart label attaches a person to a behaviour" → publish aggregate or binned series only, remove names before rendering. Review counts per paper → "Assignment clue: how many reviewers a paper had, which narrows who they were" → suppress counts below a threshold or bucket coarsely. Distinct progress patterns → "Behavioural fingerprint: a distinctive curve is recognisable even without a name" → bin the time axis, smooth the series, delay release until after decisions. Combination of the three → "Linkage attack: match reviewer behaviour to per-paper counts to infer who reviewed what" → "Evaluate views in combination, not one at a time; apply a minimum anonymity-set size before release".
- Two sentences flagged to quote: "individually harmless signals become identifying when combined", and "inference risk grows as the anonymity set becomes smaller"; the shorthand is "a view over *k* indistinguishable people supports re-identification at a rate of roughly *1/k*".
- `#ix-inference` (race) "Relative inference risk by publication choice": illustrative 0–100 scores, not measured data — Aggregate average progress, large cohort = 8 ("low"); Coarse progress bins, no names, delayed = 25 ("moderate"); Per-paper review counts published = 45 ("elevated"); Named individual progress lines = 85 ("identifying"); Named lines plus per-paper counts = 100 ("linkable").
- Quick-check answer: the clearest inference channel is "A yes/no answer to a filtered query that isolates one person" (one bit per question, attacker chooses the questions); a count over a large population is the low-risk case, and masking a sensitive column does not help "because the attack in question never needed the value: it exploits the pattern of results and metadata around it".
- `#sol-2` — "Worked answer — auditing an analytics dashboard before release", five steps: (1) "Enumerate the views, not the tables… A dashboard is an access-control decision expressed as a layout."; (2) "Ask what each view reveals and to whom… Existence and timing answers are the ones teams forget"; (3) "Find the join key… If two panels can be joined on a person, a paper, an account or a time window, treat the combination as the release unit."; (4) "Change the view, not the honesty of the users. Suppress groups below a minimum size, bin or smooth the axes, delay publication until the outcome is fixed, and drop identifiers before rendering. Where a filtered query is the risk, replace it with a pre-aggregated result the requester cannot vary."; (5) "Write the release rule and test it adversarially. State the threshold ('no published view may isolate fewer than *k* subjects'), then try to break it as an insider would… Log the queries so that anomalous enumeration is detectable after the fact."

#### `#sec-xss` — Cross-Site Scripting: Content Becomes Code
- Lead: "XSS is injection with the browser as the interpreter, and the asset being stolen is the user's trust in a site they have every reason to trust."
- Mechanism (quote): "the vulnerable site delivers attacker-controlled JavaScript to a trusted user's browser. The browser trusts the website, not the attacker — so if the website serves malicious code, the browser executes it anyway."
- One input, two outcomes: "The same comment field can display text or execute code, depending only on how the output is handled. If output is not encoded, **data becomes code**." Harmless illustration used: `<script>alert("INFO5995")</script>`.
- Three content sources: **Stored** — "the site saves the content and serves it to other users later"; **Reflected** — "the site copies the content from the request straight into the response"; **Client-side** — "the page's own script writes untrusted data into the document (the unsafe-DOM case the deck warns about)".
- Four dangers: Session theft — "Steal tokens or impersonate the user without ever learning their password"; Unauthorised actions — "Submit requests as the victim, with the victim's permissions and audit trail"; Phishing — "Replace trusted content with a deceptive interface inside the real site's origin"; Data exfiltration — "Read the page data the victim can see and transmit it elsewhere".
- Framing (quote): "XSS does not 'hack the browser'. It abuses the browser's trust in a vulnerable application — code executes in the security context of the trusted website."
- Four prevention layers: (1) **Encode output** — "Convert `<`, `>`, `&`, quotes and other characters to safe equivalents at the point of output, in the right context (HTML body, attribute, URL, script)"; (2) **Sanitise allowed HTML** — "When rich text is genuinely required, run it through a proven sanitiser with a strict allowlist — never a hand-written filter"; (3) **Use safe frameworks** — "Prefer auto-escaping templates and avoid unsafe DOM APIs that write strings as markup"; (4) **Add browser safeguards** — "Content Security Policy as an additional layer, so an injected script that slips through has nowhere to load from".
- Motto covering SQL injection and XSS at once: "validate input, encode output, keep data separate from code. Input validation is the same control in both cases; what changes is the interpreter whose grammar you must not let the data reach."
- Quick-check answer: the control that stops stored XSS is "Contextual output encoding through an auto-escaping template"; rejecting the word "script" is a denylist, and shortening sessions leaves the mechanism untouched.
- `#ix-xss` (interactive stepper, three stages): "The attack" — the site stores content (stored XSS) or copies it from the request straight into the response (reflected XSS), and "the browser receives it as part of a page it has every reason to trust"; the stepper's own labels add "The vulnerability is in the application, not in the browser", "origin: the site's security context", "the script runs with the victim's session", "No browser is hacked here: the application handed over code and the browser treated it exactly as the site's own", and "That is why XSS is an application defect with a user-facing consequence." "Why XSS is dangerous" — "Each of these is an ordinary action in the site's own origin." "Preventing XSS" — "Encoding is context-sensitive: HTML body, attribute, URL and script are different grammars", and closing with "Validate input. Encode output. Keep data separate from code."

#### `#sec-system` — System Security: Hardening the Deployed System
- Lead: "The lecture's second half changes the subject from building securely to running securely. Deployment changes the problem: the system is now reachable, observable and continuously attacked."
- Software vs system security table: Focus — "Build secure software" vs "Protect deployed systems"; Objective — "Prevent vulnerabilities" vs "Detect and respond to attacks"; When — "Development and testing" vs "Operation and maintenance"; Examples — "SQL injection, XSS" vs "IDS, IPS".
- The deployment-boundary diagram (inline SVG, `arch-diagram`): labelled "BEFORE DEPLOYMENT" (Design — "abuse cases, trust boundaries"; Build — "secure coding, review, SAST"; Test — "adversarial paths, DAST") and "AFTER DEPLOYMENT" (Run — "hardened defaults, least privilege"; Monitor — "logs, alerts, IDS"; Respond — "IPS, incident"), with a "deploy" marker between them and a dashed arrow captioned "attack surface changes with users, traffic, configuration and time". Bottom banner: "Prevention is not enough: the same lifecycle keeps going after the release" / "design - build - test - deploy - monitor - respond".
- Diagram caption (quote): "Everything left of the deployment boundary reduces the chance that a weakness exists; everything to the right reduces the time a weakness stays useful to an attacker."
- Five threat classes with controls: **Brute force** — "Repeated login attempts against the same accounts" — rate limiting, lockout with backoff, MFA, breached-credential checks, detection of distributed attempts. **Malware** — "Malicious code and ransomware" — patch management, least privilege, application control, endpoint detection, offline and tested backups. **Scanning** — "Discovery of exposed services" — minimise the attack surface, close unused ports and paths, segment networks, remove version banners. **Denial of service** — "Resource exhaustion" — capacity and quotas, upstream filtering, rate limits, graceful degradation, timeouts on expensive operations. **Insider misuse** — "Abuse of legitimate access" — least privilege, separation of duties, just-in-time access, audit logging, review of privileged activity.
- Hardening a deployed system (six items): "Secure defaults and baselines — the deployment-stage defect from earlier in the week"; "Remove what is not needed — services, accounts, sample data, debug endpoints"; "Least privilege — for people, services and the database accounts behind them"; "Segmentation and egress control — so a single foothold is not a network position"; "Centralised logging with retention — without it, detection and response have no raw material"; "MFA on every administrative path — including the ones that 'are only internal'".
- Vulnerability management as a control (five steps): **Identify** — "inventory components (a software bill of materials), scan hosts and images, watch advisories"; **Prioritise** — "combine severity with internet exposure, exploit availability and asset value"; **Remediate** — "patch, upgrade, or apply a documented compensating control when patching is impossible"; **Verify** — "rescan and regression-test; a closed ticket is not evidence"; **Report** — "track exposure window and mean time to remediate, not ticket counts".
- Why examinable (quote): "Equifax was an unpatched component and Log4Shell was a vulnerable library. Neither was a clever attack on cryptography; both were failures of the maintenance and dependency processes described here."

#### `#sec-detect` — Detection and Response: IDS and IPS
- Lead: "two technologies that inspect the same activity and differ only in what they are allowed to do about it."
- IDS definition (quote): "Observes host or network activity and **alerts** on suspicious behaviour. It sits on a monitoring path rather than in the traffic flow, and it *does not automatically stop the attack*. Think security camera: it sees the intruder and raises the alarm."
- IPS definition (quote): "Observes traffic like an IDS but sits **inline** and can automatically intervene: *inspect → decide → act*. It can block malicious traffic, drop suspicious packets, reset connections and quarantine hosts. Think security guard: it sees the intruder and blocks the door."
- Comparison table: Purpose — "Detect attacks" vs "Detect and block"; Action — "Generate alerts" vs "Automatically intervene"; Deployment — "Monitoring path" vs "Inline with traffic"; Response — "Passive" vs "Active"; Failure mode — "An attack proceeds while the team reads the alert" vs "A false positive becomes an outage, because the control is in the path".
- Where it watches: **HIDS** — "one computer or server: process, file, log and account activity"; **NIDS** — "traffic across a network segment: connections, protocols and payloads". Tools named in the deck: **Snort**, **Suricata**, **Zeek**.
- How it detects: **Signature-based** — "matches known attack patterns. Precise and explainable, but blind to anything not yet written down"; **Anomaly-based** — "flags deviation from normal behaviour. Can catch novel activity, at the cost of far more false positives". "Every deployment is a trade-off between the two, tuned against the base rate of real attacks on that network."
- Discussion question answered (quote): "would an IDS alone stop a brute-force login attack? No. An IDS is passive by design — it detects failures and alerts the team while the thousands of attempts continue. Stopping it needs an active control: an inline IPS, rate limiting and lockout on the authentication path, or MFA so that a correct guess is not sufficient. The IDS still earns its place, because it is what tells you the prevention layers are being tested."
- Quick-check answer: "Detection worked and prevention was missing: an IDS is passive, so blocking requires an inline IPS or controls on the login path" — the IDS is not misconfigured (blocking is not its job), signature databases do detect brute force, and the distributed sources show why per-IP blocking alone is insufficient.
- `#sol-3` — "Worked scenario — designing the control set for a public login endpoint", five steps: (1) "Classify the threat. Repeated login attempts are brute force; attempts against many accounts with previously breached passwords are credential stuffing. The distinction matters because credential stuffing defeats complexity rules and per-account lockout, and shows up as a low failure rate per account spread over many accounts."; (2) "Prevention first (build time). Rate limiting per account, per source and per subnet; lockout with exponential backoff rather than a permanent lock that becomes its own denial of service; MFA so a correct password is not sufficient; checks against known-breached credential lists; generic error messages so the response does not confirm which usernames exist."; (3) "Detection second (run time)… failure rate per account, distinct accounts per source, source diversity for one account, success immediately after a burst of failures, and authentication from an implausible location."; (4) "Response, decided in advance… an inline control that no one has tuned will eventually block a legitimate customer."; (5) "Measure what the control set actually buys… detection coverage, false-positive rate, alert volume against analyst capacity, time from first attempt to block, and the fraction of accounts protected by MFA… With MFA coverage at 40%, enrolment usually beats another detection rule."
- `#ix-detect` (interactive stepper): stages "The attack" (login endpoint, "1,000s of attempts"), "IDS — security camera" ("monitoring path, not inline"), and the discussion prompt "Discuss: would an IDS alone stop this attack?"; labels add "What is at stake: one correct guess is an account takeover, and the attempts are cheap because they are automated."

#### `#sec-m-defs` — Definitions and the risk model
- Definitions (quote): "A **vulnerability** is a weakness that can be used to violate a security property. An **exploit** is the means of using it. A **threat** is the actor or event that would do so. A **control** is anything that reduces the chance of success or the impact. Note the deck's usage: the weakness lives in the application, so the fix usually does too."
- Software vs system security (quote): "**Software security** builds secure software before deployment: focus, objective and activity all sit in development and testing. **System security** protects deployed systems: the objective changes from preventing vulnerabilities to detecting and responding to attacks, and the activity from development to operation and maintenance."
- Access control vs inference (quote): "**Direct attacks** (SQL injection) manipulate a query through unsafe input handling. **Indirect attacks** (inference) use queries the system permits and learn from what the answers reveal. The first is a defect in code; the second is a defect in what the system is willing to disclose."
- Risk model: R = T × V × I — T "the likelihood that a threat acts", V "the likelihood that a vulnerability is exploitable", I "the impact". "The product form is the examinable part: driving any one factor to zero removes that path, and reducing one factor without the others gives the attacker an easy substitute."
- Residual risk / defence in depth: "If a system has n independent controls and control i fails with probability p_i, the chance that *all* of them fail is R_res = I ∏ p_i". Worked: "Three layers each failing with p = 0.3 give 0.3³ = 0.027: the impact is reached in under 3% of attempts." Caveat: "the product assumes independence, and in software it is exactly what fails. If one vulnerable library appears in three of the layers, those three failures share a single cause and the product collapses towards the largest of them" — printed as R_res ≥ I ∏ p_i "with equality only when the layers are independent". "That inequality is why the deck treats vulnerable components and patch latency as security controls rather than housekeeping."
- Notation caveat (quote): "Week 8 is written in prose and diagrams. The symbols below are a *revision aid* introduced here so that the week's relationships can be written compactly; they are not lecture notation and should not be quoted as such. The one exception is TPR and FPR, which are standard detection terminology."
- Symbol grid (12 symbols): T threat likelihood — "How often an actor attempts the attack — risk model"; V vulnerability likelihood — "Whether the weakness is exploitable as found — risk model, prioritisation score"; I impact — "Consequence if the attack succeeds — risk and residual-risk models"; p_i layer failure probability — "Probability that control i fails — defence in depth"; W exposure window — "Days from exploitable to remediated — vulnerability management"; q daily compromise rate — "Probability an exposed host is compromised in a day — exposure risk"; π base rate — "Prior probability that an event is a real attack — detection arithmetic"; TPR true positive rate — "Fraction of real attacks detected — detection arithmetic"; FPR false positive rate — "Fraction of benign events flagged — detection arithmetic, IPS tuning"; k anonymity set — "Indistinguishable subjects behind a published view — inference and privacy"; H(X) entropy — "Information a signal carries, in bits — inference and privacy"; A, L, r alphabet, length, rate — "Secret alphabet size, secret length, guesses per second — brute-force costing".
- Quick-check answer: with three layers on the same unpatched base image, "The layers share a common cause of failure, so the product overstates the protection" — "Three layers always multiply to 0.027" is wrong because independence is the point, and "adding a fourth layer on the same image restores the independence assumption" is wrong because it adds cost without independence; the missing control is dependency and patch management.

#### `#sec-m-exposure` — Exposure windows and vulnerability management
- Exposure window printed as: W = t_exploit − t_patch, annotated "(negative means remediation happened first)"; and P(compromise) = 1 − (1 − q)^W where q is the daily compromise probability. (See §2b: the printed difference direction and the worked example disagree; the worked example uses deployment day minus exploit day.)
- Worked example: exploit published on day 0, patch available day 5, organisation's median deployment time 30 days, "so W = 30 − 0 = 30 days for the affected hosts"; with q = 0.01, P(compromise) = 1 − 0.99³⁰ ≈ 1 − 0.740 = 0.26 — "Roughly a one-in-four chance per host, from timing alone."
- Change one variable: "Deploy the same patch in 7 days instead of 30: 1 − 0.99⁷ ≈ 0.068, about 7%. Cutting the window by 77% cuts the risk by roughly 74%."
- Model limits (quote): "q is a modelling assumption, not a measurement, and compromise events are correlated (one worm sweeps every exposed host). The examinable conclusion is the monotonic one: risk rises with the window, so *time to remediate is a security parameter*."
- Metrics: mean time to remediate MTTR = (1/n) Σ t_i; coverage C = "assets remediated / assets affected"; prioritisation score S = severity × exposure × exploitability. "Ticket counts and 'percentage of findings closed' are activity measures: they improve when a team closes easy findings. W, MTTR and C are exposure measures, and they improve only when the risky assets actually change."
- Quick-check answer: with equal CVSS severity, fix the internet-facing, publicly-exploitable finding first — "Severity is one factor in the prioritisation score. Public exploit code plus internet exposure means A's window is already open and being scanned; B's risk is real but not yet reachable by an automated attacker." Fixing "whichever is quicker" is wrong because prioritising on closure rate is not risk-based.
- `#ix-m-vulnmgmt` (sequence) — six steps: "Inventory the components and versions that are actually deployed"; "Prioritise by severity, internet exposure, exploit availability and asset value"; "Remediate: patch, upgrade, or apply a documented compensating control"; "Verify by rescanning and regression-testing the affected paths"; "Report exposure window, mean time to remediate and coverage - not ticket counts"; "Feed what was learned back into requirements, design and dependency policy".
- `#sol-m1` — "Worked answer — ranking three findings with the prioritisation score" (values 1–5, invented for the exercise): vulnerable library on the public web tier = 4 × 5 × 5 = **100**; missing authorisation check on an internal admin API = 4 × 2 × 4 = **32**; outdated TLS configuration on a legacy printer = 3 × 1 × 1 = **3**. Notes: "S = 100 for the library means an automated attacker can reach it today. S = 32 for the authorisation gap is lower only because the API is not internet-facing — and a single foothold would change that exposure factor from 2 to 5, making it the top finding. Scores are a snapshot of the estate, not of the code."; "if it holds credentials or is reachable from the user network, the *exposure* estimate is wrong, not the finding"; "If the library is patched in 3 days and the admin API in 14, the two exposure windows are W₁ = 3 and W₂ = 14 against the same q, so the API's residual risk is the larger of the two even though its score is smaller. Ranking decides the order; the window decides the outcome."

#### `#sec-m-detection` — Detection arithmetic: why an IDS is noisy
- Confusion matrix in rates: TPR = TP/(TP+FN); FPR = FP/(FP+TN). "TPR (the detection rate) is what the vendor quotes. FPR is what determines the workload, because the numerator of the false-positive rate is multiplied by an enormous number of benign events."
- Precision / base-rate fallacy: with base rate π = P(attack), P(attack | alert) = TPR·π / (TPR·π + FPR·(1 − π)). "This is Bayes' rule, and it is the reason a '99% accurate' detector can be wrong almost every time: when π is tiny, the second term in the denominator is dominated by the false-positive rate times the huge benign population."
- Worked example: N = 1,000,000 events/day; π = 10⁻⁴ → "100 attacks and 999,900 benign events"; detector TPR = 0.90, FPR = 0.001 → "TP = 0.90 × 100 = 90", "FP = 0.001 × 999,900 ≈ 1000"; "the team receives about 1090 alerts a day to find 90 real ones"; precision = 90/1090 ≈ 8.3%; the page adds "Roughly eleven alerts for every real attack" (recomputed 12.1 — see §2b); "This is not a broken detector; it is what a low base rate does to any detector."
- What improves the analyst's day: "Halving the false-positive rate to 0.0005 doubles precision to about 15%. Raising the detection rate to 0.99 adds 10 more true positives out of ~1100 alerts. Neither is as effective as *reducing the event population*: filtering the sensor to the authentication and egress traffic that matters cuts N by an order of magnitude and improves precision in proportion."
- Connect to the deck: "Signature-based detection usually has a lower false-positive rate on known patterns; anomaly-based detection can reach attacks nobody wrote a signature for, at a much higher false-positive cost… an IPS makes the choice expensive, because a false positive inline becomes an outage rather than a wasted alert."
- Alert capacity as a control parameter: "If an analyst can triage c alerts per day, the number of sensors you can deploy is bounded by c divided by the alert rate A = N[TPR·π + FPR(1−π)]. Beyond that bound, real alerts are missed because they are queued behind noise — the failure mode the deck describes as an attack continuing while the team reads the alert."
- Quick-check answer: with TPR = 0.99, FPR = 0.01 and π = 1 in 100,000, "Almost every alert will be a false positive, because the base rate is tiny" — "For every real attack the detector raises about 1000 false alerts, so only about 1 alert in 1000 is real." Recompute: precision = (0.99 × 10⁻⁵)/(0.99 × 10⁻⁵ + 0.01 × 0.99999) ≈ 9.9 × 10⁻⁶ / 1.00098 × 10⁻² ≈ 0.099% ≈ 0.1%.
- `#sol-m2` — "Worked answer — tuning one sensor": sensor generates 4,000 alerts/day, sampled triage suggests 20 are real, team can triage 400/day. (1) "P(attack | alert) ≈ 20/4000 = 0.5%. The problem is quantified, and it is not the team's speed."; (2) "For a web-tier sensor with prevention already in place, a missed attack is recoverable… On this sensor, reducing FPR is worth more than raising TPR."; (3) "Change the population and the rules, in that order. Restrict the sensor to authentication, authorisation failures and egress traffic; suppress signatures that can only fire on traffic the estate no longer runs; and require two conditions before alerting on a single event."; (4) "Set the target as precision, not sensitivity. A workable target on this sensor is precision above 20% at a volume under 400 alerts a day — that is, roughly 80 real detections a day."; (5) "If this sensor were an IPS, change the threshold again. Inline, a false positive is an outage, so the acceptable FPR is far lower and the rules must be narrower. That asymmetry — not the technology — is the real difference between the deck's security camera and security guard."

#### `#sec-m-privacy` — Inference, anonymity and the cost of guessing
- Every yes/no answer is at most one bit: "If the subject is one of k indistinguishable people (the **anonymity set**), then P(identify) ≈ 1/k and k′ = k / 2^m after m independent yes/no answers… To isolate one individual from k candidates therefore takes about ⌈log₂ k⌉ answers. This is why the deck says inference risk grows as the anonymity set becomes smaller, and why a combination of harmless signals is the dangerous case: each signal halves the field."
- Worked leakage chain: k = 200 reviewers, no names → 1/200 = 0.5%; add per-paper review counts → plausible set 20 → "a reduction of about 3.3 bits": log₂200 − log₂20 = 7.64 − 4.32 ≈ 3.3; add behavioural fingerprints → 8 distinguishable classes = "log₂8 = 3 more bits"; "Total leakage: about 6.3 bits, leaving an effective anonymity set of 200/2^6.3 ≈ 2.5 people. The linkage attack works because the bits *add*."
- Release rule: "For a target re-identification risk of at most 5%, the anonymity set must satisfy k ≥ 1/0.05 = 20 *after* every published signal is considered" — printed as k_effective ≥ 1/P_max.
- Entropy of a released signal: H(X) = −Σ p_i log₂ p_i. "Uniform over 8 classes gives H = 3 bits; a highly distinctive pattern (say one class with p = 0.9) gives H ≈ 0.57 bits." (See §2b: the p = 0.9 value is not reproducible at 0.57.) "Entropy is the right currency for inference because it composes: the combined leakage of independent signals is H(X) + H(Y), and it is bounded by the anonymity you intended to provide, log₂ k."
- Brute-force cost: N = A^L; T₅₀ = A^L / 2r; H = L log₂ A bits. Assumption quoted: "The model assumes the secret is uniformly random. Real passwords are not, which is why an attacker uses a ranked list instead of an exhaustive search — and why rate limiting, lockout and MFA matter more than length alone."
- Key-strength table (columns: Alphabet; Length L; Search space A^L; Entropy L log₂ A; T₅₀ at 10⁴ guesses/s): 10 (digits, a PIN), L = 4 → 10⁴, 13.3 bits, 0.5 s; 26 (lowercase), L = 8 → 2.1 × 10¹¹, 37.6 bits, 121 days; 36 (lowercase + digits), L = 8 → 2.8 × 10¹², 41.4 bits, 4.5 years; 62 (mixed case + digits), L = 12 → 3.2 × 10²¹, 71.5 bits, 5.1 × 10⁹ years; 94 (printable ASCII), L = 16 → 3.7 × 10³¹, 104.9 bits, 5.9 × 10¹⁹ years. (All five rows independently recomputed and confirmed — see §2c.)
- Worked exhaustive search: "A random 8-character lowercase-plus-digit password has 36⁸ ≈ 2.8 × 10¹² candidates. At r = 10⁴ guesses per second off-line, T₅₀ = 2.8×10¹²/(2×10⁴) ≈ 1.4×10⁸ s ≈ 4.5 years."
- Online case: "Rate limiting to 5 attempts per account per 15 minutes gives 480 attempts a day, so the expected time becomes 1.4×10¹²/480 ≈ 2.9×10⁹ days — millions of years. Policy, not entropy, did the work."
- Credential stuffing: "With 10,000 accounts and 5 attempts each that is 50,000 attempts: about *5 seconds* at 10⁴/s, and per-account lockout never triggers because each account sees only five failures. The defence is checking credentials against breach lists and requiring MFA — not adding a character class."
- Stated assumption: "T₅₀ measures a uniform search. If the password is one of the ten thousand most common, the expected time is seconds. Every brute-force answer should therefore name both the search model and the policy controls that bound online attempts."
- Quick-check answer: with per-team counts, a per-team time series and the team roster, the model is "Information accumulates: the signals together shrink the anonymity set below the intended size" — not a cryptographic failure and not availability.
- `#sol-m3` — "Worked answer — defending an internal analytics view" (5,000-person organisation; per-team activity counts, daily time series, "top contributor" list capped at three names per team): (1) team of 500 → k = 500 → 1/500 = 0.2% "is the number the design intends to protect"; (2) "Naming three people out of 500 has already removed them from the set: for those individuals k = 1, and P(identify) = 1. A feature that names people cannot be anonymous, whatever the rest of the page does."; (3) "with 16 patterns that is 4 more bits, cutting an effective k = 500 to about 31" (500/2⁴ = 31.25); (4) "Require k_effective ≥ 20 after all signals are combined; suppress the named list, bin the series to weekly, and round counts. Then attempt the attack yourself"; (5) "log the queries, reject filters that isolate fewer than k subjects, and treat aggregation as a disclosure decision rather than a reporting convenience… A^L says a random secret is expensive to guess, while an anonymity set of size k says a person is cheap to isolate once the signals add up."

## 2. FORMULAS AND NUMERIC DRILLS

### 2a. Every formula on the Foundations page, with arithmetic

**Risk (product model).** `R = T × V × I`.
T = threat likelihood (how often an actor attempts the attack), V = vulnerability likelihood (whether the weakness is exploitable as found), I = impact.
Rule: "driving any one factor to zero removes that path, and reducing one factor without the others gives the attacker an easy substitute."
Drill: if T = 0.3, V = 0.4, I = $250,000 → R = 0.3 × 0.4 × 250,000 = 0.12 × 250,000 = $30,000.

**Residual risk with n layers.** `R_res = I ∏(i=1..n) p_i` — "with equality only when the layers are independent"; printed as `R_res ≥ I ∏ p_i`.
Worked (page): p = 0.3 for three layers → 0.3 × 0.3 = 0.09; 0.09 × 0.3 = **0.027**; "the impact is reached in under 3% of attempts."
Drill: p = 0.2, 0.5, 0.5, 0.5, I = $600,000 → 0.2 × 0.5 = 0.1; 0.1 × 0.5 = 0.05; 0.05 × 0.5 = 0.025; 600,000 × 0.025 = **$15,000**.
Failure of independence: "If one vulnerable library appears in three of the layers, those three failures share a single cause and the product collapses towards the largest of them."

**Exposure window.** Page prints `W = t_exploit − t_patch` with "(negative means remediation happened first)"; the worked example computes deployment day minus exploit day: exploit published day 0, patch deployed day 30 → "W = 30 − 0 = 30 days". Treat the examinable definition as the number of days from exploitable to remediated (the symbol grid says exactly that: "Days from exploitable to remediated — vulnerability management").

**Compromise probability over the window.** `P(compromise) = 1 − (1 − q)^W`.
Worked (page): q = 0.01, W = 30 → 0.99³⁰ ≈ 0.740 → 1 − 0.740 = **0.26** ("Roughly a one-in-four chance per host, from timing alone").
Worked (page): q = 0.01, W = 7 → 0.99⁷ ≈ 0.932 → 1 − 0.932 = **0.068** ("about 7%"). "Cutting the window by 77% cuts the risk by roughly 74%": (30 − 7)/30 = 76.7%; (0.260 − 0.068)/0.260 = 73.9%.
Drill: q = 0.02, W = 10 → 0.98¹⁰ ≈ 0.8171 → 1 − 0.8171 = **0.183 ≈ 18%**.

**Metrics.** `MTTR = (1/n) Σ(i=1..n) t_i`; `C = assets remediated / assets affected`; `S = severity × exposure × exploitability`.
Worked (page, invented 1–5 values): 4 × 5 × 5 = **100**; 4 × 2 × 4 = **32**; 3 × 1 × 1 = **3**. Windows: W₁ = 3 days, W₂ = 14 days, "so the API's residual risk is the larger of the two even though its score is smaller."

**Detection rates.** `TPR = TP/(TP+FN)`; `FPR = FP/(FP+TN)`.

**Precision (Bayes / base-rate fallacy).** `P(attack | alert) = (TPR × π) / (TPR × π + FPR × (1 − π))`, π = P(attack).
Worked (page): N = 1,000,000 events/day, π = 10⁻⁴ → attacks = 1,000,000 × 0.0001 = **100**; benign = 1,000,000 − 100 = **999,900**. TPR = 0.90 → TP = 0.90 × 100 = **90**. FPR = 0.001 → FP = 0.001 × 999,900 = 999.9 ≈ **1000**. Alerts = 90 + 1000 = **1090**. Precision = 90/1090 = 0.08257 ≈ **8.3%**.
Worked (page): FPR halved to 0.0005 → FP = 0.0005 × 999,900 ≈ 500 → alerts = 90 + 500 = 590 → 90/590 = 0.1525 ≈ **15%** ("doubles precision to about 15%").
Worked (page): TPR raised to 0.99 → TP = 0.99 × 100 = 99 → alerts = 99 + 1000 = 1099 → 99/1099 ≈ **9.0%**.
Worked (page quick-check): TPR = 0.99, FPR = 0.01, π = 10⁻⁵ → precision = 9.9 × 10⁻⁶ / (9.9 × 10⁻⁶ + 0.01 × 0.99999) = 9.9 × 10⁻⁶ / 1.000980 × 10⁻² ≈ **0.00099 ≈ 0.1%**; the page's phrasing: "For every real attack the detector raises about 1000 false alerts, so only about 1 alert in 1000 is real" (recomputed ratio 0.01/0.99 × (1 − π)/π ≈ 1010).

**Alert rate and analyst capacity.** `A = N[TPR·π + FPR(1 − π)]`; number of deployable sensors bounded by `c / A` where c = alerts triaged per day.
Check against the worked example: 1,000,000 × (0.9 × 0.0001 + 0.001 × 0.9999) = 1,000,000 × (0.00009 + 0.0009999) = 1,000,000 × 0.0010899 = **1089.9 ≈ 1090 alerts/day**.
Worked (page, `sol-m2`): 4,000 alerts/day, 20 real → precision ≈ 20/4000 = **0.5%**; target "precision above 20% at a volume under 400 alerts a day — that is, roughly **80 real detections** a day" (0.20 × 400 = 80).

**Anonymity set.** `P(identify) ≈ 1/k`; `k′ = k / 2^m` after m independent yes/no answers; isolation takes about `⌈log₂ k⌉` answers; release rule `k_effective ≥ 1/P_max`.
Worked (page): k = 200 → 1/200 = **0.5%**. Roster narrows to 20 → log₂200 − log₂20 = 7.6439 − 4.3219 = **3.322 ≈ 3.3 bits**. 8 behavioural classes → log₂8 = **3 bits**. Total 3.3 + 3 = **6.3 bits**. 2^6.3 = e^(6.3 × 0.693147) = e^4.366827 = 78.79 → k_eff = 200/78.79 = **2.5 people**. 5% target → k ≥ 1/0.05 = **20**.
Worked (page, `sol-m3`): k = 500 → 1/500 = **0.2%**; named top-3 list → those individuals have k = 1, P(identify) = **1**; 16 distinguishable patterns → log₂16 = **4 bits** → k_eff = 500/16 = **31.25 ≈ 31**; threshold k_eff ≥ 20.

**Entropy.** `H(X) = −Σ p_i log₂ p_i`.
Uniform over 8 classes → H = 8 × (1/8 × log₂8) = 8 × (0.125 × 3) = **3 bits** ✓.
p = 0.9 two-outcome case → −0.9 log₂0.9 − 0.1 log₂0.1 = 0.9 × 0.152003 + 0.1 × 3.321928 = 0.136803 + 0.332193 = **0.468996 ≈ 0.47 bits** (the page prints ≈ 0.57 — see §2b).
p = 0.9 over 8 classes with the remaining 0.1 spread evenly → 0.136803 + 7 × (0.014286 × 6.12785) = 0.136803 + 0.612786 = **0.7496 ≈ 0.75 bits**.
Composition: independent signals add, H(X) + H(Y), bounded by log₂ k.

**Brute force / guessing cost.** `N = A^L`; `T₅₀ = A^L / 2r`; `H = L log₂ A` bits.
Check: 26⁸ = 2.0883 × 10¹¹; 8 × log₂26 = 8 × 4.70044 = 37.60 bits; T₅₀ = 2.0883 × 10¹¹ / 2 × 10⁴ = 1.0442 × 10⁷ s = 120.9 days.
Worked (page): 36⁸ ≈ 2.8 × 10¹² → T₅₀ = 2.8 × 10¹² / (2 × 10⁴) = 1.4 × 10⁸ s; 1.4 × 10⁸ / 86,400 = 1620 days ≈ **4.5 years**.
Worked (page): online, 5 attempts per account per 15 minutes = 5 × 4 × 24 = **480 attempts/day** → 1.4 × 10¹² / 480 = **2.9 × 10⁹ days** ≈ 7.9 million years ("millions of years. Policy, not entropy, did the work").
Worked (page): credential stuffing, 10,000 accounts × 5 attempts = **50,000 attempts** → 50,000 / 10⁴ = **5 seconds**; per-account lockout never triggers.
Drill: A = 26, L = 6, r = 10⁴ → N = 26⁶ = 308,915,776 ≈ 3.1 × 10⁸; H = 6 × 4.70044 = **28.2 bits**; T₅₀ = 308,915,776 / 20,000 = **15,446 s ≈ 4.29 hours**.

### 2b. Recomputation notes — where the page's printed numbers differ from the arithmetic

These are page-internal inconsistencies found when recomputing. Both the printed value and the recomputed value are given so a downstream author never has to guess.

1. **W direction.** The formula is printed `W = t_exploit − t_patch` ("negative means remediation happened first"), but the worked example computes 30 − 0 = 30 where 30 is the median *deployment* day and 0 is the *exploit-publication* day, and the symbol grid defines W as "Days from exploitable to remediated". The consistent reading: W = (day remediated) − (day exploitable).
2. **"Roughly eleven alerts for every real attack"** (sec-m-detection): alerts/TP = 1090/90 = **12.1**, i.e. about twelve.
3. **"Raising the detection rate to 0.99 adds 10 more true positives out of ~1100 alerts"**: TP = 0.99 × 100 = 99, so the gain is **+9**, and alerts become 99 + 1000 = **1099**; precision ≈ 9.0%.
4. **"3,600 wasted alerts a day"** (sol-m2): with 4,000 alerts of which 20 are real, the waste is 4,000 − 20 = **3,980**. 3,600 would correspond to 400 real alerts (precision 10%), which contradicts the stated 20.
5. **Entropy "H ≈ 0.57 bits" for a class with p = 0.9**: not reproducible — binary entropy at p = 0.9 is **0.469 bits**, and with 8 classes and the remaining 0.1 spread evenly it is **0.750 bits**.
6. **`#ix-db-map` title** says "seven places to get it wrong" but the JSON `points` array lists **nine** hotspots.
7. Minor rounding: 26⁸ is printed 2.1 × 10¹¹ (2.088 × 10¹¹ ✓), 36⁸ printed 2.8 × 10¹² (2.821 × 10¹² ✓), 62¹² printed 3.2 × 10²¹ (3.226 × 10²¹ ✓), 94¹⁶ printed 3.7 × 10³¹ (3.716 × 10³¹ ✓), 36⁸ T₅₀ printed 4.5 years (4.47 ✓), 62¹² T₅₀ printed 5.1 × 10⁹ years (5.11 × 10⁹ ✓), 94¹⁶ T₅₀ printed 5.9 × 10¹⁹ years (5.89 × 10¹⁹ ✓). ## 3. PITFALLS

1. **"Software security is encryption and penetration testing" is wrong because it names a control and a late check instead of the lifecycle property; the page says the exam framing must name the lifecycle scope and the two halves (prevent before deployment, detect and respond after it), and that Equifax, Log4Shell and MOVEit were exploited through software and dependency weaknesses, "not by breaking encryption" — so "we use TLS" is not a security answer.**
2. **Treating an IDS as a blocking control is wrong because detection and prevention are different jobs; the page says an IDS "sits on a monitoring path rather than in the traffic flow, and it does not automatically stop the attack", and that stopping a brute-force attack "needs an active control: an inline IPS, rate limiting and lockout on the authentication path, or MFA".**
3. **Reading a 99% detection rate as "99% of alerts are real" is wrong because precision is not TPR; the page's formula P(attack | alert) = TPR·π / (TPR·π + FPR(1−π)) with π = 10⁻⁵, TPR = 0.99, FPR = 0.01 gives precision ≈ 0.1%, i.e. "only about 1 alert in 1000 is real".**
4. **Counting three layers that share a component as defence in depth is wrong because the product assumes independence; the page says "if the same vulnerable library sits in the web tier, the job runner and the report generator, one supply-chain defect defeats three 'layers' at once", and the Foundations page prints R_res ≥ I ∏ p_i with equality only when the layers are independent.**
5. **Fixing SQL injection with filters, denylists or hand-escaping is wrong because it leaves the statement structure input-dependent; the page says "escaping quotes by hand — encoding context varies and denylists are famously incomplete", "client-side validation alone — the attacker simply does not use your form", and that only parameter binding removes the class "because validation can be bypassed by any path that reaches the query builder — an internal API, a batch job, a support tool".**
6. **Fixing injection screen-by-screen is wrong because the defect lives in the query builder; the page's worked triage says "Injection is fixed per query builder, not per screen… the filter that exists on the UI screen does not protect the other three" routes.**
7. **Hiding database error messages as the injection fix is wrong because it changes disclosure, not parsing; the page says "it reduces information leakage, not the injection".**
8. **Treating a valid session as authority is wrong because authentication is not authorisation; the page says "Identity is not authority. A valid session says who the caller is; an authorisation check on every object is what says what they may do. Confusing the two is broken access control (OWASP A01)" — and the OWASP table maps broken access control to "A valid session is trusted as a permission".**
9. **Assuming "no names" makes a published view anonymous is wrong because distinctive patterns and counts are themselves signals; the page says "a distinctive curve is recognisable even without a name", that "individually harmless signals become identifying when combined", and that its named-lines-plus-counts case scores 100 ("linkable") on the illustrative risk scale.**
10. **Assuming masking a sensitive column removes inference risk is wrong because the attack never needed the value; the page says it "exploits the pattern of results and metadata around it", and that each yes/no answer still carries "at most one bit".**
11. **Prioritising remediation by severity alone (or by closure counts) is wrong because severity is one factor and timing is a parameter; the page's score is S = severity × exposure × exploitability, its worked ranking gives 100 versus 32 for equal-severity findings, it warns that "ticket counts and 'percentage of findings closed' are activity measures: they improve when a team closes easy findings", and it warns that the daily compromise rate q is "a modelling assumption, not a measurement" with correlated compromise events — so only the monotonic conclusion (risk rises with the window) is safe to state.**
12. **Treating a long password as sufficient protection is wrong because T₅₀ assumes a uniform search and ignores online policy; the page says rate limiting to 480 attempts a day turns 4.5 years into about 2.9 × 10⁹ days ("Policy, not entropy, did the work"), that real passwords are not uniform "which is why an attacker uses a ranked list", and that credential stuffing (10,000 accounts × 5 attempts ≈ 5 seconds) "defeats complexity rules and per-account lockout".**

## 4. TESTABLE CLAIMS

1. The deck defines software security as "an engineering property across the complete software lifecycle — design, develop, test and maintain software so it resists attack and protects users' data", with two halves: prevent vulnerabilities before deployment and keep protecting the system after it. — `chapter8-study.html#sec-software`
2. The three incidents the deck uses are Equifax (2017, unpatched web application component, roughly 147 million people affected), Log4Shell (2021, vulnerable logging library, CVE-2021-44228, remote code execution) and MOVEit (2023, SQL injection, CVE-2023-34362, mass data theft). — `chapter8-study.html#sec-software`
3. The six lifecycle stages and their characteristic defects are requirements/abuse case omitted, design/trust boundary missed, implementation/unsafe data handling, testing/adversarial path skipped, deployment/insecure default and maintenance/patch delayed; the illustrative shift-left cost curve for one defect is 1x, 6x, 15x, 40x and 100x across those stages and is labelled "not lecture data". — `chapter8-study.html#sec-lifecycle`
4. The deck's five headline weaknesses are SQL injection, cross-site scripting, broken access control, security misconfiguration and vulnerable components, mapped to A03 (twice), A01, A05 and A06 of the OWASP Top 10 (2021), and their shared root cause is "the system trusts data, identity, configuration or dependencies more than it should." — `chapter8-study.html#sec-owasp`
5. The full OWASP 2021 list runs A01 Broken Access Control, A02 Cryptographic Failures, A03 Injection, A04 Insecure Design, A05 Security Misconfiguration, A06 Vulnerable and Outdated Components, A07 Identification and Authentication Failures, A08 Software and Data Integrity Failures, A09 Security Logging and Monitoring Failures, A10 Server-Side Request Forgery. — `chapter8-study.html#sec-owasp`
6. Defence in depth is six layers in order — secure coding (prevent), testing (challenge), static analysis (inspect, SAST), dynamic analysis (probe, DAST/fuzzing/scanning), monitoring (observe), IDS/IPS (detect/block) — and it "only pays off when the layers are genuinely independent". — `chapter8-study.html#sec-defence`
7. A database is "a managed system for storing, relating, querying and updating persistent data" (engines named: PostgreSQL, MySQL, MongoDB, Redis, Neo4j), its crown jewels are personal data, financial data, credentials and intellectual property, and "a compromise affects not only the stored records, but every application and decision that depends on them", against the objective of "controlled, correct and dependable use of data — not merely keeping attackers outside". — `chapter8-study.html#sec-database`
8. SQL injection succeeds "when user-controlled text is interpreted as SQL syntax", and the key message is that attackers "exploit insecure application code — not the database itself", with the canonical teaching illustration `alice' OR '1'='1`. — `chapter8-study.html#sec-injection`
9. The structural fix for injection is a prepared statement whose SQL text is constant with values bound to placeholders; the supporting controls are input validation, least privilege and correctly used ORM query APIs, while hand escaping, client-side validation, a WAF alone and hiding error messages are not the fix. — `chapter8-study.html#sec-injection`
10. An inference attack "does not bypass access control" but learns sensitive information indirectly by combining permitted answers, classically a query such as `... WHERE username = 'alice' AND salary > 100000` whose row-or-no-row result discloses the secret. — `chapter8-study.html#sec-inference`
11. In the conference case study each published signal adds leakage — named progress lines, per-paper review counts and distinct progress patterns — and "individually harmless signals become identifying when combined", with re-identification risk roughly 1/k. — `chapter8-study.html#sec-inference`
12. XSS delivers attacker-controlled JavaScript to a trusted user's browser in stored, reflected or client-side form, it "does not hack the browser" but abuses the browser's trust in a vulnerable application, and its four controls are contextual output encoding, a proven allowlist sanitiser for genuinely needed HTML, auto-escaping frameworks with safe DOM APIs, and CSP as an additional layer. — `chapter8-study.html#sec-xss`
13. Software security builds secure software before deployment (focus build, objective prevent, during development and testing, examples SQL injection and XSS) while system security protects deployed systems (objective detect and respond, during operation and maintenance, examples IDS and IPS); the five threat classes are brute force, malware, scanning, denial of service and insider misuse, and hardening covers secure defaults, removing what is not needed, least privilege, segmentation and egress control, centralised logging with retention, and MFA on every administrative path. — `chapter8-study.html#sec-system`
14. Vulnerability management is identify (inventory/SBOM, scan, advisories), prioritise (severity with internet exposure, exploit availability and asset value), remediate (patch, upgrade or a documented compensating control), verify (rescan and regression-test — "a closed ticket is not evidence") and report (exposure window and mean time to remediate, not ticket counts). — `chapter8-study.html#sec-system`
15. An IDS observes host or network activity and alerts from a monitoring path and does not automatically stop the attack, while an IPS sits inline and can "inspect → decide → act", so an IPS false positive becomes an outage; HIDS covers one host, NIDS a network segment, tools named are Snort, Suricata and Zeek, and detection is signature-based or anomaly-based. — `chapter8-study.html#sec-detect`
16. Risk is the product R = T × V × I, and residual risk with n independent layers is R_res = I ∏ p_i with equality only when the layers are independent, so R_res ≥ I ∏ p_i in general. — `chapter8-math.html#sec-m-defs`
17. The exposure window is the time from exploitable to remediated, and P(compromise) = 1 − (1 − q)^W; with q = 0.01 and W = 30 the page computes 1 − 0.99³⁰ ≈ 0.26, and with W = 7 it computes ≈ 0.068. — `chapter8-math.html#sec-m-exposure`
18. Detection precision is P(attack | alert) = TPR·π / (TPR·π + FPR(1 − π)), and with N = 1,000,000, π = 10⁻⁴, TPR = 0.90 and FPR = 0.001 the page gets 90 true positives, about 1000 false positives, 1090 alerts and precision ≈ 8.3%. — `chapter8-math.html#sec-m-detection`
19. Inference is quantified by the anonymity set: P(identify) ≈ 1/k, k′ = k/2^m after m yes/no answers, about ⌈log₂ k⌉ answers isolate one subject, and a 5% re-identification target needs k ≥ 20. — `chapter8-math.html#sec-m-privacy`
20. Brute-force cost is N = A^L with T₅₀ = A^L/2r and H = L log₂ A bits: 36⁸ ≈ 2.8 × 10¹² gives T₅₀ ≈ 1.4 × 10⁸ s ≈ 4.5 years off-line, while rate limiting to 480 attempts a day makes the same account effectively unguessable and credential stuffing (10,000 accounts × 5 attempts) takes about 5 seconds. — `chapter8-math.html#sec-m-privacy`

| `anonymity-model` | Anonymity model | `P(identify) ≈ 1/k`, `k′ = k/2^m` after m yes/no answers, and about `⌈log₂ k⌉` answers isolate one subject from k candidates. | chapter8-math.html#sec-m-privacy |
| `entropy` | Entropy of a released signal | `H(X) = −Σ p_i log₂ p_i`; uniform over 8 classes gives 3 bits, entropy composes across independent signals, and it is bounded by `log₂ k`. | chapter8-math.html#sec-m-privacy |
| `guessing-cost` | Cost of guessing a secret | `N = A^L` candidates, `T₅₀ = A^L / 2r` seconds at r guesses per second, and `H = L log₂ A` bits — with online attempts bounded by policy such as lockout and MFA rather than entropy alone. | chapter8-math.html#sec-m-privacy |

## 7. FLASHCARD SEEDS

1. **Front:** What is the Week 8 deck's definition of software security?
   **Back:** Security as an engineering property across the complete software lifecycle — design, develop, test and maintain software so it resists attack and protects users' data. It has two halves: prevent vulnerabilities before deployment, and continue protecting the system after deployment. (`chapter8-study.html#sec-software`)

2. **Front:** Name the six lifecycle stages and the characteristic defect of each.
   **Back:** 0 Requirements — abuse case omitted; 1 Design — trust boundary missed; 2 Implementation — unsafe data handling; 3 Testing — adversarial path skipped; 4 Deployment — insecure default; 5 Maintenance — patch delayed. (`chapter8-study.html#sec-lifecycle`)

3. **Front:** What is the shared root cause of the deck's five headline weaknesses, and which OWASP 2021 categories do they map to?
   **Back:** "The system trusts data, identity, configuration or dependencies more than it should." SQL injection and XSS → A03 Injection; broken access control → A01; security misconfiguration → A05; vulnerable components → A06. (`chapter8-study.html#sec-owasp`)

4. **Front:** Why does a prepared statement remove the SQL injection class when input validation does not?
   **Back:** Validation decides what a field may contain; parameter binding decides how the statement is assembled. Binding fixes the SQL structure before data is supplied and the value "can never be parsed as SQL", whereas validation can be bypassed by any other path to the query builder — an internal API, a batch job or a support tool. (`chapter8-study.html#sec-injection`)

5. **Front:** An inference attack returns no secret at all. Why is it still a disclosure, and what limits it?
   **Back:** Each permitted yes/no answer carries at most one bit (row or no row), and the attacker chooses the questions, so low-information answers compose into a high-value secret. Risk is bounded by the anonymity set: re-identification is roughly 1/k, so a 5% target needs k ≥ 20. (`chapter8-study.html#sec-inference`, `chapter8-math.html#sec-m-privacy`)

6. **Front:** What is the one structural difference between an IDS and an IPS, and what does each cost you when it is wrong?
   **Back:** Deployment and action: an IDS sits on a monitoring path, is passive and only alerts, so an attack proceeds while the team reads the alert; an IPS sits inline and can block, drop, reset or quarantine, so a false positive becomes an outage. Both inspect the same activity. (`chapter8-study.html#sec-detect`)

7. **Front:** State the four Foundations formulas behind "why is the IDS so noisy, and what does guessing a secret cost?"
   **Back:** Precision `P(attack | alert) = TPR·π / (TPR·π + FPR(1 − π))` — with π = 10⁻⁴, TPR = 0.90, FPR = 0.001 and 1,000,000 events, that is 90 true positives among ~1090 alerts ≈ 8.3%. Alert rate `A = N[TPR·π + FPR(1 − π)]` bounds how many sensors c triaged alerts a day can support. Guessing cost `N = A^L`, `T₅₀ = A^L/2r`, `H = L log₂ A` — 36⁸ ≈ 2.8 × 10¹² gives T₅₀ ≈ 1.4 × 10⁸ s ≈ 4.5 years at 10⁴ guesses/s, but rate limiting to 480 attempts a day makes it millions of years. (`chapter8-math.html#sec-m-detection`, `chapter8-math.html#sec-m-privacy`)
