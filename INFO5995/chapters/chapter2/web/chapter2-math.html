Foundations: the arithmetic behind AI-assisted discovery

Week 2 is a workflow week, not a theorem week — so this page does the equivalent job. It pins down the definitions the lecture relies on, gives you a compact notation for an investigation, then quantifies the four things that actually decide whether AI-assisted discovery works: the token budget, the screening arithmetic of an unverified finding list, the coverage of a fuzzing campaign, and the cost of verifying a claim before you act on it.

Definitions verified against the lecture deck Screening and coverage maths is standard detection theory Cost figures are illustrative, not lecture numbers

Definitions that must be exact

These five terms carry the whole week. Write each one in a single sentence, with the consequence included.

Hallucination

The model produces something that sounds correct but is not grounded in reality. In this unit: a reported vulnerability with no reachable path through the code — fluent, specific, and unverifiable.

Static analysis

Examining code without executing it — parsing it into a representation and applying rules or queries to that representation. It gives deterministic, reproducible, whole-codebase coverage with file-and-line output; it cannot observe runtime behaviour, and a warning is not a reachable vulnerability.

Fuzzing

Supplying generated or mutated inputs to a running program and observing the result. Unlike a static warning or an AI claim, a fuzzing crash is dynamic evidence: it demonstrates that the input actually reaches the fault.

Reasoning model

A model that performs additional internal processing — an internal scratchpad, often hundreds or thousands of tokens, exposed only as a “thinking” indicator and an effort setting — before producing its answer. The deck's caveat: more reasoning can improve performance, but it does not guarantee a correct answer.

AI agent (security context)

A model that can decide whether to answer directly or call a tool to gather evidence, then reason over the tool's result. The tool supplies facts; the model supplies the decision about what to do next. Authority and boundaries are a separate design decision from capability.

The one relationship to remember

A candidate finding is a claim, and a claim is only as useful as the evidence attached to it. Formally, a finding is a triple

\[ F \;=\; \langle\, \text{location},\; \text{mechanism},\; E \,\rangle \]

where \(E\) is the evidence. If \(E = \varnothing\) the triple describes a hypothesis, not a vulnerability — regardless of how fluent the prose around it is. All of this week's countermeasures exist to force \(E \neq \varnothing\).

Tokens, context and the cost of looking

The deck's three constraints are all quantities: repositories are huge, the context window is small, and text is processed in a relatively “cheap” way. Put numbers on them and the workflow design follows.

1. The context budget

A prompt must fit the window, together with everything the model will generate and everything the conversation has already accumulated:

\[ T_{\text{system}} + T_{\text{history}} + T_{\text{context}} + T_{\text{output}} \;\le\; W \]

Practical consequence: a long investigation fills its own window. Every tool result and every earlier exchange competes with the code you still want to show — which is why the deck prescribes summarising what has already been checked into a file or a table instead of carrying the whole transcript.

2. Slicing a codebase that does not fit

If \(L\) is the size of the target and \(\ell\) the size of one review unit, the number of units to process is

\[ n \;=\; \left\lceil \frac{L}{\ell} \right\rceil \]

With \(L = 400\,000\) tokens (a mid-sized repository) and a generous \(\ell = 8\,000\) tokens, \(n = 50\) units. Note what this does not give you: a unit boundary cuts call chains, so cross-module data paths are exactly the ones a slice-and-prompt workflow is most likely to miss.

3. The cost of one pass

Ignoring the conversation history term for a single-pass run:

\[ \text{cost} \;\approx\; c \cdot n \cdot \left( \ell + \overline{T}_{\text{out}} \right) \]

Two facts about this expression matter more than the number it produces. Cost is linear in the number of units, so coverage is bought in slices. And the deck's countermeasure to missed findings — run multiple times, change the phrasing, use different models and temperatures — multiplies this expression by the number of passes \(m\). Re-running for coverage is a deliberate cost, not a free retry.

Screening arithmetic: what an unverified list really costs

An AI report is a screening test. Standard detection arithmetic tells you exactly what is wrong with acting on one before verification — and why the false-positive problem is a budget problem, not an annoyance.

1. Precision, recall and the false-positive rate

Let \(TP\) be real vulnerabilities correctly reported, \(FP\) the fabricated or unreachable ones, and \(FN\) the real ones missed. Then

\[ P \;=\; \frac{TP}{TP + FP}, \qquad R \;=\; \frac{TP}{TP + FN}, \qquad \mathrm{FPR} \;=\; \frac{FP}{TP + FP} \;=\; 1 - P \]

Recall measures what you failed to see; precision measures what you will waste time on. A tool can be excellent at one and useless at the other, so never quote a single number as “the accuracy”.

2. The verification budget

If a report contains \(N = TP + FP\) candidates and each candidate costs \(C_v\) human minutes to confirm or refute, the screening cost is

\[ T_{\text{verify}} \;=\; N \cdot C_v, \qquad T_{\text{wasted}} \;=\; FP \cdot C_v \;=\; (1-P)\cdot N \cdot C_v \]

Worked figure: \(N = 200\), \(C_v = 4\) minutes. Then \(T_{\text{verify}} = 800\) minutes ≈ 13.3 hours. At \(P = 0.25\), three quarters of that — 600 minutes, 10 hours — is spent refuting fabrications. At \(P = 0.10\) the same list costs the same 13.3 hours for 20 real findings instead of 50. Lower precision does not save time; it converts the same time into less result.

3. The cost of a miss

A missed vulnerability is not free just because nothing was reported. With \(FN\) misses and an average cost of exposure \(C_{\text{exp}}\) (incident response, remediation, disclosure, downtime),

\[ C_{\text{miss}} \;=\; FN \cdot C_{\text{exp}} \]

This is why the two failure modes are managed differently. Against hallucination you demand evidence, because every fabrication spends \(C_v\). Against misses you spend more passes and more techniques, because every miss hands \(C_{\text{exp}}\) to somebody else.

Why the deck's countermeasures are stated as questions, not settings. “Ask for concrete proof. Ask for a minimal reproducible example. Ask for the exact execution trace.” Each of those requests is a filter on the right-hand side of \(P = TP/(TP+FP)\): it does not make the model more capable, it makes candidates cheap to reject. A finding that cannot produce a trace can be dismissed in seconds instead of traced by hand, and \(T_{\text{wasted}}\) collapses.
A tool reports 200 candidates at \(P = 0.25\), and \(C_v = 4\) minutes per candidate. Roughly how much human time is spent refuting findings that are not real?
About 800 minutes, because every candidate must be checked

Coverage, fuzzing and the cost of finding one bug

Two more quantities decide whether a technique is worth running: how much of the input space it reaches, and how much effort each confirmed finding costs in total.

1. Coverage is a fraction of a space you cannot enumerate

For a fuzzing campaign, define coverage over the observable surface of the target — basic blocks, branches, or the fraction of the input space that reaches them:

\[ \text{cov} \;=\; \frac{|\text{covered}|}{|\text{reachable}|}, \qquad 0 \le \text{cov} \le 1 \]

Coverage is a proxy, not a verdict. High statement coverage with low branch coverage hides the paths that only execute under a rare guard, and those are where interesting faults live. Always ask which denominator a coverage number uses.

2. Campaigns find bugs at a decreasing rate

Empirically, a fuzzing campaign's cumulative unique findings tend to follow a saturating curve rather than a line:

\[ B(t) \;=\; B_{\max}\left(1 - e^{-\lambda t}\right) \]

where \(t\) is elapsed fuzzing time and \(\lambda\) the discovery rate constant. Three consequences worth remembering: the first minutes are the most productive; the marginal bug gets steadily more expensive; and you can only tell a plateau from a slow region by changing the seed corpus, the mutation strategy or the harness — the same lesson as “a single prompt run misses things”.

3. Cost per confirmed finding

Putting the pieces together for one technique over one target:

\[ C_{\text{finding}} \;=\; \frac{C_{\text{run}} + N \cdot C_v + C_{\text{proof}}}{TP_{\text{confirmed}}} \]

where \(C_{\text{run}}\) is compute and model spend, \(N\cdot C_v\) is the screening cost from the previous section, \(C_{\text{proof}}\) is the cost of building the minimal reproducer, and only confirmed findings are counted in the denominator. This is the number to compare between techniques — not raw finding counts, and not token price.

Classifying an AI finding

Most Week 2 questions reduce to “here is something a model said — what do you do with it?”. Run the claim through these steps in order and the answer writes itself.

StepLook forMarks are lost when…
1. Evidence\(E \neq \varnothing\): file and line, data path, execution trace, minimal reproducerYou accept a fluent paragraph as proof
2. LocationDoes that line say what the model said it says?You trust the quotation without opening the file
3. Data pathEvery hop is present in the code, not in the narrativeYou assume a value reaches a sink because both exist somewhere in the project
4. ControlIs the input attacker-controlled and is the code reachable in the deployed configuration?You ignore authentication, encoding or a framework control that breaks the chain
5. TriggerObserved behaviour in an authorised environmentYou describe what “would” happen instead of what did
6. Minimise and assessSmallest reproducing case; impact stated with preconditionsYou overstate impact or leave the reproduction unrepeatable
7. VerdictConfirmed, refuted or unresolved — all three are resultsYou report only the confirmed items and let the rest be re-chased
The step students skip

Step 4. A data path can be complete and still not be a vulnerability, because the input cannot be controlled by an attacker in the deployment that matters, or because a control upstream removes the dangerous characters. “The path exists” and “an attacker can walk it” are two different claims, and the second one is the one that gets reported.

Worked classification. Three findings from an AI-assisted review of one service. Place each one with the checklist, using the arithmetic from this page.

1

“Critical: hardcoded credentials in the configuration loader.” No file, no line, no excerpt. Step 1 fails immediately: \(E = \varnothing\). This is the hallucination case — and note the cost asymmetry. Five seconds to ask for the location; if you had sent it to an engineer instead, you would have paid \(C_v\) minutes for nothing. Verdict: reject and re-ask with the evidence contract attached.

2

“User-controlled string concatenated into a query at search.js:118”, with the data path quoted. Steps 1–3 pass: the line matches, the path is real. Step 4 is where it is decided — an upstream encoder in the request pipeline neutralises the dangerous characters, so the input is not attacker-controlled at the sink. Verdict: refuted, with the control named. This is the honest false positive, and recording the reason is what stops it being re-chased next month.

3

“Integer overflow in the parser's length check, reachable with a 4 GB body.” Steps 1–4 pass on paper, but the deployment caps request bodies far below the trigger, and testing it requires a configuration the team does not run. Verdict: unresolved — not refuted, because the code genuinely overflows; not confirmed, because the preconditions are outside your authorised environment. State the limit and hand it over.

4

What the triage cost. Suppose the first pass returned 200 candidates at \(C_v = 4\) minutes each: 800 minutes, 13.3 hours, to triage the list. Finding 1 is rejected before it reaches a human; finding 2 is refuted in about 6 minutes at the code; finding 3 is handed over. The economics of the week live in that first filter, not in the model's raw intelligence.

5

The sentence that earns the mark. “An AI finding is a hypothesis until it carries evidence: I locate the code, trace the data path by hand, check that the input is attacker-controlled under the deployed configuration, observe the effect in an authorised environment, minimise the case, and record the verdict — confirmed, refuted or unresolved — because refuted candidates and unresolved limits are results too.”
