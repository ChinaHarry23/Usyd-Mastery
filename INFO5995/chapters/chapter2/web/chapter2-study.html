Why AI Is on the Security Agenda

The lecture opens with the constraint that forces the whole topic: modern software is too large to inspect manually, line by line.

The opening claim of Week 2: the volume of code, dependencies and artefacts in a real system already exceeds what a human review team can read exhaustively — so the practical question is not “can AI find bugs?” but “where in the workflow can a pattern-matching assistant add evidence, and where must a human take over?”

What the assistant is genuinely good at

  • Reading text cheaply and at volume — source, diffs, logs, traces
  • Recognising shapes it has seen before in training data
  • Driving the text-based tools that already exist
  • Summarising an investigation so a human can audit the reasoning

What it cannot supply

  • Ground truth: it does not know whether its answer is true
  • Authorisation: it cannot decide what it is allowed to touch
  • Proof: a plausible finding is not a demonstrated one
  • Judgement about impact, scope and disclosure
The framing to keep for the whole week: the goal is not to ask AI “find the vulnerabilities”. The goal is to investigate with AI — give it context, give it evidence, give it boundaries, and never trust a finding until you have verified it.
QuestionWrong first questionRight first question
Capability“Can the AI find a vulnerability here?”“What evidence would prove one exists?”
Authority“Can the AI do it?”“Is the AI authorised to act?”
Scope“Point it at the repository.”“Which targets, which techniques, which limits?”
Outcome“It produced a list of bugs.”“What did we learn about the system?”

How an LLM Responds

The lecture needs only enough about LLMs to reason about their role in security. That minimum is a picture: a prompt goes in, a response comes out, and the response is a prediction over patterns learned during training.

Key takeaway 1 — LLMs predict patterns

LLMs can appear intelligent, but they generate responses by predicting likely patterns. They do not automatically know whether an answer is true or correct. Why this matters for security: many vulnerabilities also follow recognisable patterns. That is exactly why AI can help identify suspicious code — and exactly why every finding still needs evidence and verification.

Three behaviours the deck demonstrates

Sampling is not deterministic

The same prompt does not always produce exactly the same response. Two identical requests can return two different findings, which is a feature for coverage and a problem for reproducibility — so record the prompt, the model and the settings alongside every finding.

Context changes the response

“What are we working on today?” answered with “It's Sunday” produces a different reply than the same question asked cold. Earlier messages provide context that shapes what the model says next, which is why a stale or contaminated conversation degrades an investigation.

The system prompt is a control layer

The system prompt sets the model's instructions, role and behavioural boundaries before the user interacts with it. Change “you are a friendly assistant” to “you are a security reviewer reporting evidence only” and the same user prompt produces a materially different analysis.

Boundaries are part of the design, not an afterthought: when a request carries harmful intent, the model should recognise it and respond within its safety boundaries. In a security investigation the same principle applies structurally — the agent's permitted targets, tools and actions are defined before the work starts, not negotiated while it runs.
A student runs the same prompt twice against the same file and receives two different vulnerability lists. What is the correct reading?
The model learned from the first response and changed its mind
Output is not deterministic, so the run conditions must be recorded and repeated runs are a coverage technique
The second list is the accurate one because it had more time to reason

Hallucination

Hallucination means the model produces something that sounds correct but is not grounded in reality. In vulnerability discovery that takes the shape of a reported weakness with no path through the code that reaches it — a plausible narrative supported by nothing. The lecture's reaction is not to abandon the tool but to pause, think, and reduce the room for invention.

Consequences for your own reviews: supply the syntax (or the language, the build files and a representative module) before asking for analysis; prefer artefacts with high signal; and treat an analysis of decompiled or proof-level material as a hypothesis generator, never as a conclusion.
You ask a model to review a binary's decompiled output for memory-safety bugs. Why is this a harder task than reviewing the original C source?
The decompiled file is usually much larger
There is less natural-language and structural signal, fewer clean paired examples, and the code is low-level and ambiguous
Decompilers cannot recover enough code to analyse at all

Reasoning Models: The Aha Moment for Security

A reasoning model does more internal processing before producing its answer. The lecture's example is the OpenAI o-series family, whose behaviour is described by four observable properties.

1. Internal scratchpad

Some internal working happens before the model speaks.

2. That work can be long

Hundreds or thousands of tokens of internal reasoning.

3. A visible indicator

You may see a “thinking” indicator while it works.

4. Controllable effort

Effort is often selectable — low, medium, high in some variants.

The caveat the deck states explicitly: more reasoning can improve performance, but it does not guarantee a correct answer. Reasoning reduces the rate of shallow answers; it does not create ground truth.
The aha moment for security

After o3-class and R1-class reasoning models: security has completely changed; things that did not work before are now starting to work; and we start to find real vulnerabilities on a large scale. Read this as a shift in the economics of investigation — deep multi-step analysis became cheap enough to run across many targets — not as a claim that the output is verified.

Before reasoning models

Single-pass pattern matching: the model answers immediately from the surface of the prompt. Useful for triage and for explaining a snippet you already suspect, weak at following a data flow across several files.

With reasoning models

The model can hold an intermediate chain of steps — trace a value from input to sink, hold several hypotheses at once, notice that hypothesis two contradicts the code it read in step one. The hidden reasoning is effort you can scale, and it is also a step you cannot audit directly.

Terminal AI Agents: Tools, Evidence and Boundaries

The deck's next step is blunt: reasoning is not enough. Code repositories can be huge — thousands of files, projects that depend on each other — while the context window is small.

The three facts that force a new architecture

  • Repositories are enormous and interdependent
  • The context window cannot hold them
  • LLMs handle text in a relatively “cheap” way — that is their advantage

What already exists to be driven

  • Basic terminal tools: grep, ls, cd, cat, top
  • Networking tools
  • Static analysis and dynamic analysis programs
Definition — an AI agent

An AI agent can decide whether to answer directly or use a tool to gather more evidence. It emits a tool-call instruction, receives the tool result, and uses that result to decide what to do next or what to answer. The tool gathers evidence; the AI reasons over it.

The evidence loop: a tool call returns facts, the model reasons over those facts, and only a human closes the loop by reproducing the finding. The dashed arrow is the part that makes an agent useful and dangerous at once — it decides its own next tool call.

From AI agent to security investigation: the first question is not “can the AI do it?” but “is the AI authorised to act?” An agent with terminal access is executing commands against real systems. The security boundary — which targets, which tools, which actions, what it may never touch — has to be enforced somewhere deliberate, and the deck's point is that this is a design decision, not a default.

Using AI to Find Vulnerabilities: Context, Evidence, Boundaries

The deck's operating rules are three lines long, and every one of them is a design instruction: AI is powerful but it is not careful by default; you must give it context, evidence and boundaries; and never trust a finding until you verify it.

Context

Bad prompts produce shallow answers; partial code produces shallow analysis. Supply the language, the build files, the module boundary, the framework in use, and the contract the code is supposed to satisfy.

Evidence

Ask for the tool output, the file and line, the execution trace, the minimal reproducible case. A claim with no artefact attached is a hypothesis, not a finding.

Boundaries

State what the agent may read, run and change, and what it must never touch. Define the definition of done before the investigation starts.

Weak promptWhy it failsStronger framing
“Find the vulnerabilities.”No artefact, no scope, no output contract; invites a confident list with no proof“Review this module for untrusted input reaching a query. For each candidate, give file, line, the data path and the input that would trigger it. Report ‘none found’ if the path does not exist.”
“Is this code secure?”A yes/no question answers itself; you get a verdict instead of an analysis“List the assumptions this code makes about its inputs, then say which of those assumptions the caller violates.”
“Here are 40 000 lines. Find bugs.”The context window cannot hold it; the model samples the surface and stops“Start by listing the entry points, then analyse one entry point at a time and record what has already been checked.”
“You are a helpful assistant.”No role boundaries, so the model optimises for a satisfying answer“You are a security reviewer. Report only what the evidence supports; state explicitly when a claim is unverified.”

Failure Modes and How to Counter Them

Three named failure modes each come with the deck's own countermeasures. Learn them as problem-and-response pairs: that is how they appear in an exam question.

Models can be lazy

Problem: the model stops at the first obvious issue. If it works for too long it is not user friendly — models were trained not to work for too long.

What to do:

  • Summarise what has already been checked, in a file or a table
  • Explicitly ask for new and different issues
  • Ask for edge cases
  • Ask for non-obvious logic flaws

Models can hallucinate

Problem: it reports fake vulnerabilities.

What to do:

  • Ask for concrete proof
  • Ask for a minimal reproducible example
  • Ask for the exact execution trace
  • Ask it to generate a PoC (then verify that PoC yourself)

Models can miss things

Problem: it overlooks vulnerabilities.

What to do:

  • Run multiple times
  • Change the phrasing
  • Use different models
  • Use different temperatures
  • Ask the model to critique its own answer

Models are sensitive to framing and short on context

Problem: bad prompts give shallow answers; partial code gives shallow analysis.

What to do:

  • Rewrite the prompt around the artefact and the contract
  • Give the module, not the fragment
  • Ask a narrower question with a defined output format
  • Split a large target into units you can actually supply
One sentence that covers the section: the countermeasures are not about making the model smarter — they are about making the claim checkable. Every technique above either forces the model to attach evidence, or forces the search to cover ground a single run would have skipped.

Human Verification: From Finding to Evidence

The point the deck returns to twice: never trust a finding until you verify it. Verification is a procedure, not a feeling of confidence.

VerdictWhat you haveWhat you do next
ConfirmedA reachable path and a demonstrated effectMinimise, assess impact, report with evidence and a proposed fix
RefutedThe path does not reach the sink, or the input cannot be attacker-controlledRecord it as refuted with the reason — a refuted candidate is a result, and it prevents the same false lead being chased twice
UnresolvedThe code is ambiguous, the dependency is unavailable, or you lack authorisation to testState the limit explicitly and hand it to a human with the context needed to decide
The AI solved it — but did we learn anything? The deck asks this question because an investigation has value beyond its answer. What you want to see in the transcript is the process: failures → adaptation → partial success → verification. That visible chain is what makes the result auditable, teachable and repeatable — and it is also what distinguishes investigation from asking a machine for a lucky guess.
Responsible use

Every example in this unit is conceptual and standards-based. Analysis stays inside systems you are authorised to test, findings are reported through the agreed channel, and no third-party system is ever targeted. Capability and trust are matched: the more powerful the tooling, the more explicit the authorisation must be.

Worked example — designing an investigation, not making a request. Scenario: you are handed a small web service and asked to use AI to find vulnerabilities, within an authorised lab environment.

1

Set the boundaries first. Written scope: this service, in this lab, read-only for the agent, no outbound network. That is the answer to “is the AI authorised to act?”, and it is decided before any prompt is written.

2

Build the context package. Language and framework, build files, the module map, the routes that accept untrusted input, and the contract the code is meant to satisfy. Partial code produces shallow analysis, so the unit of work is one entry point with its callees — not the whole repository.

3

Combine the techniques. Static analysis gives deterministic coverage and file-and-line output; the LLM triages and clusters that output and explains which warnings are reachable; manual review judges intent and design; fuzzing supplies dynamic proof for the candidates that are reachable. No single technique is asked to do the whole job.

4

Prompt for evidence, not verdicts. “For each candidate give file, line, the data path from source to sink, and the input that would trigger it. If the path does not exist, say so.” This is the countermeasure to hallucination: a fake finding cannot survive the demand for a trace.

5

Cover the gaps a single run leaves. Run again with different phrasing, a different model and a different temperature; ask for edge cases and non-obvious logic flaws after summarising what has already been checked. Non-determinism is turned from a defect into a coverage technique.

6

Verify by hand, then report. Open each file, trace the data path yourself, construct the trigger in the lab, minimise it, state the impact and its preconditions, and record what was refuted along the way. The report is the evidence chain, not the model's list.

Worked example — triaging one AI report. A model returns: “Critical SQL injection in the user search function; user input is concatenated into the query string.”

1

Locate. Open the file at the stated line. If the code there is a parameterised query built with bound placeholders, the finding is already refuted — record the reason and move on. Most false positives die at this step.

2

Trace the data path. Is the value that reaches that line actually attacker-controlled? Follow it back through validation, encoding, the framework's own escaping and the caller. A path that breaks anywhere in that chain refutes the candidate.

3

Test the trigger. In the authorised lab instance, supply the input and observe. A returned error, a changed result set or a crash is evidence. A description of what “would” happen is not.

4

Minimise. Reduce to the smallest input that still shows the behaviour, so a reviewer can reproduce it in seconds. This is also the test of whether you understood the mechanism rather than the symptom.

5

Check the inverse. Ask the model to argue why the finding is wrong: “give the strongest reason this input cannot reach the sink.” A model asked to critique its own answer often finds the framework control it missed the first time — and sometimes fails to, which raises your confidence in the confirmed case.

6

Write the verdict. One of three outcomes — confirmed (evidence, impact, fix), refuted (the reason, so nobody re-chases it), or unresolved (the precise limit, handed to a human). Any of the three is a professional result; only an unverified claim is not.

Tutorial exercise — working backwards from an artefact you did not build. The deck introduces the mobile pipeline as the lab's shape: Kotlin / Java human-readable code is built and compiled into an APK, which is what you receive; you then install and run it. Your task is to work backwards — understand, investigate, verify.

1

Name what you have and what you lost. You hold the compiled package, not the source: symbol names may be stripped or obfuscated, and the manifest, resources and native libraries are part of the artefact. Job one is to reconstruct enough structure to ask sensible questions.

2

Set the boundary before touching it. Analysis of an app you are authorised to assess, in an isolated environment, with no interaction with the app's live backend. This is the same authorisation question as for any agent with tools — capability matched by trust.

3

Choose the right technique for each layer. Manifest and permission review is structural and deterministic, so it is read directly. Decompiled bytecode is where AI-assisted reading is weakest — less natural-language signal, fewer clean paired examples, low-level and ambiguous — so treat any AI claim about decompiled code as a hypothesis to be checked against the code itself.

4

Ask for structure, then for suspicion. First: “list the entry points, exported components and the trust boundary between app and backend.” Only then: “which of these handle untrusted data, and what would a data path from input to a sensitive sink look like?” Splitting the two keeps the model grounded in the artefact you supplied.

5

Verify dynamically. Observe the app running in the isolated environment and let behaviour — not the narrative — decide. Failures, adaptations and partial successes are the raw material of the investigation log: failures → adaptation → partial success → verification.

6

Report the process as well as the finding. Because the same week's lecture asks whether we learned anything when the AI solved it, the write-up should show what was tried, what failed, what the tool reported, and which step a human confirmed. That is the difference between an answer and an investigation.
