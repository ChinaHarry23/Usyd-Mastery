Mobile Security in the Age of AI

The deck opens with a warning against complacency: AI does not replace mobile security, it creates new actors that can interact with mobile systems. The valuable data has not moved — it is still on the phone.

The organising question for the whole week: what crosses each boundary in a mobile platform, and who should be allowed through?

Selected smartphone operating systems (2026)

Android ~70% — used by Samsung, Xiaomi, Oppo, Vivo, Google Pixel and others; an open-source core (the Android Open Source Project, AOSP) with many vendor variants. iOS ~30% — used only on iPhones. Everything else <1% — HarmonyOS (Huawei), KaiOS, and Linux-based experimental systems such as Sailfish OS and Ubuntu Touch. Sources: gs.statcounter.com and appmagic.rocks, as cited in the deck.

Why the split matters for defence: the deck makes Android the focus because of its market share and because its architecture is open enough to inspect. Market share sets where attacker effort goes; architecture sets which controls you can actually reason about.
PlatformShare (2026)Ecosystem shapeSecurity consequence
Android~70%AOSP core plus many vendor variants and app storesVendor customisation adds code and channels that the AOSP security model does not cover by itself
iOS~30%One vendor, one device family, one storeA smaller, more uniform surface — but the same class of risk for the data an app already holds
HarmonyOS, KaiOS<1%Regional and low-end ecosystemsFewer eyes, shorter support windows, and update paths that are harder to audit
Sailfish OS, Ubuntu Touch<1%Linux-based experimental systemsUseful for study because their permission and packaging models are visible, not because they are widely attacked

Why Android is not entirely open source

AOSP is the open core. A shipping phone is not AOSP: vendors add proprietary hardware drivers and their own applications, and Google's own mobile services and app store are separate, licensed components. The security consequence is concrete — anything added above the core is code you must reason about separately, and anything that ships as a system app carries the privileges of a system app.

A team is designing a security review process and can only cover one platform deeply. On what grounds does the deck justify choosing Android?
Because every line of Android on a shipping phone is open source and therefore auditable
Because it holds about 70% of the market and its architecture is open enough to inspect
Because iOS has no meaningful attack surface left to study

Android Is the Gatekeeper

Apps are isolated by default. Your app starts isolated from every other app, and Android decides what may cross each boundary. Communication happens only through controlled mechanisms.

Every request leaves your app through a gate that Android controls. A missing or misconfigured control is what exposes an app and its data.

How an app reaches the hardware

The app asks Android to perform an action; it never controls the device directly. A camera app calls the camera API, Android checks the permission, the framework manages the request, and a hardware abstraction layer translates it for the actual device. Every layer controls what the layer above it can do.

More privilege means more impact

LayerTrust levelWhat a compromise there buys an attacker
AppslowestWhatever that single app can reach: its own files, its granted permissions, the components it can start
Framework servicesmediumThe ability to answer permission and intent questions on behalf of the system
Native services / HALhighDirect control of hardware: camera, microphone, radios, sensors
KernelhighestThe device itself — every sandbox, every app and every control at once
The point of layering: to control the whole phone, malicious code must escape its sandbox and cross several security boundaries. No single control is the only line of defence — that is what makes the model survivable when one control fails.
Why does the deck insist that a privileged or system app is a bigger problem than a normal app when it is compromised?
Because a privileged app can do more and therefore causes more harm if compromised
Because system apps run outside the sandbox and the permission model
Because system apps are installed on more devices

Where Can an Android Attack Happen?

Android has several layers, so a threat can target the device, the software running on it, or the access an app is allowed to use. The deck splits that space into three bands.

BandWhere the attack actsDeck examplesQuestion that separates it
HardwarePhysical access and connected devicesJuice jacking at a compromised public USB charging stationCan I trust what I am plugging into?
RuntimeBugs while software is executingBuffer overflow, use-after-free, type confusionCan crafted input make the program misbehave?
Gray zoneLegitimate app access that creates harmContacts, photo-library and location access that goes beyond what the feature needsWas the access necessary, proportionate and used responsibly?

Two ways an attack can enter: a hardware attack begins when the phone is physically connected to something untrusted — unsafe connection. A runtime attack begins when software fails while it is running — unsafe execution. The difference is where the attack starts, not how damaging it turns out to be.

The gray zone is a design question, not a bug. WhatsApp may hold contacts access, TikTok or REDNOTE may hold photo-library access, and Google Maps may hold precise location. In each case the deck's question is the same: does the feature need the entire address book, the entire album, location all the time? The user allowed it, but the security question is also whether the access was necessary and proportionate.

Worked example — working one incident through the classification. Scenario: a conference attendee charges a phone at a free public charging kiosk. The kiosk also presents itself as a data device, and the phone's screen offers “allow access to phone data”. The attendee taps Allow.

1

Place it in the classification. Nothing has corrupted memory and no app permission is involved, so this is not a runtime attack and not the gray zone. The attack begins at physical contact with an untrusted device: hardware band, unsafe connection.

2

Find the boundary that was crossed. The USB port was treated as a power channel but it is also a data channel. The device, not the attacker, asked the question — so the control that failed is the one that decides what a connected host may do.

3

State the attacker's requirement honestly. The compromise needs the user to accept a prompt, or a platform flaw that answers it without the user. That is why the countermeasure is framed as trust in the connection and not merely as user education.

4

Write the countermeasures at the right level. Carry your own power supply or a power-only adapter; treat an unfamiliar port as a data port; keep the device locked and decline data prompts; and for managed fleets, restrict what a host connection is permitted to do by policy.

5

Answer the control question. The deck's question for this band is “can I trust what I am plugging into?”. The defensible answer is that you cannot know, so the design decision must be to make trust unnecessary — charge without a data connection.

A banking app's transfer screen opens correctly from a link, but the app never verifies that the person tapping the link is the logged-in account holder. Which band does this failure belong to?
Runtime attack, because the failure happens while the software is executing
Hardware attack, because the request came from outside the device
Gray zone, because legitimate access is being used to produce an unintended effect

An APK Is the App on Disk

Android apps are installed as APK files — the installable package that carries code, resources and settings from the developer to the device. The developer builds it; the device installs and runs it.

User-installed apps

WhatsApp, Spotify, and the app your team builds. Installed from a store or a file, running under an ordinary app user ID, limited to what it is granted.

System apps

Settings, Phone, and vendor applications. Shipped with the platform, often holding privileges an ordinary app cannot obtain — which is why a flaw there matters more.

Four parts to inspect first

An APK behaves like a ZIP archive. For security analysis, start with AndroidManifest.xml (components, permissions and security configuration), classes.dex (compiled application code), res/ and assets/ (screens, images and packaged files), and META-INF/ (signing and certificate information).

Security analysis focuses on both configuration and code. A manifest that exports a component is not a vulnerability on its own, and neither is code that computes a price. The finding appears where a configuration decision and a code path meet.
An analyst has one hour and an unfamiliar APK. According to the deck's ordering, where should the reading start?
In res/layout/, to see every screen the app can display
In AndroidManifest.xml, to establish what exists and what is exposed
In META-INF/, to confirm the signing certificate first

JADX reads the APK's bytecode and writes a folder of readable source-like files. The direction of the transformation matters for how much you can trust the result:

Security takeaway, in the deck's own three steps: if code is delivered to a user's device, assume that someone can inspect it. Mobile apps can be reverse engineered; compiled code is not secret; and you should never store sensitive secrets in the client app. Protect secrets on trusted servers — not inside the APK.
A team hides an API key by splitting it across three string constants and reassembling it at runtime. What is the correct assessment?
The key is safe, because decompilers cannot reconstruct strings built at runtime
The key is still recoverable, so the secret belongs on a trusted server instead of in the client
The key is safe as long as the APK signature verifies on install

The Four App Components

Every Android app is assembled from four kinds of component, each with a different job. The lecture concentrates on activities, because a screen is where user intent and attacker intent meet.

ComponentJobDeck exampleWhat is at risk if it is reachable
ActivitiesScreens the user interacts withLogin, home, settingsA screen that performs a sensitive action on open, without checking who opened it
ServicesWork in the backgroundMusic playbackUnbounded background work: battery, data, and actions taken without a visible screen
Broadcast receiversRespond to system eventsLow-battery alertA forged or replayed event triggering a response the developer assumed was system-originated
Content providersShare data between appsContacts or calendarBulk data exposure: one misconfigured provider can leak a whole dataset, not one record

Focus: activities. An activity combines a screen layout with the code that controls it. activity_login.xml says what the screen looks like; Login.java says what the screen does; AndroidManifest.xml tells Android which activities the app can start. In SafeCampus those are MainActivity, Login and Profile.

Intents: One Tap Can Leave Your App

An intent is the message Android delivers to another screen or app. It is the request, not the destination — and that distinction is where the security questions start.

Mental model

app → intent → destination. Tapping “share photo” in your app builds an intent with an action (SHARE) and data (photo.jpg). Android, not your app, finds a destination: the camera, photos, email, WhatsApp or Instagram.

Explicit intent

One exact destination. Your code names the activity directly — for example, the login button starting LoginActivity. There is no ambiguity about who receives the message.

Implicit intent

Your code describes the action, not the app. Android offers the choices — a chooser for Gmail, Photos or a share target. The receiver is decided by the system at runtime.

The deck's own question — “which type is more dangerous?” — has a precise answer: neither intent type is dangerous by itself. Security depends on who can start the activity and on whether the activity checks authentication. An activity with no lock is the real danger, whichever kind of intent reaches it.

Worked example — deciding whether an intent design is safe. Scenario: the SafeCampus app has a Profile activity that loads the signed-in student's record and a ResetPassword activity that takes the new password from the intent.

1

Ask who can start it. Read the manifest: is the component exported, and does it carry an intent filter that other apps can match? An explicit intent from inside the app is not the only route in.

2

Ask what the activity checks. Profile should confirm there is a valid session and that the session owns the record being requested. Rendering a screen is not the same as authorising the data behind it.

3

Treat every extra as untrusted input. An intent can carry parameters that arrive from outside the app. A password supplied by an intent is attacker-controlled input, so it must never be accepted as proof of identity.

4

State the verdict. Profile is safe only if it authenticates and authorises before rendering. ResetPassword is unsafe by construction: because possession of an intent is not proof of anything, the operation must require a logged-in session and an out-of-band confirmation.

5

Name the countermeasure that generalises. Export only what must be public; authenticate before acting; validate anything that crossed a boundary. The intent type never had to change.

The Manifest: Identity Card and Security Map

AndroidManifest.xml tells Android what exists, what starts first, and what outsiders can reach. The deck's instruction is blunt: open the manifest before reading the Java code.

QuestionWhere the answer livesWhat you are looking for
1. What exists?<activity>, <service>, <receiver>, <provider>The full inventory of components the app can be made to run
2. What starts first?The launcher activityThe entry point a user reaches, and the route everything else hangs from
3. What is requested?<uses-permission>Camera, location, storage, network and the rest of the capability list
4. What is exposed?exported and intent filtersWhich components another app can start — the part of the app that is genuinely public

Decode an intent filter with three questions

1. What action? <action android:name="…" /> — MAIN, VIEW, SEND, DIAL and so on. The action says what the sender wants done.

2. How is it used? <category android:name="…" /> — LAUNCHER, DEFAULT, BROWSABLE. The category says how the component should be treated.

3. What data? <data … /> — a URL scheme, a file type, a phone number. The data says which inputs will match.

MAIN = starting action LAUNCHER = appears in the app launcher exported="true" = public app entry point

The rule that follows: look for MAIN + LAUNCHER first, then check whether the exported access is expected and safe. A public entry point is normal for a launcher activity and abnormal for a screen that moves money.

Worked example — triaging an exported activity. Scenario: a manifest excerpt exports a TransferActivity and declares a filter with MAIN, LAUNCHER and a custom myapp://transfer data scheme. The activity's code reads an amount and a toAccount value from the intent.

1

Sort the questions. What exists: an activity. What starts first: check whether this activity also holds the launcher action, or whether a different activity does. What is requested: read the permission list. What is exposed: an exported activity with a browsable data scheme.

2

Decode the filter. Action: MAIN is the starting action, but a custom myapp:// scheme means any app — or any web page that can trigger the scheme — can reach it. Data: the scheme plus whatever the caller appends. That appended part is attacker-controlled.

3

Read the code path. The activity parses amount and toAccount and calls the transfer routine. Two things must be true before this is acceptable: the values must be validated against an expected form, and the caller must be an authenticated session permitted to move that money.

4

The finding. A deep link that opens a transfer screen must not send money merely because the screen opened. If authentication, authorisation or confirmation is missing, the harmless-looking exported activity is a way to act as the user.

5

The countermeasures, in order of strength. Do not export a component that need not be public. If it must be public, require an authenticated and authorised session before the screen renders. Validate every parameter. And require explicit user confirmation for the sensitive action itself.

An activity is exported and carries an intent filter with action MAIN and category LAUNCHER. What is the most defensible reading?
It is the app's public starting point: expected for a launcher activity, but still worth checking what it does on open
It is automatically a vulnerability, because exported components can be started by any app
It tells you the activity requests no dangerous permissions

Deep Links Are Untrusted Input

A deep link is a URL that opens a specific screen inside an app; Android matches it using intent filters. The useful framing for security is not “convenience feature” but “an input channel that anyone can write to”.

1 tap coupon link
myapp://discount?code=…
→
Android matches the intent filter
scheme + host + path
→
2 the matching screen opens
shopping app → discount screen
The rule the deck states plainly

Treat every deep link as untrusted input. Parameters can be changed by anyone. A link may open a sensitive screen, but it must never bypass the security checks that screen depends on.

CheckQuestion to answerWhat failing it looks like
1. ValidateIs the URL and the input in it what the app expects?A parameter whose value the developer never imagined reaches business logic directly
2. AuthenticateIs the user logged in, and are they authorised for this action?A sensitive screen renders for whoever followed the link
3. ConfirmFor a sensitive action, has the user agreed to this specific action?The screen opening is the action — a transfer happens because a link was tapped
The sentence that covers the whole section: validate input + check session + confirm sensitive actions. Skipping any one of the three converts a feature that saves a tap into a way to act as the user — because attackers may manipulate the inputs, or simply trick a user into an action they did not intend.
A deep link opens a password-reset screen with the new password supplied as a URL parameter. Which missing check does this violate most directly?
Validation — the password string was not checked against an expected format
Session and confirmation — the link is being treated as authorisation for a sensitive account action
Registration — the app failed to register the link scheme with the platform

The UI Tree and Mobile Agents

A mobile agent is AI that observes and interacts with a mobile app automatically. It repeats one simple loop, and the loop is what makes it useful — and what makes it part of the attack surface.

UI tree

A machine-readable map of the screen's elements and their properties. Each element becomes structured data: TEXT (Gmail), TYPE (button or image), CLICKABLE (true or false), BOUNDS (screen location). The agent then knows what is visible, what is clickable, and where to act.

Loop stageWhat the agent doesWhat it needs from the appSecurity question
ObserveReads the screen and its UI elementsAn accessible UI tree with labelled elementsDoes the exposed metadata reveal anything the screen did not intend to show?
DecideChooses the next actionElement roles and state that make the choice unambiguousCan a label be crafted so the agent chooses the wrong action?
ActTaps, types, swipes or opensA target that is genuinely the element it appears to beIs the action authorised for this user, at this moment?
RepeatObserves the result and continuesA stable, honest screen state after each actionCan the loop be driven somewhere the user never agreed to go?
Security takeaway: automation can inspect and operate the UI at scale, and UI structure may expose sensitive labels or state. Treat UI metadata and automated actions as part of the app's attack surface — a screen that is safe for a human to look at is not automatically safe for a machine to enumerate.

What agents make easier to defend

  • Consistent labelling and accessibility metadata, because automation needs to find elements reliably
  • Explicit confirmation steps, because a machine can repeat an action far faster than a person
  • Server-side authorisation, because the agent can reach every screen the UI tree exposes

What agents make easier to attack

  • Volume: an automated actor tries every reachable screen, not the two a user would find
  • Metadata leakage: labels and state can carry information the visible screen hides
  • Intent confusion: an action taken without a human behind it is hard to distinguish from one the user meant

Worked example — hardening an app for automated clients. Scenario: a university app exposes a UI tree with labelled buttons for Enrol, Drop unit and Pay fees. A student builds an agent that reads the tree and completes enrolment automatically.

1

Identify what the agent can actually reach. Everything the UI tree exposes. The tree is the attack surface: an element the agent can find is an element it can operate, whether or not a human would ever look for it.

2

Separate reversible from irreversible actions. Enrolling and dropping a unit have deadlines and financial consequences; paying fees moves money. The design response differs per action, so classify before defending.

3

Move authorisation off the screen. A UI check is a usability aid, not a security control. The server must re-check the session, the student's eligibility and the deadline for every request, because a client — human or agent — can be scripted.

4

Require explicit confirmation for the sensitive step only. Confirming everything trains people to confirm blindly. Confirming the fee payment, with the amount and the account restated, keeps the check meaningful.

5

Review the metadata you publish. Every label, content description and state in the UI tree is data. If a label exposes an internal status or an identifier, remove it from the tree rather than relying on nobody reading it.

Why does the deck call UI metadata part of the app's attack surface?
Because exposing a UI tree grants the reader extra Android permissions
Because the tree is machine-readable: anything in it can be read and acted on at scale, and it may reveal labels or state the screen hides
Because automation makes the app's sandbox unnecessary

Week 3 Recap

Android is the gatekeeper

Apps start isolated. Android decides what crosses each boundary through three controls: the sandbox, intents and permissions. Safe by default — until a control is missing or misconfigured.

Architecture

Classify by entry, not by damage

Hardware (unsafe connection), runtime (unsafe execution), gray zone (legitimate access that creates harm). Each band has its own question and its own countermeasure.

Threat model

An APK is readable

Manifest, dex, resources, signing information. Decompile the dex to inspect logic — and assume that anyone can, which is why secrets belong on a trusted server.

Analysis

Intent type is not the risk

Explicit or implicit, the question is who can start the component and whether it checks authentication. The manifest tells you who; the code tells you whether.

Components

Deep links are untrusted input

Validate input, check the session, confirm sensitive actions. A link may open a sensitive screen; it must never bypass the checks that screen relies on.

Input

Agents widen the surface

The UI tree turns a screen into structured data. Automation can inspect and act at scale, so UI metadata and automated actions are part of what must be defended.
