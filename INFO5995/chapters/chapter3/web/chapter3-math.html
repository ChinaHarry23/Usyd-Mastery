Foundations: the mobile security model, written precisely

Week 3 is a systems week, so this page does the equivalent of a formula sheet: it fixes the threat-model vocabulary, writes the sandbox and permission model as relationships you can reason about, turns “where does this data live?” into a table of named storage classes with their exposure, and ends with the artefact-to-finding workflow that turns an APK into defensible findings.

Threat model & attack surface

The deck's framing question is the one to carry into every mobile assessment: what crosses the boundary — and who should be allowed through? A threat model is how you answer it on purpose rather than by accident.

Threat model — four questions, in this order

1. What are we building? 2. What can go wrong? 3. What are we going to do about it? 4. Did we do a good enough job? Answer them for a mobile app and the second question immediately becomes platform-specific, because the app is not the only thing running on the device.

Attack surface (week 3 definition)

The set of places where data or control can cross a trust boundary. On the study page that produced exactly three lists: other apps, system resources (camera, files, location), and the messages an app will accept (activities, services, receivers, providers, deep links).

1. The attack surface is a sum, not a feeling

Let \(C\) be the app's components. Each component contributes an exposure term, and a component only contributes when all three conditions hold at once:

\[ \text{Surface}(C) \;=\; \sum_{c \in C} \mathbb{1}\!\left[\,\text{exported}(c) \;\wedge\; \lnot\text{auth}(c) \;\wedge\; \text{sensitive}(c)\,\right] \]

Read the indicator function as a checklist: the component must be reachable from outside, must not require authorisation, and must do something that matters. Drop any one of the three and the term is zero — which is exactly why “is this a finding?” is a question about a conjunction, not about a keyword.

2. Risk composes the same way it does everywhere else

The Week 1 risk language still applies; only the inputs change:

\[ R \;=\; T \times V \times I \]

On mobile, \(T\) is who can reach the entry point (any installed app, any web page that can trigger a link, anyone with physical access), \(V\) is whether the control that should have stopped them is present, and \(I\) is what the app can do or disclose once reached. A high-impact action behind an authenticated server check has \(V \approx 0\) for a remote attacker; the same action on an exported screen with no session check has \(V \approx 1\).

3. Privilege is transitive, so impact grows with the layer

Write the attacker's cost as the product of the boundaries that must be crossed. With \(p_i\) the probability of crossing boundary \(i\):

\[ \Pr(\text{full compromise}) \;=\; \prod_{i=1}^{n} p_i \qquad\text{and impact scales with the layer reached} \]

This is the arithmetic behind the deck's trust table. Apps are the cheapest layer to reach and the least valuable to own; the kernel is the most expensive and the most valuable. That is why defence in depth is not redundancy — each boundary multiplies the attacker's cost by a factor below one.

The sandbox & permission model

Two mechanisms do most of the work on Android: apps are separated from each other, and access to protected resources is granted explicitly. Write both down and the week's analysis questions become mechanical.

Sandbox

Apps are isolated by default: each app normally has its own user ID and its own sandbox. Android — not the app — decides what may cross each boundary, so communication between apps happens only through controlled mechanisms.

Sandbox as a policy on the attacker's reach

Model a sandboxed app as a tuple \(\langle u, D_u, G_u \rangle\): its own user ID \(u\), the data directory \(D_u\) it owns, and the set of permissions \(G_u\) it has been granted. File access is a policy decision:

\[ \text{allow}(a, f) \;=\; \big[\, \text{owner}(f) = u_a \,\big] \;\vee\; \big[\, \text{perm}(f) \in G_a \,\big] \]

The first clause is possession: an app can always read files it owns. The second is a decision made at the boundary. Everything the study page calls a “gate” is an instance of this second clause — camera, location, files, microphone, and the system services that broker them.

Privilege tiers and blast radius

Order the layers by the trust the deck assigns them: apps, framework services, native services and HAL, kernel. If a compromise at layer \(\ell\) exposes everything at or below \(\ell\), then the blast radius is monotonic in \(\ell\):

\[ \ell_{\text{apps}} \;\prec\; \ell_{\text{framework}} \;\prec\; \ell_{\text{native/HAL}} \;\prec\; \ell_{\text{kernel}} \qquad\Longrightarrow\qquad B(\ell_1) \subseteq B(\ell_2) \;\text{ whenever }\; \ell_1 \prec \ell_2 \]

Practical use: when you rank findings, you are really ranking \(\ell\). A missing check in an app is bounded by that app's grants; the same class of mistake inside a framework service is not.

Permissions — what must be written in an answer

A permission protects a capability rather than a file: camera, location, files, microphone and the rest. It is requested in the manifest, granted by the user or the platform, and checked when the resource is actually used. A permission that was granted once is not consent for unlimited collection — the gray-zone question (“necessary and proportionate?”) survives every grant.

Storage, secrets & proportionality

The deck states the conclusion before the technique: never store sensitive secrets in the client app — protect secrets on trusted servers. This section turns that instruction into a table of storage classes you can name in an answer.

The three storage classes

App-private internal storage — owned by the app's user ID, protected by the sandbox. External or shared storage — shared with other apps and with the user; treat it as public. Credential or key storage — platform key material that the app can use without ever reading the secret itself. Putting a value in the wrong class is a design defect, not a coding mistake.

Storage classWho can read itAcceptable contentNever put here
App-private internal storageThe app's own user ID; the platformCached sessions, preferences, non-sensitive stateLong-lived passwords or shared secrets, if a server-side alternative exists
External / shared storageOther apps and the user; increasingly also backup and sync pathsUser-visible media the app is meant to hand overTokens, keys, personal data the app is not prepared to publish
Platform credential / key storageThe app may use the key; it does not get to read raw key materialKeys for signing, encryption and authenticationAnything the client fundamentally should not be able to do alone
Packaged in the APKAnyone — decompilation is expectedPublic configuration, endpoint names, feature flagsAPI keys, signing keys, credentials, anything a server should hold

Why client-side secrets fail — the search space argument

Suppose a secret has \(H\) bits of entropy and an attacker who can inspect the client gets one guess per attempt at rate \(r\). The expected time to recover it is

\[ \mathbb{E}[t] \;=\; \frac{2^{H-1}}{r} \]

For a 4-digit PIN, \(2^{H} = 10^{4}\); at \(r = 100\) guesses per second the expected recovery time is about \(50\) seconds. Raise the secret to an 8-character mixed-alphabet password and \(2^{H}\) reaches roughly \(2^{52}\), which at the same rate is geological. The asymmetry is the whole argument: a secret that ships to the client is not protected by its length, it is protected only by the attacker's patience — and the attacker sets that.

How to write this in an exam: “Client-side secrets are recoverable because the code is delivered to the device and can be decompiled, so the correct control is architectural rather than cryptographic. Store the secret on a trusted server, keep long-lived keys in platform key storage so the app never holds raw key material, and store nothing sensitive in the APK or in shared storage.”
A team must let the app call a third-party paid API. Where should the API key live?
In the APK, obfuscated so that decompiled code cannot reveal it
On a trusted server that the app calls through a mediated endpoint
In a file in the app's external storage directory

Worked answer — choosing storage for four values. A campus app holds: (a) a session token, (b) an API key for a paid timetable service, (c) a user's saved PDFs, (d) a signing key used to prove the app's requests came from the app.

1

(a) Session token. Keep it in app-private storage or in memory, scoped as narrowly as possible and expiring quickly. It is a bearer credential, so its lifetime is the control — a token that cannot be refreshed is far less valuable to an attacker than one that lives for months.

2

(b) Paid API key. Not in the app at all. Put it on a server you control and have the app call your endpoint. The client cannot be trusted with a secret whose disclosure costs money, and no amount of obfuscation changes that.

3

(c) Saved PDFs. These are the user's own documents, so they may live in app storage or a user-visible location — but decide deliberately, because shared storage means other apps and backup paths can reach them. If they can contain personal data, keep them app-private and export on request.

4

(d) Signing key. Generate it in platform credential storage so the app can use it without reading it, and design the server side to accept only what that key proves. If the client could export the key, then anyone who decompiles the app can impersonate it — which means the key was never proving anything.

5

The sentence that earns the mark. “Each value was placed by asking who must be able to read it: only the app (private storage), nobody on the device (a server), the user themselves (shared storage), or nobody at all, not even the app (platform key storage). The APK itself holds no secrets, because decompilation is expected.”

Artefact → finding workflow

The deck's analysis order is configuration first, then code. Written as a workflow, that gives a repeatable table: for each artefact, one question, one evidence source, and one class of finding.

Deep-link validation as an explicit predicate

A deep link is untrusted input, so model the decision rather than the prose. For an incoming URL \(u\), a session \(s\) and an action \(a\):

\[ \text{allow}(u, s, a) \;=\; \text{valid}(u) \;\wedge\; \text{authenticated}(s) \;\wedge\; \text{authorised}(s, a) \;\wedge\; \big(\lnot\text{sensitive}(a) \,\vee\, \text{confirmed}(a)\big) \]

All four conjuncts are required. The formula is a compact way to answer the common exam follow-up — which single check was missing? — because a missing check is a false conjunct, and false conjuncts are visible one at a time.

Worked answer — writing a finding so it can be acted on. Observation: an exported activity accepts a reset action from a deep link, reads the new password from a URL parameter, and applies it without asking for the current password.

1

Name the artefact. The manifest exports the component and declares a browsable filter; the code path is in the decompiled activity. Evidence exists in two artefacts, which is what makes the finding solid rather than speculative.

2

Name the boundary. External input crossed into an authentication action. That is one boundary, not three, and saying so keeps the finding readable.

3

Test the predicate. \(\text{valid}(u)\) is unchecked because the password string is used as supplied; \(\text{authenticated}(s)\) is missing because anyone can compose the link; \(\text{authorised}(s, a)\) is missing for the same reason; \(\text{confirmed}(a)\) is missing because opening the screen performs the action.

4

State the impact in terms of the risk model. \(T\) is broad (any app, any web page that can trigger the scheme), \(V\) is near one (four missing conjuncts), \(I\) is account takeover. High risk, and the reason is the middle term — not the sensitivity of the screen.

5

Pair it with countermeasures, strongest first. Do not accept a password from a link at all; require an authenticated session and the current credential; confirm the action explicitly; validate every parameter; and stop exporting anything that need not be public.

During a review you find an exported ViewProfile activity with no session check, and it is the only exported component. What is the most defensible risk statement?
The risk is maximal because the component is exported
Threat is broad, the control is missing, and impact is whatever the profile discloses — so the risk is real and the countermeasure is a session check or dropping the export

The two sentences that summarise the week

1. Security modelling asks what crosses the boundary — and who should be allowed through. 2. If code is delivered to a user's device, assume that someone can inspect it, so never store sensitive secrets in the client app.

Instance one is the architecture claim; instance two is the consequence. Almost every Week 3 question is a special case of one of them.
