Week 7: Secure Network, TCP/UDP, TLS and HTTPS

Your login may already be verified — but your data still has to travel. Packets on an Untrusted Path

The week opens with a question that has nothing to do with cryptography: once a login is accepted, the data still has to cross networks nobody in the conversation controls.

The framing claim from the deck: network security protects data while it moves across untrusted networks. Everything else this week — IP, UDP, TCP, TLS, HTTPS — is machinery for doing that in a place where every hop is somebody else's equipment.

The lecture traces one email from a laptop to a mailbox to make the path concrete. Nothing about it is specific to email: the same six steps describe an HTTP request, a bank transfer or a DNS lookup.

Terminology

Unprotected data is data that is readable or modifiable by any device on the path. The deck's mental model is a chain of custody: your device, your router, your ISP, other networks, the destination network, the destination host — each one a place where a copy or an edit can happen. Data in transit is the only thing this week's controls protect; data at rest and application logic are separate problems.

Exam framing: “the internet is untrusted” is not an argument, it is a premise. The markable version names the four capabilities (read, change, pretend, block), maps each to a property, and then says which layer supplies the property.

IP, UDP and TCP: What Each Layer Promises

IP moves packets. It promises nothing about whether they arrive, in what order, or how many copies you get. Transport protocols exist to repair that — and to stop there.

IP: addressing and best-effort delivery

Every packet carries a destination IP address and is forwarded hop by hop. The deck's list of what can happen is deliberately unsentimental: packets can be lost, late, out of order or duplicated. IP does not promise delivery, order or uniqueness — which is exactly why UDP and TCP sit above it.

UDP: fast datagrams, no waiting

UDP sends independent packets with almost no overhead: no connection setup, no retransmission, no ordering guarantee. The application decides what to do about loss. It is the right choice when late data is less valuable than fresh data — voice calls, online games, and DNS queries.

Three ideas that make TCP work

Sequence numbers label every byte so the receiver can rebuild the stream and notice gaps. Cumulative acknowledgements tell the sender which byte is expected next — the deck's example is an ACK 131 that means “everything up to byte 130 arrived”. Windows let the receiver control how much data may be in flight, which is how TCP adapts to a slow or congested path.

The three-way handshake is what the deck calls “connection state before application data starts moving”. Both endpoints agree to start, synchronise sequence numbers, and then begin reliable transfer. When something is missing, the receiver keeps acknowledging the byte it still expects, no progress is made, and the sender retransmits the missing range. TCP does not replace IP: it detects problems above IP and recovers from them.

The line that sets up the rest of the week: TCP makes delivery reliable, and it is still not secure. It offers no secrecy and no server identity. Order, acknowledgement and retransmission answer “did it arrive?”; they say nothing about who is on the other end or who else is reading.

Worked example — read the trace, then name the guarantee. A capture of one connection shows these four lines. For each, state what TCP has established and what it still has not established.

1

SYN → SYN-ACK → ACK. Established: both endpoints exist, are reachable, and have synchronised initial sequence numbers; the server has allocated connection state. Not established: anything about identity. The handshake proves an address responded, not which organisation or service it belongs to.

2

Seq 1–40, 41–70, 71–100, 101–130 followed by ACK 131. Established: the receiver rebuilt an ordered byte stream from packets that may have arrived in any order. Not established: that the bytes mean what they appear to mean. Reordering is repaired; tampering is not detected.

3

Seq 41–70 missing, receiver keeps sending ACK 41. Established: the sender will retransmit, because no progress triggers recovery. Not established: confidentiality. Every one of those bytes crossed the path in the clear.

4

The sentence that earns the mark. “TCP answers the delivery question — order, acknowledgement and retransmission — and leaves the security questions open: whether the content was private, whether it was changed, and whether the endpoint is the server it claims to be.”

Network Attacks: Reconnaissance, Availability and Forged Identity

Three attack families from the deck set the agenda for the rest of the week, and each one attacks a different part of the stack.

1. Port scanning: what is exposed?

The question reconnaissance asks

Which network services are reachable? A scan walks a range of ports and notes which ones answer — through a completed handshake, a half-open handshake, or the way a closed port refuses.

The key idea from the deck

An open port reveals a reachable service; the risk depends on what is running and how it is configured. Reconnaissance does not equal compromise — it identifies possible entry points.

PortServiceWhat an attacker learns from an answerDefensive question
22SSH — remote loginA remote administration surface exists and is reachableIs it restricted to a management network, and is password login disabled?
80HTTP — webPlaintext web traffic is being servedShould it do anything except redirect to HTTPS?
443HTTPS — secure webA TLS service is reachable; the version and suites are enumerableIs the minimum version enforced and the certificate chain correct?
3306MySQL — databaseA database is exposed beyond the application tierWhy is it reachable from outside the application's segment at all?
53DNS — name resolutionRecursive or authoritative service, often unauthenticatedIs it rate limited and, where it matters, signed?

2. SYN flood: what if the final ACK never comes?

The attacker repeats only the beginning of the handshake. The server allocates state and answers each SYN, and because no final ACK ever arrives, those entries stay in the backlog until the server gives up on them. The service may still be running, but legitimate clients struggle to connect: this is a denial-of-service attack against availability.

Why the state is the vulnerability: TCP was designed to keep connection state, and a SYN is a request to create it. The attack asks the server to make a promise — and to keep paying for it — on the word of an address that was never verified. The standard mitigation, SYN cookies, removes the promise: the server encodes the connection parameters into its own sequence number and allocates nothing until the ACK actually arrives.

3. Spoofing: making the network believe a lie

ARP spoofing and IP spoofing operate at different layers, but both falsify addressing information so that traffic goes somewhere it should not, or appears to come from somewhere it did not.

ARP spoofingIP spoofing
ScopeOne local network segmentAny network the forged packet can reach

Context determines the impact. The deck's wording is careful: spoofing can enable redirection, impersonation or other attacks. The same forged address is a nuisance on a guest network and a catastrophe in front of a database segment — which is why network segmentation is treated as a control in its own right. Segmentation does not encrypt anything; it limits what a single foothold can reach.
A SYN flood is running against a web server that is still serving cached pages to existing sessions. Which property is under attack, and what is the correct description of the impact?
Confidentiality: the attacker is reading the handshake traffic
Availability: the backlog fills with half-open connections, so legitimate clients cannot connect
Integrity: the attacker is replaying completed handshakes

Man-in-the-Middle: Becoming the Path

Individually, reading, changing, impersonating and blocking are annoying. An attacker who owns the path can combine all four — and the deck's warning is that both endpoints may still think the conversation is normal.

Definition

A man-in-the-middle (MITM) attack is an active attack in which the adversary inserts itself between two endpoints and relays their traffic, so that each side believes it is talking directly to the other. The deck's three phases: get in the path, impersonate or relay, and stay unnoticed.

PhaseHow it is doneWhy it works
1. Get in the pathRogue Wi-Fi, ARP spoofing, a compromised network device, a hijacked route or a poisoned name resolutionTraffic follows addressing and routing information, and neither is authenticated at the internet layer
2. Impersonate or relayTerminate the connection on both sides, or forward it unchanged and copy what passesEach endpoint authenticates a connection to its immediate peer, not an end-to-end path
3. Stay unnoticedKeep latency and behaviour plausible; strip or downgrade protection where possibleWithout an authenticated channel, endpoints have no independent way to compare notes

What the attacker gains, mapped to properties

  • Read → confidentiality
  • Change → integrity
  • Redirect → trust: traffic is sent somewhere else entirely
  • Block → availability

Why TCP is not the answer

TCP will happily deliver the attacker's bytes in perfect order and retransmit anything that goes missing. Reliability is not authenticity: an ordered, acknowledged byte stream can be entirely false. The deck's transition line is the whole point — reliable delivery is not enough; security comes from authentication plus encryption.

Worked example — classify the scenario. A staff member joins a “free airport Wi-Fi” network. A browser later reports a certificate warning for the bank; the user clicks through it and the session proceeds normally.

1

Phase. Getting into the path used a rogue access point, so this is phase 1 of the MITM model. No exploit was needed: the client chose the attacker as its gateway.

2

What TLS did. TLS still did its job. The attacker cannot present a certificate for the bank's name that chains to a trusted root, so the client received a name or issuer mismatch — an integrity and authentication failure, correctly detected.

3

Where it broke. The decision to continue. Once the user accepts the warning, the attacker is a legitimate endpoint of that session: read, change, redirect and block all become available, and the padlock icon afterwards means only that a TLS session exists, not that it reaches the bank.

4

Countermeasures, in order of effect. HSTS with includeSubDomains and preload removes the click-through for a known site; a certificate-pinning or policy-enforcing client refuses the connection outright; managed devices can require a trusted profile instead of a self-signed interception proxy. The network-side controls (dynamic ARP inspection, 802.1X, avoiding rogue access points) make phase 1 harder but cannot be relied on alone.

5

The sentence that earns the mark. “An active attacker on the path turns confidentiality, integrity, trust and availability into a single decision made by the client: whether to validate the server's certificate and hostname.”

An attacker relays every byte between a client and a server, terminating TLS separately on each side with a certificate the client rejects. Which statement is correct?
TCP failed, because the relay broke the byte stream
The relay worked, but certificate validation failed, which is exactly how TLS is meant to defeat a MITM
TLS was not in use, so there was nothing to detect the relay

This is the hinge of the whole week. The deck lists what TCP cannot do and then introduces the layer that can.

What changed in TLS 1.3 (RFC 8446)

TLS 1.3 is a redesign, not a tweak. It removed RSA key transport, static Diffie-Hellman, CBC-mode cipher suites, RC4, 3DES, renegotiation and compression. Everything that remains is an AEAD cipher suite with an ephemeral key exchange, so forward secrecy is mandatory: the session key is derived from a Diffie-Hellman secret that is never transmitted, which is why a later compromise of the server's long-term key does not decrypt recorded sessions. The cipher suite now names only the record protection and the hash; authentication is negotiated separately.

Cipher suiteRecord protectionHash for the key scheduleNote

The record protocol: what happens to your bytes

Application data is fragmented into records, each record is encrypted so its content stays confidential, and an authentication tag is added so tampering is detected before anything is released to the application. The deck's one-line summary: application data → TLS record → protected bytes on the network.

Two properties worth stating precisely

Integrity covers metadata, not just content: the tag is computed over the sequence number and content type as well as the payload, so records cannot be silently reordered, dropped or replayed. Authentication happens once, at the start: after the handshake, the session keys do the work, and the certificate is not re-checked per record.

In TLS 1.3, why does compromising a server's long-term private key not decrypt sessions that were recorded earlier?
Because the recorded traffic is re-encrypted after the key is rotated
Because session keys come from an ephemeral key exchange whose secret was never transmitted; the long-term key only signs the handshake
Because the certificate is encrypted, so the long-term key was never sent

Certificates: Which Key Do You Trust?

TLS can only authenticate the server if the client already knows which key to trust. That is the entire job of the certificate system, and the deck treats it as a bridge back to the cryptography weeks.

The bridge, in the deck's own words: a certificate binds a server name to a public key, and a digital signature lets the browser verify that binding. A trusted certificate authority signs the server certificate; the browser checks the CA's signature and the website name, trusts the server's key, and only then uses it to create session keys.

Why the hostname check is not optional: a certificate proves that some name is bound to some key. Only the hostname check proves that the name is yours. An attacker in the path can always obtain a valid certificate for a domain they control; the check is what makes that certificate useless against your bank.
Standards anchor: the validation procedure above is the practical form of RFC 5280 path validation. In deployment, NIST SP 800-52 Rev 2 adds the policy layer: a minimum protocol version, approved cipher suites, and a documented certificate and key-management process.

HTTPS in Practice: Same Request, Protected

HTTPS is HTTP inside TLS. The request does not change; what changes is that it is protected before it crosses the network — and that is only true if the deployment does not hand the protection back.

HTTPHTTPS
Port and framingPort 80, plaintextPort 443, HTTP protected by TLS
Can be readYes, by anything on the pathNo — records are encrypted
Can be modifiedYes, silentlyTampering is detected by the record tag
Server identityNot establishedVerified by certificate and hostname check
MITM riskInherentReduced to a validation decision the client must get right

What HTTPS protects

  • Confidentiality — attackers cannot read the content in transit
  • Integrity — silent changes to traffic are detected
  • Authentication — the browser verifies the server's certificate

What HTTPS does not fix

  • Weak passwords — users can still be phished
  • Malware — the device may already be compromised
  • Server-side breaches — the website may still be vulnerable
HSTS: turning a policy into a browser behaviour

HTTP Strict Transport Security is a response header, typically Strict-Transport-Security: max-age=63072000; includeSubDomains; preload. Once a browser has seen it, that host is treated as HTTPS-only: plaintext requests are upgraded before they leave the device, and certificate errors become non-bypassable. With includeSubDomains the policy covers every subdomain, and preload submits the host to the browser vendors' built-in list so even the first visit has no plaintext window.

Deployment mistakeWhat the attacker does with itFix
Plain HTTP remains reachable and no HSTS is setSSL stripping: rewrite the links so the session continues in the clearRedirect on the same host, then send HSTS with a long max-age
Weak minimum version or legacy suites enabledProtocol downgrade to a version with known weaknessesRequire TLS 1.2 or 1.3; disable CBC-only and RC4 suites
Pages load some resources over HTTPMixed content: an unauthenticated script rewrites the protected pageServe every subresource over HTTPS and set a content security policy
Certificate about to expireNothing needs to be attacked — users are trained to click through warningsAutomate issuance and renewal, and monitor expiry
Cookies without the Secure attributeA downgraded request leaks the session cookieSet Secure, HttpOnly and an appropriate SameSite policy

Worked example — audit an HTTPS deployment. A service redirects http://shop.example to https://www.shop.example, sends no HSTS header, and serves its product images from http://cdn.example.

1

Name the first failure. The redirect crosses from shop.example to www.shop.example. The first plaintext request is fully exposed and can be answered by an attacker before the redirect ever reaches the real server — a cross-host redirect is not a substitute for HSTS.

2

Name the second failure. No HSTS header means the plaintext window reopens on every new browser profile, cleared cache, or first visit. Adding Strict-Transport-Security: max-age=63072000; includeSubDomains; preload on the HTTPS response removes it for subsequent visits and, once preloaded, for the first one too.

3

Name the third failure. Images over http://cdn.example are mixed content. Even with a valid TLS session on the main page, an attacker on the path can substitute an image, and for active content such as scripts the browser may block it or the page may silently lose its integrity guarantee.

4

State what is already correct. The main page is protected by TLS on 443, and the server identity is verified by certificate and hostname check. The remaining risk is entirely about keeping the session protected rather than starting it.

5

The sentence that earns the mark. “HTTPS protects data in transit; HSTS protects the decision to use it. Without a same-host redirect, a long-lived HSTS policy and no mixed content, the attacker no longer needs to break TLS — they only need to be there before it starts.”

A site serves HTTPS correctly but never sends an HSTS header. Which attack does this leave available, and to whom?
SSL stripping on the first visit, to an attacker already in the path
Recovery of the session keys from a later server compromise
Decryption of the TLS records by an observer of the encrypted session

When the Implementation Breaks the Promise

TLS can be well designed and still leak everything, because a protocol is only as good as the code that parses its messages. Heartbleed is the deck's case study.

The heartbeat extension, and the bug

Heartbeat was a keep-alive: one side sends a small payload with a declared length, and the peer echoes those bytes back, so both sides know the other is still responsive without renegotiating the session. Heartbleed was the implementation failing to check that the length the client claimed matched the payload it actually sent. A request that said “here is 1 byte” but asked for 64 KB made the server return up to 64 KB of whatever was next to that buffer in memory.

The transferable pattern: Heartbleed is not really a story about TLS. It is a story about a parser that trusted a number supplied by the other side. The same shape appears in length-prefixed file formats, in decompression, in deserialisation and in protocol gateways — which is why the deck pairs the case with the reminder that protocol security depends on careful implementation and input validation.

Week 7 Recap

The path is untrusted, so the endpoints must do the work

Read, change, pretend, block. Network security protects data while it moves; nothing on the path can be asked to enforce that for you.

Threat model

IP best effort, UDP datagrams, TCP byte stream

IP promises nothing; UDP adds speed and no state; TCP adds order, acknowledgements and retransmission. None of them adds secrecy or identity.

Transport layer

TLS 1.3 is one round trip of AEAD and authentication

Hello, certificate, key exchange, Finished — with ephemeral key agreement, an encrypted handshake and a tagged record for every message after it.

Secure channel

Trust is a client-side decision

A certificate binds a name to a key. The chain, the validity window and the hostname match are what turn a MITM from an interception into a detected failure.
