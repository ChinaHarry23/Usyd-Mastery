Foundations: the arithmetic of a connection that has to be trusted

Week 7 is a protocol week, so the numbers are the ones a practitioner actually reasons with: how many bytes the headers cost, how sequence numbers and windows bound throughput, how many round trips a handshake consumes, how the TLS 1.3 key schedule derives traffic secrets, which key sizes are equivalent, and how long an HSTS policy or a certificate really protects you. Every formula below is tied to a figure from the deck or a named standard.

Encapsulation and the cost of protection

Every layer adds a header, and every byte of header is a byte not carrying application data. This is the arithmetic that tells you what TLS costs in practice — and it is small, which is worth knowing before anyone argues that encryption is too expensive.

1. The wire length of an HTTP request

One application payload of \(P\) bytes costs the following on an Ethernet path:

\[ L_{\text{wire}} \;=\; L_{\text{eth}} + L_{\text{ip}} + L_{\text{tcp}} + L_{\text{tls}} + P \;=\; 14 + 20 + 20 + 22 + P \;=\; 76 + P \]

The MTU is 1500 bytes, so the IP packet can carry at most \(1500 - 20 - 20 = 1460\) bytes of TCP payload. Because the TLS record overhead sits inside that TCP payload, the application bytes per full-size record are \(1460 - 22 = 1438\).

2. Efficiency, with and without TLS

Define efficiency as the fraction of transmitted bytes that are application data:

\[ \eta \;=\; \frac{P}{L_{\text{wire}}} \]

With TLS: \( \eta = 1438 / 1514 = 0.9498 \). Without TLS: \( \eta = 1460 / 1514 = 0.9643 \). The protection therefore costs about 1.5 percentage points of payload efficiency — 22 bytes per 1460, or roughly \(1.5\%\) of a full-size TCP segment.

Record size is a trade-off, not a constant. Larger records amortise the 22-byte overhead better but add latency for interactive traffic, because the receiver cannot process a record until it has all of it. The TLS 1.3 maximum plaintext of \(2^{14} = 16384\) bytes is a compromise; a request/response workload typically uses records of a few hundred bytes and pays proportionally more overhead.

Sequence numbers, windows and round-trip budgets

TCP reliability looks like magic until you write it as modular arithmetic and a timing budget. Both are examinable.

1. Sequence space and cumulative acknowledgement

Sequence numbers are 32-bit counters, so they are defined modulo \(2^{32}\):

\[ seq_{n+1} \;=\; (seq_n + \mathrm{len}_n) \bmod 2^{32}, \qquad seq \in [0,\; 2^{32}) \]

A cumulative acknowledgement names the next byte the receiver expects, not the last byte it received:

\[ ACK \;=\; seq_{\text{first}} + \text{bytes received contiguously} \]

The deck's example numbers this directly: segments \(1\!-\!40\), \(41\!-\!70\), \(71\!-\!100\), \(101\!-\!130\) produce \(ACK = 131\), meaning “all bytes up to 130 arrived”. If the segment \(41\!-\!70\) is lost, the receiver keeps answering \(ACK = 41\), and after a retransmission timeout the sender resends that range.

2. A window is a bandwidth-delay product

A sender cannot have more unacknowledged bytes in flight than the window allows, so throughput is bounded by how often acknowledgements return:

\[ \text{throughput} \;\le\; \frac{W}{\mathrm{RTT}}, \qquad W_{\min} \;=\; C \times \mathrm{RTT} \]

\(W_{\min}\) is the bandwidth-delay product: the amount of data that must be in flight to keep the pipe full. The window field is 16 bits, so \(W \le 65535\) bytes unless the window-scaling option multiplies it by \(2^{k}\).

1

Worked calculation. A path has \(C = 100\ \mathrm{Mbit/s}\) and \(\mathrm{RTT} = 50\ \mathrm{ms}\). The bandwidth-delay product is \(100 \times 10^{6} \times 0.05 = 5 \times 10^{6}\) bits \(= 625{,}000\) bytes.

2

Compare with the unscaled window. \(W = 65535\) bytes gives at most \(65535 / 0.05 = 1.31\ \mathrm{MB/s} \approx 10.5\ \mathrm{Mbit/s}\) — about a tenth of the available capacity.

3

Find the scaling factor. We need \(65535 \times 2^{k} \ge 625{,}000\), so \(2^{k} \ge 9.54\), giving \(k = 4\). The advertised window becomes \(65535 \times 16 = 1{,}048{,}560\) bytes, comfortably above the bandwidth-delay product.

4

State the general lesson. Throughput on a long, fast path is limited by \(W / \mathrm{RTT}\), not by link speed. This is the same arithmetic that makes a one-round-trip handshake worth redesigning a protocol for.

3. Retransmission timeout

RFC 6298 estimates the timeout from a smoothed round-trip time and its variation:

\[ SRTT \leftarrow (1-\alpha)\,SRTT + \alpha R, \qquad RTTVAR \leftarrow (1-\beta)\,RTTVAR + \beta\,|SRTT - R| \] \[ RTO \;=\; SRTT + 4 \cdot RTTVAR \]

with \(\alpha = 1/8\) and \(\beta = 1/4\). Example: \(SRTT = 400\ \mathrm{ms}\) and \(RTTVAR = 100\ \mathrm{ms}\) give \(RTO = 400 + 400 = 800\ \mathrm{ms}\). RFC 6298 also requires a floor of one second; production stacks lower it, which is why a loss on a fast path can be repaired in tens of milliseconds rather than a second.

At \(\mathrm{RTT} = 50\ \mathrm{ms}\), a TLS 1.3 connection reaches the first request byte after about \(2 \times 50 = 100\ \mathrm{ms}\), against roughly \(150\ \mathrm{ms}\) for TLS 1.2. Resumption with a pre-shared key can send early data immediately, at the price of replay risk: the server processes the first flight before it has proved the client is live, so 0-RTT data must be restricted to requests that are safe to repeat.

4. Half-open state is a resource equation

A SYN is a request to allocate state. A server that accepts \(\lambda\) SYNs per second and keeps each half-open entry for \(T\) seconds needs

\[ N_{\text{half-open}} \;\approx\; \lambda \times T \]

entries. With the classic SYN-ACK retransmission schedule \(1+2+4+8+16+32 = 63\) seconds and \(\lambda = 1000\) SYNs per second, the attacker demands about \(63{,}000\) simultaneous entries; a backlog of \(1024\) overflows in roughly one second. SYN cookies change the equation to \(N_{\text{half-open}} = 0\) by moving the state into the server's own sequence number until the ACK proves the client is real.

Worked example — reading a loss trace numerically. Sender transmits segments \(1\!-\!40\), \(41\!-\!70\), \(71\!-\!100\), \(101\!-\!130\). The capture shows three acknowledgements from the receiver: \(ACK\ 41\), \(ACK\ 41\), \(ACK\ 41\). Later the sender retransmits \(41\!-\!70\) and the next acknowledgement is \(ACK\ 131\).

1

What the repeated ACK means. By the definition above, \(ACK = seq_{first} + \text{contiguous bytes}\). The receiver has byte 1 onward, so the highest contiguous byte is 40 and every subsequent segment leaves the expected byte at 41.

2

Why the receiver does not buffer-and-forget. It does buffer \(71\!-\!130\), but a cumulative acknowledgement cannot say so. Duplicate ACKs are the signal that data is missing without a timeout having to expire.

3

Why \(ACK\ 131\) follows the retransmission. Once \(41\!-\!70\) arrives, the contiguous prefix extends from byte 1 to byte 130, so the next expected byte is 131 — and the buffered data is released upward as one ordered stream.

4

Sequence-number arithmetic. Real TCP does not start at 1: it picks a random initial sequence number \(ISN\) and every value above is \((ISN + k) \bmod 2^{32}\). The deck's 1–130 numbering is the same arithmetic with \(ISN = 1\).

The TLS 1.3 key schedule and key sizes

TLS 1.3 derives every key from a hash-based key schedule, and its security reduces to two hardness assumptions plus one counting argument. This section is the one to reproduce from memory.

1. HKDF: extract, then expand

The key schedule is HKDF (RFC 5869) instantiated with the handshake hash, either SHA-256 or SHA-384:

\[ \mathrm{PRK} \;=\; \mathrm{HMAC}(salt,\ \mathrm{IKM}), \qquad \mathrm{OKM} \;=\; \mathrm{HKDF\text{-}Expand}(\mathrm{PRK},\ info,\ L) \]

Extract concentrates whatever entropy the input has into a fixed-size pseudorandom key; expand stretches it into as many output bytes as the cipher needs, binding the result to a label \(info\).

2. Three secrets, two derivations

Each stage mixes the previous secret with a new input, using a fixed label so that two stages never share key material:

\[ \text{Early} \;=\; \mathrm{HKDF\text{-}Extract}(0,\ \mathrm{PSK}) \] \[ \text{Handshake} \;=\; \mathrm{HKDF\text{-}Extract}\big(\mathrm{DeriveSecret}(\text{Early}, \text{"derived"}),\ \mathrm{ECDHE}\big) \] \[ \text{Master} \;=\; \mathrm{HKDF\text{-}Extract}\big(\mathrm{DeriveSecret}(\text{Handshake}, \text{"derived"}),\ 0\big) \] \[ \mathrm{DeriveSecret}(S, label) \;=\; \mathrm{HKDF\text{-}Expand\text{-}Label}\big(S,\ label,\ H(\text{""})\big) \]

Traffic secrets are then split into a key and an initialisation vector, and the handshake is authenticated with a finished key:

\[ key = \mathrm{HKDF\text{-}Expand\text{-}Label}(secret, \text{"key"}, \text{""}, K), \qquad iv = \mathrm{HKDF\text{-}Expand\text{-}Label}(secret, \text{"iv"}, \text{""}, 12) \] \[ \text{Finished} \;=\; \mathrm{HMAC}\big(finished\_key,\ \mathrm{TH}\big), \qquad \mathrm{TH} = H(\text{ClientHello} \,\|\, \text{ServerHello} \,\|\, \cdots) \]

Because \(\mathrm{TH}\) covers every message in order, a modified handshake produces a different Finished value — that is the integrity guarantee for the negotiation itself.

3. Ephemeral Diffie-Hellman and forward secrecy

Both sides pick a secret exponent and exchange a public value modulo a fixed prime (or over an elliptic curve):

\[ A = g^{a} \bmod p, \qquad B = g^{b} \bmod p, \qquad Z = B^{a} = A^{b} = g^{ab} \bmod p \]

Recovering \(a\) from \(A\) is the discrete-logarithm problem; recovering \(Z\) from \(A\) and \(B\) is the computational Diffie-Hellman problem. \(Z\) is fed into the key schedule as the \(\mathrm{ECDHE}\) input and is never transmitted. If the server's long-term signing key leaks later, an attacker who recorded the session can recompute neither \(a\), nor \(b\), nor \(Z\), so the session keys stay unknown — that is forward secrecy. TLS 1.3 makes this mandatory by removing RSA key transport and static DH entirely.

4. AEAD: nonce discipline is a counting argument

A record is sealed with a unique nonce and authenticated over content and metadata:

\[ (C, T) = \mathrm{AEAD.Encrypt}(key,\ nonce,\ aad,\ P), \qquad nonce = iv \oplus \mathrm{seq} \]

The forgery probability for a random 128-bit tag is \(2^{-128}\) per attempt. Reusing a nonce under the same key is catastrophic for GCM, so TLS 1.3 uses a counter rather than randomness: \(\mathrm{seq}\) increments for every record, and RFC 8446 sets per-key usage limits plus a KeyUpdate message to rekey before the counter can wrap.

If nonces were chosen at random instead, the birthday bound gives the collision probability after \(q\) records with an \(n\)-bit nonce:

\[ p \;\approx\; 1 - e^{-q(q-1)/2^{n+1}} \;\approx\; \frac{q^{2}}{2^{\,n+1}} \]

For \(n = 96\) and \(q = 2^{32}\), \(p \approx 2^{64}/2^{97} = 2^{-33} \approx 1.2 \times 10^{-10}\) — small, but not zero, which is exactly why the counter form is used.

5. Entropy of a key versus entropy of a password

For a uniformly random key of \(k\) bits, entropy and guessing probability are direct:

\[ H = \log_2 2^{k} = k\ \text{bits}, \qquad \Pr[\text{guess}] = 2^{-k} \]

A password is not uniformly random over its alphabet. For length \(L\) over an alphabet of size \(N\) the upper bound is

\[ H_{\max} = L \log_2 N \]

so an eight-character lowercase password has at most \(8 \log_2 26 \approx 37.6\) bits — less than a third of the weakest TLS 1.3 session key, and far less in practice because human choices are not uniform. This is the arithmetic behind the deck's insistence that HTTPS does not fix weak passwords.

Worked example — which part of the handshake protects what. A capture shows a ClientHello offering TLS_AES_128_GCM_SHA256 and a key share for X25519, a ServerHello selecting the same suite, then encrypted handshake messages, then application records.

1

What the cipher-suite name tells you. \(128\) is the AEAD key length and \(256\) is the hash used by HKDF. It says nothing about the strength of the server's signature, which is negotiated separately through the signature-algorithm extension.

2

What X25519 contributes. The key share is \(g^{a}\) in an elliptic-curve group with about 128-bit security. The matching secret \(a\) stays on the client, so the record keys derived from \(Z\) are ephemeral by construction.

3

Why the certificate can be encrypted. Once both hellos have been exchanged, each side can compute the handshake secret. The certificate, CertificateVerify and Finished messages therefore travel under the handshake traffic keys, which is why a passive observer cannot even see which certificate was presented.

4

Where the signature fits. CertificateVerify contains a signature over the transcript hash, made with the private key matching the certificate's public key. That is the step that converts an anonymous key exchange into an authenticated one; without it, X25519 would agree a key with anybody, including an attacker.

5

Numerical summary. 1 RTT of handshake, 128-bit AEAD key, 128-bit ephemeral group, 128-bit collision-resistant hash, and one 16-byte tag per record: about \(2^{-128}\) forgery probability per attempt and no single long-term secret whose later compromise decrypts the session.

Certificate validation as a decision procedure

Path validation is a conjunction of predicates. If any one of them is false the connection must stop, which is why the hostname check deserves the same emphasis as the signature check.

1. A signature is a trapdoor computation

With RSA, signing uses the private exponent and verification uses the public one:

\[ s \equiv m^{d} \pmod n, \qquad m' \equiv s^{e} \pmod n, \qquad m = \mathrm{EMSA\text{-}PSS\text{-}Encode}\big(H(\text{TBS})\big) \]

Verification succeeds only if \(m' = m\), so the encoded hash — and therefore the certificate body — is bound to the signer. The padding is not decoration: textbook RSA is malleable, and schemes such as PSS exist so that a signature cannot be turned into a different valid signature. Elliptic-curve schemes (ECDSA, EdDSA) provide the same guarantee from a different hardness assumption, which is why TLS 1.3 negotiates the signature algorithm separately from the cipher suite.

2. Chain validity is a logical AND

For a chain \(C_0\) (leaf), \(C_1, \dots, C_{m-1}\) (intermediates) and a trust anchor \(R\):

\[ \mathrm{Valid} \;=\; \underbrace{\bigwedge_{i=0}^{m-2} \mathrm{Sig}\big(C_i,\ pk(C_{i+1})\big)}_{\text{every link is signed}} \;\wedge\; \underbrace{\bigwedge_{i=0}^{m-1} \mathrm{Time}(C_i)}_{\text{inside its validity window}} \;\wedge\; \mathrm{Name}(C_0, host) \;\wedge\; \mathrm{Usage}(C_i) \;\wedge\; \neg\,\mathrm{Revoked}(C_i) \]

Read it as a checklist rather than a formula: signature, time, name, usage, revocation. A single false term makes the whole conjunction false, and the browser is required to refuse the connection — not to warn and continue.

3. Time, lifetime and renewal

A certificate is only authorised between two instants:

\[ t_{\text{notBefore}} \;\le\; t_{\text{now}} \;\le\; t_{\text{notAfter}}, \qquad t_{\text{notAfter}} - t_{\text{notBefore}} \;\le\; 398\ \text{days} \]

The 398-day ceiling is the CA/Browser Forum limit that applies to publicly trusted TLS server certificates. Short lifetimes reduce the exposure from a stolen key, but they turn issuance into a continuously operating system: with a lifetime \(L\) and an issuance lead time \(\ell\), renewal must begin at \(t_{\text{notAfter}} - \ell\) with \(\ell\) comfortably larger than the worst-case issuance delay, or the service fails closed at the moment of expiry.

4. Name matching is exact, not approximate

A certificate may list several subject alternative names (SANs). A wildcard matches exactly one label:

\[ \texttt{*.example.com} \;\text{matches}\; \texttt{www.example.com}, \quad \text{but not} \quad \texttt{a.b.example.com}, \quad \text{nor} \quad \texttt{example.com} \]

Formally, if the pattern is \(*.\ell_1.\ell_2\ldots\ell_j\) and the presented name is \(x_1.x_2.\ldots x_{j+1}\), the match requires \(j+1\) labels with \(x_2 = \ell_1, \ldots, x_{j+1} = \ell_j\). This is also why a certificate for \(example.net\) can never be presented for \(example.com\): the names differ in a label that the pattern must compare exactly.

5. Transparency logs are Merkle trees

Certificate Transparency records every issued certificate in an append-only log whose root is a hash of all entries. Proving that one certificate is included costs only a logarithmic number of sibling hashes:

\[ \big|\text{proof}\big| \;=\; \lceil \log_2 n \rceil\ \text{hashes} \]

For a log with \(n = 10^{9}\) certificates that is 30 hashes — a few hundred bytes — which is why an inclusion proof can be stapled to a handshake. Tamper-evidence follows from the hash chain: changing one leaf changes every subsequent root.

Worked example — evaluate the conjunction. A client receives a chain of three certificates and a certificate whose SAN reads DNS:*.shop.example, DNS:shop.example. The user typed https://checkout.shop.example.

1

Signature and chain. The leaf must be signed by the intermediate's public key, and the intermediate by the root's. If either link fails, the conjunction is false and no later check matters.

2

Time. Both the leaf and each intermediate must satisfy \(t_{\text{notBefore}} \le t_{\text{now}} \le t_{\text{notAfter}}\). Expiry of an intermediate breaks the chain just as surely as expiry of the leaf.

3

Name. The SAN list contains *.shop.example and shop.example. The requested host checkout.shop.example has exactly one label in the wildcard position, so it matches; a request to a.checkout.shop.example would not, because the wildcard covers exactly one label.

4

Usage and revocation. The leaf must assert serverAuth extended key usage, and each issuer must be a CA with the appropriate basic constraints. Revocation status must be checked or at least stapled and validated; absence of a status response is a policy decision the operator has to make explicitly.

5

Result. Every predicate is true, so the client uses the certified public key to authenticate the key exchange. Had any single term been false, the correct behaviour is to terminate — which is the difference between TLS as a control and TLS as a padlock icon.

HSTS, downgrade and operational arithmetic

The last mile of HTTPS is not cryptography; it is policy with numbers attached. These are the numbers.

1. An HSTS policy is a time window

The header declares how long the host must be treated as HTTPS-only:

\[ \texttt{Strict-Transport-Security: max-age}=\Delta,\qquad \Delta \ge 31{,}536{,}000\ \text{s} \]

The threshold is one year (365 days) and is a preload-list requirement, not a browser requirement; a two-year value \(\Delta = 63{,}072{,}000\) s is the common production choice. The protection is a state machine: before the first response arrives the browser has no policy, so the first request for a host is downgradeable unless the host is on the built-in preload list, which requires a long max-age, includeSubDomains and the preload token.

2. Every redirect and every handshake is a round trip

A plaintext request that must first be redirected pays the redirect latency before the handshake even starts. With \(r\) redirects and a fresh TLS session:

\[ T_{\text{first byte}} \;\approx\; (1 + r) \times \mathrm{RTT} \;+\; T_{\text{handshake}} \]

For \(r = 1\) and \(\mathrm{RTT} = 50\ \mathrm{ms}\), the redirect alone costs about \(50\ \mathrm{ms}\) — and, worse, that round trip is in plaintext, which is precisely the window an attacker needs. HSTS removes the redirect by having the browser rewrite the URL to https before anything is sent.

3. Downgrade protection is a sentinel value

If a client offers TLS 1.3 and the server negotiates TLS 1.2 or below, the server is required to make that visible in its random value:

\[ \text{ServerHello.random}[24..32) \;=\; \texttt{44 4F 57 4E 47 52 44 01} \quad (\text{"DOWNGRD}\backslash\texttt{01"}) \]

The client compares the received bytes and aborts the handshake if a downgrade is being signalled. This is the protocol-level defence; HSTS is the deployment-level one, and a minimum-version policy on the server is the third: an attacker who cannot negotiate an old version has nothing to downgrade to.

4. Small probabilities that decide designs

Two figures are worth remembering because they explain otherwise odd engineering choices:

\[ \Pr[\text{tag forgery}] \;=\; 2^{-t}, \qquad \Pr[\text{nonce collision}] \;\approx\; \frac{q^{2}}{2^{\,n+1}} \]

With a 128-bit tag, a blind forgery attempt succeeds with probability \(2^{-128}\) per attempt — so integrity failures are engineered, not guessed. With random \(n\)-bit nonces, the second expression is why AES-GCM nonces are counters: the failure mode is not a rare collision but a catastrophic key-recovery event, and no probability that grows with traffic volume is acceptable for it.
