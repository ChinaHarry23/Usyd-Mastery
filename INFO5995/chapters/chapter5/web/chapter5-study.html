Beyond Confidentiality: What Encryption Cannot Do

Week 4 ended with confidentiality. This week starts from the two attacks that confidentiality alone does not stop — and from the question that organises everything that follows: what guarantee is missing?

Where we are coming from. The one-time pad gives the strongest possible confidentiality guarantee, but only under four strict conditions: the key is truly random, as long as the message, used exactly once, and kept secret. A 1 GB message therefore needs a fresh 1 GB key — the hard part was never the XOR, it was managing the key. So the question changed to semantic security: no efficient attacker should learn significant information from the ciphertext. This week asks what else a real system has to guarantee.

AttackWhat the attacker actually doesGuarantee that is missing
Message modificationFlips bits or splices ciphertext so that C becomes C′. The receiver decrypts to a different message and never notices.Integrity — detecting unauthorised modification
ReplayRecords a valid encrypted message — “extend the assignment deadline by 1 day” — and sends exactly the same bytes again later. No understanding and no modification is required.Freshness — proof that the message is new and not stale
Forgery / imitationCreates a message that appears to come from Alice, without Alice ever sending it.Authenticity — proof of who created the message
The gap in one sentence

Encryption gives confidentiality: it hides the content. It does not prove that a message is unchanged (integrity) or new (freshness), and it does not prove who sent it (authenticity). Confidentiality hides content; integrity, freshness and authenticity make a message trustworthy.

1. Hide the message
→
2. Detect changes
→
3. Prove origin
→
4. Trust the key

Confidentiality (encryption / AEAD) → integrity (hash / MAC / AEAD) → authenticity (MAC / digital signature) → identity binding (certificates / fingerprints).

The lecture's closing instruction, used as a method: when you meet a security problem, do not reach for an algorithm. Ask first which guarantee is missing, then choose the primitive that provides exactly that guarantee.
Eve records an encrypted instruction that transfers $100, and re-sends the identical ciphertext to the bank an hour later. The bank decrypts it correctly. Which guarantee failed?
Confidentiality, because the ciphertext travelled over the network twice
Integrity, because the message reached the bank twice
Freshness: the bank cannot tell a new message from a recorded one

Hash Functions: A Fingerprint, Not a Secret

A hash turns an input of any practical length into a fixed-length digest. It answers one question very well — has this data changed? — and says nothing about who produced it.

Cryptographic hash function

A function that maps an input of any practical length to a fixed-length digest. It is deterministic (the same input always gives the same digest), fixed-length (a short and a huge input produce the same output size), one-way (recovering the input from the digest should be hard), efficient to compute, and exhibits the avalanche effect: a tiny input change produces a widespread, unpredictable output change. Hashing is not encryption — there is no key and no decryption.

PropertyWhat the attacker is givenExpected classical work for an n-bit digest
Pre-image resistanceA digest h(x); find the input xAbout 2n — brute force over the input space
Second-pre-image resistanceA specific input x; find x′ ≠ x with the same digestAbout 2n — also a fixed target
Collision resistanceNothing; find any pair x ≠ y with h(x) = h(y)About 2n/2 — the birthday effect, so collisions are the cheapest attack
SHA-256("hello") = 2cf24dba5fb0a30e26e83b2ac5b9e29e… SHA-256("hell0") = 04a6f55face2f46be8c23f627d539827… SHA-256("password123") = ef92b778bafe771e89245b89ecbc08a4… one character in, about half of the 256 output bits change

Digests truncated for display, as in the lecture demo. Changing one character should scatter the output unpredictably — that is the avalanche effect, and it is why a hash is a fingerprint rather than a summary.

Where hashes are usedWhat is actually being checkedTypical modern choice
File integrityRecompute the digest and compare it with the expected valueSHA-256 / SHA-3
Password storageA password-hashing function or KDF with a tunable cost — never raw SHA-256, and never an unsalted hashArgon2id / scrypt / bcrypt / PBKDF2
Signatures and MACsThe digest (or a keyed construction over it) is what gets authenticatedHMAC / digital signatures

Proof of workFind an input whose digest has a required prefix — expensive to find, cheap to verifyHash-based puzzles

Which hash would you choose today?

  • MD5 — do not choose: collision resistance is broken
  • SHA-1 — do not choose: collision resistance is broken
  • SHA-256 — good default, widely supported
  • SHA-3 — good alternative from a different design family; it is a standardised modern option, not merely a future one

Hashing a password does not create a key

SHA-256("password123") looks random, but looks random is not high entropy. A hash can spread the bits of its input; it cannot create unpredictability that was never there. A human-chosen password has far fewer than 256 bits of entropy, so its digest is guessable at the same cost as the password itself. For cryptographic keys, generate randomness with a CSPRNG.

Why hashing can be used for proof of work. Find a number x such that hash("send email" || x) starts with 000000. The sender must try many values of x; the verifier checks a single hash. Asymmetry — expensive to find, cheap to verify — is the whole point, and it exists only because hashing is one-way.
Alice sends a message M together with SHA-256(M). Eve replaces both the message and the digest with her own pair. Bob recomputes the hash and it matches. What has Bob actually verified?
That Eve does not know the secret key used to compute the digest
Only that the message is consistent with the digest — not who created it
That the message content stayed confidential

MAC and HMAC: A Digest With a Secret Key

A plain hash is a fingerprint anyone can recompute. Add a shared secret and the fingerprint becomes a tag that only a key holder can produce.

Message authentication code (MAC)

A keyed tag over a message. Three operations: KeyGen produces a shared key K; Tag(K, M) → T produces the tag; Verify(K, M, T) → {0,1} accepts only when the recomputed tag matches. HMAC is the standardised hash-based MAC construction (NIST FIPS 198-1). A MAC provides integrity and sender authenticity — but only for parties who share the secret key.

CaseWhat arrives at BobDecisionWhy
AM and T arrive unchangedAcceptThe recomputed tag matches under the shared key K
BM has been changed, the old T is replayedRejectThe tag no longer matches the message
CA new fake M with a new fake T, created without KRejectEve cannot compute a valid tag without the key

The attacker's goal is to pass verification without K. That means either modifying an existing valid pair (change the amount or the deadline) or forging a completely new one (fake a new instruction). Even after observing many valid message–tag pairs, Eve still cannot produce a new pair that verifies.

The HMAC construction (FIPS 198-1)

HMAC(K, m) = H( (K0 ⊕ opad) ‖ H( (K0 ⊕ ipad) ‖ m ) ). The key K is first turned into a block-sized key K0 (hashed first if it is longer than the block, zero-padded if it is shorter). ipad is the byte 0x36 repeated B times and opad is 0x5c repeated B times, where B is the hash block size (64 bytes for SHA-256). The nested inner/outer structure is the point: a naive keyed hash such as H(K ‖ m) inherits structural weaknesses from the underlying hash.

What a MAC cannot do

  • No public verification: a MAC proves authenticity only while K stays secret from attackers
  • Anyone with K can forge: if many people share one key, every one of them can create a valid tag
  • No replay protection by itself: a recorded message and tag still verify tomorrow — add a nonce, timestamp or sequence number

Where MAC fits in a modern stack

  • Encryption — confidentiality only
  • MAC / HMAC — integrity and authenticity between key holders
  • AEAD — both together (AES-GCM, ChaCha20-Poly1305)
  • Secure channel — TLS / HTTPS, which is where you actually meet all of this
The boundary that motivates the next section. A MAC says “whoever made this tag knew K”. If millions of users must verify a software update, sharing K with all of them means any single user can forge an update that everyone else accepts. Public verification breaks the shared-secret model — which is exactly why digital signatures exist.
Eve changes one byte of a message that is protected by HMAC-SHA-256 and replays the original tag unchanged. What happens at the verifier?
Verification fails, because the recomputed tag over the modified message no longer matches
The verifier decrypts the tag and repairs the modified byte
Verification succeeds, because the tag was never changed

Digital Signatures: Private Signing, Public Verification

Hash detects change; a MAC adds a shared secret; a signature solves the remaining problem — many verifiers, one signer, and no secret handed out.

MAC / HMAC

  • One shared secret key K
  • If many people know K, any of them can create a valid tag
  • Good for closed groups that already share a secret
  • Cannot support public verification

Digital signature

  • One private signing key SKA, many public verification keys PKA
  • Only the owner can sign; anyone with the public key can verify
  • Designed for public verification at scale
  • This is why software updates, app packages and certificates use signatures
The scenario that settles the argument. A publisher ships an update to millions of users. If the publisher shared one MAC key with everyone, then any malicious user would hold K, could publish a fake update with a perfectly valid tag, and every other user would accept it. A MAC proves authenticity only while its key is secret from attackers — so it cannot be used for public verification.
Digital signatures provideWhat that means
IntegrityThe signed content cannot be changed unnoticed — change either the message or the signature and verification fails
Origin authenticationThe signature is tied to the signer's private key, so a valid signature proves control of that key
Public verifiabilityAnyone who has the public key can check the signature, without being able to create one
Non-repudiation supportOnly when identity, key ownership and audit evidence are established — the signature alone is not a legal conclusion
What signatures do not providePrecise wording to use instead
Confidentiality. Signing does not encrypt the message; anyone who receives it can still read it unless encryption is also used.“Encrypt to hide; sign to prove origin and detect changes.”
A raw mathematical guarantee of identity. A valid signature proves control of a private key — connecting that key to a person or domain is a separate trust problem.“A valid signature proves control of a private key; the certificate says whose key it is.”
Safety from a badly built scheme. Raw textbook RSA signatures are malleable; approved schemes apply an encoding such as PSS (RSA-PSS, ECDSA and EdDSA are the FIPS 186-5 options).“Hash, then sign with an approved padding scheme — never raw RSA.”
Never describe signing as “encrypting with the private key”. The two operations use the same mathematics in RSA, but they carry different guarantees: encryption hides content for one recipient; signing proves origin and detects change for anyone. The lecture is explicit that signing does not hide the message.

Worked example — a secure software update, end to end. The developer publishes an update; the user device decides whether to install it.

1

Publish. The developer produces the update file M and its signature: the published package is M plus S. The private signing key SKdev never leaves the developer.

2

Hash. H = H(M) reduces the update to a fixed-length digest, so the signature only has to cover a short value.

3

Sign. S = Sign(SKdev, H(M)). Only the holder of SKdev can produce S.

4

Verify. The device recomputes H(M′) from what it downloaded and checks Verify(PKdev, M, S). A single changed byte changes the digest and breaks verification; a fake update signed with somebody else's key fails under PKdev.

5

Decide. Valid signature → install. Modified or fake update → reject before install. This is why signatures, not shared MAC keys, protect software distribution.

6

Name the remaining gap. Everything above assumes the device holds the right PKdev. A valid signature proves control of a private key; it does not prove whose key it is. That is the certificate and PKI problem in the next two sections.

A vendor signs its installer with a private key and publishes the installer plus the signature. Which statement is correct?
The vendor must distribute its private key so that users can verify the installer
Users verify with the vendor's public key, and the installer remains readable to anyone
Signing encrypts the installer, so only users with the public key can read it

Public-Key Cryptography: RSA

Symmetric cryptography assumes both sides already share a key. Public-key cryptography splits the key in two, so one half can be published and the other never leaves its owner.

Public-key (asymmetric) cryptography

A key pair whose two halves are mathematically linked: a public key that may be shared widely, and a private key that must remain with its owner. The pair performs three different jobs — encrypt (public key encrypts, private key decrypts: RSA-OAEP), sign (private key signs, public key verifies: RSA-PSS, ECDSA, EdDSA) and agree (each side combines its own private value with the peer's public value: Diffie-Hellman, ECDH).

Multiplying two large primes is easy; factoring their product is believed hard. Raising g to a power modulo p is easy; inverting it is the discrete logarithm problem. Everything in this section is built on one of those two gaps.

RSA key generation, step by step

StepOperationToy values used below
1Choose two distinct large primes p and qp = 61, q = 53
2Compute the modulus n = p · q — its bit length is the “key size”n = 3233
3Compute φ(n) = (p − 1)(q − 1)φ(n) = 3120
4Choose a public exponent e with 1 < e < φ(n) and gcd(e, φ(n)) = 1e = 17
5Compute the private exponent d ≡ e−1 (mod φ(n))d = 2753
6Publish (n, e); keep (n, d) secret — p, q and φ(n) must never be publishedpublic (3233, 17) · private (3233, 2753)

Why decryption recovers the message

Because e · d ≡ 1 (mod φ(n)), raising a ciphertext to the power d undoes raising the message to the power e: me·d ≡ m (mod n). That is Euler's theorem, and it is also why φ(n) must stay secret — anyone who learns p and q can compute d in moments.

Three rules that matter in practice

  • Never use raw RSA. Textbook RSA is deterministic and malleable; approved schemes apply OAEP for encryption and PSS for signatures.
  • One key pair, one job. NIST FIPS 186-5 states that an RSA signature key pair shall not be used for other purposes such as key establishment.
  • Respect the minimum size. The standard requires a modulus of at least 2048 bits, with p and q of equal bit length and 216 < e < 2256.
Why hybrid encryption exists. Modular exponentiation with a 2048-bit modulus is orders of magnitude slower than AES. Real systems therefore use public-key cryptography only to protect a short secret — encrypt a random session key with RSA-OAEP, or agree one with Diffie-Hellman — and then protect the bulk data with AES-GCM or ChaCha20-Poly1305. The asymmetric step is the short setup, not the payload.
Which statement about an RSA key pair is correct?
Anyone who knows n and e can compute the private exponent d
Publishing n and e lets anyone encrypt or verify, while only d can decrypt or sign
RSA replaces AES, so bulk files are encrypted directly with the public key

Worked example — RSA with the toy parameters p = 61, q = 53, e = 17, message m = 65.

1

Modulus. n = p · q = 61 × 53 = 3233. The key size is the bit length of n, so this toy key is about 12 bits — real keys are 2048 bits or more.

2

Totient. φ(n) = (p − 1)(q − 1) = 60 × 52 = 3120.

3

Check e. gcd(17, 3120) = 1, so e = 17 is a valid public exponent. (The Euclidean algorithm gives 3120 = 17 × 183 + 9, then 17 = 9 + 8, then 9 = 8 + 1.)

4

Private exponent. Running the extended Euclidean algorithm backwards gives 1 = 2 × 3120 − 367 × 17, so d ≡ −367 ≡ 2753 (mod 3120). Check: 17 × 2753 = 46 801 = 15 × 3120 + 1. ✓

5

Encrypt. c = me mod n = 6517 mod 3233 = 2790, computed with repeated squaring rather than 17 multiplications.

6

Decrypt. m = cd mod n = 27902753 mod 3233 = 65. The arithmetic is modular exponentiation in both directions; what makes it safe is that computing d needs the factorisation of n, and nothing published reveals it.

Diffie-Hellman: Agreeing on a Secret in Public

Diffie-Hellman solves key establishment, not bulk encryption: two parties who have never met derive the same secret while an observer sees every value they exchange.

StepWhoWhat happens
1PublicAgree on a large prime p and a generator g. Eve can see both.
2AlicePick a secret exponent a, compute A = ga mod p, send A to Bob. Keep a private.
3BobPick a secret exponent b, compute B = gb mod p, send B to Alice. Keep b private.
4BothAlice computes Ba mod p; Bob computes Ab mod p. Both equal gab mod p — the shared secret.
5BothRun the shared value through a key-derivation function to obtain fresh session keys, then protect the traffic with an AEAD cipher.

What Diffie-Hellman alone does not give you

Nothing about who is on the other end. Eve can sit in the middle, replace Alice's public value with her own when talking to Bob (and vice versa), and end up sharing one secret with Alice and a different one with Bob. Diffie-Hellman creates a shared secret; authentication is what tells you who shares it — a certificate or signature binds the public values to a verified identity.

Why ephemeral keys are the default

If each session generates a fresh exponent and discards it afterwards, then compromising a long-term key later does not reveal past session keys. Ephemeral Diffie-Hellman over elliptic curves (ECDHE) is the usual choice, and approved group parameters matter: bad primes or unvalidated public values enable small-subgroup attacks that leak the private exponent.

1. Authenticate
→
2. Agree (ECDHE)
→
3. Derive (KDF)
→
4. Protect (AEAD)

Key agreement is one layer, not the whole protocol: a certificate or signature verifies the peer, ECDHE produces the shared secret, a KDF creates fresh session keys, and an AEAD cipher protects the traffic.

Read the key sizes correctly. Key length is not security level. A 2048-bit RSA modulus is assessed at roughly 112 bits of security because the best known attack is factoring, not brute force; a 256-bit elliptic curve gives about 128 bits because the best known attack is the discrete logarithm in a much smaller group. Matching a primitive to a required security level is a lookup in the standards, not a guess.
Alice and Bob complete an unauthenticated Diffie-Hellman exchange over a channel Eve can read and write. What do they actually know at the end?
That they are talking to each other, because only Alice knows a and only Bob knows b
That they share a secret with somebody who knows a matching exponent — not who that somebody is
That the exchanged values g, p, A and B stayed confidential

Worked example — a Diffie-Hellman exchange with the toy group p = 23, g = 5.

1

Public parameters. p = 23 and g = 5 are published. In a real deployment p would be a large prime (or an approved elliptic-curve group), and 23 would be breakable by hand.

2

Alice. Picks a = 6, computes A = 56 mod 23. Using repeated squaring: 52 = 25 ≡ 2, 53 ≡ 10, so 56 = (53)2 ≡ 100 ≡ 100 − 92 = 8. She sends A = 8 and keeps a = 6.

3

Bob. Picks b = 15, computes B = 515 mod 23. From 512 ≡ 18 and 53 ≡ 10, B ≡ 18 × 10 = 180 ≡ 180 − 161 = 19. He sends B = 19 and keeps b = 15.

4

Alice's side. K = Ba mod p = 196 mod 23. Since 19 = 515, this is 590 mod 23; the order of 5 modulo 23 is 22, and 90 ≡ 2 (mod 22), so K = 52 mod 23 = 2.

5

Bob's side. K = Ab mod p = 815 mod 23 = (56)15 = 590 ≡ 52 = 2 (mod 23). Both sides agree on K = 2 without ever sending it.

6

Why this is safe at scale. Eve sees p = 23, g = 5, A = 8, B = 19 and would only have to search 22 exponents here. With a real group of about 256 bits the search space is around 2256, and no efficient classical method for the discrete logarithm is known. The toy numbers show the mechanism, not the security.

Whose Key Is It? Certificates and PKI

A valid signature proves control of a private key. It does not prove whose key it is. If Eve swaps in her own public key, every signature check still succeeds — for the wrong person.

Trust is a binding problem, not only a mathematics problem. Something outside the signature has to connect a public key to an identity.

Identity claimTrusted binding: evidence and processWhat it gives you
“This is Alice” / “This is example.com”Certificates — a CA signs a public key for a domain or organisationA key bound to a name by a party you already trust
Web PKICertificate authorities — trusted third parties whose roots ship with the operating system or browserYou trust a small set of roots instead of every key you meet
Directory lookupPublic-key directories — a trusted service publishes identity–key mappingsScalable lookup, but the directory itself must be trusted
Server identity in SSHKnown host keys — the client remembers the server key after first trustTrust on first use; a changed key becomes a loud warning
Out-of-band checkKey fingerprints — humans compare a short representation of the keyVerification that does not depend on any infrastructure

What an X.509 certificate actually contains

FieldWhy it exists
Version and serial numberIdentifies the certificate uniquely so it can be referenced, renewed and revoked
IssuerNames the CA that signed this certificate — the next link in the chain
Validity (not before / not after)A bounded lifetime; an expired certificate is invalid even if every signature checks out

Chain validation, in the order a client should do it. Build a chain from the server certificate to a locally trusted root; verify each signature up the chain; check that every certificate is inside its validity window; check that the name you asked for appears in the subject or the subject alternative names; and check revocation (CRL or OCSP) and key usage. Only then is the public key “the server's key” in any meaningful sense.
You verify a server's signature with the public key you were handed, and it is valid. What have you established?
That whoever produced the signature holds the matching private key — the key's owner still depends on the certificate
That the key necessarily belongs to the domain you intended to reach
That the session content is confidential

Choosing a Primitive: Guarantee First

Four tools, four key models. Choosing between them is a question about the guarantee you need — confidentiality, integrity, authenticity, or public verification — not about which one sounds strongest.

ToolKey modelConfidentialityIntegrity / authenticityPublic verification
HashNo keyNoChange detection onlyAnyone can recalculate it
MAC / HMACShared secretNoYes — between key holdersNo
Digital signaturePrivate / public key pairNoYesYes
AEADShared secretYesYes — between key holdersNo
Question to askPrimitive that answers it
Did the data change?Hash (SHA-256 / SHA-3)
Did someone with the shared secret create this valid tag?MAC / HMAC
Does this message verify under this public key?Digital signature (RSA-PSS, ECDSA, EdDSA)
Whose public key is this?Certificates, trusted directories, fingerprints
Are the contents protected and authenticated together?AEAD (AES-GCM, ChaCha20-Poly1305)
The takeaway to memorise: hash = fingerprint. MAC = shared-key authenticity. Signature = public verification. AEAD = encryption and integrity together. Modern systems combine these blocks rather than asking one tool to do every job — and getting the combination wrong is a design failure, not a mathematical one.

Common misuses

  • Using a MAC where millions must verify — any key holder can forge
  • Using a plain hash as proof of origin — anyone can recompute it
  • Describing a signature as encryption — it hides nothing
  • Trusting a valid signature without checking whose key it is

What good practice looks like

  • AEAD by default for traffic; AES-GCM or ChaCha20-Poly1305
  • Hash, then sign with an approved scheme — never raw RSA
  • Bind public values to identities with certificates or signatures
  • Add a nonce, timestamp or sequence number wherever replay matters

Week 5 Recap

Hash = fingerprint

Any practical input becomes a fixed-length digest. It detects change, scales to many files, and proves nothing about who created the data.

Integrity only

MAC = shared-key authenticity

Add a secret to the digest and only key holders can produce a valid tag. Great inside a closed group; useless for public verification.

Integrity + authenticity

Signature = public verification

Private signing key, public verification key. Integrity, origin authentication and public verifiability — without hiding the message.

One signer, many verifiers

Trust = binding, not mathematics

Certificates, CAs, directories and fingerprints are what connect a public key to an identity. A valid signature only proves control of a key.
