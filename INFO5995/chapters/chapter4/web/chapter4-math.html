Foundations: the arithmetic behind Week 4's confidentiality

Week 4 is the most quantitative week of the unit: a cipher is a function, key strength is a number of bits, and every failure mode has a formula behind it. This page writes those formulas down, works them on the deck's own numbers, and ends with the checklist that turns “use AES” into a defensible construction.

XOR, the One-Time Pad and Perfect Secrecy

Everything the one-time pad can do follows from four properties of the XOR operation. Nothing else in this week's confidentiality material is as cheap to prove or as easy to get wrong.

1. XOR is its own inverse

Bitwise exclusive-OR, written \(\oplus\), returns 1 exactly when its two inputs differ. The identity that makes the one-time pad work is that any value XORed with itself cancels:

\[ x \oplus x = 0, \qquad x \oplus 0 = x \]

Therefore encryption and decryption are the same operation applied with the same key:

\[ C = M \oplus K \qquad\text{and}\qquad C \oplus K = (M \oplus K) \oplus K = M \]

2. The ciphertext of a one-time pad is independent of the plaintext

Fix a ciphertext value \(c\) and a candidate message \(m\). There is exactly one key that produces \(c\) from \(m\), namely \(k = m \oplus c\). If \(K\) is uniform over \(\{0,1\}^{n}\), then

\[ \Pr[C = c \mid M = m] = \Pr[K = m \oplus c] = 2^{-n} \]

which does not depend on \(m\) at all. By Bayes' rule the posterior equals the prior, \(\Pr[M = m \mid C = c] = \Pr[M = m]\): the ciphertext gives the attacker no information about the message. That is perfect secrecy, and it is why the deck says the ciphertext reveals nothing when all four conditions hold.

3. The four conditions are the proof's assumptions

Drop any one and the argument above fails. The table states which term of the derivation each condition protects.

ConditionFormal statementWhat breaks without it
Truly random\(K\) uniform on \(\{0,1\}^{n}\)\(\Pr[K = k]\) is not \(2^{-n}\), so the posterior no longer equals the prior
Same length\(|K| = |M| = n\) bitsA short key must repeat, and repetition is reuse
Kept secretOnly sender and receiver know \(K\)The attacker can compute \(M = C \oplus K\) directly
Never reused\(K_i \neq K_j\) for \(i \neq j\)The key cancels out of \(C_1 \oplus C_2\)

4. Key reuse collapses the secrecy to \(M_1 \oplus M_2\)

Encrypt two messages with the same key and XOR the ciphertexts:

\[ C_1 \oplus C_2 = (M_1 \oplus K) \oplus (M_2 \oplus K) = M_1 \oplus M_2 \]

The key has vanished. What remains is the XOR of two plaintexts — a classical cryptogram that falls to frequency analysis and crib dragging, because English text XORed with English text leaks letter-position structure. Key reuse destroys perfect secrecy, and this is the identity to quote whenever an exam question asks why the one-time pad is impractical.

Modular Arithmetic and Search Spaces

Symmetric ciphers hide the message with the key. Public-key cryptography, which arrives in Week 5, hides the key behind a hard mathematical problem instead — and that problem is stated in modular arithmetic. The deck plants the seed with Diffie–Hellman's one-way gap, so it belongs on this page as a preview.

Notation

\(a \bmod n\) is the remainder of \(a\) on division by \(n\), always in \(\{0, 1, \dots, n-1\}\). The set of remainders is written \(\mathbb{Z}_n\). Two integers are congruent modulo \(n\), written \(a \equiv b \pmod{n}\), when \(n\) divides \(a - b\).

Modular exponentiation is efficient in one direction

Diffie–Hellman works in \(\mathbb{Z}_p^{*}\) for a large prime \(p\) and a generator \(g\). Each side picks a private exponent and publishes the corresponding value:

\[ y = g^{x} \bmod p \]

Easy forward. Given \(g\), \(p\) and \(x\), computing \(y\) costs about \(\log_2 x\) modular squarings and multiplications by repeated squaring — a few hundred operations for a 256-bit exponent, not \(2^{256}\).

Hard backward. Given \(g\), \(p\) and \(y\), recovering \(x\) is the discrete-logarithm problem, for which no efficient classical method is known for suitable large parameters. Publishing \(y\) therefore does not reveal \(x\), and this one-way gap is what makes key agreement possible.

Why this is a preview, not this week's material. Week 4 needs only the shape of the argument: a published public value plus a hidden private value. The full construction, the man-in-the-middle substitution attack and the countermeasure — binding the public values to a verified identity — are Week 5, and the deck introduces them in the same section.

Search space is exponentiation, not multiplication

The size of the key space grows exponentially in the key length, which is why adding bits to a key is so much more effective than lengthening a password:

\[ \bigl|\{0,1\}^{n}\bigr| = 2^{n} \]

The deck's comparison of a 4-bit key with a 128-bit key is a comparison of \(2^{4} = 16\) with \(2^{128} \approx 3.4 \times 10^{38}\). The useful identity for mental arithmetic is the doubling rule:

\[ 2^{n+1} = 2 \cdot 2^{n} \qquad\text{and}\qquad 2^{10} \approx 10^{3} \]

So each extra key bit doubles the work for a brute-force attacker, and every ten bits multiplies it by roughly a thousand. A 56-bit key (DES) is \(2^{56} \approx 7.2 \times 10^{16}\) candidates; a 112-bit effective key (3DES) is \(2^{112} \approx 5.2 \times 10^{33}\) — about \(2^{56}\) times larger.

Key Length, Entropy and Security Levels

Two numbers are constantly confused. Key length is how many bits the field occupies; entropy is how many bits an attacker actually has to guess. Only the second one measures strength.

1. Effective work is bounded by entropy, not by field width

Let \(H\) be the Shannon entropy of the key-generation process, in bits, and \(n\) the number of bits in the key field. Then

\[ W \;\le\; 2^{H} \;\le\; 2^{n} \]

A perfectly uniform \(n\)-bit key has \(H = n\) and the two bounds meet. A key derived from a memorable phrase has \(H \ll n\): the deck's INFO5995-INFO5995! occupies 18 characters but is generated by a guessable rule, so if only about 16 bits vary, \(W \le 2^{16} = 65{,}536\) — even inside a 128-bit field. LONG ≠ STRONG.

2. Estimating the entropy of a passphrase

For a phrase drawn from a known structure, entropy is (number of free choices) × (bits per choice). Approximating a common English word as one of about \(2^{11}\) plausible words and a random digit as \(2^{3.3}\):

\[ H \;\approx\; 11 \cdot w \;+\; 3.3 \cdot d \;+\; 5 \cdot s \]

where \(w\) is the number of independently chosen words, \(d\) the number of random digits and \(s\) the number of random symbols. Three well-chosen words and two symbols gives \(33 + 10 \approx 43\) bits — respectable for a password, hopeless for a cipher key. Cipher keys are generated, never composed: use the operating system CSPRNG, which the deck names as the source in the lifecycle's first stage.

3. Key sizes are not comparable across families

“Bigger is stronger” only holds within one family. A 256-bit RSA modulus is trivially factorable; a 256-bit AES key is not attackable. The comparison is made at a stated security level — the classical work factor of the best known attack — not at the bit length of the key.

4. The lifecycle stages as a coverage checklist

Write the five stages as a product of indicators, each of which must be 1 for the key to survive:

\[ S_{\text{key}} = G \cdot St \cdot U \cdot R \cdot D \]

Generate with a CSPRNG, store in a keystore or HSM, use with least exposure, rotate or revoke on policy and on suspicion, destroy every active and backup copy. A zero anywhere makes the product zero, exactly as with grounded innovation on the Week 1 foundations page: a perfectly generated key that is written to a log has no security at all.

The AES Round as a Diffusion Argument

AES's rounds are not decoration. Each step exists to defeat one specific kind of attack, and the arithmetic of the round tells you which.

The state, the S-box and the round key

The 128-bit block is arranged as a 4×4 matrix of bytes, \(s_{r,c}\) for row \(r\) and column \(c\), filled column by column. Each round applies four operations in a fixed order:

\[ \text{SubBytes} \;\to\; \text{ShiftRows} \;\to\; \text{MixColumns} \;\to\; \text{AddRoundKey} \]

SubBytes replaces each byte with its entry in a fixed 16×16 S-box. Formally it is the affine transformation of the multiplicative inverse in \(\mathrm{GF}(2^{8})\), which is where the non-linearity comes from: without a non-linear step the whole cipher would be a system of linear equations over bits and would fall to linear algebra.

ShiftRows rotates row \(r\) left by \(r\) bytes, so row 0 is unchanged and row 3 moves by three. MixColumns multiplies each column by a fixed polynomial modulo \(x^{4}+1\) over \(\mathrm{GF}(2^{8})\). AddRoundKey XORs the state with the round key from the key schedule — the only key-dependent step.

Why the order of the steps matters

Confusion and diffusion are the two classical design goals, and each AES step serves exactly one of them:

StepGoal servedEffect on the stateAttack it defeats
SubBytesConfusionNon-linear per-byte substitutionLinear and differential cryptanalysis over the byte structure
ShiftRowsDiffusionMoves bytes between columns without changing themAttacks that treat each column as an independent 32-bit cipher
MixColumnsDiffusionOne byte in a column changes all four bytes of that columnKeeping a plaintext difference confined to a single byte
AddRoundKeyKey injectionXOR with a round key; no non-linearityRecovering the key from plaintext–ciphertext pairs without the schedule

ShiftRows alone spreads a byte across columns; MixColumns alone spreads it within a column. Applied together over several rounds, a change in one input bit reaches every byte of the state. That is the diffusion argument, and it is why the round count is 10 for AES-128, 12 for AES-192 and 14 for AES-256: longer keys need more rounds to keep the same margin against the best known attacks.

The avalanche measurement

Diffusion is testable. Encrypt two plaintexts that differ in exactly one bit under the same key and count the differing output bits:

\[ D = \frac{1}{128}\sum_{i=1}^{128} \bigl[\, C_i \neq C'_i \,\bigr] \]

A well-designed cipher drives the expected value of \(D\) towards \(\tfrac{1}{2}\). Measured over many random input pairs, AES's result is statistically indistinguishable from that figure, which is the practical statement of the avalanche property. The same property, applied to a hash function, is what makes a digest detect a single altered bit.

THE FOUR STEPS ON A 4 × 4 STATE (rows = words of the state) SUB-BYTES every byte replaced by S[byte] non-linear SHIFT-ROWS row 0 → 0, row 1 → 1, row 2 → 2, row 3 → 3 diffuse MIX-COLUMNS each column × fixed polynomial in GF(2^8) diffuse ADD-ROUND-KEY state ⊕ round key key only ROUND COUNT 10 (AES-128) | 12 (AES-192) | 14 (AES-256) FINAL ROUND omits MixColumns

Worked answer — a diffusion question. “Explain why AES uses both ShiftRows and MixColumns, when MixColumns already changes four bytes for every one that changes.”

1

Say what each step does to a change. MixColumns spreads one changed byte across the four bytes of its own column only. ShiftRows moves bytes between columns but does not change any byte value on its own.

2

Show why one alone is not enough. With MixColumns and no ShiftRows, a difference that starts in one column stays in that column forever: the state decomposes into four independent 32-bit ciphers, and an attacker can attack each column separately. With ShiftRows and no MixColumns, a changed byte moves around but never multiplies, so the number of active bytes grows far too slowly to defeat differential cryptanalysis in 10 rounds.

3

Combine them. SubBytes makes the transformation non-linear; ShiftRows relocates bytes into new columns; MixColumns then spreads each relocated byte across its new column. Two rounds are enough for a single-byte difference to reach every byte of the state, and the remaining rounds keep it there.

4

Name the pay-off. Full diffusion is what makes the avalanche measurement come out near one half, and it is why the round count is fixed at 10, 12 or 14 rather than chosen per message. The argument is structural: it does not depend on the key, which is exactly what Kerckhoffs's principle requires of a public design.

Hash Properties and the Birthday Bound

Hash functions are the one primitive this week whose security margin is half what its output size suggests. The reason is a counting argument, and it decides which digests are still acceptable.

1. Three properties, three different work factors

For a hash function with an \(n\)-bit output, the three standard security properties have different costs:

\[ \text{preimage: } 2^{n} \qquad \text{second preimage: } 2^{n} \qquad \text{collision: } 2^{n/2} \]

Preimage resistance — given a digest, find a message mapping to it. The only known generic method is brute force, so the cost is about \(2^{n}\). Second preimage resistance — given one message, find a different one with the same digest — also \(2^{n}\). Collision resistance — find any two messages with the same digest — is the odd one out, and the birthday bound is why.

2. The birthday bound

Generate \(q\) digests at random from a space of \(N = 2^{n}\) values. The probability that at least two of them match is, to a very good approximation,

\[ P(\text{collision}) \;\approx\; 1 - e^{-q(q-1)/(2N)} \;\approx\; 1 - e^{-q^{2}/(2N)} \]

Setting the exponent to about 1 gives the collision threshold:

\[ q \;\approx\; \sqrt{2N} \;=\; \sqrt{2 \cdot 2^{n}} \;\approx\; 2^{n/2} \]

So a collision becomes likely after only about \(2^{n/2}\) messages — not \(2^{n}\). For SHA-256 with \(n = 256\), that is \(2^{128}\) work, which is still out of reach and equal to the AES-128 security level. For MD5 with \(n = 128\), it is \(2^{64}\): achievable on ordinary hardware, and the reason MD5 is unusable for any security purpose. For SHA-1 with \(n = 160\), the bound is \(2^{80}\), and practical collisions have been demonstrated — which is why SHA-1 is deprecated rather than merely discouraged.

3. Why a digest length must be twice the intended security level

The table above is the practical consequence. If a system needs a 128-bit security level from a hash — to match AES-128, say — then it needs a digest whose birthday bound is \(2^{128}\), which means \(n/2 = 128\), which means \(n = 256\) bits. A 128-bit digest can never deliver 128-bit collision resistance, no matter how good the hash function is, because the counting argument applies to any function with a 128-bit output.

This is why the modern default is SHA-256 or larger, and why a design that says “we hash with MD5 for speed and the output is 128 bits” is off by \(2^{64}\).

4. What the properties do not give you

None of the three properties is integrity against an active attacker. Formally, a hash is unkeyed: anyone can compute \(H(m')\) for a modified message \(m'\). Given a message–digest pair \((m, H(m))\) from an untrusted channel, an attacker who can modify the message simply supplies \((m', H(m'))\). Integrity against that attacker requires a value the attacker cannot recompute:

\[ \text{MAC: } \mathrm{tag} = F(K, m) \qquad \text{signature: } \sigma = \mathrm{Sign}(sk, H(m)) \]

In both cases the attacker lacks the key. The hash inside a signature is there to compress an arbitrary-length message to a fixed size that the signature scheme can handle — not to provide the security. In an AEAD construction the tag \(T\) does the same job for a ciphertext. This is precisely the deck's asterisk on the word “hash” in the goal table, and it is the most commonly examined distinction of the week.

Worked answer — sizes and levels. “A system needs to protect 1 GB backups, verify firmware images and sign invoices, all at a 128-bit security level. Choose the primitives and justify the sizes.”

1

Backups — confidentiality plus integrity. A symmetric AEAD at the 128-bit level: AES-128-GCM. Key length 128 bits gives a search space of \(2^{128}\), which meets the stated level. The nonce must be unique per encryption under the key: reuse breaks GCM's confidentiality and authentication together.

2

Firmware — integrity against an attacker. A hash alone is not enough: the attacker who replaces the image replaces the published digest too. Use a digital signature, or a MAC when the device already shares a secret with the publisher. The digest inside the signature should be SHA-256, because the signature's collision resistance is limited by the hash's birthday bound \(2^{n/2} = 2^{128}\), which matches the required level.

3

Invoices — non-repudiation. A MAC cannot give it, because both parties hold the same key and either could have produced the tag. Only a signature with a private key held by one owner can. At the 128-bit level the recommended key size is RSA-3072 (or an equivalent elliptic-curve key, which is far shorter for the same level), with SHA-256 as the digest. Note the asymmetry the table showed: 3072 bits of RSA is required to match 128 bits of AES.

4

State the levels, not the lengths. The markable sentence is: “All three sit at the 128-bit security level: AES-128 for the bulk data, SHA-256 as the digest, and RSA-3072 or an equivalent elliptic-curve key for the signature — because key sizes are only comparable within a family, and a hash's collision resistance is capped at half its digest length.”

A design uses SHA-1 to fingerprint a 1 GB software release and argues that a 160-bit digest is plenty because the attacker would need \(2^{160}\) work. What is wrong with the argument?
Collision resistance costs about \(2^{80}\), not \(2^{160}\), because of the birthday bound — and SHA-1 collisions have been demonstrated in practice
SHA-1 outputs 128 bits, not 160, so the work factor is even lower
The digest must be smaller to raise the birthday bound

Construct-Selection Checklist

Most Week 4 exam questions reduce to “is this construction fit for the stated goal?”. Run the six steps in order and the justification writes itself.

StepLook forMarks are lost when…
1. GoalOne of the five goals from the deck's tableYou answer “which algorithm is strongest?” instead
2. AttackerPassive, active, or in possession of the keyYou claim a bare hash gives integrity against an active attacker
3. Primitive familySymmetric for bulk, asymmetric for trust, hybrid for a protocolYou propose public-key encryption for bulk data
4. ConstructionCipher + mode + nonce strategy + authenticationYou name AES and stop, without saying which mode
5. Key\(2^{n}\) search space and \(H\) bits of real entropyYou equate key length with entropy
6. LifecycleFive stages, each with an ownerYou say “the key is stored securely” and stop there

Worked answer — a full review in six steps. Design under review: “we encrypt user documents with AES-256 in CBC mode using a fixed IV, hash each document with MD5 to prove it has not been changed, and store the key in the database next to the data.”

1

Goal. The stated goals are confidentiality of stored documents and proof that they have not been changed. Those are two goals, so one primitive will not cover both.

2

Attacker. Documents live in a database alongside their keys, so the relevant attacker is someone who reaches the database — an active attacker with the ciphertext and the key. That is the strongest realistic case here, and it defeats both choices.

3

Primitive family. Symmetric is correct for bulk document data. No asymmetric primitive is needed for confidentiality here.

4

Construction. Two faults. A fixed IV in CBC means the first block of every document encrypts identically, so two documents with the same opening reveal that fact. And MD5 is collision-broken: at \(n = 128\) the birthday bound is \(2^{64}\), and practical collisions exist, so it cannot support a claim of integrity. In any case an unkeyed hash cannot prove integrity against an attacker who can also edit the stored hash. Replace with AES-GCM (or ChaCha20-Poly1305) under a unique per-document nonce, which delivers both goals with one tag.

5

Key. AES-256 gives a \(2^{256}\) search space, which is more than enough — but it is the wrong thing to worry about, because the key is stored in the same database as the ciphertext. No key length survives that, and the effective entropy of the key is irrelevant once the attacker simply reads it.

6

Lifecycle. Storage fails stage 2 and stage 3 of the five-stage lifecycle. Replace with envelope encryption: a per-document data key wrapped by a key-encryption key held in a keystore or HSM, with access restricted, key material never logged, and a rotation plan that re-wraps the data keys rather than re-encrypting every document.

7

The one-sentence verdict. “The primitive is fine and everything around it is wrong: a fixed IV leaks equality of first blocks, MD5 cannot support an integrity claim at \(2^{64}\) collision work and is unkeyed anyway, and a key stored beside its own ciphertext has no protection regardless of its length. Move to AES-GCM with a unique nonce per document and put the key in a keystore under envelope encryption.”
