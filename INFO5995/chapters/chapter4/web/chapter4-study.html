What Cryptography Actually Guarantees

The deck's opening move is to refuse the word “secure”. Cryptography is a set of mathematical techniques that protect information and communication even when the network or the system cannot be fully trusted — and each technique delivers one specific guarantee under one defined threat model.

The chain to memorise: information → cryptographic primitive (algorithm + parameters + key, when required) → security guarantee. A primitive is never “strong” in the abstract; it is strong for a stated goal against a stated attacker.

Trust the algorithm, not the channel

The first lecture's warning was “don't trust anyone”. Cryptography is how we build trust out of mathematics instead of out of the network: secure communication and secure computation rest on the properties of an algorithm, not on the honesty of the path between two parties.

Crypto is everywhere

Cryptography protects data from being read or changed. Remove it and online banking stops working, card payments stop being safe, passwords become readable by anyone on the network, software updates can be replaced by attackers, and messaging can be intercepted.

The asterisk is examinable. A bare hash is only a fingerprint: an attacker who can modify the data can replace the message and its hash. Integrity against an active attacker requires a MAC, a digital signature or an AEAD construction — not a hash on its own.
A team publishes a file together with its SHA-256 hash on the same web server. Which guarantee have they actually delivered?

Confidentiality, because the hash hides the file contents

Kerckhoffs's Principle: Public Algorithm, Secret Key

Week 4 poses the design question directly — is hiding the best way to keep something safe? — and answers it with a nineteenth-century principle that still governs every modern standard.

Kerckhoffs's principle

The security of a system should depend on its key, not on its design remaining obscure. Auguste Kerckhoffs, a Dutch cryptographer writing in the 19th century, framed it as “the enemy knows the system”.

Security by obscurity

The natural instinct: a good secret is your best defence, so keep the mechanism hidden. The deck's line is that even dogs bury bones — hiding is the obvious move, and it is the one that fails first, because the mechanism leaks.

Security by transparency

True security comes from openness. The algorithm is published, reviewed and attacked by everyone; the only thing protected is the key. This is what modern cryptography does: public algorithm + secret key.

Why openness is stronger

  • Public review and trust — thousands of cryptanalysts have tested AES; nobody has tested your home-grown scheme.
  • Scalability — changing a key is cheap; redesigning an algorithm is not.

What the principle does not say

  • It does not say keys may be public. The key is the one secret, and it must stay secret.
  • It does not say implementations may leak. Padding oracles and timing leaks attack the key, not the published design.

AES(key, plaintext) → ciphertext. Everyone may know that you used AES; nobody may know the key.
Why this principle makes the rest of the week possible: because the algorithm is public, we can standardise it (FIPS 197), analyse it in the open, accelerate it in hardware, and reason about security in terms of key length. Everything that follows — search space, entropy, lifecycle — is about protecting one short secret instead of one large design.
A vendor argues that its file encryption is safe because the scrambling routine is proprietary and undocumented. What is the correct assessment under Kerckhoffs's principle?
It is safe, because an attacker cannot read the algorithm
Its security rests on obscurity, so it will fail as soon as the design leaks — and public review, which is how AES earned trust, never happened
Proprietary algorithms are always weaker than published ones, so the only fix is to publish the source code

Symmetric Encryption: One Shared Secret

Encryption changes who can understand the data. The simplest key model is one secret that both sides already hold: Alice and Bob must each possess the same key K.

Symmetric encryption

A single shared secret key drives both directions: \(C = \mathrm{Enc}(K, M)\) and \(M = \mathrm{Dec}(K, C)\). High throughput, small overhead and suitability for large data come from the fact that the same short key protects an arbitrarily long message.

HELLO CLASS plaintext
→
KEY shared secret K
→
9F A2 71 … ciphertext
→
HELLO CLASS decrypt with the same K
The algorithm may be public. Security depends on controlling the key.

Why it is useful

  • High throughput
  • Small overhead
  • Ideal for bulk data: files, disks and network traffic

What can go wrong

  • Key leakage
  • Unsafe sharing of the secret
  • Nonce or IV mistakes
The one sentence to remember: if K is exposed, anyone holding K can decrypt the data. There is no second factor and no recovery — which is exactly why the second half of this week is about protecting K, and why Week 5 exists at all.

In practiceMost real protocols use both: a short asymmetric setup to establish trust or keys, then a long symmetric session for bulk data.

The One-Time Pad: Perfect Secrecy, and Why It Stays in the Textbook

Before practical ciphers, the deck proves what is theoretically possible. A random key exactly as long as the message, XORed into the plaintext, gives a ciphertext that reveals nothing about the message.

One-time pad

Create a random key the same length as the message. Encrypt by combining each bit of plaintext with each bit of key using XOR, and decrypt by XORing the ciphertext with the same key again: \(C = M \oplus K\) and \(M = C \oplus K\).

PLAINTEXT (M) 10110010 ONE-TIME KEY (K) 01011001 -------- XOR CIPHERTEXT (C) 11101011 DECRYPT: C ⊕ K = 11101011 ⊕ 01011001 = 10110010 = M

Truly random

No predictable pattern. Generated by a cryptographic random-bit generator, not by a human or a formula.

Same length

One key bit for every message bit. A 1 GB message needs a fresh 1 GB key.

Kept secret

Known only to sender and receiver, and shared in advance through a channel nobody else can read.

Never reused

A fresh key for every message. This is the condition that fails first in practice.

When all four conditions hold, the ciphertext reveals nothing about the plaintext. Not “very little” — nothing. This is the strongest confidentiality statement in the whole week.

The cost, and the reuse failure

The guarantee is exceptional; the key-management cost is the problem. Key length equals message length, the key must be distributed securely in advance, message-sized secret material has to be stored, and the key must be destroyed so it can never be reused.

Reuse the key once and the secrecy collapses. For two messages under the same key:

\[ C_1 \oplus C_2 = (M_1 \oplus K) \oplus (M_2 \oplus K) = M_1 \oplus M_2 \]

The key cancels out. The attacker now holds the XOR of two plaintexts, which is enough to recover both with ordinary language statistics. Key reuse destroys perfect secrecy — and that limitation is what motivates practical stream and block ciphers.

Worked example — from the ideal to the deployable. The exam question is usually phrased as “why is the one-time pad not used in practice?”. Answer it by walking the four conditions and then naming what a practical cipher changes.

1

State the ideal. Perfect secrecy: with a truly random key used once, at the same length as the message, \(C = M \oplus K\) leaks nothing about \(M\).

2

Cost it. Key length equals message length, so protecting a 1 GB file needs a 1 GB key. Every message needs its own key, and every key must be delivered in advance over a channel that is already secure — the problem you were trying to solve.

3

Show the reuse failure. Two ciphertexts under one key XOR to \(M_1 \oplus M_2\). The key disappears from the equation, so the attacker's problem no longer involves the secret at all.

4

Name the replacement. Practical systems keep the goal (a short secret protecting a long stream) and change the key model: a stream cipher expands a short key and a unique nonce into a keystream, and a block cipher transforms fixed-size blocks under a mode of operation that keeps repeated encryptions from matching.

5

Close with the discipline that survives. The one-time pad's “never reuse” rule does not go away. It reappears as nonce discipline: a nonce must never repeat under the same AEAD key.

An engineer keeps one long random key file and XORs each outgoing message with the next slice of it, never repeating a slice. What is the status of this design?
It is still a one-time pad — it is secure only as long as no slice is ever reused and the randomness is genuine, which is exactly the condition that is hard to guarantee operationally
It is insecure because one-time pads are obsolete
It becomes secure only if the key file is truncated and the same beginning is reused

Stream Ciphers and Block Ciphers

Practical ciphers answer the one-time pad's question — how can a short key protect a long stream of data? — in one of two ways. The distinction describes how the cipher handles input, not how strong the algorithm is.

Stream cipher

Protects a flowing sequence. The key and a nonce seed a generator that produces a keystream, and each message bit is XORed with one keystream bit: \(C = M \oplus \mathrm{keystream}\). Natural for continuous data. The deck's modern example is ChaCha20.

Block cipher

Transforms fixed-size blocks. The message is split into blocks \(M_1, M_2, M_3, M_4\) and the cipher maps each block to a same-size block. AES uses 128-bit blocks; a mode of operation safely handles messages longer than one block.

message blocks M1   M2   M3   M4
→
block cipher 128-bit block
→
ciphertext blocks C1   C2   C3   C4
A block cipher alone handles exactly one block. Everything longer is the mode's job.
Modern protocols normally use authenticated encryption — not a raw cipher by itself. A stream cipher or a block cipher is a component. The deployable unit is a complete construction: cipher + mode + nonce strategy + authentication mechanism.

A developer says “I used AES, so the data is safe”. What is missing from that statement?

Inside AES: A Public, Repeatable Round Function

AES is the week's worked example of Kerckhoffs's principle in hardware: a fully public specification, adopted as FIPS 197, whose entire secrecy lives in the key schedule. Step through its round function byte by byte.

AES (Advanced Encryption Standard)

A symmetric block cipher with a 128-bit block and a key of 128, 192 or 256 bits. Its round count grows with the key: 10 rounds for AES-128, 12 for AES-192 and 14 for AES-256. Widely accelerated in hardware, which is why it is the default in modern protocols.

StepWhat it doesWhy the design needs it
SubBytesEach state byte is replaced by its entry in a fixed public 16×16 substitution box (S-box)Supplies non-linearity. Without it the cipher would be a solvable system of linear equations
ShiftRowsRow r of the 4×4 state is rotated left by r bytesSpreads bytes across columns so a change in one byte affects several columns
MixColumnsEach column is multiplied by a fixed polynomial over GF(28)Diffuses change within a column; combined with ShiftRows it diffuses across the whole state
AddRoundKeyThe state is XORed with a round key derived from the key scheduleThe only step that involves the secret. Everything else is public and key-independent
Block size: 128 bits
Key sizes: 128 / 192 / 256 bits
Rounds: 10 / 12 / 14
Public specification: FIPS 197
Hardware accelerated

Structure: a substitution–permutation network

Every round applies the same four steps in the same order, under a different round key. The final round omits MixColumns. Because the structure is public and identical for every user, an attacker knows exactly what the cipher is doing — and still cannot invert it without the key.

Why diffusion is the point

Confusion hides the relationship between key and ciphertext; diffusion spreads one plaintext bit across the whole state. After enough rounds, changing a single plaintext bit changes roughly half of the output bits — the avalanche property you will measure on the Foundations page.

Exam framing: never describe AES as “a secret algorithm”. It is the opposite — a published standard whose security depends entirely on the key, which is why the rest of this week is about key generation, key length, entropy and lifecycle.
Which AES round step is the only one that involves the secret key?
SubBytes, because the S-box is secret
ShiftRows, because the rotation amount depends on the key
AddRoundKey, which XORs the round keys produced by the key schedule

Modes of Operation: The Same AES Reveals Different Things

The same AES primitive can be used in very different ways. The mode decides what an observer of the ciphertext can learn, and whether tampering can be detected at all.

ModeHow blocks relateRepeated plaintextPatternsIntegrity
ECB — electronic codebookEach block is encrypted independentlyRepeated plaintext → repeated ciphertextPatterns remain visibleNone
CBC — cipher block chainingEach block depends on the previous ciphertext blockRepeated plaintext gives different ciphertextHides repeated patternsConfidentiality only; authentication is separate
GCM — Galois/counter modeCounter-based encryption plus an authentication tagDetermined by the nonce, never by the plaintextHides contentDetects tampering
WHY ECB FAILS — encrypt two identical blocks under one key PLAINTEXT [ ATTACK ][ AT DAWN ][ ATTACK ][ AT DAWN ] ECB [ 4F 1C ][ 9A 03 ][ 4F 1C ][ 9A 03 ] ^ ^ identical plaintext blocks produce identical ciphertext blocks, so the structure of the message is visible without any key.
ECB is the classic exam answer for “what not to do”. It is not that AES is weak; it is that encrypting each block independently publishes any repetition in the plaintext. CBC fixes the repetition by chaining, but it still provides confidentiality only — authentication must be designed separately, and doing that wrongly is a well-known source of padding-oracle attacks. GCM does both.
KEY K secret
UNIQUE NONCE N public, never repeated under K
PLAINTEXT M the bulk data
→
AES-GCM encrypt + authenticate
→
CIPHERTEXT C plus TAG T
(C, T) = Enc(K, N, M). If C or T changes, verification fails and the plaintext is rejected.
A 4 MB file is encrypted with AES in ECB mode. The ciphertext visibly contains the same 16-byte pattern at four separate offsets. What has gone wrong?
The mode, not the cipher: ECB encrypts blocks independently, so identical plaintext blocks become identical ciphertext blocks
The block size is too small at 128 bits
The same key was reused for each of the four blocks

Choose Complete Constructions, Not Algorithm Names

Selection question to ask: what security property does the complete construction guarantee? A cipher, a mode, a nonce strategy and an authentication mechanism together form the usable thing.

Modern defaults

  • AES-GCM — AES block cipher plus GCM authenticated mode; widely accelerated in hardware
  • ChaCha20-Poly1305 — stream cipher plus authenticator; strong software performance

Legacy — learn, do not choose

  • AES-CBC — can provide confidentiality, but needs a separate secure authentication design
  • DES, 3DES, RC4 — obsolete or prohibited in modern designs; retained only for history and migration discussions
SymmetricAsymmetricHybrid
Best forProtecting lots of dataEstablishing trust or keysBuilding a complete protocol
Key modelOne shared secretPublic / private pairShort asymmetric setup + long symmetric session
ExamplesAES-GCM, ChaCha20-Poly1305X25519, RSA-OAEP, RSA-PSS, EdDSATLS, envelope encryption
What still needs careKey sharing + nonce disciplineIdentity binding + private-key custodyComposition + lifecycle

Four ways strong primitives still fail in weak systems:

  1. Nonce reuse — repeating a nonce under one AEAD key can reveal relationships or worse.
  2. No authentication — encryption without integrity can permit controlled modification.
  3. Weak key lifecycle — keys leak through logs, backups, memory, access control or poor rotation.
  4. Unsafe composition — ECB, home-grown protocols and error oracles defeat good primitives.
Takeaway from the deck: choose a proven AEAD, design the protocol, then engineer the key lifecycle. In that order — because the choice of primitive determines what the protocol can promise, and the lifecycle determines whether the promise survives contact with operations.

Worked example — reviewing a file-encryption design. A team proposes: “AES-128 in ECB mode, the key is stored in the application config file, and we hand the same key to every customer install.” Review it.

1

Mode. ECB encrypts each 128-bit block independently, so repeated plaintext blocks produce repeated ciphertext blocks. For structured files — spreadsheets, database pages, images — the layout of the content remains visible. Replace with AES-GCM (or ChaCha20-Poly1305 where hardware AES is unavailable).

2

Integrity. ECB provides none. An attacker who flips a ciphertext bit flips the corresponding plaintext bit with no detection. An AEAD returns a tag, and the receiver rejects the message when the tag does not verify. Replace with an authenticated construction.

3

Nonce. GCM requires a unique nonce per encryption under the same key. A file-encryption design must therefore guarantee that the nonce is generated fresh — not derived from a filename or a counter that restarts. Add a nonce strategy before adopting GCM, not after.

4

Key custody. A key in a plain config file is readable by anyone with filesystem access, and it leaks through backups and support bundles. Replace with a keystore or HSM, restricted access, and no logging of key material.

5

Key per install. One key shared by every customer means one compromise breaks every customer, and rotation becomes a mass migration. Replace with a per-install data key wrapped by a key-encryption key — envelope encryption — so rotation is a re-wrap rather than a re-encrypt of all data.

6

The one-sentence verdict. “AES is the right primitive, but the construction is wrong in four independent ways: the mode leaks patterns, there is no integrity, the nonce strategy is undefined, and the key is neither protected nor scoped. Choose AES-GCM, define the nonce, move the key into a keystore, and give each install its own data key.”

What Makes a Key Strong: Length, Entropy, Lifecycle

A key is valuable because it is difficult to predict — and carefully controlled. Three separate properties are in play, and conflating them is the most common Week 4 mistake.

Key roleWho may hold itWhat operation it enables
Symmetric secretShared by the authorised partiesEncrypt + decrypt bulk data
Private keyKept by one ownerDecrypt • sign • derive secrets
Public keyDesigned for distributionEncrypt • verify • establish keys
Four slogans worth memorising: public ≠ unprotected • private ≠ shared • secret ≠ memorable. The role of a key determines who may possess it and what operation it enables — nothing more and nothing less.

Key length sets the maximum search space

An n-bit key has \(2^n\) possible bit strings — if every string can really occur.

\[ \text{search space} = 2^{n} \qquad 2^{4} = 16 \qquad 2^{128} \approx 3.4 \times 10^{38} \]

Four bits are small enough to enumerate by hand; 128 bits are a vast candidate space. Length helps only when generation and implementation preserve the full search space.

Length is not entropy

Entropy is the attacker's uncertainty before the key is generated — not the number of characters the key occupies.

HUMAN PATTERN CSPRNG OUTPUT INFO5995-INFO5995! 7f2a19c0b6e3d84a 915cf207ab469d31 Long, but built from a Generated from a cryptographic guessable rule random-bit generator

If only 16 bits vary, the effective search is at most \(2^{16}\) candidates — even inside a 128-bit field. LONG ≠ STRONG.

A strong key can still fail through poor handling

The five-stage lifecycle the deck lays out. Security must survive every stage, from creation to destruction:

StageWhat good looks likeFailure it prevents
1. GenerateOS CSPRNG, secure entropy sourcePredictable keys from human patterns or weak seeding
2. StoreKeystore or HSM, restricted accessLeakage through config files, backups and logs
3. UseLeast exposure, never log the keyKey material in logs, crash dumps and memory dumps
4. Rotate / revokePolicy plus a response plan to compromiseOne leaked key staying valid forever
5. DestroyRemove active and backup copiesA retired key still decrypting old data
The week's summary formula: strong cryptography = strong primitive + unpredictable key + disciplined lifecycle. Every one of the four failure modes in the previous section is a failure of the second or third term.
A service derives its AES key with sha256("GoldenRetriever2019"). The key is 256 bits long. How strong is it?
256 bits of security, because SHA-256 outputs 256 bits
Far weaker than 256 bits: the effective search space is the guessing space of the phrase, not the output length of the hash
Secure, provided the hash function is a standard one such as SHA-256

Cryptographic Hash Functions: A Fixed-Length Fingerprint

A hash function maps an input of any length to a short fixed-length digest. It is the second primitive family in the week's toolkit, and it is also the one most often misused.

Cryptographic hash function

A public function \(h = H(m)\) that maps a message of arbitrary length to a fixed-length digest. It is one-way (preimage resistant), collision resistant and produces a different digest for even a one-bit change in the input (the avalanche effect).

PropertyWhat it meansWhat it is used for
Preimage resistanceGiven a digest, finding any message that produces it costs about \(2^{n}\) work for an n-bit digestIntegrity by fingerprint; password verification with a salt and a slow KDF
Second preimage resistanceGiven a message, finding a different message with the same digest is infeasibleDetecting substitution as well as corruption
Collision resistanceFinding any two messages with the same digest costs about \(2^{n/2}\) work (the birthday bound)Choosing digest length; why MD5 and SHA-1 are deprecated
AvalancheChanging one input bit changes about half the output bitsDetecting modification at all, even a single flipped bit
AlgorithmDigestStatus in modern designs
MD5128 bitsBroken — practical collisions; unsuitable for any security purpose
SHA-1160 bitsDeprecated — collisions demonstrated; retained only for legacy data
SHA-256256 bitsStandard default digest (SHA-2 family)
SHA-512512 bitsStandard, larger margin on the birthday bound
SHA-3224–512 bitsStandard alternative with a different internal design (sponge construction)
What a hash does not do. A bare hash is only a fingerprint: an attacker who can modify the data can replace both the message and its hash. It also provides no confidentiality — the digest is not encryption, and it cannot be reversed to recover the message. For integrity against an active attacker, use a MAC, a signature or an AEAD.

Where hashes earn their place

  • Software update manifests and release checksums
  • Content addressing and integrity checks in storage systems
  • Key derivation (HKDF) and password hashing with a salt and a deliberately slow function
  • Building blocks inside MACs, signatures and certificate fingerprints

Where they are misused

  • As a substitute for a MAC over data an attacker can edit
  • As a way to “encrypt” data — hashing is not encryption
  • As a password store without a salt and a slow KDF
  • With a deprecated digest (MD5, SHA-1) in a new design

Worked example — choosing a primitive for three requirements. A team must (a) protect a 2 GB backup on disk, (b) let users verify that a firmware image has not been altered, and (c) let a customer prove that a signed invoice came from the vendor.

1

(a) Bulk backup. This is confidentiality plus integrity over a lot of data, so the requirement is symmetric and authenticated: AES-GCM or ChaCha20-Poly1305 with a per-backup unique nonce, and a per-install data key wrapped by a key-encryption key. ECB is excluded because it leaks structure; CBC alone is excluded because it supplies no integrity.

2

(b) Firmware verification. The question is “has this exact image been altered?” against an attacker who can modify the download. A bare SHA-256 published on the same site as the image does not answer it, because the attacker edits both. Use a digital signature over the image from a key the device already trusts, or a MAC when the verifier already shares a secret with the publisher. This is where Week 5's signatures and certificates take over; the important point here is that a hash on its own is not enough.

3

(c) Signed invoice. Non-repudiation is required, and the vendor must not be able to deny authorship. Only a digital signature over a hash of the document, bound to an identity through a certificate, gives that — a MAC cannot, because both parties hold the same key and either could have produced the tag.

4

The pattern behind all three answers. Name the goal first (confidentiality, integrity, non-repudiation), then the attacker's capability, then the primitive, then the key model and lifecycle. Choosing “the strongest algorithm” before naming the goal is the mistake the deck warns about.

A downloads page publishes an installer and, next to it, SHA-256: 8f14e4…. What does this actually protect against?
Accidental corruption and download errors — not an attacker who controls the download page, who can replace both the installer and its published digest
An attacker learning the contents of the installer, because the hash hides them
Any modification by any attacker, because SHA-256 is collision resistant

Week 4 Recap

Match the primitive to the goal

Confidentiality, integrity, authentication, non-repudiation, key establishment. Different goals need different tools, and a bare hash is only a fingerprint.

Guarantees

Public algorithm, secret key

Kerckhoffs's principle: the enemy knows the system. Security must rest on the key, which is why openness, review and standardisation are strengths rather than risks.

Design principle

Perfect secrecy is not deployable

The one-time pad proves what is possible: a random key as long as the message, used once. Key length equals message length, and reuse collapses the secrecy to M1 ⊕ M2.

Theory

AES is a component, not a construction

128-bit blocks, 10/12/14 rounds, public specification. The mode decides what the ciphertext reveals: ECB leaks patterns, CBC hides them but adds no integrity, GCM does both.

Practice

Length is not entropy

Search space is 2^n only if every bit can vary. A memorable 128-bit-looking passphrase built from a rule has almost no entropy: LONG ≠ STRONG.

Key strength

Strong crypto = primitive + key + lifecycle

Generate with a CSPRNG, store in a keystore or HSM, use with least exposure, rotate on policy, destroy every copy. Nonce reuse and unsafe composition defeat good primitives.

Three ideas to leave with. (1) Public algorithms, protected secrets — security should depend on strong keys, not on hiding how the system works. (2) Encryption is only one part — a secure channel also needs integrity, authentication and safe key establishment. (3) Strong primitives must be composed correctly — good algorithms still fail through weak protocols, poor randomness or mishandled keys.
Where Week 5 picks up. Symmetric encryption left one difficult question open: Alice and Bob want the speed of symmetric encryption, but how does K reach both sides? Sending K across the network lets an observer copy it. Agreeing on K without sending K is the job of Diffie–Hellman — and once agreement exists, authentication is needed to stop a man in the middle from substituting both public values.
