Foundations: the arithmetic of building and running securely

Week 8 is a systems week, so this page does the quantitative work the lecture leaves implicit: one risk model that explains why layers help and why shared dependencies break them, the exposure-window arithmetic behind vulnerability management, the detection mathematics that explains why an IDS is noisy, and the anonymity model behind inference attacks. Every formula is a revision aid for the concepts on the study guide — the notation is introduced here, not taken from the deck.

Definitions and the risk model

Marks in this unit are lost on definitions more often than on ideas. Fix the vocabulary first, then the relationship that makes defence in depth an argument rather than a slogan.

Vulnerability, exploit, threat, control

A vulnerability is a weakness that can be used to violate a security property. An exploit is the means of using it. A threat is the actor or event that would do so. A control is anything that reduces the chance of success or the impact. Note the deck's usage: the weakness lives in the application, so the fix usually does too.

Software security vs system security

Software security builds secure software before deployment: focus, objective and activity all sit in development and testing. System security protects deployed systems: the objective changes from preventing vulnerabilities to detecting and responding to attacks, and the activity from development to operation and maintenance.

Access control vs inference

Direct attacks (SQL injection) manipulate a query through unsafe input handling. Indirect attacks (inference) use queries the system permits and learn from what the answers reveal. The first is a defect in code; the second is a defect in what the system is willing to disclose.

1. Risk as a product of three factors

Week 1's risk language, applied to a software system:

\[ R \;=\; T \times V \times I \]

where \(T\) is the likelihood that a threat acts, \(V\) the likelihood that a vulnerability is exploitable, and \(I\) the impact. The product form is the examinable part: driving any one factor to zero removes that path, and reducing one factor without the others gives the attacker an easy substitute.

2. Defence in depth, and when it is an illusion

If a system has \(n\) independent controls and control \(i\) fails with probability \(p_i\), the chance that all of them fail is:

\[ R_{\text{res}} \;=\; I \prod_{i=1}^{n} p_i \]

Three layers each failing with \(p = 0.3\) give \(0.3^{3} = 0.027\): the impact is reached in under 3% of attempts. But the product assumes independence, and in software it is exactly what fails. If one vulnerable library appears in three of the layers, those three failures share a single cause and the product collapses towards the largest of them:

\[ R_{\text{res}} \;\ge\; I \prod_{i=1}^{n} p_i \qquad \text{with equality only when the layers are independent} \]

That inequality is why the deck treats vulnerable components and patch latency as security controls rather than housekeeping.

Exposure windows and vulnerability management

Equifax was an unpatched component; Log4Shell was a vulnerable library. Both are questions of time, and time can be measured.

1. The exposure window

Let \(t_{\text{exploit}}\) be the moment exploitation becomes possible — public exploit code, or a scan that finds the service — and \(t_{\text{patch}}\) the moment the fix is deployed in production:

\[ W \;=\; t_{\text{exploit}} - t_{\text{patch}} \qquad\text{(negative means remediation happened first)} \]

If an exposed host is compromised with daily probability \(q\), the chance it survives the whole window is:

\[ P(\text{compromise}) \;=\; 1 - (1-q)^{W} \]
1

Worked example. An exploit is published on day 0. A patch is available on day 5, but the organisation's median deployment time is 30 days, so \(W = 30 - 0 = 30\) days for the affected hosts.

2

Assume a 1% daily compromise rate for scanned, internet-facing and unpatched hosts (\(q = 0.01\)):

\[ P(\text{compromise}) \;=\; 1 - 0.99^{30} \;\approx\; 1 - 0.740 \;=\; 0.26 \]

Roughly a one-in-four chance per host, from timing alone.

3

Now change one variable. Deploy the same patch in 7 days instead of 30: \(1 - 0.99^{7} \approx 0.068\), about 7%. Cutting the window by 77% cuts the risk by roughly 74%.

4

Say what the model is not. \(q\) is a modelling assumption, not a measurement, and compromise events are correlated (one worm sweeps every exposed host). The examinable conclusion is the monotonic one: risk rises with the window, so time to remediate is a security parameter.

2. Metrics that are actually about risk

Mean time to remediate, coverage and a prioritisation score:

\[ \overline{\text{MTTR}} \;=\; \frac{1}{n}\sum_{i=1}^{n} t_i \qquad\qquad C \;=\; \frac{\text{assets remediated}}{\text{assets affected}} \] \[ S \;=\; \text{severity} \times \text{exposure} \times \text{exploitability} \]

Ticket counts and “percentage of findings closed” are activity measures: they improve when a team closes easy findings. \(W\), MTTR and \(C\) are exposure measures, and they improve only when the risky assets actually change.

Two findings have the same CVSS severity. Finding A is on an internet-facing service with public exploit code; finding B is on an internal reporting host with no known exploit. Which do you fix first, and why?
Finding B, because internal systems are harder to monitor
Finding A, because exploitability and internet exposure dominate when severity is equal
Whichever is quicker to fix, to keep the closure rate high

Worked answer — ranking three findings with the prioritisation score. A monthly scan reports three issues on the same estate, each scored 1–5 on the three factors (illustrative values, invented for the exercise).

If the library is patched in 3 days and the admin API in 14, the two exposure windows are \(W_1 = 3\) and \(W_2 = 14\) against the same \(q\), so the API's residual risk is the larger of the two even though its score is smaller. Ranking decides the order; the window decides the outcome.

Detection arithmetic: why an IDS is noisy

The deck's IDS detects and alerts, and it can detect by signature or by anomaly. This section is the arithmetic behind the trade-off, and behind the question every security team is asked: why are there so many alerts?

1. The confusion matrix, in rates

For a detector over a stream of events, with attacks as the positive class:

\[ \mathrm{TPR} \;=\; \frac{TP}{TP+FN} \qquad \mathrm{FPR} \;=\; \frac{FP}{FP+TN} \]

\(\mathrm{TPR}\) (the detection rate) is what the vendor quotes. \(\mathrm{FPR}\) is what determines the workload, because the numerator of the false-positive rate is multiplied by an enormous number of benign events.

2. Precision and the base-rate fallacy

The question an analyst actually asks is “given an alert, is it an attack?”. With base rate \(\pi = P(\text{attack})\):

\[ P(\text{attack} \mid \text{alert}) \;=\; \frac{\mathrm{TPR}\,\pi}{\mathrm{TPR}\,\pi + \mathrm{FPR}\,(1-\pi)} \]

This is Bayes' rule, and it is the reason a “99% accurate” detector can be wrong almost every time: when \(\pi\) is tiny, the second term in the denominator is dominated by the false-positive rate times the huge benign population.

1

Worked example. A network sensor sees \(N = 1{,}000{,}000\) events per day. One event in 10,000 is a genuine attack, so \(\pi = 10^{-4}\) and there are 100 attacks and 999,900 benign events.

2

The detector: \(\mathrm{TPR} = 0.90\) and \(\mathrm{FPR} = 0.001\) — figures a vendor would be pleased to publish.

\[ TP = 0.90 \times 100 = 90 \qquad FP = 0.001 \times 999{,}900 \approx 1000 \]

So the team receives about \(1090\) alerts a day to find 90 real ones.

3

Precision:

\[ P(\text{attack}\mid\text{alert}) \;=\; \frac{90}{1090} \;\approx\; 8.3\% \]

Roughly eleven alerts for every real attack. This is not a broken detector; it is what a low base rate does to any detector.

4

What actually improves the analyst's day. Halving the false-positive rate to \(0.0005\) doubles precision to about 15%. Raising the detection rate to 0.99 adds 10 more true positives out of ~1100 alerts. Neither is as effective as reducing the event population: filtering the sensor to the authentication and egress traffic that matters cuts \(N\) by an order of magnitude and improves precision in proportion.

5

Connect it back to the deck. Signature-based detection usually has a lower false-positive rate on known patterns; anomaly-based detection can reach attacks nobody wrote a signature for, at a much higher false-positive cost. Choosing between them is choosing a point on this curve — and an IPS makes the choice expensive, because a false positive inline becomes an outage rather than a wasted alert.

Alert capacity is a control parameter. If an analyst can triage \(c\) alerts per day, the number of sensors you can deploy is bounded by \(c\) divided by the alert rate \(A = N\left[\mathrm{TPR}\,\pi + \mathrm{FPR}(1-\pi)\right]\). Beyond that bound, real alerts are missed because they are queued behind noise — the failure mode the deck describes as an attack continuing while the team reads the alert.
A vendor offers a detector with \(\mathrm{TPR} = 0.99\) and \(\mathrm{FPR} = 0.01\) for a network where only 1 event in 100,000 is an attack. What should you expect?
Roughly 99% of alerts will be real attacks
Almost every alert will be a false positive, because the base rate is tiny
The alert volume will be unchanged because the false-positive rate is only 1%

Worked answer — tuning one sensor. A web-tier sensor generates 4,000 alerts a day. Sampled triage suggests 20 are real. The team can triage 400 a day. Decide what to change.

1

Measure precision before tuning anything. \(P(\text{attack}\mid\text{alert}) \approx 20/4000 = 0.5\%\). The problem is quantified, and it is not the team's speed.

2

Decide which error is cheaper here. For a web-tier sensor with prevention already in place, a missed attack is recoverable (monitoring and logs still exist); 3,600 wasted alerts a day is not, because it hides the 20 that matter. On this sensor, reducing \(\mathrm{FPR}\) is worth more than raising \(\mathrm{TPR}\).

3

Change the population and the rules, in that order. Restrict the sensor to authentication, authorisation failures and egress traffic; suppress signatures that can only fire on traffic the estate no longer runs; and require two conditions before alerting on a single event. Each step reduces the benign numerator that \(\mathrm{FPR}\) multiplies.

4

Set the target as precision, not sensitivity. A workable target on this sensor is precision above 20% at a volume under 400 alerts a day — that is, roughly 80 real detections a day. State the target, then re-measure. Without a written target, every tuning argument is about taste.

5

If this sensor were an IPS, change the threshold again. Inline, a false positive is an outage, so the acceptable \(\mathrm{FPR}\) is far lower and the rules must be narrower. That asymmetry — not the technology — is the real difference between the deck's security camera and security guard.

Inference, anonymity and the cost of guessing

Two quantitative ideas close the week: a sequence of permitted answers is a measurement, and a brute-force attack has a price.

1. Every yes/no answer is at most one bit

The deck's salary example asks whether one person's salary exceeds a threshold. The response is a row or no row: one bit about that person. If the subject is one of \(k\) indistinguishable people (the anonymity set), then:

\[ P(\text{identify}) \;\approx\; \frac{1}{k} \qquad\qquad k' \;=\; \frac{k}{2^{m}} \quad\text{after } m \text{ independent yes/no answers} \]

To isolate one individual from \(k\) candidates therefore takes about \(\lceil \log_2 k \rceil\) answers. This is why the deck says inference risk grows as the anonymity set becomes smaller, and why a combination of harmless signals is the dangerous case: each signal halves the field.

1

Worked example. A conference publishes a chart with 200 reviewers' progress lines, no names. The anonymity set is \(k = 200\), so a random guess identifies a given reviewer with probability \(1/200 = 0.5\%\).

2

Add the per-paper review counts. If counts reveal that a paper had 3 reviewers and the set of plausible reviewers for it is 20, that is the new anonymity set — a reduction of about 3.3 bits:

\[ \log_2 200 - \log_2 20 \;=\; 7.64 - 4.32 \;\approx\; 3.3\ \text{bits of information gained} \]
3

Add behavioural fingerprints. If progress patterns fall into 8 distinguishable classes, that is \(\log_2 8 = 3\) more bits. Total leakage: about 6.3 bits, leaving an effective anonymity set of \(200/2^{6.3} \approx 2.5\) people. The linkage attack works because the bits add.

4

Turn it into a release rule. For a target re-identification risk of at most 5%, the anonymity set must satisfy \(k \ge 1/0.05 = 20\) after every published signal is considered — which means suppressing counts below a threshold, binning the time axis, and evaluating views in combination rather than one at a time.

\[ k_{\text{effective}} \;\ge\; \frac{1}{P_{\max}} \]

2. Entropy of a released signal

For a signal whose values occur with probabilities \(p_i\), the information it carries is:

\[ H(X) \;=\; -\sum_{i} p_i \log_2 p_i \]

Uniform over 8 classes gives \(H = 3\) bits; a highly distinctive pattern (say one class with \(p = 0.9\)) gives \(H \approx 0.57\) bits. Entropy is the right currency for inference because it composes: the combined leakage of independent signals is \(H(X) + H(Y)\), and it is bounded by the anonymity you intended to provide, \(\log_2 k\).

3. What a brute-force attack costs

For a secret of length \(L\) drawn from an alphabet of size \(A\), the search space and the expected time to find it at \(r\) guesses per second are:

\[ N = A^{L} \qquad\qquad T_{50} \;=\; \frac{A^{L}}{2r} \qquad\qquad H = L \log_2 A \ \text{bits} \]

The model assumes the secret is uniformly random. Real passwords are not, which is why an attacker uses a ranked list instead of an exhaustive search — and why rate limiting, lockout and MFA matter more than length alone.

Worked example — exhaustive search. A random 8-character lowercase-plus-digit password has \(36^{8} \approx 2.8 \times 10^{12}\) candidates. At \(r = 10^{4}\) guesses per second off-line, \(T_{50} = 2.8\times10^{12}/(2\times10^{4}) \approx 1.4\times10^{8}\ \text{s} \approx 4.5\) years. Strong by this model.

2

The same account, online. Rate limiting to 5 attempts per account per 15 minutes gives 480 attempts a day, so the expected time becomes \(1.4\times10^{12}/480 \approx 2.9\times10^{9}\) days — millions of years. Policy, not entropy, did the work.

3

Now the attack that actually happens. Credential stuffing tries one leaked password against many accounts. With 10,000 accounts and 5 attempts each that is 50,000 attempts: about 5 seconds at \(10^{4}\)/s, and per-account lockout never triggers because each account sees only five failures. The defence is checking credentials against breach lists and requiring MFA — not adding a character class.

4

State the assumption. \(T_{50}\) measures a uniform search. If the password is one of the ten thousand most common, the expected time is seconds. Every brute-force answer should therefore name both the search model and the policy controls that bound online attempts.

A published report gives per-team counts, a time series per team, and the team roster. Which model explains why this is a privacy problem even though no individual value is shown?
A cryptographic failure in the reporting pipeline
Information accumulates: the signals together shrink the anonymity set below the intended size
A denial-of-service risk from publishing aggregate load

Worked answer — defending an internal analytics view. An operations dashboard for a 5,000-person organisation shows per-team activity counts, a daily time series, and a “top contributor” list capped at three names per team. Decide what changes.

1

Compute the baseline. For a team of 500, the anonymity set is \(k = 500\), so a random guess identifies a member with probability \(1/500 = 0.2\%\). That is the number the design intends to protect.

2

Follow the “top contributor” list. Naming three people out of 500 has already removed them from the set: for those individuals \(k = 1\), and \(P(\text{identify}) = 1\). A feature that names people cannot be anonymous, whatever the rest of the page does.

3

Add the time series. A daily series distinguishes a person who worked at 3 a.m. on one day. If a team's series is distinctive, \(\log_2\) of the number of distinguishable patterns is the extra leakage; with 16 patterns that is 4 more bits, cutting an effective \(k = 500\) to about 31.

4

Apply a threshold rule and test it. Require \(k_{\text{effective}} \ge 20\) after all signals are combined; suppress the named list, bin the series to weekly, and round counts. Then attempt the attack yourself: join two views, compare two days, and see whether the identity falls out. If it does, the threshold was wrong.

5

Remember the two-sided answer. The same reasoning defends the database: log the queries, reject filters that isolate fewer than \(k\) subjects, and treat aggregation as a disclosure decision rather than a reporting convenience. And note the link to the guessing model — \(A^{L}\) says a random secret is expensive to guess, while an anonymity set of size \(k\) says a person is cheap to isolate once the signals add up.

Definitions to write out in full

  • Software security — security as a lifecycle property; prevent before deployment, keep protecting after it
  • Database — a managed system for storing, relating, querying and updating persistent data; more than files
  • SQL injection — malicious input changes the query executed by an application, because user text is interpreted as SQL syntax
  • Inference attack — no access-control bypass; sensitive information is derived from permitted answers
  • IDS — observes host or network activity, alerts, does not automatically stop the attack
  • IPS — observes like an IDS but sits inline and can automatically intervene
