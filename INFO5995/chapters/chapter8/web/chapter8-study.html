What Software Security Is

Week 8 opens with a deliberately broad definition, because the failures in the deck are spread across the whole lifecycle rather than concentrated in any one stage.

The deck's working definition: security is an engineering property across the complete software lifecycle — design, develop, test and maintain software so it resists attack and protects users' data.

Definition — software security

The set of engineering practices that keep a system trustworthy while it is under attack, applied continuously from requirements to maintenance. It has two halves that the deck keeps together: prevent vulnerabilities before deployment, and continue protecting the system after deployment.

The CIA triad from Week 1 becomes concrete once it is applied to software the organisation wrote or assembled itself:

PropertyAt the software layerRepresentative controls
C — ConfidentialityPrevent unauthorised disclosure of the data the system stores, moves or logsAuthentication, authorisation, encryption in transit and at rest, masking, least privilege
I — IntegrityPrevent unauthorised change to data, to configuration and to the code path that processes themConstraints, transactions, input validation, signed artefacts, audit logs
A — AvailabilitySustain dependable access for authorised workloadsReplication, capacity planning, rate limiting, graceful degradation, DoS resistance

The security mindset the deck asks for

  • Assume the input is hostile, the dependency is stale and the default is unsafe.
  • Ask what the system trusts, then ask why it should.
  • Treat security as a property of the process, not a feature to be added late.

Why secure systems still get hacked

The deck's answer is blunt: a software weakness, a configuration issue or a dependency gave the attacker a way in. Many major breaches exploit software vulnerabilities rather than breaking cryptography — so “we use TLS” is not a security answer.

Exam framing: never answer “software security is encryption and penetration testing”. The markable version names the lifecycle scope and the two halves — prevent before deployment, detect and respond after it — and then gives one example of each.
Which statement matches the Week 8 deck's definition of software security?
The practice of encrypting data at rest and in transit so that stolen files are unreadable
An engineering property maintained across the complete lifecycle, before and after deployment
The final penetration test that certifies a release before it ships

Where Vulnerabilities Come From

The deck's central diagram: a vulnerability can be introduced — or removed — at every lifecycle stage, and each stage has a characteristic defect.

StageCharacteristic defectWhat it looks like in the running system
0. RequirementsAbuse case omittedNobody specified how the system must behave when a user lies, replays or escalates, so “undefined” becomes the behaviour
1. DesignTrust boundary missedA component accepts data from a zone it was never meant to trust; privilege sits in the wrong tier
2. ImplementationUnsafe data handlingInput is concatenated into a command, or content is written into a page unencoded
3. TestingAdversarial path skippedTests prove the happy path works; nobody tried to make the system fail in an interesting way
4. DeploymentInsecure defaultA debug endpoint, sample account or permissive rule ships enabled because it was convenient in development
5. MaintenancePatch delayedA known vulnerability stays unpatched while a working exploit is public and scanning for it is automated
The deck's cost argument: “the later a defect is discovered, the more architecture, data and operations may already depend on it.” A missing trust boundary found in design costs a conversation; the same defect found in production costs an incident, a migration and a disclosure.
A service ships with the database vendor's sample administrator account still enabled and reachable from the internet. Which lifecycle defect is this, in the deck's vocabulary?
Unsafe data handling at the implementation stage
Patch delayed at the maintenance stage
Insecure default at the deployment stage

Defence in Depth: Build Time and Run Time

The deck's answer to “but we might miss something” is six layers of controls that work together across the lifecycle. Layered controls stop one missed defect from becoming a successful attack.

LayerWhenStrongest againstBlind to
Secure codingBuildWhole classes of injection, encoding and authorisation mistakesThe mistakes you did not notice making
TestingBuildLogic, specification and integration errors on the paths you thought ofThe paths nobody thought to test
Static analysisBuildTainted data flow, unsafe APIs, known-bad patterns across the whole codebaseConfiguration, runtime state; it also produces false positives that must be triaged
Dynamic analysisBuild / pre-releaseReal behaviour: authorisation gaps, dependency versions, runtime errorsCode paths that the probe never reaches
MonitoringRunKnowing that something happened at all, and reconstructing it afterwardsAttacks that look like ordinary traffic
IDS / IPSRunKnown attack patterns, and inline blocking of themNovel behaviour; false positives that cost availability
The honest caveat about layers: defence in depth only pays off when the layers are genuinely independent. If the same vulnerable library sits in the web tier, the job runner and the report generator, one supply-chain defect defeats three “layers” at once. That is why vulnerability management (later in this page) is a security control and not just housekeeping.
Management asks which layer can tell them that an attack is happening right now, rather than whether the code could be attacked. What is the correct answer?
Secure coding, because well-written code cannot be attacked
Static analysis, because it reads every line of code
Monitoring plus IDS/IPS, the run-time half of the deck's bar

Database Security: Crown-Jewel Data

The lecture's second block moves from software in general to the component that concentrates everything worth stealing.

Definition — database

A managed system for storing, relating, querying and updating persistent data. The deck stresses that a database is more than files: it enforces structure, relationships, transactions, concurrency and controlled access to shared state.

Relational

Tables, rows, columns and constraints. Structure is declared up front and enforced by the engine; queries are expressed in SQL.

PostgreSQL MySQL

Non-relational

Documents, key-value pairs, graphs or wide columns. Structure is often carried by the application, which moves part of the validation burden into code.

MongoDB Redis Neo4j

Security implication from the deck: a compromise affects not only the stored records, but every application and decision that depends on them. The database is where the consequences of a small software defect become population-scale.

👤 Personal data

Identity, contact and behavioural records — the material of identity theft and surveillance.

💳 Financial data

Payments, transactions and account history, which are also regulated.

🔑 Credentials

Passwords, tokens and access secrets — stealing these converts one breach into many.

💡 Intellectual property

Research, source data and commercial knowledge, where the loss cannot be undone by reissuing a card.

Goal at the data layerThe deck's wordingControls
ConfidentialityOnly authorised subjects can view specific dataAuthentication, least privilege, encryption, masking
IntegrityData remains accurate, valid and traceableConstraints, transactions, validation, audit logs
AvailabilityAuthorised workloads can access data when requiredReplication, backup, recovery, capacity and DoS resistance
The objective, in the deck's words: controlled, correct and dependable use of data — not merely keeping attackers outside. A database that nobody can query is not secure; it is unavailable.

SQL Injection: When Data Becomes a Command

The deck's first worked attack. The mechanism is small, the consequences are large, and the fix is structural rather than cosmetic.

Mechanism: malicious input changes the SQL query executed by an application. The attack succeeds when user-controlled text is interpreted as SQL syntax.

Key message from the deck: attackers exploit insecure application code — not the database itself. The database faithfully executes the statement it was given; the application built the wrong statement.
StageWhat happensWhat the system sees
1. Normal inputThe field carries a value: Username: aliceA username that matches one row
2. Malicious inputThe value is written to end the string literal early and append a condition that is always true. The lecture's canonical illustration is the tautology alice' OR '1'='1Still just text in a form field
3. Executed queryThe application concatenates the value into the statement, so the appended text is parsed as SQL rather than as dataA WHERE clause that is true for every row
4. ResultThe query returns records it should not, or authenticates a caller who should not beAuthentication bypass, unauthorised data access

The illustration above is the classic teaching example used in the deck and in the OWASP guidance it cites. It is included to make the mechanism visible; the control that removes the mechanism is parameter binding, covered below.

The structural fix: keep data out of the statement

✕ String concatenation

Input is merged into the command, so the value can change the command's grammar.

"SELECT * FROM users WHERE username='" + username + "'"

The statement is a function of user input. Nothing separates the two.

✓ Prepared statement

The SQL structure is fixed before user data is supplied; the value travels separately and is bound into the placeholder.

cursor.execute( "SELECT * FROM users WHERE username=?", (username,) )

The statement is a constant. Only the parameter varies, and it can never be parsed as SQL.

The four controls the deck pairs with binding

  • Prepared statements — the structural defence; use them everywhere, including in reporting and admin tooling
  • Input validation — constrain what the field may contain (type, range, syntax)
  • Least privilege — limit what the database account can do; a reporting account that cannot modify schema is not a route to mass deletion
  • ORM frameworks — safe query APIs by default, but only when they are used correctly: raw fragments and string-built filters reintroduce the flaw

What is not the fix

  • Escaping quotes by hand — encoding context varies and denylists are famously incomplete
  • Client-side validation alone — the attacker simply does not use your form
  • A web application firewall alone — a useful additional layer, but the code still trusts input as syntax
  • Hiding error messages — it reduces information leakage, not the injection
InputValidation ruleSafe handling
UsernameLetters and numbers onlyReject characters outside the allowlist
AgeInteger from 0 to 120Parse as a number; enforce the range
EmailValid email structureUse a trusted email validator
CommentsText, not executable markupEncode HTML output; sanitise only if HTML is genuinely allowed
Two rules to keep separate in an exam answer. Validation decides what a field may contain; parameter binding decides how the statement is assembled. Only the second removes the injection class, because validation can be bypassed by any path that reaches the query builder — an internal API, a batch job, a support tool. The deck's motto covers both: separate user input from SQL commands, and validate input before processing, encode before output.
A team blocks single quotes and the word OR at the input boundary. Why is this not a fix for SQL injection?
Because input filtering slows down the request path
Because denylists are incomplete and bypassable, while parameter binding makes the statement structure independent of input
Because the fix is instead to hide database error messages from users

Worked example — triaging a suspected injection defect. A user reports that a search field “returns rows that do not match what I typed”. Work the report the way the week's material implies.

1

Find the construction, not the payload. Locate every place the search value reaches the database. The question is not “what did they type?” but “is the statement string a constant?” If the value is concatenated, interpolated or formatted into the SQL text anywhere, the defect is confirmed.

2

Check every route to that code. Injection is fixed per query builder, not per screen. The same helper is usually reachable from the UI, an internal API, a scheduled export and a support console — and the filter that exists on the UI screen does not protect the other three.

3

Fix structurally. Replace the assembled statement with a prepared statement: fixed SQL text, values bound to placeholders. Where dynamic identifiers are genuinely required (a sort column, for example), map them through an allowlist rather than binding them — parameters carry values, never structure.

4

Add the layers the deck lists. Validation on the field, least privilege on the database account (the web tier rarely needs DROP or unrestricted SELECT across schemas), ORM query APIs used correctly, and a regression test that asserts the structure is constant.

5

Assume it was used, then verify. An injection defect that has been reachable is a possible data exposure: review the audit log for unusual query patterns and volumes, check for unexpected schema or account changes, and confirm the fix in the deployed environment rather than only in the branch. Then ask the maintenance question — what dependency scanning or review step would have caught this before release?

Inference Attacks and Privacy Leakage

The second attack family in the deck does not need a vulnerability at all. It needs only queries the system is willing to answer.

Definition — inference attack

An attack in which the adversary does not bypass access control but learns sensitive information indirectly, by combining answers to legitimate queries. The deck classifies it as an indirect database threat, next to SQL injection's direct manipulation of the query.

The deck's minimal example

A permitted query filters on a secret it never returns: a query of the form ... WHERE username = 'alice' AND salary > 100000 produces either a row or no row.

The salary is never disclosed. The existence of a result answers the question anyway.

Why “no result” is still an answer

Each answer carries little information — at most one bit. But a sequence of low-information answers can reveal a high-value secret, because the attacker chooses the questions and keeps the ones that narrow the space.

That is why the mitigation is about what the system is willing to answer, not only about who may ask.

Design consequence: aggregation and filtering are themselves disclosure decisions. If a view can isolate a group small enough to be identified, it is an inference channel even when every field in it is legitimate.

The conference-reviewing case study

The deck's worked example is a peer-review system with three privacy rules in place: reviewers are anonymised, authors must not see discussion of their own submission, and reviewer identities are visible only to co-reviewers of the same paper. The system then publishes a procrastination chart of progress over time — and the privacy breaks anyway.

Leakage channelWhat it revealsControl
Named progress linesIdentity signal: the chart label attaches a person to a behaviourPublish aggregate or binned series only; remove names before rendering
Review counts per paperAssignment clue: how many reviewers a paper had, which narrows who they wereSuppress counts below a threshold, or bucket them coarsely
Distinct progress patternsBehavioural fingerprint: a distinctive curve is recognisable even without a nameBin the time axis, smooth the series, delay release until after decisions
Combination of the threeLinkage attack: match reviewer behaviour to per-paper counts to infer who reviewed whatEvaluate views in combination, not one at a time; apply a minimum anonymity-set size before release
Two sentences to quote: “individually harmless signals become identifying when combined”, and “inference risk grows as the anonymity set becomes smaller.” Both are why the Foundations page treats anonymity as a number: a view over k indistinguishable people supports re-identification at a rate of roughly 1/k.
Which published view is the clearest inference channel, even though it returns no secret value at all?
A count of all submissions in the conference
A yes/no answer to a filtered query that isolates one person
A report in which the sensitive column is masked

Worked answer — auditing an analytics dashboard before release. A team wants to publish a live operations dashboard built from the same tables that hold customer records. Decide what may ship.

1

Enumerate the views, not the tables. Write down every panel, filter and export the dashboard offers, because each one is a query the system is agreeing to answer. A dashboard is an access-control decision expressed as a layout.

2

Ask what each view reveals and to whom. For every panel: does it return a value, a count, an existence answer, or a pattern over time? Existence and timing answers are the ones teams forget, and they are precisely the deck's inference channel.

3

Find the join key. The dangerous step is combining two harmless views: behaviour plus metadata, or a pattern plus a count. If two panels can be joined on a person, a paper, an account or a time window, treat the combination as the release unit.

4

Change the view, not the honesty of the users. Suppress groups below a minimum size, bin or smooth the axes, delay publication until the outcome is fixed, and drop identifiers before rendering. Where a filtered query is the risk, replace it with a pre-aggregated result the requester cannot vary.

5

Write the release rule and test it adversarially. State the threshold (“no published view may isolate fewer than k subjects”), then try to break it as an insider would: vary the filters, combine the panels, compare two snapshots taken at different times. Log the queries so that anomalous enumeration is detectable after the fact.

Cross-Site Scripting: Content Becomes Code

XSS is injection with the browser as the interpreter, and the asset being stolen is the user's trust in a site they have every reason to trust.

Mechanism: the vulnerable site delivers attacker-controlled JavaScript to a trusted user's browser. The browser trusts the website, not the attacker — so if the website serves malicious code, the browser executes it anyway.

One input, two outcomes

The same comment field can display text or execute code, depending only on how the output is handled. If output is not encoded, data becomes code.

Content the field might hold — here the deck's harmless illustration:

<script>alert("INFO5995")</script>

Where the content comes from

  • Stored — the site saves the content and serves it to other users later
  • Reflected — the site copies the content from the request straight into the response
  • Client-side — the page's own script writes untrusted data into the document (the unsafe-DOM case the deck warns about)
Why XSS is dangerousWhat the attacker gets
Session theftSteal tokens or impersonate the user without ever learning their password
Unauthorised actionsSubmit requests as the victim, with the victim's permissions and audit trail
PhishingReplace trusted content with a deceptive interface inside the real site's origin
Data exfiltrationRead the page data the victim can see and transmit it elsewhere
The deck's framing to remember: XSS does not “hack the browser”. It abuses the browser's trust in a vulnerable application — code executes in the security context of the trusted website.

Preventing XSS: four layers

#ControlWhat it does
1Encode outputConvert <, >, &, quotes and other characters to safe equivalents at the point of output, in the right context (HTML body, attribute, URL, script)
2Sanitise allowed HTMLWhen rich text is genuinely required, run it through a proven sanitiser with a strict allowlist — never a hand-written filter
3Use safe frameworksPrefer auto-escaping templates and avoid unsafe DOM APIs that write strings as markup
4Add browser safeguardsContent Security Policy as an additional layer, so an injected script that slips through has nowhere to load from
The motto that covers SQL injection and XSS at once: validate input, encode output, keep data separate from code. Input validation is the same control in both cases; what changes is the interpreter whose grammar you must not let the data reach.
Which control actually stops stored XSS from executing in a victim's browser?
Rejecting any input containing the word “script”
Contextual output encoding through an auto-escaping template
Shortening session lifetimes to a few minutes

System Security: Hardening the Deployed System

The lecture's second half changes the subject from building securely to running securely. Deployment changes the problem: the system is now reachable, observable and continuously attacked.

Software securitySystem security
FocusBuild secure softwareProtect deployed systems
ObjectivePrevent vulnerabilitiesDetect and respond to attacks
WhenDevelopment and testingOperation and maintenance
ExamplesSQL injection, XSSIDS, IPS
The deck's split, drawn as a timeline. Everything left of the deployment boundary reduces the chance that a weakness exists; everything to the right reduces the time a weakness stays useful to an attacker.

The five threat classes the deck names

ThreatDeck's descriptionControls that change the odds
Brute forceRepeated login attempts against the same accountsRate limiting, lockout with backoff, MFA, breached-credential checks, detection of distributed attempts
MalwareMalicious code and ransomwarePatch management, least privilege, application control, endpoint detection, offline and tested backups
ScanningDiscovery of exposed servicesMinimise the attack surface, close unused ports and paths, segment networks, remove version banners
Denial of serviceResource exhaustionCapacity and quotas, upstream filtering, rate limits, graceful degradation, timeouts on expensive operations
Insider misuseAbuse of legitimate accessLeast privilege, separation of duties, just-in-time access, audit logging, review of privileged activity

Hardening a deployed system

  • Secure defaults and baselines — the deployment-stage defect from earlier in the week
  • Remove what is not needed — services, accounts, sample data, debug endpoints
  • Least privilege — for people, services and the database accounts behind them
  • Segmentation and egress control — so a single foothold is not a network position
  • Centralised logging with retention — without it, detection and response have no raw material
  • MFA on every administrative path — including the ones that “are only internal”

Vulnerability management as a control

  • Identify — inventory components (a software bill of materials), scan hosts and images, watch advisories
  • Prioritise — combine severity with internet exposure, exploit availability and asset value
  • Remediate — patch, upgrade, or apply a documented compensating control when patching is impossible
  • Verify — rescan and regression-test; a closed ticket is not evidence
  • Report — track exposure window and mean time to remediate, not ticket counts
Why this is examinable: Equifax was an unpatched component and Log4Shell was a vulnerable library. Neither was a clever attack on cryptography; both were failures of the maintenance and dependency processes described here. The Foundations page makes the exposure window a number you can compute.

Detection and Response: IDS and IPS

The deck's closing block: two technologies that inspect the same activity and differ only in what they are allowed to do about it.

IDS — Intrusion Detection System

Observes host or network activity and alerts on suspicious behaviour. It sits on a monitoring path rather than in the traffic flow, and it does not automatically stop the attack. Think security camera: it sees the intruder and raises the alarm.

IPS — Intrusion Prevention System

Observes traffic like an IDS but sits inline and can automatically intervene: inspect → decide → act. It can block malicious traffic, drop suspicious packets, reset connections and quarantine hosts. Think security guard: it sees the intruder and blocks the door.

FeatureIDSIPS
PurposeDetect attacksDetect and block
ActionGenerate alertsAutomatically intervene
DeploymentMonitoring pathInline with traffic
ResponsePassiveActive
Failure modeAn attack proceeds while the team reads the alertA false positive becomes an outage, because the control is in the path

Where it watches

  • HIDS — one computer or server: process, file, log and account activity
  • NIDS — traffic across a network segment: connections, protocols and payloads

Common tools named in the deck: Snort Suricata Zeek

How it detects

  • Signature-based — matches known attack patterns. Precise and explainable, but blind to anything not yet written down
  • Anomaly-based — flags deviation from normal behaviour. Can catch novel activity, at the cost of far more false positives

Every deployment is a trade-off between the two, tuned against the base rate of real attacks on that network.

The deck's discussion question, answered: would an IDS alone stop a brute-force login attack? No. An IDS is passive by design — it detects failures and alerts the team while the thousands of attempts continue. Stopping it needs an active control: an inline IPS, rate limiting and lockout on the authentication path, or MFA so that a correct guess is not sufficient. The IDS still earns its place, because it is what tells you the prevention layers are being tested.
An IDS reports 2,000 failed logins from 300 source addresses and the attack is still succeeding. What is the correct conclusion?
The IDS is misconfigured, because it should have blocked the sources
Detection worked and prevention was missing: an IDS is passive, so blocking requires an inline IPS or controls on the login path
Signature databases cannot detect brute force, so nothing could have been done

Worked scenario — designing the control set for a public login endpoint. The endpoint is internet-facing, serves customers in many countries, and is the only way into the account area. Lay out prevention, detection and response the way the week's material frames them.

1

Classify the threat. Repeated login attempts are brute force; attempts against many accounts with previously breached passwords are credential stuffing. The distinction matters because credential stuffing defeats complexity rules and per-account lockout, and shows up as a low failure rate per account spread over many accounts.

2

Prevention first (build time). Rate limiting per account, per source and per subnet; lockout with exponential backoff rather than a permanent lock that becomes its own denial of service; MFA so a correct password is not sufficient; checks against known-breached credential lists; generic error messages so the response does not confirm which usernames exist.

3

Detection second (run time). Alert on the patterns that separate an attack from forgetfulness: failure rate per account, distinct accounts per source, source diversity for one account, success immediately after a burst of failures, and authentication from an implausible location. Feed the web tier, the identity provider and the network sensor into the same timeline.

4

Response, decided in advance. An IPS or edge control can drop or throttle the sources and reset connections automatically; the identity provider can force a credential reset for accounts that show a successful login after a burst; the incident process preserves logs and notifies the account holders. Decide these actions before the incident, because an inline control that no one has tuned will eventually block a legitimate customer.

5

Measure what the control set actually buys. Track detection coverage, false-positive rate, alert volume against analyst capacity, time from first attempt to block, and the fraction of accounts protected by MFA. The deck's guiding question applies: where should we place the next control to reduce risk most effectively? With MFA coverage at 40%, enrolment usually beats another detection rule.
