Where Week 3 Left Off

Week 4 opens with a recap of everything digital, because the analogue half of the unit is built on top of it. Nothing here is new; it is the vocabulary the rest of the lecture assumes.

The recap in one line

A microcontroller is a complete small computer on one chip — CPU, memory and input/output peripherals — that runs one program forever in setup() (once) and loop() (repeatedly). Its pins are digital: each one is either near 0 V (LOW) or near the supply voltage (HIGH).

The two refactors the deck performs on the traffic light. First, structure: the timing constants and the pin numbers move to the top, and each phase becomes a function, so loop() reads as a sequence of intentions. Second, and this is the part that matters, the waiting has to go — the deck links straight to the Arduino reference page for delay() and asks what the problem is.

Everything in this week is one of two conversions. On the way in, a physical quantity is turned into a voltage and then into an integer (analogue input). On the way out, an integer is turned into an average voltage or a brightness (analogue output). Every sensor and actuator in the unit is a variation on those two paths.

Non-Blocking Timing: the Problem with delay()

The traffic light works, and it is still wrong. delay() does nothing but wait, and while it waits the microcontroller is not reading anything or doing anything else.

const int RED = 8, YELLOW = 9, GREEN = 10; const int BUTTON = 2; void loop() { digitalWrite(RED, HIGH); delay(2000); // loop() is frozen inside this call digitalWrite(RED, LOW); digitalWrite(YELLOW, HIGH); delay(1000); digitalWrite(YELLOW, LOW); digitalWrite(GREEN, HIGH); delay(2000); digitalWrite(GREEN, LOW); }

What delay() actually costs

  • Inputs are not read: a pedestrian pressing the button during the 2 s red phase is invisible, and the press is lost.
  • Nothing else can run: a second output, a sensor, an incoming serial message all wait.
  • The real period is longer than the sum of the delays, because the work between them takes time too. Timed this way, the light slowly drifts.

The pattern that replaces it

  • Store the moment the last event happened, not the time until the next one.
  • Ask millis() every pass: has enough time elapsed yet?
  • When it has, do the work, then re-arm the timestamp. The rest of loop() runs thousands of times a second in between.
const unsigned long PHASE_MS = 2000; unsigned long phaseStart = 0; // when the current phase began int phase = 0; void loop() { unsigned long now = millis(); if (now - phaseStart >= PHASE_MS) { // time to move on? phaseStart = now; // re-arm: schedule, never wait phase = (phase + 1) % 3; applyPhase(phase); } if (digitalRead(BUTTON) == LOW) { // still runs during the 2 s phase requestCrossing(); } }
Subtract, do not compare absolutely. Write now - phaseStart >= PHASE_MS rather than now >= phaseStart + PHASE_MS. millis() returns an unsigned long that wraps back to zero after about 49.7 days, and only the subtraction form survives the wrap-around.
A sketch waits for a 2 s green phase with delay(2000). A pedestrian presses the button 0.4 s into that phase. What happens?
The press is stored in a buffer and handled after the delay finishes
The press is lost, because the pin is not read until the delay returns
The processor wakes on the pin change and handles the press immediately

Worked example — a three-phase traffic light that never blocks. Red 2 s, yellow 1 s, green 2 s, with a button that must be noticed at any moment.

1

Turn the timeline into a table. The phases are (red, 2000), (yellow, 1000), (green, 2000). Give each phase a duration rather than a delay, because the duration is now data the loop consults.

2

Record a start time, not a countdown. phaseStart = millis() when a phase begins. The elapsed time is then millis() - phaseStart, which is always correct even if the loop is busy for a few milliseconds.

3

Test the elapsed time once per pass. if (millis() - phaseStart >= durations[phase]) — when it is true, advance phase, call the function that sets the three LEDs, and re-arm phaseStart.

4

Put everything else after that test. Reading the button, updating a display or sending a serial line now happens on every pass of loop(), so the response time is set by how long one pass takes — microseconds — instead of by the phase length.

5

Say why it is better in one sentence. The blocking version couples the program's responsiveness to its timing; the millis() version makes time a value that is checked rather than a period that is waited out, which is what lets one loop() serve several independent behaviours at once.

Debouncing: Counting Presses Reliably

The deck counts button presses and reports what actually happens: it fails. Switches are mechanical components, and they bounce.

Contact bounce

When the metal contacts of a switch meet, they collide and rebound several times before settling. Instead of one clean transition the pin produces a burst of HIGH/LOW edges lasting roughly 0.5–10 ms. A program that counts edges therefore counts one physical press as three or four — the deck's “4× presses” versus the one press the user made. Bounce happens on release as well as on press.

const int BUTTON = 2; const unsigned long DEBOUNCE_MS = 20; int stableState = HIGH; // last level we accepted as real int lastRaw = HIGH; // last level we actually saw unsigned long lastChange = 0; // when the raw level last moved int pressCount = 0; void loop() { int raw = digitalRead(BUTTON); // 1. sample every pass if (raw != lastRaw) { // 2. it moved lastChange = millis(); // 3. restart the timer lastRaw = raw; } if (millis() - lastChange >= DEBOUNCE_MS && raw != stableState) { stableState = raw; // 4. it survived: accept it if (stableState == LOW) pressCount++; // 5. act on the accepted edge } }
ApproachHow it worksCost
Hardware RC filterA resistor and capacitor smooth the pin, usually followed by a Schmitt trigger to restore clean edgesExtra components, and the time constant is fixed once soldered

Same pattern as the traffic light. Debouncing is a timing problem, so it is solved with millis(), not with delay(). The deck's takeaway is exactly this pairing: use millis() for non-blocking programs, and implement software debouncing for reliable button input.

Digital and Analogue: a Discrete Machine in a Continuous World

The lecture's headline for the second half of the unit is blunt: Arduinos are digital only. Everything analogue they appear to do is an approximation built out of discrete steps.

The world is continuous

Light, temperature, force, bend and position vary smoothly. Between any two values there is another value: a voltage can be 2.5001 V as easily as 2.5 V. Signals like these are analogue.

The microcontroller is discrete

It stores finite patterns of bits and does one thing per clock edge. It can represent 1024 input levels, or 256 output levels — not infinitely many. Every analogue quantity it touches is therefore an approximation.

Four terms worth having exactly right

Transducer — a device that converts one form of energy into another. Sensor — an input transducer: light, force or heat in, an electrical property out. Actuator — an output transducer: electrical energy out, light, sound, motion or heat in the world. Sampling is measuring a continuous signal at discrete moments in time; quantisation is rounding each measurement to the nearest of a finite set of levels. Digitising is both at once.

analogRead(): the ADC and Its Resolution

On the input side the microcontroller does have real analogue hardware: a multiplexer and a 10-bit successive-approximation ADC behind the six pins labelled A0 to A5.

10 bits 1024 codes 0–1023 VREF = 5 V by default 1 step ≈ 4.9 mV ~100 µs per reading

The two questions the deck asks about a potentiometer

The slide shows a potentiometer wired across 5 V and GND at the “100 %” position and asks: what is the highest voltage possible on the potentiometer? and what is the highest value read by the Arduino?

Answers: the wiper can never exceed the supply it is connected to, so the highest voltage is 5 V; the highest number analogRead() returns is 1023, because that is the largest value ten bits can hold. Turned fully the other way, the wiper sits at 0 V and the reading is 0.

Resolution is not accuracy. Ten bits describe how finely the converter reports a voltage. What it actually gets right depends on the stability of the reference, the noise on the ground and supply, the source impedance of the sensor, and the non-linearity of the converter itself. A stable 10-bit reading beats a noisy 16-bit one, which is why the next two sections are about conditioning and calibration rather than about buying a better ADC.
A 10-bit ADC with VREF = 5 V reads a sensor and returns 512. Roughly what voltage is on the pin?

Worked example — from a potentiometer to a percentage, on paper. A 10 kΩ linear potentiometer is wired with its ends on 5 V and GND and its wiper on A0. analogRead(A0) returns 743.

1

Voltage. One code is \(V_{REF}/2^{10} = 5/1024 \approx 4.883\) mV. So \(V = 743 \times 4.883\ \text{mV} \approx 3.63\) V.

2

Position. A potentiometer is a divider, so the fraction of the track from the GND end is \(743/1023 \approx 72.6\) %. If the knob has 300° of travel, that is about 218° from the anticlockwise stop.

3

Error bar. One code is 4.883 mV, so the reading is only meaningful to about ±0.1 % of the track. Averaging 16 readings would cut random noise by roughly a factor of 4, but it cannot fix a quantisation step that is already there.

4

The code. int raw = analogRead(A0); then float volts = raw * (5.0 / 1023.0); and int percent = map(raw, 0, 1023, 0, 100);. Print all three to the serial monitor and turn the knob: if the numbers move smoothly and reach both ends, the wiring and the arithmetic are both right.

5

Why 1023 in the sketch and 1024 in the arithmetic? map() treats 1023 as the end of the range, so it interpolates over 1023 gaps and reports a tidy 100 %. The ideal quantiser has 1024 steps of \(V_{REF}/1024\). The two differ by 0.1 % — below the noise floor — but you should be able to say which one you used and why.

analogWrite() and PWM: Faking an Analogue Output

The light bulb can only be on or off. The deck's question is how to dim it to 50 % — and the answer is not a voltage at all, but a duty cycle.

PWM — pulse width modulation

Switch a digital output on and off rapidly, fast enough that the load cannot follow, and vary the fraction of each period spent on. That fraction is the duty cycle \(D = t_{on}/T\), and the average voltage the load sees is \(V_{avg} = D \times V_{CC}\). At 50 % duty on a 5 V pin the average is 2.5 V, and an LED looks half as bright.

Two traps with analogWrite(). First, it only works on the PWM pins; on any other pin the Arduino core falls back to a plain digital write, so a value of 128 or more simply switches it HIGH. Second, PWM is a square wave: a piezo speaker or a motor will buzz at the PWM frequency, and a sensor measuring the same supply rail will see the ripple. If you need a steady voltage, follow the PWM pin with a resistor and capacitor whose cutoff is far below the PWM frequency.

Voltage Dividers: Turning Resistance into a Reading

The ADC measures a voltage, but most cheap analogue sensors change their resistance. The voltage divider is the two-resistor circuit that bridges the two.

The divider relation

Two resistors in series across a supply, with the output taken from the junction:

\[ V_{out} \;=\; V_{in} \cdot \frac{R_2}{R_1 + R_2} \]

where \(R_2\) is the resistor between the output node and ground. The same current flows through both, so the voltage splits in proportion to the resistances. A potentiometer is simply a divider with a moving junction: the wiper cuts the track into \(R_{top}\) and \(R_{bottom}\), and the output is \(V_{in} \cdot R_{bottom}/(R_{top}+R_{bottom})\).

Sensor as the top resistor

With the sensor between 5 V and the output, and a fixed resistor to ground, \(V_{out}\) falls as the sensor's resistance rises. Solve for the sensor: \(R_{s} = R_{fixed}(V_{in}-V_{out})/V_{out}\).

Sensor as the bottom resistor

With the fixed resistor on top, \(V_{out}\) rises with the sensor's resistance: \(R_{s} = R_{fixed} \cdot V_{out}/(V_{in}-V_{out})\). This is the more common arrangement for light and force sensors, because a shorted sensor then reads 0 V rather than 5 V.

SensorElectrical changeWhy a divider is needed
Potentiometer (10 kΩ)Resistance from wiper to each endIt is a divider; wire the ends to 5 V and GND and the wiper straight to A0
Photoresistor (LDR)Resistance falls from megohms in the dark to hundreds of ohms in bright lightThe swing is enormous, so pick the fixed resistor near the geometric mean of the two extremes to keep the mid-range readable
ThermistorResistance changes with temperature, strongly non-linearlyA divider makes it readable; the curve still has to be linearised in software
Force-sensing resistorResistance falls as force risesDivider first, then calibration — the response is roughly proportional to conductance, not resistance
Flex sensorResistance rises as the strip bendsA divider plus a fixed resistor of the same order as the flat resistance
Accelerometer, gyroscope, magnetometer modulesOutput a voltage (or digits) directlyNo divider — but the analogue versions are ratiometric, so the reference and the sensor supply should be the same rail
Choosing the fixed resistor. The divider converts a resistance range into a voltage range, and only part of that voltage range is useful. Pick \(R_{fixed}\) close to the sensor's resistance at the middle of the range you care about: that centres the output near 2.5 V and gives the largest swing for the ADC to resolve. A divider also draws current continuously, so a small resistance gives a stiffer, less noise-prone signal at the cost of battery life — and a resistance that is too large interacts badly with the ADC's own input impedance.

Exam nuance. The deck lists accelerometers, gyroscopes and magnetometers under analogue sensors because the sensing element is analogue, and breakout boards do exist with analogue outputs. In practice most of the modules you buy put the same element on a chip with an I²C or SPI interface, so the microcontroller reads digits rather than a voltage. Say both: the quantity is analogue, the interface may well be digital, and what that changes is where the quantisation happens.

Calibration and the Serial Monitor

A raw count of 743 means nothing on its own. Calibration is the step that gives it a unit — and the serial monitor is the instrument you calibrate with.

Calibration

Establishing the relationship between what the sensor reports and what is actually there, by measuring the sensor's output at known reference points. Two points are enough for a linear sensor: record the count at the minimum and at the maximum, then map everything in between. Without it you have a number that responds to the world but does not describe it.

Two-point (linear) calibration

With two known references, a raw reading \(r\) becomes a physical value \(x\):

\[ x \;=\; x_{1} + (r - r_{1})\cdot\frac{x_{2}-x_{1}}{r_{2}-r_{1}} \]

which is exactly what map(value, fromLow, fromHigh, toLow, toHigh) computes in integer arithmetic: map(raw, rawMin, rawMax, 0, 180) turns a flex sensor's observed range into degrees.

const int FLEX = A0; int rawMin = 1023, rawMax = 0; // observed extremes, seeded the wrong way round void loop() { int raw = analogRead(FLEX); if (raw < rawMin) rawMin = raw; // auto-calibrate while the user exercises it if (raw > rawMax) rawMax = raw; int angle = map(raw, rawMin, rawMax, 0, 180); angle = constrain(angle, 0, 180); // map() happily returns nonsense if raw is outside Serial.print(raw); Serial.print('\t'); Serial.print(rawMin); Serial.print('\t'); Serial.print(rawMax); Serial.print('\t'); Serial.println(angle); delay(50); }

What the serial monitor gives you

  • Serial.begin(9600) in setup(), then Serial.print() and Serial.println() in the loop.
  • The baud rate must match the monitor's; the classic symptom of a mismatch is a wall of garbage characters.
  • The Serial Plotter draws the same numbers as a graph, which is how you spot drift, spikes and the exact moment a sensor saturates.

What it costs

  • Printing is slow: a few lines per pass can stretch loop() from microseconds to milliseconds. Gate the printing with the millis() pattern.
  • Pins 0 and 1 are the UART, so they must stay free while the monitor is open.
  • Print with a fixed number of decimals (Serial.print(v, 2)) or the default formatting will hide small changes.

Worked example — calibrating a force sensor and reporting it. The sensor is an FSR in a divider with a 10 kΩ resistor to ground: 5 V → FSR → A0 → 10 kΩ → GND. With no load the reading is 8; pressing hard by hand it reaches 890. A 1 kg mass gives 640.

1

Establish the extremes. Record the resting value and the largest value you can reach, over several seconds of use, rather than trusting a single sample: here 8 and 890. These two numbers are the calibration.

2

Turn them into a percentage. map(raw, 8, 890, 0, 100), wrapped in constrain() so that a reading below 8 reports 0 rather than a negative number.

3

Anchor one physical point. The 1 kg mass gives 640, so 640 counts corresponds to a known force. Report in a unit you can defend: percent of the sensor's own range is honest; grams would need a proper calibration rig at several masses.

4

Tame the noise. Take 8 readings in a tight loop and average them before mapping. Averaging \(N\) independent readings reduces random noise by about \(\sqrt{N}\), so 8 readings is roughly a factor of 3.

5

Watch it on the serial monitor. Print the raw value, the running minimum, the running maximum and the mapped result on one tab-separated line. Turn on the Serial Plotter: the moment the raw trace flattens at 1023, the divider is saturated and no amount of software will recover the lost range.

Week 4 Recap

The deck closes with five takeaways. Everything on this page is one of them.

Write modular Arduino code

Pin numbers and timing constants at the top, one function per behaviour, and a loop() that reads as a list of intentions.

Structure

Time with millis(), not delay()

Store when something happened and test the elapsed time each pass, so inputs are read and outputs updated thousands of times a second.

Timing

Debounce every mechanical input

Contacts bounce for up to about 10 ms. Accept a new level only after it has been stable for a chosen interval.

Input quality

Control intensity with PWM

Arduinos are digital only: brightness and speed come from a duty cycle on the ~ pins, not from a variable voltage.

Output

Read and calibrate analogue sensors

analogRead() gives 0–1023 against the reference; a divider brings resistive sensors into range, and two known points give the value a unit.
