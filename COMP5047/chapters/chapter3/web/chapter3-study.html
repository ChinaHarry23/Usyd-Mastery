Digital Signals: Everything Reduces to Two States

The whole week rests on one decision: treat a voltage as a number or as a state. Digital I/O takes the second option and never looks back.

Definition

A digital signal is a voltage that the hardware interprets as one of exactly two discrete states. On a 5 V board the pin is either HIGH (close to the supply voltage) or LOW (close to ground). A digital pin therefore carries one bit of information at a time, not a measurement.

Note what the animation does not claim. The physical voltage is still continuous — electrons do not move in steps. What makes the signal digital is the threshold band the receiver applies: anything comfortably above the upper threshold is read as HIGH, anything comfortably below the lower threshold is read as LOW, and the region between them is deliberately treated as undefined.

LevelWhat the pin is doingTypical value on a 5 V ATmega328P board
Output HIGHThe pin actively sources current towards the supply rail≥ 4.2 V (5 V nominal)
Input HIGHThe receiver reads a logic 1≥ 3.0 V (≈ 0.6 × VCC)
Input LOWThe receiver reads a logic 0≤ 1.5 V (≈ 0.3 × VCC)
Output LOWThe pin actively sinks current towards ground≤ 0.9 V (0 V nominal)
Datasheet note: the deck's reminder that every electronic part has a datasheet is exactly why the numbers above exist. The gap between 1.5 V and 3.0 V is the noise margin. A small amount of electrical noise on a wire cannot flip a digital reading unless it is larger than that gap — which is why digital signalling is used for anything that has to travel across a breadboard full of jumper wires.

setup() runs once, loop() runs forever

An Arduino sketch has no main(). The framework supplies one, and it looks like this in the deck's slides:

setup(); while (true) { loop(); }

Everything you write lives inside those two functions, and the division of labour is strict: setup() configures the board and runs exactly once after every reset; loop() is called again and again for as long as the board has power.

GPIO Pins and the Digital I/O API

A microcontroller pin is not a fixed-purpose component like a resistor. Software decides what it does, which is exactly what “general purpose” means.

Definition

GPIO — general-purpose input/output — describes a pin whose direction and behaviour are chosen by the program rather than fixed by the circuit. Before a GPIO pin will behave predictably you must tell it which direction it faces, using pinMode().

pinMode() modeWhat the pin becomesWhen you use it
OUTPUTA driver: digitalWrite() connects the pin to 5 V or to 0 VAnything you want to switch: LEDs, buzzers, relays, motor drivers
INPUTA high-impedance sensor of voltageReading a signal that something else already drives — another board, a sensor with a digital output
INPUT_PULLUPAn input with a resistor to 5 V switched on inside the chip, so the idle state is HIGHEvery plain push button. It removes the need for an external resistor and stops the pin from floating

The deck's four-quadrant slide is the map of the whole I/O API. Learn the quadrant, and you know which function to reach for before you know its arguments.

DigitalAnalogue
InputdigitalRead(pin) → returns HIGH or LOWanalogRead(pin) → returns a number on the ADC's scale Week 4
OutputdigitalWrite(pin, value) → drives the pin to HIGH or LOWanalogWrite(pin, value) → actually PWM on a digital pin Week 4

HIGH : LOW); }
Two facts about pins that are easy to lose marks on. First, a GPIO pin is a logic device, not a power supply: it can source or sink a small current (tens of milliamps at most) and nothing more. Second, the pin number in your code is the number printed on the header, not the physical position of the socket — pin 13 is the same pin whether the board is an Uno or a clone.

Voltage, Current and Ohm's Law

Current only flows in a closed loop, and the loop has three quantities you can name. This is the physics the rest of the unit assumes.

The three quantities

Voltage (V, volts) is the electrical potential difference that pushes charge around the circuit — the deck's pump analogy. Current (I, amperes) is the rate at which charge actually flows. Resistance (R, ohms) is how strongly a component opposes that flow.

Ohm's law

\[ V = R \times I \qquad\Longleftrightarrow\qquad I = \frac{V}{R} \qquad\Longleftrightarrow\qquad R = \frac{V}{I} \]

The law is a relationship, not a recipe: fix any two of the three quantities and the third is determined. Every calculation in this chapter is one rearrangement of it.

A series circuit: the pin sources current, the resistor limits it, the LED converts some of it into light, and the current returns to ground. There is exactly one path, so the same current flows through every part.

Two principles from the deck govern everything you will wire this semester:

1. Current takes every available path

When the circuit branches, current flows through every branch, and it divides between them in inverse proportion to their resistance. The lower-resistance branch carries the larger share. A path with almost no resistance carries almost all of it.

2. All the energy must be used

The supply voltage is shared out across the components in the loop. Each component “drops” a portion of it, and the drops must add back up to the supply. If a component cannot drop its share, no current flows at all.

Short circuit. Substitute R ≈ 0 into Ohm's law and the current is unbounded: I = 1.5 V / 0 Ω → ∞. In a real circuit the current is limited only by the internal resistance of the battery and the wires, which is enough to melt tracks, destroy components and start fires. This is why a wire straight from 5 V to GND is never acceptable, and why the button wiring later in this chapter needs a resistor in the loop.

Driving an LED Without Destroying It

An LED is the simplest actuator in the kit and the easiest to kill. Two numbers from its datasheet decide the whole circuit.

Key LED facts

An LED is a diode: current flows through it in one direction only, from the anode (the longer leg) to the cathode (the shorter leg, and the flat side of the package). It has a forward voltage drop Vf — about 1.8–2.2 V for a red LED, closer to 3.0 V for blue and white — and it has no meaningful internal resistance, so it cannot limit its own current.

Why a resistor is mandatory. The LED fixes the voltage across itself at Vf. The rest of the supply voltage must appear across something, and if there is nothing else in the loop, the current is limited only by the wiring — effectively a short circuit through a diode. The series resistor is that “something else”.

Sizing the series resistor

The supply is shared: Vsupply = VR + Vf, so the resistor must drop VR = Vsupply − Vf. Choose the current you want, then apply Ohm's law:

\[ R = \frac{V_{supply} - V_f}{I} \]

The deck works this through with real numbers. Take a 3 V supply and a red LED that drops 2–2.4 V. The resistor sees VR = 0.8 V, and with R = 220 Ω the current is I = 0.8 / 220 = 3.6 mA — a sensible, visible current. Now try the same LED on a 1.5 V cell: the supply never reaches the LED's forward voltage, so no current flows and the LED stays dark. Voltage, not current, decides whether the diode conducts at all.

“What if we take out the resistor?” The deck asks this about a 1.5 V cell and a 220 Ω resistor, and the answer is the same at every voltage: with R out of the loop, the only limit on the current is the internal resistance of the source and the wires. The LED's forward current rating (commonly 20 mA continuous) is exceeded immediately, and the part fails — often with a visible pop.

Worked example — moving the same LED to a 3.3 V board. You have a red LED with Vf = 2.0 V and you want 8 mA through it on an ESP32 running at 3.3 V.

1

Find the voltage the resistor must drop. VR = Vsupply − Vf = 3.3 − 2.0 = 1.3 V. Everything else in the loop already has its share accounted for.

2

Apply Ohm's law. R = VR / I = 1.3 / 0.008 = 162.5 Ω. Watch the units: 8 mA is 0.008 A, not 8.

3

Round to a real resistor. Standard values near 162.5 Ω are 150 Ω and 180 Ω. Pick the larger one, 180 Ω, because rounding down increases the current. Check it: I = 1.3 / 180 = 7.2 mA — slightly dimmer than requested, and safely inside the LED's rating.

4

Sanity-check the other end. With no resistor, I is limited only by the source; with a 100 Ω resistor, I = 13 mA, which is still fine for the LED but is a large ask of a 3.3 V logic pin. The resistor protects the pin as much as the LED.

You replace a 330 Ω series resistor with a 100 Ω one on the same 5 V circuit. What happens?

The LED gets brighter and the pin is now sourcing about 30 mA, which is too much for continuous operation
The LED gets dimmer because the resistor drops more voltage

Breadboards and the First Circuit

A breadboard is not a random grid of holes. It is a wiring pattern that has been moulded into plastic, and knowing the pattern is the difference between a working circuit and twenty minutes of confusion.

The deck's note — “internally connected in this direction” — refers to the columns. Five holes in a column are one electrical node; the two power rails are two more nodes that run the whole length of the board.

BoardHow it connectsRole in prototyping
BreadboardSpring clips, no solderingThe default for trying a circuit. Reusable, and the only one that survives being wrong.
PerfboardComponent legs soldered to individual plated holesA semi-permanent version of the same layout once the circuit works
StripboardSoldered to long parallel copper strips that you cut to breakCompact, and closer to a real product than perfboard
PCBCustom copper traces, etched or orderedThe finished article. No flexibility left, which is why you only commit after the breadboard works.
Placing a series component. A resistor whose legs go into A10 and A15 sits across two different columns, so its two ends are in two different nodes — which is exactly what a series part needs. Put both legs in the same column (A10 and C10) and you have shorted the component out instead: the current simply bypasses it.

Reading a Button: Switches, Floating Pins and Pull-ups

A switch is the simplest sensor there is — and the one that produces the most confusing bugs, because an open switch is not a logic level at all.

Switch family from the deckHow it behavesTypical use
Slide / toggle / rockerMaintains its position; stays on or off after you let goPower and mode selection
Push button (momentary)Closes the circuit only while heldThe default input for a prototype
Tilt switchA ball bridges two contacts when the part is oriented a certain wayOrientation sensing, simple motion triggers
Reed switchContacts close in the presence of a magnetic fieldDoor and lid detection, non-contact triggering
Multi-way switchSelects one of several pathsMode dials with more than two positions
The problem with a bare switch. As the deck puts it, our switch can only open or close a circuit. When the button is not pressed, nothing at all is connected to the input pin — the pin is floating and will read whatever electrical noise the room happens to be carrying. And if you wire the switch straight from the pin to 5 V with no resistor, then pressing it drives the pin to 5 V but the moment any other path to ground exists you have created a short circuit.

The fix is a resistor that holds the pin at a known level whenever the switch is open. There are two ways to place it, and they give opposite logic.

Pull-down: idle LOW

A resistor (typically 10 kΩ) from the pin to GND, plus a switch from the pin to 5 V. With the switch open the resistor holds the pin at 0 V, so digitalRead() returns LOW. Pressing the button overrides it and the pin goes HIGH.

Reading: pressed = HIGH. Nothing is inverted, and the resistor is harmless because it only carries current while the button is held.

Pull-up: idle HIGH

A resistor from the pin to 5 V, plus a switch from the pin to GND. With the switch open the pin sits at 5 V, so the reading is HIGH. Pressing the button drags the pin down to 0 V.

Reading: pressed = LOW. This is active-low, and it is why the deck says “we must invert the behaviour”.

Both circuits solve the floating-pin problem; they differ only in which rail the resistor pulls towards. The pull-up version is the one the Arduino can build internally with INPUT_PULLUP.

void setup() { pinMode(BUTTON_PIN, INPUT_PULLUP); // internal pull-up: idle HIGH } void loop() { // Active-low: the pin is dragged to GND when the button is pressed, // so LOW means "pressed" and the logic has to be inverted. bool pressed = (digitalRead(BUTTON_PIN) == LOW); digitalWrite(LED_PIN, pressed ? HIGH : LOW); }
Why the internal pull-up is preferred in this unit. The deck notes that Arduino has built-in pull-up resistors. Enabling one costs a line of code and no components, and it keeps the button's other leg on GND rather than on 5 V — which means a stray short to ground through a mistaken jumper is far less dangerous than a stray short from 5 V. The price is the inverted logic, which every sketch must then handle explicitly.

Worked example — diagnosing a button that “presses itself”. A student reports that the LED flickers constantly and sometimes toggles when nobody is near the board. The sketch reads pin 2 with pinMode(2, INPUT) and the button is wired between pin 2 and 5 V.

1

Name the symptom precisely. Random readings from a digital input almost always mean the pin is never held at a defined level. This is the floating-input case, not a broken button.

2

Trace the two states. Button pressed: the pin is connected to 5 V and reads HIGH, but nothing limits the current, so any accidental path to ground is a short. Button released: the pin is connected to nothing and floats.

3

Choose the fix. Re-wire the button between pin 2 and GND and change the sketch to pinMode(2, INPUT_PULLUP). Now the released state is actively held at 5 V through the internal resistor, and the pressed state is 0 V.

4

Handle the inversion. Because the wiring is active-low, the condition becomes digitalRead(2) == LOW. Writing == HIGH out of habit is the single most common follow-up bug; the LED then lights when the button is not pressed.

5

Verify with evidence, not with the LED. Print the raw reading with Serial.println(digitalRead(2)) and watch it: a correct wiring shows a clean 1 with the button released and a clean 0 while it is held. Flickering numbers at the moment of the press are bounce, and that is the next section.

A button is wired between pin 4 and GND, and pinMode(4, INPUT_PULLUP) has been called. Which condition means “the button is being held down”?
digitalRead(4) == HIGH

The reading is somewhere between HIGH and LOW

Switch Debouncing

One press is not one transition. It is a burst of them, and the firmware has to decide which of those transitions are real.

Definition

Contact bounce is the rapid, unwanted opening and closing of a mechanical switch's contacts in the first milliseconds after it is operated. Debouncing is any technique — electrical or in software — that makes the firmware see a single clean transition per press.

Bounce is mechanical, not electrical, and it is not a fault: the metal surfaces are springy, so they rebound against each other before settling. A small tactile button typically settles within about 1–5 ms, but a program that samples the pin thousands of times per second will catch every rebound and can count one press as five.

Hardware debouncing

An RC filter — a resistor and capacitor across the switch — smooths the voltage so the fast bounces never reach the pin, and a Schmitt-trigger input converts the now-slowly-changing voltage back into a clean edge. Costs two components, and works even for circuits with no software.

Software debouncing

Read the pin, notice that it changed, then wait until the reading has been stable for a fixed window before believing it. Implemented either with a blocking delay() or, better, non-blocking with millis() so the rest of the program keeps running.

The trade-off to state in an exam answer. The debounce window is bounded from both sides. Too short and bounce leaks through as extra events; too long and a genuine second press that arrives quickly is swallowed. A window of roughly 5–50 ms is the usual compromise, because human presses last far longer than that while bounce does not.
const int BUTTON_PIN = 2; const int LED_PIN = 13; const unsigned long DEBOUNCE_MS = 5; // ignore changes faster than this bool ledState = false; bool lastReading = HIGH; bool stableReading = HIGH; unsigned long lastChange = 0; void setup() { pinMode(BUTTON_PIN, INPUT_PULLUP); pinMode(LED_PIN, OUTPUT); } void loop() { bool reading = digitalRead(BUTTON_PIN); if (reading != lastReading) { // the pin moved: restart the window lastChange = millis(); lastReading = reading; } if (millis() - lastChange >= DEBOUNCE_MS && reading != stableReading) { stableReading = reading; // the change survived the window if (stableReading == LOW) { // falling edge = press (active-low) ledState = !ledState; digitalWrite(LED_PIN, ledState); } } }

Compare this with the tempting shortcut: if (digitalRead(BUTTON_PIN) == LOW) { delay(200); toggle(); }. It does suppress the bounce, but it also stops the whole program for 200 ms, during which no other input is read and no other output is updated. The millis() version keeps loop() turning and simply refuses to believe a reading that has not held still.

Worked example — counting the consequences of a missing debounce. A sketch increments a counter on every LOW reading of an active-low button, and loop() takes 50 µs per pass. Bounce lasts 2 ms and produces, on average, one readable transition every 100 µs.

1

How many samples fit in the bounce window? 2 ms ÷ 50 µs = 40 passes of loop(). The firmware is sampling the pin 20 000 times per second, which is far faster than the mechanical event it is watching.

2

How many of those look like presses? With a transition every ~100 µs, roughly 2 ms ÷ 100 µs ≈ 20 LOW readings. A naive counter therefore adds about 20 for a single press — or worse, an unpredictable number, because bounce is not periodic.

3

What the debounce window changes. Requiring 5 ms of stability means the 2 ms burst is discarded entirely. The accepted transition happens 5 ms after the contacts settle, adding a fixed, predictable latency of a few milliseconds.

4

Why the latency is acceptable. Perceptual thresholds for direct manipulation are in the tens of milliseconds, so 5 ms is imperceptible. The debounce window buys correctness at a cost the user cannot detect — the standard trade in physical interface design.

A student “fixes” button bounce with if (digitalRead(BTN) == LOW) { delay(200); count++; }. What is wrong with it?
It does not debounce at all, so the count still runs away
It works, but delay() blocks the whole program for 200 ms and the counter still increments repeatedly while the button is held
The delay is too short for the bounce to have finished

Sketch 3 — Latching button: input, state and debouncing

bool ledState = false; // state that persists between loops void loop() { bool reading = digitalRead(BUTTON_PIN); if (reading != lastReading) { // pin moved — restart the settle window lastChange = millis(); lastReading = reading; } if (millis() - lastChange >= DEBOUNCE_MS && reading != stableReading) { stableReading = reading; if (stableReading == LOW) { // accept only the press edge ledState = !ledState; // toggle the stored state digitalWrite(LED_PIN, ledState); } } }
State in a variable Non-blocking timing Edge, not level
Debugging order matters. Electrical problems and logic problems produce the same symptom — an LED that will not light — so always settle the electricity first. Measure the pin with digitalWrite(pin, HIGH) in a sketch that does nothing else; if the LED lights, the fault is in your logic, and no amount of re-reading the if statement will find a reversed LED.

Week 3 Recap

Digital means two states

A pin is HIGH or LOW, never “about 2.4 V”. Threshold bands and the noise margin between them are what make a breadboard full of wires reliable.

Signals

pinMode() before anything else

OUTPUT, INPUT or INPUT_PULLUP. A GPIO pin has no default purpose; the program assigns it one, and it does so in setup().

GPIO

Ohm's law sizes every resistor

V = R × I. For an LED: R = (Vsupply − Vf) / I. No resistor means no current limit, which means a dead LED.

Current limiting

Every switch needs a defined idle state

A pull-up or pull-down resistor stops the input floating. The internal pull-up inverts the logic: pressed becomes LOW, and the sketch must say so.

Buttons

One press, many transitions

Contacts bounce for a few milliseconds. Accept a reading only after it has been stable for a window — and use millis(), not delay(), so the rest of the program keeps running.

Debouncing

Check yourself

Can you state the four-quadrant I/O API from memory, size a series resistor for a given LED, and explain why a bare switch produces random readings?
