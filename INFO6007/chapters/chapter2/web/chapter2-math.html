Foundations: the vocabulary and the arithmetic behind a methodology choice

Week 2 is a process week, but every process decision in it can be costed. This page pins down the definitions the lecture relies on, then does the arithmetic that Weeks 3 and 4 will build on: WBS decomposition and the critical path for the tutorial's twelve-week app, earned value with PV, EV and AC, a weighted scorecard for choosing a methodology, expected monetary value for a release strategy, Little's Law for a Kanban board, and the numbers behind all three triple-constraint changes.

Definitions that must be exact

Marks in this unit are lost on definitions more often than on ideas. Write each of these as one sentence with the consequence included.

Project lifecycle

The structured sequence of phases a project goes through from start to finish: defining, planning, executing, monitoring & controlling and closing. It gives a road map for managing work, reducing risk and ensuring success.

Project management methodology

A structured approach or system of practices used to plan, execute and manage projects efficiently — a repeatable framework for delivering work successfully from start to finish.

Waterfall

A linear, sequential methodology in which each phase must be completed before the next begins. Requirements are collected up front and no change is expected once that phase ends, which makes it strong on milestones and documentation and weak on late change.

Agile and Scrum

Agile is a flexible, iterative approach that breaks a project into small increments (sprints or iterations) — a mindset rather than a management technique. Scrum is an agile framework that delivers work in time-boxed sprints of typically one to four weeks, with empirical process control, team collaboration and continuous feedback.

Kanban and DevOps

Kanban is a visual workflow management method focused on continuous delivery, limiting work in progress and workflow transparency. DevOps is a set of practices integrating development and operations to shorten the development lifecycle, increase deployment frequency and deliver high-quality software continuously.

Requirement gathering, charter, stakeholder

Requirement gathering is identifying, collecting and documenting stakeholders' needs and expectations for a new or updated system. A project charter is the formal document that authorises the project and grants the project manager authority over organisational resources. A stakeholder is anyone who impacts or is impacted by the project, positively or negatively.

WBS and the critical path

A methodology decides how often you re-plan; it does not remove the need to decompose scope and sequence it. Weeks 3 and 4 assume you can already do both, so here is the arithmetic on the tutorial's own twelve-week project.

Decomposition arithmetic

A work breakdown structure decomposes scope into deliverables and then into work packages small enough to estimate and assign. Two rules do the work: the 100% rule (the children of a node together account for exactly all of the parent's scope — no gaps, no overlaps), and unique numbering, so every element has exactly one parent.

Counting work packages

If level \(\ell\) branches into \(b_\ell\) children, the number of leaves after \(L\) levels is

\[ W \;=\; \prod_{\ell=1}^{L} b_\ell \qquad\text{and, if the branching factor is uniform,}\qquad W = b^{L}. \]

Three branches over two levels gives \(3^2 = 9\) work packages; four branches over three levels gives \(4^3 = 64\), which is a decomposition nobody will maintain. The practical test is not the count but the size of the leaf: a work package should be estimable, assignable to one accountable person, and short enough to report on inside one reporting period.

Forward pass, backward pass, float

With \(d_i\) the duration of activity \(i\), \(P(i)\) its predecessors and \(S(i)\) its successors:

\[ EF_i = ES_i + d_i, \qquad ES_j = \max_{i \in P(j)} EF_i \] \[ LS_i = LF_i - d_i, \qquad LF_i = \min_{j \in S(i)} LS_j \] \[ TF_i = LS_i - ES_i = LF_i - EF_i, \qquad FF_i = \min_{j \in S(i)} ES_j - EF_i \] \[ T \;=\; \max_i EF_i \;=\; \text{the length of the longest path} \]

Total float \(TF\) is how long an activity can slip without moving the project end date; free float \(FF\) is how long it can slip without moving any successor. Critical activities have \(TF = 0\).

Worked example — the full pass, then the compression the tutorial asks for.

1

Forward pass. \(ES_{1.1} = 0\), so \(EF_{1.1} = 0 + 1 = 1\). Design starts when inception ends: \(ES_{1.2} = 1\), \(EF_{1.2} = 3\). The two build packages both start at 3: \(EF_{1.3.1} = 6\), \(EF_{1.3.2} = 5\). Reminders follow the map: \(ES_{1.3.3} = 5\), \(EF_{1.3.3} = 7\). Testing waits for both predecessors: \(ES_{1.4.1} = \max(6, 7) = 7\), \(EF_{1.4.1} = 11\). Release: \(ES_{1.4.2} = 11\), \(EF_{1.4.2} = 12\). Project duration \(T = 12\) weeks.

2

Backward pass. Set \(LF_{1.4.2} = 12\), so \(LS_{1.4.2} = 11\). Then \(LF_{1.4.1} = 11\) and \(LS_{1.4.1} = 7\). Testing's predecessors inherit \(LF = 7\): \(LS_{1.3.1} = 7 - 3 = 4\) and \(LS_{1.3.3} = 7 - 2 = 5\). Reminders' predecessor: \(LF_{1.3.2} = 5\), \(LS_{1.3.2} = 3\). Design feeds both build packages, so \(LF_{1.2} = \min(4, 3) = 3\) and \(LS_{1.2} = 1\). Finally \(LF_{1.1} = 1\), \(LS_{1.1} = 0\).

3

Float. \(TF_{1.3.1} = 4 - 3 = 1\). Everything else has \(TF = 0\), so the critical path is 1.1 → 1.2 → 1.3.2 → 1.3.3 → 1.4.1 → 1.4.2 with length \(1 + 2 + 2 + 2 + 4 + 1 = 12\). Check the alternative route: \(1 + 2 + 3 + 4 + 1 = 11\), which is exactly the one week of float on 1.3.1.

4

Compress to eight weeks (tutorial Change B). Only critical activities shorten a project, so start there — and watch the float move. Deferring the reminders package (1.3.3) removes the 12-week path 1.1 → 1.2 → 1.3.2 → 1.3.3 → 1.4.1 → 1.4.2, but the timetable build immediately becomes critical at \(1 + 2 + 3 + 4 + 1 = 11\) weeks. One week gained, not two: the float on 1.3.1 has been consumed. A second test stream halves testing from 4 to 2 weeks, and the longest remaining path becomes \(1 + 2 + 3 + 2 + 1 = 9\). The last week needs the timetable build crashed from 3 weeks to 2 with an extra contractor: \(1 + 2 + 2 + 2 + 1 = 8\). The arithmetic of the trade: \(12 - 1_{\text{defer 1.3.3}} - 2_{\text{parallel test}} - 1_{\text{crash 1.3.1}} = 8\) weeks, and the deferred package releases \(\$24{,}000\) of the budget with it.

5

Why the answer is not “work faster”. Removing four weeks from twelve means removing a third of the calendar. Reducing durations without changing the network is crashing: it costs money (the second test stream) or quality (less testing). Reducing scope changes the network, which is free at the schedule level and honest at the scope level — provided the sponsor agrees to the later release.

Earned value: measuring a methodology by its numbers

Waterfall, Scrum, Kanban and DevOps differ in rhythm, not in accountability. Whatever the cadence, the same three measurements answer “are we getting what we paid for?”.

The three measurements

Planned value (PV) is the budgeted cost of the work scheduled by a date. Earned value (EV) is the budgeted cost of the work actually completed by that date. Actual cost (AC) is what was really spent. BAC is the total approved budget. Note that EV counts budget, not effort and not invoices: it is the value of finished work.

Variances and indices

\[ CV = EV - AC \qquad SV = EV - PV \] \[ CPI = \frac{EV}{AC} \qquad SPI = \frac{EV}{PV} \]

Positive is good for both variances. For the indices, exactly 1.00 is on plan; below 1 is over budget (CPI) or behind schedule (SPI). Note the units: \(CV\) and \(SV\) are dollars, \(CPI\) and \(SPI\) are ratios.

Forecasting the finish

\[ EAC = \frac{BAC}{CPI} \qquad ETC = EAC - AC \qquad VAC = BAC - EAC \qquad TCPI = \frac{BAC - EV}{BAC - AC} \]

\(EAC\) is the forecast final cost if the efficiency achieved so far continues; \(ETC\) is what is still expected to be spent; \(VAC\) is the forecast over- or under-run; and TCPI is the cost efficiency the remaining work must achieve to land exactly on BAC. A TCPI above about 1.10 is usually a signal to re-baseline or descope rather than to demand heroics.

Worked example — from the numbers to a decision. Same project, week 6: BAC $180,000, EV $81,000, AC $99,000, CPI 0.818, SPI 0.90.

1

Forecast the finish. \(EAC = BAC / CPI = 180{,}000 / 0.818 = \$220{,}000\). The forecast over-run is \(VAC = 180{,}000 - 220{,}000 = -\$40{,}000\). At $12,000 per activity-week, that is \(40{,}000 / 12{,}000 = 3.3\) activity-weeks of work that the budget cannot pay for.

2

Test the “work harder” option. \(TCPI = (BAC - EV)/(BAC - AC) = 99{,}000 / 81{,}000 = 1.22\). The remaining work would have to be delivered at 122% of the planned cost efficiency. Since the team has managed 82% so far, this is not a plan; it is a wish.

3

Price the descope. Removing the assessment reminders package (2 activity-weeks, $24,000) plus one activity-week from the campus map package ($12,000) removes $36,000 of the $40,000 gap, leaving roughly $4,000 to be absorbed by contingency. That is what “descope by $40,000” looks like in WBS terms.

4

Protect the quality constraint. The testing package is $48,000, the largest single line in the WBS, and it is what makes the app secure, accessible and reliable — the tutorial's stated quality expectation. Cutting it converts a cost over-run into a risk of an unsuccessful launch, which is not a trade the project manager is entitled to make alone. Take the options to the sponsor with the arithmetic attached.

Choosing a method: weights, expected value and flow

Three pieces of arithmetic turn “which methodology?” from an opinion into a defensible recommendation: a weighted scorecard, an expected monetary value, and Little's Law.

1. A weighted scorecard

Score each methodology \(m\) on each criterion \(k\) from 1 to 5, weight the criteria so that \(\sum_k w_k = 1\), and compare:

\[ S_m \;=\; \sum_{k=1}^{K} w_k\, s_{k,m}, \qquad 0 \le w_k \le 1, \qquad \sum_{k=1}^{K} w_k = 1, \qquad 1 \le s_{k,m} \le 5 \]

Because the weights sum to 1, \(S_m\) stays on the 1–5 scale and can be read directly: 5.00 is perfect on every criterion.

2. Expected monetary value

Price a risk, or a decision that changes it, with

\[ EMV \;=\; \sum_i p_i\, I_i \]

Compare two release strategies for the same app. A single big-bang release carries a 20% chance of a failed launch costing $120,000, so \(EMV = 0.20 \times (-\$120{,}000) = -\$24{,}000\). A staged release cuts the failure probability to 10% and the blast radius to $60,000, so \(EMV = 0.10 \times (-\$60{,}000) = -\$6{,}000\), but it adds $12,000 of integration overhead. Staged total: \(-\$6{,}000 - \$12{,}000 = -\$18{,}000\).

Break-even: staging wins while its overhead is below the expected-loss reduction, \(\$24{,}000 - \$6{,}000 = \$18{,}000\). Above that, the cheaper risk is to release once.

3. Little's Law for a Kanban board

For a stable system, work in progress, throughput and cycle time are locked together:

\[ WIP \;=\; TH \times CT \qquad\Longleftrightarrow\qquad CT \;=\; \frac{WIP}{TH} \]

The support team from the lecture completes \(TH = 10\) tickets per day. With 30 items in progress, \(CT = 30 / 10 = 3\) days. Cutting the WIP limit to 20 gives \(CT = 20 / 10 = 2\) days — provided throughput holds. If pulling less work also drops throughput to 8 per day, \(CT = 20 / 8 = 2.5\) days, and the gain is much smaller. The limit is a hypothesis about the bottleneck, not a magic number.

The tutorial's arithmetic: what each change really costs

The Week 2 tutorial gives one baseline and three changes. Put numbers on the baseline once, and each change becomes a calculation rather than a debate.

The baseline (UniConnect, outsourced to a local software company)

Scope: personal timetable, assessment reminders, campus map, emergency notifications (four features). Time: 12 weeks, ready before next semester. Cost: maximum budget $180,000. High-level quality expectation: the app must be secure, accessible and reliable.

Three baseline rates worth having at your fingertips

\[ \text{cost per week} = \frac{180{,}000}{12} = \$15{,}000 \qquad \text{cost per feature} = \frac{180{,}000}{4} = \$45{,}000 \] \[ \text{schedule per feature} = \frac{12}{4} = 3\ \text{weeks} \]

Every change below is a movement in one of these three rates, and every response is an argument about which of the others absorbs it.

The pattern. Each change pressures the constraints it did not move. Scope grew, so time and cost felt it; time shrank, so cost and scope felt it; cost shrank, so time and scope felt it. Quality — secure, accessible, reliable — is the constraint nobody in the scenario has volunteered to reduce, which is precisely why a project manager who says nothing about it will lose it by default.

Worked example — Change C, costed three ways. The budget falls from $180,000 to $135,000 and the deadline stays at 12 weeks.

1

What the cut buys. The original run rate was \(\$180{,}000 / 12 = \$15{,}000\) per week. The new budget funds \(135{,}000 / 15{,}000 = 9\) weeks at that rate. Either the burn rate falls to \(135{,}000 / 12 = \$11{,}250\) per week (75% of the original team and services) or the work has to fit into nine weeks of the original capacity.

2

Option 1 — descope by 25%. \(\$135{,}000 / \$45{,}000 = 3\) features' worth of money for 4 features of scope. Deliver three. Retaining the timetable and emergency notifications protects the features with the clearest safety and equity case; deferring the map and reminders is the shippable compromise.

3

Option 2 — keep four features at 75% of the effort each. Every work package loses a quarter of its effort, including testing: \(0.75 \times \$48{,}000 = \$36{,}000\) for security, accessibility and integration testing. The arithmetic balances and the quality expectation does not: the stated requirement was that the app be secure, accessible and reliable, and testing is the only work package that produces the evidence for it.

4

Option 3 — re-baseline honestly. Keep the four features and ask the sponsor for \(EAC - BAC = \$45{,}000\) more, or a later release date. Stating the number with its evidence is better project management than absorbing it silently: the tutorial's own summary is that a reduced budget means less scope, more time, or a revised baseline — never all four constraints unchanged.

5

The sentence that earns the marks. “A 25% budget reduction with a fixed deadline and a fixed quality expectation cannot be absorbed by the same scope. The arithmetic gives three consistent responses — descope by roughly one quarter, extend the date, or increase the budget — and the project manager's job is to put those three options to the sponsor rather than choose the invisible fourth, which is to let quality absorb the cut.”

The four numbers to memorise

\(15{,}000\) per week, \(45{,}000\) per feature, 3 weeks per feature, and \(2/3\) of the schedule when 12 weeks becomes 8.

The three formulas to carry into Week 3 and 4

\(TF = LS - ES\) for the schedule, \(CPI = EV/AC\) and \(SPI = EV/PV\) for control, and \(EAC = BAC/CPI\) for the forecast.
